Допишите обобщённую `Queue[T]`. Очередь задач в воркере выглядит
безобидно: `append` в конец и `q = q[1:]` из начала. Но в проде у неё
находятся две утечки:

- извлечённые элементы остаются в массиве, пока его не переаллоцируют. Если
  это указатели на запросы с телами по мегабайту, сборщик мусора их не
  освободит;
- после ночного всплеска до миллиона задач очередь опустела, а массив на
  миллион элементов живёт дальше.

Что проверяют скрытые тесты:

- порядок FIFO при перемешанных `Push`/`Pop`, `Pop` из пустой очереди;
- после каждого `Pop` выполняется `Cap() <= max(64, 4*Len())`, в том числе
  когда очередь опустошают после 100 000 элементов;
- очередь, в которой постоянно лежит один элемент, после 100 000 пар
  `Push`/`Pop` не растёт;
- объекты, извлечённые через `Pop`, собираются сборщиком мусора
  (`runtime.SetFinalizer` + `runtime.GC()`), даже если в очереди
  ещё остались элементы.

<Reveal>

```go
type Queue[T any] struct {
	buf  []T
	head int
}

func (q *Queue[T]) Push(v T) { q.buf = append(q.buf, v) }

func (q *Queue[T]) Pop() (T, bool) {
	var zero T
	if q.head == len(q.buf) {
		return zero, false
	}
	v := q.buf[q.head]
	q.buf[q.head] = zero
	q.head++

	n := q.Len()
	switch {
	case n == 0:
		if cap(q.buf) > 64 {
			q.buf = nil
		} else {
			q.buf = q.buf[:0]
		}
		q.head = 0
	case cap(q.buf) > max(64, 4*n):
		nb := make([]T, n, 2*n)
		copy(nb, q.buf[q.head:])
		q.buf, q.head = nb, 0
	}
	return v, true
}

func (q *Queue[T]) Len() int { return len(q.buf) - q.head }
func (q *Queue[T]) Cap() int { return cap(q.buf) }
```

**Обнулить слот до сдвига.** Сборщик мусора сканирует массив целиком, а не
только видимую часть слайса. `q.buf[q.head:]` скрывает элемент от вашего
кода, но не от GC. Поэтому `q.buf[q.head] = zero` обязательно. По той же
причине `slices.Delete` начиная с Go 1.22 обнуляет освободившийся хвост.

**Индекс `head` вместо `q.buf = q.buf[1:]`.** Сдвиг заголовка слайса
уменьшает `cap`, и следующий `append` при нехватке места переаллоцирует
массив. Память от этого не растёт, но решать, когда её отдавать, всё
равно приходится. С явным `head` видно, сколько места мёртвое.

**Сжатие с гистерезисом.** Переезжаем в массив вдвое больше числа живых
элементов, когда живых стало меньше четверти. Если сжимать до `n`, а
расти при `n+1`, то чередование `Push`/`Pop` на границе даст копирование
на каждой операции. Зазор между 2× и 4× даёт амортизированное O(1).

**Опустевшую большую очередь отпускаем целиком** (`q.buf = nil`), а
маленькую переиспользуем, чтобы не аллоцировать заново на каждом цикле.

**Что спросят дальше.** Почему не кольцевой буфер: он тоже подходит и
лучше под постоянной нагрузкой, но растить и сжимать его сложнее, потому
что при копировании элементы нужно разворачивать. И почему
`runtime.SetFinalizer` годится для теста, но не для логики: момент его
вызова не гарантирован.
