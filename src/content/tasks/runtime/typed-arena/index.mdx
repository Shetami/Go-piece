Парсер строит AST из десятков тысяч узлов на каждый запрос. В профиле
видно, что половина CPU уходит на `mallocgc` и сборку мусора. Классический
ответ — арена: выделить память большими блоками, раздавать узлы из них, а
в конце запроса сбросить всё одной операцией. В Go 1.20 был
экспериментальный пакет `arena`, но он так и остался экспериментом.
Напишем обобщённую арену сами, поверх обычных слайсов.

Что проверяют скрытые тесты:

- 1000 вызовов `New` дают 1000 разных обнулённых указателей, и запись
  через один указатель не портит другие;
- после `Reset` объекты выдаются **обнулёнными**, даже если раньше в них
  писали;
- `Reset` и повтор той же нагрузки в 1000 объектов выполняются **без
  единой аллокации** (`testing.AllocsPerRun`);
- после `Reset` объекты, на которые ссылались элементы арены, собираются
  сборщиком мусора, хотя сама арена ещё жива.

<Reveal>

```go
type Arena[T any] struct {
	chunks    [][]T
	cur       int
	used      int
	chunkSize int
	n         int
}

func NewArena[T any](chunkSize int) *Arena[T] {
	return &Arena[T]{chunkSize: chunkSize}
}

func (a *Arena[T]) New() *T {
	if len(a.chunks) == 0 || a.used == a.chunkSize {
		if len(a.chunks) > 0 {
			a.cur++
		}
		if a.cur == len(a.chunks) {
			a.chunks = append(a.chunks, make([]T, a.chunkSize))
		}
		a.used = 0
	}
	p := &a.chunks[a.cur][a.used]
	a.used++
	a.n++
	return p
}

func (a *Arena[T]) Reset() {
	for i := 0; i < len(a.chunks) && i <= a.cur; i++ {
		clear(a.chunks[i])
	}
	a.cur, a.used, a.n = 0, 0, 0
}

func (a *Arena[T]) Len() int { return a.n }
```

**Блоки фиксированного размера, а не один растущий слайс.** С
`a.buf = append(a.buf, zero); return &a.buf[len-1]` при каждом росте
создаётся новый массив, а выданные указатели остаются в старом. Ничего не
ломается, потому что старый массив держат эти указатели, но арена
перестаёт быть ареной: при каждом росте всё копируется, старые массивы
живут, пока на них есть указатели, и памяти уходит почти вдвое больше. Блоки, которые никогда не растут, дают стабильные адреса.

**`Reset` оставляет блоки себе.** Если написать `a.chunks = nil`, каждый
запрос снова выделяет блоки, и выигрыша нет. Тест с `AllocsPerRun`
поймает это: первый прогон он делает для прогрева и не считает, поэтому
при правильной реализации аллокаций в замере ноль.

**Обнулять в `Reset`, а не в `New`.** Ленивое обнуление при повторной
выдаче экономит время, но до следующего запроса блоки держат указатели
на тела, буферы и соединения прошлого. Для сборщика мусора блок — живой
массив, и всё, на что он ссылается, тоже живое. `clear` на слайсе
компилируется в `memclr`, это быстро.

**Главный риск арены — висячие указатели.** Если `*T` пережил `Reset`, он
тихо указывает на чужой объект. В Go это не use-after-free с падением, а
логическая порча данных, которую трудно поймать. Поэтому арены
используют там, где время жизни явно ограничено: один запрос, один
батч, одна компиляция.

**Что спросят дальше.** Почему арена снижает нагрузку на GC: меньше
объектов для учёта, и блок без указателей (`T` из чисел) сборщик вообще
не сканирует. И чем арена отличается от `sync.Pool`: пул переиспользует
отдельные объекты между горутинами, а арена освобождает множество
объектов разом.
