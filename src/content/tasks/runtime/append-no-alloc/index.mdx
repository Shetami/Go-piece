Функция форматирует точку `"(x, y)"` и дописывает к буферу. Её вызывают в
горячем цикле с переиспользуемым буфером. Заготовка через `fmt.Sprintf`
выделяет память на каждом вызове. Перепишите без аллокаций.

Что проверяют скрытые тесты:

- формат: `"(3, -14)"`, дописывание к существующему содержимому, `nil` на
  входе;
- при достаточной вместимости буфера `testing.AllocsPerRun` — ровно 0.

<Reveal>

```go
func AppendPoint(dst []byte, x, y int) []byte {
	dst = append(dst, '(')
	dst = strconv.AppendInt(dst, int64(x), 10)
	dst = append(dst, ", "...)
	dst = strconv.AppendInt(dst, int64(y), 10)
	return append(dst, ')')
}
```

**Откуда аллокации в заготовке.** `fmt.Sprintf` создаёт новую строку —
одна аллокация. Аргументы уходят в `...any`, и числа, упакованные в
интерфейсы, могут уехать в кучу — ещё. Плюс внутренний буфер `fmt` (он
берётся из `sync.Pool`, но всё же). А потом `append` копирует строку в
`dst`.

**Append-стиль.** `strconv.AppendInt`, `time.Time.AppendFormat`,
`binary.AppendUvarint`, `fmt.Appendf` (Go 1.19) — функции, которые пишут в
буфер вызывающего и возвращают его. Если вместимости хватает, память не
выделяется вовсе; если нет — `append` вырастит буфер, и при следующем вызове
её уже хватит. Вызывающий переиспользует буфер через `buf[:0]`.

**`fmt.Appendf(dst, "(%d, %d)", x, y)`** — короче и тоже без итоговой строки,
но интерфейсы для аргументов остаются. Есть ли там аллокации, зависит от
версии компилятора — поэтому в горячем коде предпочитают `strconv`.

**Как проверять.** `testing.AllocsPerRun` в тестах, `go test -bench . -benchmem`
в бенчмарках и `go build -gcflags=-m` — чтобы увидеть, что и почему
уезжает в кучу.

</Reveal>
