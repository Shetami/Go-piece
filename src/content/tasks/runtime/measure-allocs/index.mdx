`testing.AllocsPerRun` работает только в тестах и считает только число
выделений. Напишите `Measure`, которая работает где угодно — в
бенчмарк-хелпере, в отладочном эндпоинте, в CLI-утилите — и заодно
считает байты.

Что проверяют скрытые тесты:

- пустая функция даёт 0 и 0; функция с тремя выделениями даёт ровно 3 и
  разумное число байт;
- **ленивая инициализация** (карта из 200 буферов при первом вызове) в
  среднее не попадает;
- **во время** замера `GOMAXPROCS` равен 1, а **после** — такой же, как
  был (тест выставляет 3);
- результат совпадает с `testing.AllocsPerRun` на той же функции.

<Reveal>

```go
func Measure(runs int, f func()) AllocStats {
	defer runtime.GOMAXPROCS(runtime.GOMAXPROCS(1))

	f()

	var before, after runtime.MemStats
	runtime.ReadMemStats(&before)
	for range runs {
		f()
	}
	runtime.ReadMemStats(&after)

	return AllocStats{
		Allocs: (after.Mallocs - before.Mallocs) / uint64(runs),
		Bytes:  (after.TotalAlloc - before.TotalAlloc) / uint64(runs),
	}
}
```

**`defer runtime.GOMAXPROCS(runtime.GOMAXPROCS(1))`.** Аргументы `defer`
вычисляются сразу. Внутренний вызов ставит 1 и возвращает прежнее
значение, а отложенный вызов вернёт его при выходе. Счётчики `MemStats`
общие на весь процесс. С одним P другие горутины не выполняются
параллельно с `f`, хотя и могут вклиниться при блокировке. Именно так
сделано в `testing.AllocsPerRun`.

**Прогрев.** Первый запуск инициализирует ленивые кэши, `sync.Once`,
растит внутренние буферы. Если усреднять вместе с ним, 200 разовых
выделений превратятся в «4 выделения на вызов» при 50 запусках, и
горячий путь без аллокаций будет выглядеть плохим.

**Правильные поля `MemStats`.** `Mallocs` и `TotalAlloc` только растут.
`HeapAlloc` и `HeapObjects` уменьшаются, если между чтениями прошла сборка
мусора, и разность может выйти отрицательной (для `uint64` — огромной).
`TotalAlloc` учитывает размер с округлением до класса: `make([]byte, 1000)`
стоит 1024 байта.

**Цена.** `runtime.ReadMemStats` останавливает мир (STW). Для теста это
нормально, а в проде вызывать его на каждый запрос нельзя. Для
мониторинга есть `runtime/metrics`: он читает те же данные без полной
остановки.

**Что спросят дальше.** Почему аллокация на стеке не видна в
счётчиках: это просто сдвиг указателя стека, `mallocgc` не вызывается.
И как увидеть, что именно выделяет память: `go build -gcflags=-m`
показывает решения escape-анализа, а `go test -memprofile` — места
выделений.
