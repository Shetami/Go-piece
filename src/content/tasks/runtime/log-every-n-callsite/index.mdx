Сервис под нагрузкой пишет «retrying request» сто тысяч раз в секунду, и
лог-пайплайн не справляется. Обычное решение — прореживание: из
каждого места в коде пропускать только каждое N-е сообщение, как
`LOG_EVERY_N` в glog/klog. Счётчик общий нельзя: редкая ошибка в одном
месте утонет в частой ошибке из другого.

Допишите `Sampler`: `if s.Allow() { log.Print(…) }`.

Что проверяют скрытые тесты:

- при `n = 3` десять вызовов из цикла дают `+..+..+..+`; при `n <= 1`
  пропускается всё;
- два вызова в **разных строках одной функции** — разные места;
- два вызова в **одной строке** (`x, y := s.Allow(), s.Allow()`) — тоже
  разные;
- вызов внутри другой функции имеет свой счётчик;
- 800 вызовов из одного места в 8 горутинах при `n = 10` пропускают
  ровно 80, гонок нет.

<Reveal>

```go
type Sampler struct {
	n      int
	mu     sync.Mutex
	counts map[uintptr]int
}

func NewSampler(n int) *Sampler {
	return &Sampler{n: n, counts: make(map[uintptr]int)}
}

func (s *Sampler) Allow() bool {
	if s.n <= 1 {
		return true
	}
	pc, _, _, ok := runtime.Caller(1)
	if !ok {
		return true
	}
	s.mu.Lock()
	c := s.counts[pc]
	s.counts[pc] = c + 1
	s.mu.Unlock()
	return c%s.n == 0
}
```

**PC — лучший ключ места вызова.** `runtime.Caller(1)` возвращает адрес
возврата в вызывающую функцию, то есть адрес конкретной инструкции
вызова. Имя функции склеивает все вызовы внутри неё. Пара
`file:line` склеивает вызовы в одной строке. Кроме того, для строки
нужна аллокация, а PC — просто число и хороший ключ для карты.

**Счётчик под мьютексом.** Прочитать, увеличить и сравнить нужно
атомарно. `sync.Map` с обычным `int` внутри даёт гонку, `atomic.Int64`
в `sync.Map` — рабочий вариант, если мест много, а горутин ещё больше.
Тест с 800 вызовами ловит потерянные инкременты: при гонке пропустится
не ровно 80.

**Про встраивание.** Даже если `Allow` встроится в вызывающего, у
разных мест будут разные адреса инструкций, так что ключ остаётся
уникальным.

**Что спросят дальше.** Карта растёт по числу мест в коде, а не по числу
событий, так что утечки нет. И чем прореживание по счётчику хуже
прореживания по времени (`LOG_EVERY_T`, `slog` с rate limit): при
всплеске в 100 раз N-й раз наступает в 100 раз чаще, и в лог снова
идёт поток.
