Допишите `ParallelMap`: хешировать тысячу файлов, ресайзить картинки,
парсить JSON-чанки — CPU-bound работу на все доступные ядра. Больше
горутин, чем `GOMAXPROCS`, здесь не ускоряет, а только добавляет
переключений. В контейнере с лимитом CPU значение `GOMAXPROCS` к тому же
не равно числу ядер машины (с Go 1.25 рантайм учитывает cgroup-лимит).

Что проверяют скрытые тесты:

- при `GOMAXPROCS = 2` и `3` одновременно работает **ровно** столько
  вызовов `f`, и после вызова `GOMAXPROCS` не изменился;
- результаты в исходном порядке, пустой вход — без ошибки;
- элемент 0 падает с ошибкой, остальные ждут `ctx.Done()`: функция быстро
  возвращает **именно эту** ошибку, а не `context.Canceled`, новые
  элементы почти не запускаются, горутин после возврата не остаётся;
- уже отменённый родительский контекст даёт `context.Canceled`.

<Reveal>

```go
func ParallelMap[T, R any](ctx context.Context, in []T, f func(context.Context, T) (R, error)) ([]R, error) {
	out := make([]R, len(in))
	workers := min(runtime.GOMAXPROCS(0), len(in))

	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	var (
		next     atomic.Int64
		errOnce  sync.Once
		firstErr error
		wg       sync.WaitGroup
	)
	for range workers {
		wg.Add(1)
		go func() {
			defer wg.Done()
			for ctx.Err() == nil {
				i := int(next.Add(1) - 1)
				if i >= len(in) {
					return
				}
				r, err := f(ctx, in[i])
				if err != nil {
					errOnce.Do(func() { firstErr = err; cancel() })
					return
				}
				out[i] = r
			}
		}()
	}
	wg.Wait()
	if firstErr != nil {
		return nil, firstErr
	}
	if err := ctx.Err(); err != nil {
		return nil, err
	}
	return out, nil
}
```

**`runtime.GOMAXPROCS(0)` читает, `GOMAXPROCS(n)` меняет.** Вызов с
положительным аргументом переключает значение для всего процесса и
вызывает stop-the-world. Библиотечная функция, которая «на минутку»
выставляет своё значение, ломает всем остальным. `runtime.NumCPU()` тоже
не подходит: он не учитывает ни ручную настройку, ни лимиты контейнера.

**N воркеров вместо N горутин на элемент.** Горутина на каждый элемент с
семафором тоже ограничивает параллелизм, но создаёт `len(in)` горутин.
Фиксированный пул, который берёт индексы через атомарный счётчик,
проще: не нужен канал заданий, и результат пишется в `out[i]` без
мьютекса, потому что каждый индекс достаётся ровно одной горутине.

**Первая ошибка, а не последняя.** После `cancel()` остальные вызовы `f`
возвращают `context.Canceled`. Если каждая ошибка перезаписывает общую
переменную, наружу уйдёт отмена вместо настоящей причины. `sync.Once`
фиксирует первую и заодно отменяет контекст ровно один раз. Так же
устроен `errgroup.Group`.

**Дождаться всех перед возвратом.** `wg.Wait()` гарантирует, что после
выхода из функции ни одна горутина не пишет в `out` и не вызывает `f`.
Вернуть результат по первой ошибке, не дождавшись остальных, значит
создать утечку и гонку.

**Что спросят дальше.** Почему для I/O-bound работы (HTTP-запросы) лимит
`GOMAXPROCS` не нужен: горутина, ждущая сеть, не занимает P. Там лимит
задаёт внешний ресурс, например размер пула соединений. И как то же
написать через `errgroup.SetLimit`.
