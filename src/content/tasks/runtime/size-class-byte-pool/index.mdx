Допишите `BytePool`. Один `sync.Pool` на все размеры работает плохо:
просишь 100 байт, получаешь буфер на 64 КБ, или наоборот слишком маленький.
Поэтому сетевые библиотеки держат корзины по степеням двойки: 64, 128, …,
64 КиБ. Так же устроен и сам аллокатор Go, у которого есть классы размеров.

Что проверяют скрытые тесты:

- `Get(n)` возвращает `len == n` и `cap` ровно размером с класс, включая
  `n = 0`, `n = 64`, `n = 65` и точные степени двойки;
- после `Put` слайсов с вместимостью 100 и 200 ни один `Get` не паникует и
  не возвращает слайс с неправильной вместимостью;
- слайс, возвращённый через `Put`, действительно переиспользуется;
- слайсы вместимостью 1 МиБ и 10 байт в пул не попадают;
- пул работает из нескольких горутин.

<Reveal>

```go
const (
	minShift   = 6
	maxShift   = 16
	numClasses = maxShift - minShift + 1
)

type BytePool struct {
	classes [numClasses]sync.Pool
}

func (p *BytePool) Get(n int) []byte {
	if n > MaxClass {
		return make([]byte, n)
	}
	shift := minShift
	if n > MinClass {
		shift = bits.Len(uint(n - 1))
	}
	if v := p.classes[shift-minShift].Get(); v != nil {
		return (*v.(*[]byte))[:n]
	}
	return make([]byte, n, 1<<shift)
}

func (p *BytePool) Put(b []byte) {
	c := cap(b)
	if c < MinClass || c > MaxClass {
		return
	}
	shift := bits.Len(uint(c)) - 1
	b = b[:0:1<<shift]
	p.classes[shift-minShift].Put(&b)
}
```

**Get округляет вверх, Put округляет вниз.** Запрос на 100 байт
обслуживает класс 128: в меньший не влезет. А слайс вместимостью 100
годится только для класса 64. Если положить его в корзину 128, то
следующий `Get(120)` сделает `b[:120]` при `cap == 100` и получит панику
`slice bounds out of range`. Это самая частая ошибка в самописных пулах.

**`b[:0:1<<shift]` — полное выражение среза.** Оно обрезает вместимость до
размера класса. Все слайсы в одной корзине становятся одинаковыми, и `Get`
может честно обещать `cap` ровно по классу. Лишние 36 байт слайса на 100
просто не используются.

**`bits.Len(uint(n-1))`** даёт показатель наименьшей степени двойки не
меньше `n`, без цикла. Для точной степени, например 128, получится 7, то
есть сама 128. Для `Put` нужно `bits.Len(uint(c)) - 1`, то есть степень
двойки не больше `c`.

**`*[]byte`, а не `[]byte`.** Заголовок слайса — три машинных слова, и
при упаковке в `any` среда выполнения копирует его в кучу. staticcheck
ругается на это (SA6002). Но честно скажем: в эталоне `&b` тоже уходит в
кучу, так что 24 байта на каждый `Put` остаются. Полностью убрать их
можно, только если поменять API и отдавать наружу сам `*[]byte`, как
делают многие библиотеки. Тогда тот же указатель и возвращается в пул.
Зато сам буфер на килобайты переиспользуется, а в этом и смысл.

**Что спросят дальше.** Почему слишком большие слайсы выбрасываются
(память будет удерживаться), и зачем в Go 1.13 у `sync.Pool` появился
victim-кэш: без него сборка мусора опустошала пул полностью, и после
каждого цикла GC случался всплеск аллокаций.
