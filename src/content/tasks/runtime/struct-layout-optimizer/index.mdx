Линтер `fieldalignment` из `go vet` говорит: «struct of size 32 could be
16». Напишите его ядро. `Layout` раскладывает поля в заданном порядке так
же, как это делает компилятор. `Optimize` предлагает порядок, при котором
структура занимает меньше всего места. В кэше на десять миллионов записей
разница между 32 и 16 байтами — это 160 МБ.

Что проверяют скрытые тесты:

- смещения и размер совпадают с `unsafe.Offsetof`/`unsafe.Sizeof` для
  настоящих структур: с `bool` вперемешку с `int64`, с массивами
  `[3]byte` и `[0]int64`, со строкой;
- структура, которая **заканчивается полем нулевого размера**
  (`struct{}`), тоже совпадает с компилятором;
- пустой список полей и структура из одного `struct{}`;
- `Optimize` даёт минимальный размер и **конкретный** порядок: равноценные
  поля остаются в исходном порядке, а входной слайс не меняется.

<Reveal>

```go
func alignUp(n, a uintptr) uintptr { return (n + a - 1) &^ (a - 1) }

func Layout(fields []Field) (offsets []uintptr, size uintptr) {
	offsets = make([]uintptr, len(fields))
	var off uintptr
	maxAlign := uintptr(1)
	for i, f := range fields {
		off = alignUp(off, f.Align)
		offsets[i] = off
		off += f.Size
		maxAlign = max(maxAlign, f.Align)
	}
	if n := len(fields); n > 0 && fields[n-1].Size == 0 && off > 0 {
		off++
	}
	return offsets, alignUp(off, maxAlign)
}

func Optimize(fields []Field) []Field {
	out := slices.Clone(fields)
	slices.SortStableFunc(out, func(a, b Field) int {
		if az, bz := a.Size == 0, b.Size == 0; az != bz {
			if az {
				return -1
			}
			return 1
		}
		switch {
		case a.Align > b.Align:
			return -1
		case a.Align < b.Align:
			return 1
		}
		return 0
	})
	return out
}
```

**Два вида паддинга.** Внутренний: перед полем смещение округляется до
его выравнивания, поэтому `bool` перед `int64` оставляет дыру в 7 байт.
Хвостовой: размер структуры округляется до максимального выравнивания
полей, чтобы в массиве `[]T` каждый следующий элемент тоже был
выровнен. Второе забывают чаще: `struct{ x int64; b bool }` занимает 16
байт, а не 9.

**Поле нулевого размера в конце стоит денег.** Если бы `struct{}` в конце
имел смещение, равное размеру структуры, то `&s.z` указывал бы на
следующий объект в памяти. Такой указатель удерживал бы чужой объект от
сборки мусора. Поэтому gc добавляет байт, и дальше срабатывает хвостовое
выравнивание. `struct{ x int32; y byte; z struct{} }` занимает 8 байт, но
стоит поставить `z` первым, и размер не изменится. Отсюда первое правило
`Optimize`: пустые поля (маркеры вроде `noCopy`, `[0]func()`) — в начало.

**Сортировка по убыванию выравнивания даёт оптимум.** В Go размер типа
всегда кратен его выравниванию, а выравнивания — степени двойки. Если поля
идут от самого строгого к самому слабому, каждое следующее смещение уже
кратно нужному выравниванию, и внутренних дыр нет. Остаётся только
хвостовой паддинг, а он от порядка не зависит. `SortStableFunc`
сохраняет исходный порядок равных полей, так что результат
детерминирован и diff получается минимальным.

**Где это важно, а где нет.** Для структур, которые живут в миллионах
копий (узлы, записи кэша, элементы слайсов), экономия реальная, к тому
же размер попадает в меньший класс размеров аллокатора. Для
конфигурации в одном экземпляре читаемость важнее. `fieldalignment` ещё
и учитывает, сколько байт с начала содержат указатели: сборщик мусора
сканирует объект только до последнего указателя.

**Что спросят дальше.** Почему `atomic.Int64` выровнен по 8 даже на 32-битных
платформах (там `int64` выровнен по 4, и `sync/atomic` раньше требовал
ставить такие поля первыми), и как проверить раскладку без `unsafe`:
через `reflect.Type.Field(i).Offset`.
