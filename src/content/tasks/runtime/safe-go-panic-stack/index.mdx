Паника в любой горутине без `recover` роняет весь процесс, со всеми
остальными запросами. Поэтому в воркерах, обработчиках сообщений из
очереди и фоновых задачах запускают горутины через обёртку, которая
превращает панику в ошибку. Но ошибка «panic: assignment to entry in nil
map» без стека бесполезна: непонятно, где это случилось.

Допишите `Go`, `PanicError.Error` и `PanicError.Unwrap`.

Что проверяют скрытые тесты:

- результат `f` (nil или ошибка) приходит в канал как есть;
- паника приходит как `*PanicError` с текстом `panic: …`, и в `Stack`
  есть **функция, которая запаниковала**;
- `panic(io.ErrUnexpectedEOF)` распознаётся через `errors.Is`, а
  `panic(nil)` — тоже паника;
- `runtime.Goexit()` внутри `f` даёт `ErrGoexit`, а не `nil` и не
  зависание;
- 100 вызовов, результат которых никто не читает, не оставляют висящих
  горутин.

<Reveal>

```go
func (e *PanicError) Error() string {
	return fmt.Sprintf("panic: %v", e.Value)
}

func (e *PanicError) Unwrap() error {
	err, _ := e.Value.(error)
	return err
}

func Go(f func() error) <-chan error {
	ch := make(chan error, 1)
	go func() {
		returned := false
		defer func() {
			if returned {
				return
			}
			if r := recover(); r != nil {
				ch <- &PanicError{Value: r, Stack: debug.Stack()}
				return
			}
			ch <- ErrGoexit
		}()
		err := f()
		returned = true
		ch <- err
	}()
	return ch
}
```

**Стек снимается внутри отложенной функции.** Когда начинается паника,
рантайм не раскручивает стек сразу. Он вызывает отложенные функции
поверх кадров паникующей горутины. Поэтому `debug.Stack()` в `defer` видит
и `chkExplode`, и строку паники. После выхода из `defer` эти кадры
исчезнут. Если снять стек позже, например в горутине, которая читает
канал, там будет только её собственный стек.

**`Goexit` — третий исход.** `runtime.Goexit` (его вызывает, например,
`t.FailNow`) выполняет отложенные функции, но это не паника, и
`recover()` возвращает `nil`. Если считать «`recover` вернул nil» нормальным
завершением, отправится результат, которого не было, или ничего не
отправится, и читатель зависнет навсегда. Флаг `returned`, выставленный
после `f()`, различает все три случая. Так же сделано в
`golang.org/x/sync/singleflight`.

**`panic(nil)` с Go 1.21 — тоже паника.** Раньше `recover()` возвращал `nil`,
и такая паника была неотличима от отсутствия паники. Теперь рантайм
подменяет значение на `*runtime.PanicNilError`, и `r != nil` работает.

**Буфер 1 — защита от утечки.** С небуферизованным каналом горутина
висит на отправке, пока кто-нибудь не прочитает результат. Вызывающий
по таймауту ушёл, и горутина осталась навсегда. Одно значение в буфере
позволяет завершиться без читателя.

**Что спросят дальше.** Почему `recover` работает только в функции,
вызванной напрямую из `defer`, и не ловит панику в **другой** горутине:
поэтому обёртка нужна на каждом `go`, и библиотечная горутина без неё —
бомба для всего процесса. И почему нельзя восстановиться после
`fatal error: concurrent map writes` — это не паника, а аварийный выход
рантайма.
