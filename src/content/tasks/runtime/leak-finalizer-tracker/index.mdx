Пул соединений медленно деградирует: через сутки все соединения
«заняты», хотя нагрузки нет. Кто-то берёт соединение и забывает
`Close` на одной из веток с ошибкой. Найти такое место помогает
отладочный трекер: ресурс, который сборщик мусора собрал без
`Close`, попадает в отчёт. `os.File` делает то же самое, только молча
закрывает дескриптор.

Допишите `Tracker` и `Resource`.

Что проверяют скрытые тесты:

- пять брошенных ресурсов после `runtime.GC()` оказываются в `Leaked()`
  (отсортированы по имени), а три закрытых там не появляются даже после
  нескольких циклов GC;
- ресурс, который ещё используется, утёкшим не считается;
- повторный `Close` возвращает `ErrClosed`;
- `OpenCount` учитывает и закрытые, и утёкшие;
- 8 горутин открывают и закрывают ресурсы, одновременно вызывая
  `Leaked()`: гонок нет, утечки посчитаны точно.

<Reveal>

```go
type Tracker struct {
	open   atomic.Int64
	mu     sync.Mutex
	leaked []string
}

type Resource struct {
	name   string
	t      *Tracker
	closed atomic.Bool
}

func (t *Tracker) Open(name string) *Resource {
	r := &Resource{name: name, t: t}
	t.open.Add(1)
	runtime.SetFinalizer(r, (*Resource).onCollected)
	return r
}

func (r *Resource) onCollected() {
	r.t.open.Add(-1)
	r.t.mu.Lock()
	r.t.leaked = append(r.t.leaked, r.name)
	r.t.mu.Unlock()
}

func (r *Resource) Close() error {
	if !r.closed.CompareAndSwap(false, true) {
		return ErrClosed
	}
	runtime.SetFinalizer(r, nil)
	r.t.open.Add(-1)
	return nil
}

func (t *Tracker) Leaked() []string {
	t.mu.Lock()
	defer t.mu.Unlock()
	out := slices.Clone(t.leaked)
	slices.Sort(out)
	return out
}

func (t *Tracker) OpenCount() int { return int(t.open.Load()) }
```

**Трекер не должен знать ресурсы в лицо.** Самое естественное решение —
`map[*Resource]struct{}` открытых ресурсов, чтобы считать их и выводить
список. Но карта держит ссылку, ресурс всегда достижим, и финализатор не
сработает никогда. Поэтому храним только счётчик, а данные для отчёта
(имя) — в самом ресурсе. Трекер про ресурсы знает, но на них не
ссылается.

**Финализатор получает объект параметром.** Если написать
`runtime.SetFinalizer(r, func(*Resource) { log(r.name) })`, замыкание
захватит `r`. Финализатор хранится в рантайме как корень сборки мусора,
а значит `r` достижим из собственного финализатора и не будет собран
никогда. В тесте это выглядит как «утечек не найдено», то есть
детектор, который молчит. Используйте параметр или метод-выражение
`(*Resource).onCollected`.

**Снять финализатор в `Close`.** `SetFinalizer(r, nil)` не только
исключает ложное срабатывание: объект с финализатором освобождается
минимум за два цикла GC. Первый цикл находит его недостижимым и
запускает финализатор, второй освобождает память.

**Финализатор — отдельная горутина.** Все финализаторы выполняются в
одной служебной горутине, конкурентно с программой. Поэтому общее
состояние защищено мьютексом, а долгий или блокирующийся финализатор
задерживает все остальные.

**Что спросят дальше.** Почему это отладочный инструмент, а не механизм
освобождения: GC не гарантирует, когда (и будет ли вообще до выхода)
вызван финализатор, и ничего не знает о дефиците дескрипторов, только о
памяти. С Go 1.24 появился `runtime.AddCleanup`: он не воскрешает объект,
допускает несколько обработчиков и не страдает от циклов.
