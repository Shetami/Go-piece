Допишите `Pool[T]` — хранилище, которое выдаёт не указатели, а
хэндлы `Handle{index, gen}`. Так устроены ECS в играх, таблицы
соединений в сетевых серверах, слоты таймеров. Объекты лежат в одном
слайсе, и сборщику мусора не нужно отслеживать тысячи отдельных
аллокаций. Удалённые слоты переиспользуются, а поколение в хэндле
гарантирует, что старая ссылка не попадёт в новый объект, занявший тот же
слот (классическая проблема ABA).

Что проверяют скрытые тесты:

- нулевой `Handle{}` недействителен всегда, даже когда занят слот 0;
- `Get` возвращает указатель на хранимый объект, а не на копию;
- после `Remove` и повторного `Insert` в тот же слот **старый** хэндл не
  даёт ни прочитать, ни удалить новый объект;
- двойной `Remove` возвращает `false` и не ломает пул: два следующих
  `Insert` получают разные слоты;
- `All` выдаёт только живые объекты в порядке слотов и корректно
  останавливается по `break`;
- удалённые объекты собираются сборщиком мусора.

```go
type slot[T any] struct {
	val T
	gen uint32
}

type Pool[T any] struct {
	slots []slot[T]
	free  []uint32
	live  int
}

func (p *Pool[T]) Insert(v T) Handle {
	var i uint32
	if n := len(p.free); n > 0 {
		i = p.free[n-1]
		p.free = p.free[:n-1]
	} else {
		p.slots = append(p.slots, slot[T]{})
		i = uint32(len(p.slots) - 1)
	}
	s := &p.slots[i]
	s.gen++
	s.val = v
	p.live++
	return Handle{index: i, gen: s.gen}
}

func (p *Pool[T]) slotOf(h Handle) *slot[T] {
	if int(h.index) >= len(p.slots) {
		return nil
	}
	s := &p.slots[h.index]
	if s.gen != h.gen || s.gen%2 == 0 {
		return nil
	}
	return s
}

func (p *Pool[T]) Get(h Handle) (*T, bool) {
	if s := p.slotOf(h); s != nil {
		return &s.val, true
	}
	return nil, false
}

func (p *Pool[T]) Remove(h Handle) bool {
	s := p.slotOf(h)
	if s == nil {
		return false
	}
	var zero T
	s.val = zero
	s.gen++
	p.free = append(p.free, h.index)
	p.live--
	return true
}

func (p *Pool[T]) Len() int   { return p.live }
func (p *Pool[T]) Slots() int { return len(p.slots) }

func (p *Pool[T]) All() iter.Seq2[Handle, *T] {
	return func(yield func(Handle, *T) bool) {
		for i := range p.slots {
			s := &p.slots[i]
			if s.gen%2 == 1 && !yield(Handle{index: uint32(i), gen: s.gen}, &s.val) {
				return
			}
		}
	}
}
```

**Чётность поколения вместо флага `used`.** Поколение растёт на единицу и
при занятии слота, и при освобождении, поэтому у занятого слота оно
нечётное, у свободного чётное. Нулевой `Handle{}` имеет `gen == 0`, то
есть чётное, и никогда не совпадёт с живым объектом. Если начинать
поколения с нуля, `Handle{}` стал бы валидной ссылкой на первый объект:
незаполненное поле структуры тихо указывало бы на чужие данные.

**Проверка в `Remove` важнее, чем кажется.** Без неё повторный `Remove`
кладёт индекс в свободный список дважды. Следующие два `Insert` получают
один слот, второй затирает первого, и хэндл первого начинает указывать
на чужой объект. Такие баги проявляются через час работы и не
воспроизводятся.

**Обнулить `val` при удалении.** Слайс слотов живёт столько же, сколько
пул, и всё, на что ссылаются значения в нём, для сборщика мусора
достижимо. Без `s.val = zero` удалённые соединения и буферы висят в
памяти, пока слот не займут снова.

**Указатель из `Get` живёт до следующего `Insert`.** `append` может
переаллоцировать `p.slots`, и старый `*T` будет указывать в брошенный
массив. Об этом стоит сказать на собеседовании. Лекарство — блоки
фиксированного размера, как в арене, или правило «не хранить `*T`,
хранить `Handle`».

**Что спросят дальше.** Что будет при переполнении `uint32`-поколения
(через 2³¹ циклов слот можно вывести из оборота), и зачем держать
свободный список стеком: недавно освобождённый слот ещё в кэше
процессора.
