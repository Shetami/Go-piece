Один `atomic.Int64` на счётчик запросов упирается в потолок на 32
ядрах. Каждое `Add` захватывает строку кэша в эксклюзивное владение, и
ядра по очереди перетаскивают её друг у друга. Решение — шардирование:
несколько счётчиков, `Add` пишет в один из них, `Value` суммирует. Но
если шарды лежат вплотную, восемь `int64` попадают в одну 64-байтную
строку, и ничего не меняется. Это и есть false sharing.

Допишите `shard` и `Counter`.

Что проверяют скрытые тесты:

- `unsafe.Sizeof(shard{})` кратен 64;
- шардов столько, сколько `GOMAXPROCS` **на момент создания**, и сам
  `GOMAXPROCS` при этом не меняется;
- 16 горутин с положительными и отрицательными приращениями дают точную
  сумму, гонок нет;
- `Add` не выделяет память.

<Reveal>

```go
type shard struct {
	n atomic.Int64
	_ [cacheLine - 8]byte
}

type Counter struct {
	shards []shard
}

func NewCounter() *Counter {
	return &Counter{shards: make([]shard, runtime.GOMAXPROCS(0))}
}

func (c *Counter) Add(delta int64) {
	c.shards[rand.IntN(len(c.shards))].n.Add(delta)
}

func (c *Counter) Value() int64 {
	var sum int64
	for i := range c.shards {
		sum += c.shards[i].n.Load()
	}
	return sum
}

func (c *Counter) Shards() int { return len(c.shards) }
```

**Добивка до строки кэша.** Поле `_ [56]byte` делает шард размером ровно
64 байта, и соседние шарды никогда не делят строку. Строго говоря,
нужно ещё, чтобы сам массив начинался на границе 64 байт. Аллокатор
Go выравнивает объекты по классу размера, и для массивов шардов это
обычно выполняется, но не гарантировано. Поэтому иногда добивают с
обеих сторон или берут 128 байт: соседние строки процессор тоже
подкачивает парами. В рантайме Go для этого есть `cpu.CacheLinePad`.

**Почему GOMAXPROCS.** Одновременно выполняется не больше `GOMAXPROCS`
горутин, значит больше шардов не даёт выигрыша, а только замедляет
`Value`. Идеально было бы брать шард по номеру P, на котором работает
горутина. Так делает `sync.Pool` через внутренний `procPin`, но
снаружи рантайма номер P недоступен. Случайный выбор — хороший
компромисс.

**`math/rand/v2` без своего генератора.** Глобальные функции `rand/v2`
используют быстрый генератор рантайма без общего мьютекса и без
аллокаций. Свой `rand.New(...)` на каждый вызов аллоцирует, а один общий
на всех становится новой точкой конкуренции.

**`Value` не атомарен как целое.** Сумма читается по шардам, и пока идёт
цикл, другие горутины продолжают добавлять. Для метрик это нормально:
значение было верным в какой-то момент во время чтения. Для «ровно N
запросов, и точка» такой счётчик не подходит.

**Что спросят дальше.** Как увидеть false sharing: бенчмарк с
`-cpu=1,4,16`, где время на операцию растёт с числом ядер. Чем плох
`[]atomic.Int64` без добивки. И почему `atomic.Int64` в структуре
безопаснее голого `int64` с `atomic.AddInt64`: он гарантированно выровнен
по 8 байт даже на 32-битных платформах.
