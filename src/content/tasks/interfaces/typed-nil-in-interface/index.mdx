`validate` возвращает `*ValidationError` и при удачной проверке отдаёт `nil`.
`check` пересобирает это в `error`. Имя непустое, ошибки быть не должно.

Напишите весь вывод программы.

<Reveal>

```
<nil>
false
сработала ветка обработки ошибки
true
```

**Интерфейс в Go — это пара: тип и значение.** Интерфейс равен `nil` только
тогда, когда обе половины пусты.

Когда `check` пишет `return validate(name)`, происходит преобразование
`*ValidationError` → `error`. Значение действительно `nil`, но тип-то есть:

```
err:   (*ValidationError, nil)   ← не nil, потому что тип заполнен
plain: (nil, nil)                ← вот это nil
```

Отсюда всё остальное. `fmt.Println(err)` печатает `<nil>`, потому что `fmt`
добирается до значения и видит нулевой указатель. А `err == nil` сравнивает
интерфейс целиком — и получает `false`. Ветка обработки ошибки срабатывает на
ошибке, которой нет.

**Почему это так опасно.** Внутри этой ветки обычно зовут `err.Error()` — и
вот тогда прилетает `invalid memory address or nil pointer dereference`, потому
что метод получает нулевой приёмник и лезет в `e.Field`. Программа падает в
месте, где «по коду» ошибки быть не может.

**Как не наступать.** Правило одно: **функция, возвращающая ошибку, объявляет
результат как `error`, а не как конкретный тип.**

```go
func validate(name string) error {      // а не *ValidationError
	if name == "" {
		return &ValidationError{Field: "name"}
	}
	return nil                          // теперь это честный nil-интерфейс
}
```

`go vet` такое не ловит, а вот `golangci-lint` с линтером `nilness` — ловит.

**Что спросят следом.** Скорее всего, про `errors.Is` и `errors.As`: они
работают с цепочкой обёрток, но от этой ловушки не спасают — `errors.Is(err, nil)`
не то же самое, что `err == nil`. И про `%v` против `%#v` в выводе: `%#v` сразу
показал бы `(*main.ValidationError)(nil)` и снял бы вопрос.

</Reveal>
