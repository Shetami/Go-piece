Напишите `Limit` — свой тип, реализующий `io.Reader`, и его метод `Read`.
Пакетный `io.LimitReader` использовать нельзя — это он и есть.

Что проверяют скрытые тесты:

- `"hello, world"` с лимитом 5 → `"hello"`;
- источник короче лимита → всё, что есть;
- лимит 0 → сразу `0, io.EOF`;
- после чтения с лимитом 4 в источнике остаются ровно все байты после
  четвёртого — лишнего из него не берут;
- чтение буфером в 2 байта работает так же, как большим.

<Reveal>

```go
type limited struct {
	r    io.Reader
	left int64
}

func (l *limited) Read(p []byte) (int, error) {
	if l.left <= 0 {
		return 0, io.EOF
	}
	if int64(len(p)) > l.left {
		p = p[:l.left]
	}
	n, err := l.r.Read(p)
	l.left -= int64(n)
	return n, err
}

func Limit(r io.Reader, n int64) io.Reader {
	return &limited{r: r, left: n}
}
```

**Метод на указателе.** `Read` уменьшает `left`, и это должно сохраниться
до следующего вызова. С методом на значении каждый вызов работал бы с
копией, и лимит никогда бы не кончался.

**Буфер обрезают до вызова источника.** Прочитать всё, что влезло в `p`, и
потом отдать вызывающему только часть — значит, потерять хвост: из
источника он уже вычитан. Тест с «остатком в источнике» это и проверяет.

**`l.left -= int64(n)`, а не `len(p)`.** Источник вправе вернуть меньше,
чем просили.

Ровно так устроен `io.LimitReader`: тип `io.LimitedReader` с полями `R` и
`N`.

</Reveal>
