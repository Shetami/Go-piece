Лог за день лежит в сотне файлов-кусков, и отдать его нужно одним потоком.
`io.MultiReader` склеит `io.Reader`, но о закрытии не знает: если открыть
все файлы заранее и закрыть в конце, на тысячах частей кончатся файловые
дескрипторы. Нужна склейка, которая закрывает каждую часть, как только та
прочитана, а общий `Close` подбирает всё, что осталось.

Напишите `Concat` по контракту из заготовки.

Что проверяют скрытые тесты:

- части с данными вместе с `io.EOF`, пустая часть посередине — поток
  `"hello!"` и закрытие каждой части сразу после её EOF; общий `Close` после
  этого ничего не закрывает повторно; `Concat()` — сразу EOF;
- `Close` на середине закрывает недочитанную и ещё не начатую части по
  порядку, обе ошибки видны; повторный `Close` — `nil`, `Read` — `ErrClosed`;
- ошибка закрытия исчерпанной части: `Read` возвращает прочитанные байты и
  ошибку `part 0: …`, чтение следующей части продолжается, а общий `Close`
  не закрывает часть второй раз;
- обычная ошибка чтения части — как есть, без автоматического закрытия.

<Reveal>

```go
var ErrClosed = errors.New("concat: read after close")

type concat struct {
	parts  []io.ReadCloser
	idx    int
	closed bool
}

func Concat(parts ...io.ReadCloser) io.ReadCloser {
	return &concat{parts: parts}
}

func (c *concat) Read(p []byte) (int, error) {
	if c.closed {
		return 0, ErrClosed
	}
	for len(c.parts) > 0 {
		n, err := c.parts[0].Read(p)
		if err == io.EOF {
			cur := c.parts[0]
			c.parts[0] = nil
			c.parts = c.parts[1:]
			i := c.idx
			c.idx++
			if cerr := cur.Close(); cerr != nil {
				return n, fmt.Errorf("part %d: %w", i, cerr)
			}
			if n > 0 {
				return n, nil
			}
			continue
		}
		if n > 0 || err != nil {
			return n, err
		}
	}
	return 0, io.EOF
}

func (c *concat) Close() error {
	if c.closed {
		return nil
	}
	c.closed = true
	var errs []error
	for _, rc := range c.parts {
		if err := rc.Close(); err != nil {
			errs = append(errs, err)
		}
	}
	c.parts = nil
	return errors.Join(errs...)
}
```

**EOF части — не EOF потока.** Если вернуть наружу `n, io.EOF` от первой
части, `io.ReadAll` остановится на первой же склейке. Контракт `io.Reader`
позволяет вернуть `n > 0, nil` — и следующий `Read` пойдёт уже в следующую
часть. Пустую часть пропускаем в том же вызове (`continue`): иначе
получится `0, nil` без прогресса.

**Убрать из списка до `Close`.** Часть исключается из `c.parts` ещё до вызова
её `Close`. Если сделать наоборот и `Close` вернул ошибку, ранний `return`
оставит часть в списке, и общий `Close` закроет её второй раз. Двойное
закрытие файла — ошибка, а двойное закрытие чужого соединения из пула — баг,
который ищут неделями.

**Индекс части — в тексте ошибки.** «disk full» среди сотни кусков ничего не
даёт; «part 37: disk full» — сразу место. `%w` сохраняет исходную ошибку для
`errors.Is`.

**Ошибка чтения — не повод закрывать.** После сетевой ошибки вызывающий может
решить повторить или выяснить состояние; закрытие — его решение, через общий
`Close`. Автоматически закрываем только то, что точно больше не нужно, —
дочитанное до конца.

Что спросят дальше: как открывать части лениво — принимать не
`io.ReadCloser`, а функции `func() (io.ReadCloser, error)`, чтобы в каждый
момент был открыт ровно один файл.

</Reveal>
