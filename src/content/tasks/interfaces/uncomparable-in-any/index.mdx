`equal` сравнивает два `any` оператором `==` и перехватывает панику, если она
случится. Пять вызовов на разных парах значений.

Напишите весь вывод программы.

<Reveal>

**Интерфейсы сравниваются в два шага.** Сначала сравниваются динамические
типы. Если они разные — результат `false`, и на этом всё. Если одинаковые —
сравниваются значения, и вот тут тип должен быть сравнимым.

- `1` и `1` — оба `int`, значения равны: `true`.
- `1` и `int64(1)` — типы разные, до значений дело не доходит: `false`.
- `[]int{1}` и `[]int{1}` — типы совпали, значит надо сравнивать слайсы, а
  слайсы несравнимы. Компилятор этого не видит: статически здесь `any == any`.
  Рантайм паникует: `runtime error: comparing uncomparable type []int`.
- `[]int{1}` и `"x"` — типы разные, `false` **без паники**, хотя внутри слайс.
- мапа и `nil` — у `nil`-интерфейса типа нет вовсе, типы не совпали, `false`.

Итого:

```
true <nil>
false <nil>
false runtime error: comparing uncomparable type []int
false <nil>
false <nil>
```

**Где это встречается.** Кэши и дедупликация на `map[any]T` или `==` по
`any`: код работает месяцами, пока туда впервые не прилетает слайс. Для
значений неизвестного типа есть `reflect.DeepEqual`, а для ключей — явная
сериализация во что-то сравнимое.

И ещё одна тонкость: `comparable` в дженериках с Go 1.20 пропускает `any`,
поэтому `func Index[T comparable]` тоже может запаниковать на слайсе внутри
интерфейса. Ограничение гарантирует, что `==` скомпилируется, но не что оно
не упадёт.

</Reveal>
