Допишите методы `Eval` и `String` для `Num`, `Add`, `Mul` и `Neg`, чтобы
все четыре реализовали `Expr`.

Что проверяют скрытые тесты:

- `Mul{Add{Num{2}, Num{3}}, Neg{Num{4}}}` вычисляется в `-20` и
  печатается как `((2 + 3) * -4)`;
- `Num{0.5}` → `"0.5"`, `Num{100}` → `"100"`;
- `fmt.Sprint(e)` печатает то же, что `e.String()`;
- узлы работают и по значению, и по указателю: `&Neg{&Num{3}}`.

<Reveal>

```go
func (n Num) Eval() float64  { return n.V }
func (n Num) String() string { return strconv.FormatFloat(n.V, 'g', -1, 64) }
func (a Add) Eval() float64  { return a.L.Eval() + a.R.Eval() }
func (a Add) String() string { return "(" + a.L.String() + " + " + a.R.String() + ")" }
func (m Mul) Eval() float64  { return m.L.Eval() * m.R.Eval() }
func (m Mul) String() string { return "(" + m.L.String() + " * " + m.R.String() + ")" }
func (n Neg) Eval() float64  { return -n.X.Eval() }
func (n Neg) String() string { return "-" + n.X.String() }
```

**Рекурсия идёт через интерфейс.** `Add` не знает, что у него внутри —
число или другое выражение: он зовёт `Eval` у поля типа `Expr`, и
динамическая диспетчеризация выбирает нужную реализацию.

**Методы на значении** — потому что узлы ничего не меняют. Бонус: набор
методов `*Num` включает методы `Num`, поэтому `&Num{3}` тоже реализует
`Expr`. С методами на указателе `Num{3}` интерфейс бы не реализовал.

**`String` делает узел `fmt.Stringer`** — `fmt.Sprint(e)` вызывает его сам.

**Добавить новый тип узла легко** — ещё один тип с двумя методами. А вот
добавить новую *операцию* (например, «упростить») — значит дописать метод
во все типы. Это известная асимметрия; если операции добавляются чаще
узлов, вместо методов используют type switch в отдельных функциях.

</Reveal>
