Каталог магазина сортируется «по рейтингу»: сначала высокий рейтинг, при
равном рейтинге — по `id` по возрастанию, товары без оценок (`rating IS NULL`)
идут в самом конце. Показываются только активные товары (`is_active`).

`OFFSET` на больших каталогах тормозит и «прыгает», когда товары
добавляются, поэтому API отдаёт страницы по **курсору**: клиент присылает
значения сортировки последней строки, которую уже видел. Сейчас это товар
`id = 12` с рейтингом `4.5`.

Верните **следующую страницу** — 6 товаров, идущих в выдаче сразу после
курсора.

- колонки: `id`, `name`, `rating`;
- порядок: как в каталоге — `rating` по убыванию, `NULL` в конце, при
  равенстве `id` по возрастанию.

Что проверяют скрытые данные: у курсора есть «соседи» с тем же рейтингом
по обе стороны, среди них есть неактивные, а страница доходит до товаров
без оценок.

<Reveal>

```sql
SELECT id, name, rating
FROM products
WHERE is_active
  AND (   rating < 4.5
       OR (rating = 4.5 AND id > 12)
       OR rating IS NULL)
ORDER BY rating DESC NULLS LAST, id
LIMIT 6;
```

Ответ:

```
15 | Капсулы | 4.5
20 | Кофе в зёрнах | 4.5
7 | Термос | 4.2
5 | Кофемолка | 3.9
2 | Кружка | NULL
9 | Поднос | NULL
```

**Условие курсора повторяет `ORDER BY` дословно.** «После курсора» — это
всё, что сортировка ставит дальше: рейтинг хуже, или рейтинг тот же, но
`id` больше, или рейтинга нет вовсе. Тай-брейкер `id` обязателен: без него
порядок товаров с оценкой 4.5 не определён, и Сито с Капсулами могли бы
поменяться местами между запросами — один товар показался бы дважды, другой
ни разу.

**Сравнение строк `(rating, id) < (4.5, 12)` здесь не подходит.** Оно
лексикографическое и работает, только когда оба ключа идут в одну сторону
(`DESC, DESC` или `ASC, ASC`). У нас `rating DESC, id ASC`: запись с
кортежем вернула бы Сито (`id = 10`), которое уже было на прошлой странице,
и потеряла бы Капсулы и Кофе. Для смешанных направлений — развёрнутое `OR`.

**`NULL` дважды ломает наивное решение.** `ORDER BY rating DESC` в Postgres
ставит `NULL` **первыми** (для `DESC` по умолчанию `NULLS FIRST`), поэтому
нужно явное `NULLS LAST`. А `rating < 4.5` для `NULL` даёт `NULL`, не
`true`, — без `OR rating IS NULL` Кружка и Поднос никогда не попадут ни на
одну страницу.

**Что спросят дальше.** Какой индекс нужен? `(rating DESC NULLS LAST, id)`
— тогда `ORDER BY … LIMIT` читает индекс по порядку и останавливается через
6 строк, а не сортирует весь каталог. Условие с `OR` планировщик хуже
превращает в диапазон индекса, чем кортеж, — поэтому на практике иногда
хранят «ключ сортировки» одним столбцом (например, `-rating` и
`coalesce(…, -1)`) или приводят направления к одному. И если курсор сам
оказался среди товаров без оценки, условие сокращается до
`rating IS NULL AND id > :id`.
