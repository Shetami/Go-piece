Маркетинг запускает рассылку. Соберите список адресов из `customers` по
правилам:

- адрес есть: не `NULL`, не пустая строка и не строка из одних пробелов;
- клиент не заблокирован. `is_blocked IS NULL` — флаг просто не
  заполняли, такой клиент **не** заблокирован;
- страна — не `BY`. Клиенты с неизвестной страной (`NULL`) в рассылку
  попадают;
- адреса нет в таблице жёстких отказов `bounces`;
- адреса сравниваются без учёта регистра и пробелов по краям
  (`lower(trim(…))`) — и с `bounces`, и между собой: на один адрес уходит
  одно письмо, даже если он записан у нескольких клиентов.

Колонки: `email` — нормализованный адрес (`lower(trim(email))`),
`customer_id` — наименьший `id` среди подходящих клиентов с этим адресом.
Порядок: по `email`.

Что проверяют скрытые данные: `NULL` во флаге блокировки и в стране,
пустые и «пробельные» адреса, строку с `NULL` в `bounces`, один адрес в
разном регистре у двух клиентов.

<Reveal>

```sql
SELECT DISTINCT ON (lower(trim(c.email)))
       lower(trim(c.email)) AS email,
       c.id                 AS customer_id
FROM customers c
WHERE nullif(trim(c.email), '') IS NOT NULL
  AND c.is_blocked IS NOT TRUE
  AND c.country IS DISTINCT FROM 'BY'
  AND NOT EXISTS (
        SELECT 1 FROM bounces b
        WHERE lower(trim(b.email)) = lower(trim(c.email)))
ORDER BY lower(trim(c.email)), c.id;
```

Ответ:

```
anna@mail.ru | 1
boris@gmail.com | 2
ivan@mail.ru | 12
vera@yandex.ru | 3
zhanna@corp.com | 10
```

**Главная ловушка — `NOT IN` по подзапросу с `NULL`.** В `bounces` есть
строка, где адрес не распарсился. `x NOT IN (a, NULL)` раскрывается в
`x <> a AND x <> NULL`, второе слагаемое — `NULL`, и всё условие не бывает
`true` ни для одной строки. Наивный запрос возвращает **пустой** список, и
рассылка молча не уходит никому. `NOT EXISTS` к `NULL` устойчив: строка с
`NULL` просто не находит пары.

**Каждое «не равно» по nullable-колонке теряет `NULL`.** `NOT is_blocked`
для `NULL` — `NULL`, и Боря с Верой и Жанной выпадают. `country <> 'BY'` —
то же для Веры. Нужны операторы, которые на `NULL` отвечают `true`/`false`:
`IS NOT TRUE` и `IS DISTINCT FROM`.

**Пустая строка — не `NULL`.** `email IS NOT NULL` пропускает `''` и
`'   '`. `nullif(trim(email), '')` сводит оба случая к `NULL` одной
проверкой.

**Дедупликация через `DISTINCT ON`.** Боря записан дважды: `' Boris@Gmail.com '`
и `boris@gmail.com`. `DISTINCT ON (ключ)` оставляет первую строку каждой
группы в порядке `ORDER BY`, поэтому `ORDER BY` обязан начинаться с того же
выражения, а следом — с тай-брейкера `c.id`, который решает, *какая* строка
первая. Итоговый порядок по `email` получается сам.

**Что спросят дальше.** Как сделать, чтобы такие данные не появлялись? Хранить
адрес уже нормализованным (или колонку `citext`), повесить уникальный индекс
на `lower(email)`, а `is_blocked` сделать `NOT NULL DEFAULT false` — трёхзначная
логика во флагах почти всегда баг схемы, а не задумка.
