Руководитель поддержки планирует смены и просит разбить обращения
**за март 2024** по сменам и типу дня. Поддержка работает по
**московскому времени** (`Europe/Moscow`, UTC+3), `created_at` хранится
как `timestamptz`.

- март — по московскому времени: с 1 марта 00:00 до 1 апреля 00:00 МСК;
- смены по московскому часу: `ночь` — 00:00–07:59, `день` — 08:00–15:59,
  `вечер` — 16:00–23:59;
- будни — понедельник–пятница, выходные — суббота и воскресенье, тоже по
  московскому календарю.

Колонки: `shift`, `weekdays`, `weekends` — количество обращений.
Порядок: `ночь`, `день`, `вечер`.

Результат не должен зависеть от часового пояса сессии базы.

<Reveal>

```sql
WITH local AS (
  SELECT created_at AT TIME ZONE 'Europe/Moscow' AS ts
  FROM tickets
),
march AS (
  SELECT extract(hour FROM ts)   AS h,
         extract(isodow FROM ts) AS dow
  FROM local
  WHERE ts >= '2024-03-01' AND ts < '2024-04-01'
),
s AS (
  SELECT CASE WHEN h < 8 THEN 1 WHEN h < 16 THEN 2 ELSE 3 END AS k, dow
  FROM march
)
SELECT CASE k WHEN 1 THEN 'ночь' WHEN 2 THEN 'день' ELSE 'вечер' END AS shift,
       count(*) FILTER (WHERE dow < 6)  AS weekdays,
       count(*) FILTER (WHERE dow >= 6) AS weekends
FROM s
GROUP BY k
ORDER BY k;
```

Ответ:

```
ночь | 2 | 1
день | 3 | 1
вечер | 1 | 3
```

**`timestamptz` — это момент, а не «часы на стене».** Postgres хранит его
в UTC и при выводе, `extract` и сравнении со строкой переводит в пояс
**сессии** (`SHOW TimeZone`). Наивный `extract(hour FROM created_at)` даёт
разный ответ на ноутбуке разработчика и на сервере отчётов. `AT TIME ZONE
'Europe/Moscow'` превращает момент в `timestamp` без пояса — ровно то, что
показывали часы в Москве, и дальше всё считается по нему.

**Сдвиг меняет не только час, но и день.** Обращение 1 (29 февраля 21:30
UTC) — это уже 1 марта 00:30 по Москве: март, ночь, пятница. Обращение 8
(31 марта 21:00 UTC) — уже апрель. Обращение 13 (пятница 21:00 UTC) — в
Москве суббота, полночь: смена ночная, день — выходной. Граница месяца,
смена и тип дня считаются после перевода, иначе они разъедутся.

**Способ записи на входе не важен.** Обращение 9 введено как `10:00+03` —
это тот же момент, что `07:00 UTC`. После `AT TIME ZONE` оно честно
попадает в дневную смену. По UTC-часам оно было бы ночным.

**Пояс по имени, а не смещению.** `AT TIME ZONE '+03'` в Postgres
трактуется по POSIX — знак наоборот, это UTC−3. Имя `Europe/Moscow`
однозначно и сам учтёт историю перехода на летнее время, если отчёт
захватит годы до 2014-го.

**Что спросят дальше.** Индекс по `created_at` работает для диапазона по
моменту, а не по выражению `AT TIME ZONE`. На большой таблице границы
месяца переводят в моменты заранее: `created_at >= '2024-03-01
00:00+03' AND created_at < '2024-04-01 00:00+03'` — и уже внутри считают
локальные часы.
