CRM ищет дубли клиентов: один и тот же телефон, записанный по-разному.
Телефон вводят как попало: со скобками, дефисами, пробелами, через `8` или
`+7`, иногда без кода страны.

Нормализация:

- оставить только цифры;
- 11 цифр, начинающихся с `7` или `8`, — российский номер: `+7` и
  последние 10 цифр;
- ровно 10 цифр — номер без кода страны: `+7` и эти 10 цифр;
- всё остальное (пусто, `NULL`, слишком короткие номера) — телефона нет,
  такие клиенты дублями не считаются.

Найдите нормализованные телефоны, которые встречаются больше чем у одного
клиента.

- колонки: `phone` (`+7XXXXXXXXXX`), `customers` — сколько клиентов,
  `ids` — их `id` по возрастанию через запятую с пробелом (`1, 2, 3`);
- порядок: `customers` по убыванию, затем `phone`.

<Reveal>

```sql
WITH digits AS (
  SELECT id, regexp_replace(phone, '[^0-9]', '', 'g') AS d
  FROM customers
),
norm AS (
  SELECT id,
         CASE WHEN length(d) = 11 AND left(d, 1) IN ('7', '8') THEN '+7' || right(d, 10)
              WHEN length(d) = 10 THEN '+7' || d
         END AS phone
  FROM digits
)
SELECT phone,
       count(*)                               AS customers,
       string_agg(id::text, ', ' ORDER BY id) AS ids
FROM norm
WHERE phone IS NOT NULL
GROUP BY phone
HAVING count(*) > 1
ORDER BY customers DESC, phone;
```

Ответ:

```
+79161234567 | 3 | 1, 2, 3
+74951112233 | 2 | 11, 12
+79030001122 | 2 | 4, 5
```

**Самый громкий дубль — пустой.** Если просто вырезать нецифровые символы,
`''` и `'  '` превращаются в одну и ту же пустую строку — и Егор с Ильёй
становятся «дублями». В проде на такой группе сливают тысячи клиентов без
телефона. Пустая строка — полноценное значение и группируется, как любое
другое; `NULL` тоже образует свою группу в `GROUP BY`. Поэтому невалидное
превращается в `NULL` (у `CASE` без `ELSE` это поведение по умолчанию) и
явно отфильтровывается.

**Нормализация до сравнения.** `+7 (916) 123-45-67`, `8 916 123 45 67` и
`9161234567` — один номер. Сначала цифры, потом приведение к одному виду:
`8` и `7` в начале 11-значного номера — одно и то же, 10 цифр — номер без
кода. Короткие `123` и `12` не должны случайно совпасть ни с чем.

**Порядок внутри `string_agg`.** Без `ORDER BY id` внутри агрегата
порядок id не гарантирован — `'2, 1, 3'` отличается от `'1, 2, 3'`, хотя
по смыслу одно и то же. А тай-брейкер `phone` решает порядок двух групп по
2 клиента.

**Что спросят дальше.** Нормализованный телефон стоит хранить отдельной
колонкой (или генерируемой: `GENERATED ALWAYS AS (…) STORED`) и повесить на
неё индекс — искать дубли при регистрации, а не отчётом. Для настоящей
нормализации международных номеров — библиотека вроде libphonenumber в
приложении, а не регулярка в SQL.
