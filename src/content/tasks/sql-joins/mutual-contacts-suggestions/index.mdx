B2B-платформа контактов хочет блок «Возможно, вы знакомы». Кандидат для
пользователя — тот, с кем у него есть **хотя бы один общий контакт**, но
кто сам ему **ещё не контакт**. Чем больше общих контактов, тем выше
кандидат.

Связь в `connections` взаимная, но хранится одной строкой в произвольном
направлении: `(1, 2)` значит и «1 знает 2», и «2 знает 1». После миграции
часть связей записана дважды — в обе стороны. Бывают и мусорные петли
«пользователь знает сам себя».

Удалённые пользователи (`is_deleted`) не предлагаются и **не считаются
общими контактами** — через них никого не рекомендуют.

- колонки: `user_name`, `suggestion`, `mutual` — число разных общих
  контактов;
- на пользователя — не больше **двух** кандидатов: с наибольшим `mutual`,
  при равенстве — с меньшим `id`;
- пользователи без кандидатов в отчёт не попадают;
- порядок: по `id` пользователя, затем `mutual` по убыванию, затем по `id`
  кандидата.

Что проверяют скрытые данные: связь, хранящаяся «против» ожидаемого
направления, связь, записанная в обе стороны, кандидат, доступный только
через удалённого пользователя, петля, пользователь, у которого все друзья
друзей уже в контактах, ничья за второе место.

<Reveal>

```sql
WITH edges AS (
  SELECT user_a AS src, user_b AS dst FROM connections
  UNION
  SELECT user_b, user_a FROM connections
),
alive AS (
  SELECT e.src, e.dst
  FROM edges e
  JOIN users s ON s.id = e.src AND NOT s.is_deleted
  JOIN users d ON d.id = e.dst AND NOT d.is_deleted
  WHERE e.src <> e.dst
),
candidates AS (
  SELECT f1.src AS user_id, f2.dst AS candidate_id, count(*) AS mutual
  FROM alive f1
  JOIN alive f2 ON f2.src = f1.dst
  WHERE f2.dst <> f1.src
    AND NOT EXISTS (
      SELECT 1 FROM alive x WHERE x.src = f1.src AND x.dst = f2.dst
    )
  GROUP BY f1.src, f2.dst
),
ranked AS (
  SELECT *, row_number() OVER (PARTITION BY user_id ORDER BY mutual DESC, candidate_id) AS rn
  FROM candidates
)
SELECT u.name AS user_name, c.name AS suggestion, r.mutual
FROM ranked r
JOIN users u ON u.id = r.user_id
JOIN users c ON c.id = r.candidate_id
WHERE r.rn <= 2
ORDER BY r.user_id, r.mutual DESC, r.candidate_id;
```

Ответ:

```
Аня | Гоша | 2
Аня | Ира | 2
Вера | Дина | 2
Гоша | Аня | 2
Гоша | Ира | 2
Дина | Вера | 2
Дина | Аня | 1
Ира | Аня | 2
Ира | Гоша | 2
```

**Неориентированный граф сначала делают симметричным.** `UNION` двух
направлений даёт по строке на каждое «кто → кого знает» и заодно
схлопывает связи, записанные в обе стороны (`UNION`, а не `UNION ALL`:
иначе `(2, 3)` и `(3, 2)` дали бы по две одинаковые дуги, и каждый общий
контакт через них посчитался бы дважды). Без симметризации связь `(3, 1)`
не нашлась бы из Ани, и её друзья друзей через Веру потерялись бы.

**Друзья друзей — самосоединение дуг: `f1.dst = f2.src`.** Каждая строка
результата — путь «пользователь → общий контакт → кандидат», поэтому
`count(*)` после группировки по паре и есть число общих контактов — при
условии, что дуги уникальны.

**Три исключения, и все — разной природы.** Путь обратно к себе (`f2.dst
<> f1.src`) — это ограничение в `WHERE`. Уже знакомые — анти-соединение
`NOT EXISTS` по тем же дугам: Боря знаком со всеми своими друзьями друзей и
остаётся без кандидатов. Удалённые — фильтр *до* самосоединения, по обоим
концам дуги: Жора знаком только с удалённым Егором, и через Егора его Ане не
предложат. Петля Зои убрана условием `src <> dst`.

**Top-2 на пользователя — окно поверх агрегата.** У Ани три кандидата:
Гоша и Ира по два общих контакта, Дина — один; ничья между Гошей и Ирой не
мешает, а Дина за бортом. Тай-брейкер по `id` в окне делает выбор
детерминированным.

**Что спросят дальше.** «Как это масштабировать на миллионы людей?» — у
популярного узла с 10 000 контактов самосоединение даёт 10⁸ путей через
него. В проде кандидатов считают офлайн, ограничивают число контактов,
через которые идёт обход, и хранят граф в обоих направлениях сразу с
индексом по `(src, dst)`.
