Складской учёт. Аудиторы присылают запросы `stock_checks`: какой был
остаток товара `sku` на складе `warehouse_id` в момент `at` (**включительно**
— движение, проведённое ровно в `at`, уже учтено).

Остаток восстанавливается так:

- берётся **последняя инвентаризация** этого товара на этом складе с
  `counted_at <= at` — её `qty` и есть остаток на момент пересчёта;
  движения, проведённые ровно в `counted_at`, в пересчёт **уже вошли**;
- к ней прибавляются все движения **после** инвентаризации и не позже
  `at`;
- если инвентаризаций до `at` не было — остаток равен сумме всех движений
  не позже `at`; если и движений нет — `0`.

- колонки: `check_id`, `qty`;
- каждый запрос — ровно одной строкой;
- порядок: по `check_id`.

Что проверяют скрытые данные: движение ровно в момент инвентаризации и
ровно в момент запроса, две инвентаризации до момента запроса, запрос
раньше первой инвентаризации, товар без инвентаризаций, два движения в одну
секунду, тот же товар на другом складе, товар, которого на складе не было.

<Reveal>

```sql
SELECT s.id AS check_id,
       coalesce(c.qty, 0) + coalesce(m.delta, 0) AS qty
FROM stock_checks s
LEFT JOIN LATERAL (
  SELECT ic.qty, ic.counted_at
  FROM inventory_counts ic
  WHERE ic.warehouse_id = s.warehouse_id
    AND ic.sku = s.sku
    AND ic.counted_at <= s.at
  ORDER BY ic.counted_at DESC
  LIMIT 1
) c ON true
LEFT JOIN LATERAL (
  SELECT sum(mv.delta) AS delta
  FROM movements mv
  WHERE mv.warehouse_id = s.warehouse_id
    AND mv.sku = s.sku
    AND mv.moved_at <= s.at
    AND (c.counted_at IS NULL OR mv.moved_at > c.counted_at)
) m ON true
ORDER BY s.id;
```

Ответ:

```
1 | 80
2 | 85
3 | 90
4 | 80
5 | 5
6 | 15
7 | 0
8 | 0
9 | 50
```

**«Последняя запись не позже момента» — это `LATERAL … ORDER BY … DESC
LIMIT 1`.** Для каждого запроса своя точка отсчёта: запрос 2 (9 апреля) опирается
на пересчёт 1 апреля, запрос 3 (10 апреля) — уже на пересчёт 10-го. Обычным
соединением это не выразить без размножения: условие `counted_at <= at`
найдёт *все* прошлые инвентаризации.

**Второй `LATERAL` видит результат первого.** Подзапрос движений ссылается
на `c.counted_at` — колонку, которую только что выбрал предыдущий `LATERAL`.
Так в одном `FROM` строится цепочка «сначала найди опору, потом досчитай от
неё». Агрегат без `GROUP BY` всегда возвращает ровно одну строку (с `NULL`,
если движений нет), поэтому `m` не размножает и не теряет запросы.

**Границы асимметричны, и обе важны.** Движение в момент инвентаризации
уже в пересчёте — `moved_at > counted_at` строго: иначе у запроса 1 спишется
лишний −3, а у запроса 3 — −4. Движение в момент запроса — учтено:
`moved_at <= at`. Запрос 6 попадает ровно на два одновременных списания.

**Опоры может не быть.** У товара B нет инвентаризаций — остаток считается
от нуля по всем движениям (запрос 6). Запрос 9 сделан до первой
инвентаризации — учитывается только приход 30 марта. `LEFT JOIN LATERAL` и
ветка `c.counted_at IS NULL` покрывают оба случая; `CROSS JOIN LATERAL` их
бы потерял.

**Склад — часть ключа.** Товар A есть на двух складах; соединение только
по `sku` смешает их остатки (запрос 5).

**Что спросят дальше.** «Как сделать это быстро на миллионах движений?» —
индекс `(warehouse_id, sku, moved_at)` и такой же для инвентаризаций:
оба `LATERAL` станут короткими проходами по индексу. А для отчёта «остаток
на каждый день» выгоднее один проход с нарастающей суммой по окну.
