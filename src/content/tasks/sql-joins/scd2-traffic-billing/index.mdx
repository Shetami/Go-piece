Провайдер выставляет счета за трафик за **июнь 2024 года**. Трафик клиента
по дням — в `usage`. Каждый день тарифицируется по тарифу, который
действовал у клиента **в этот день**.

**История тарифов** `client_tariffs` — SCD2: версия действует на `[valid_from,
valid_to)`, у текущей `valid_to` пуст. Менеджеры иногда заводят новую версию,
не закрыв старую, поэтому версии могут пересекаться. Правило: в день действует
версия с **самым поздним `valid_from`**, при равенстве — с **самым поздним
`loaded_at`**.

**Справочник** `tariffs`: при смене цены старую строку тарифа не удаляют, а
помечают `archived = true`. Цена берётся из неархивной строки с тем же `code`.

- колонки: `client`, `billed_gb` — гигабайты, которые удалось
  протарифицировать, `unbilled_gb` — гигабайты в дни, когда у клиента не было
  тарифа, `amount` — `sum(gb × price_per_gb)`, `round(…, 2)`;
- клиенты без трафика в июне — в отчёте с нулями;
- порядок: по `client`.

Что проверяют скрытые данные: смена тарифа ровно в день потребления, две
версии с одинаковым `valid_from`, незакрытая старая версия под новой, день
после окончания короткой версии, трафик до подключения, трафик за май,
архивная цена тарифа.

<Reveal>

```sql
WITH priced AS (
  SELECT u.client_id, u.gb, t.price_per_gb
  FROM usage u
  LEFT JOIN LATERAL (
    SELECT ct.tariff_code
    FROM client_tariffs ct
    WHERE ct.client_id = u.client_id
      AND ct.valid_from <= u.day
      AND (ct.valid_to IS NULL OR u.day < ct.valid_to)
    ORDER BY ct.valid_from DESC, ct.loaded_at DESC
    LIMIT 1
  ) v ON true
  LEFT JOIN tariffs t ON t.code = v.tariff_code AND NOT t.archived
  WHERE u.day >= '2024-06-01' AND u.day < '2024-07-01'
)
SELECT c.name AS client,
       coalesce(sum(p.gb) FILTER (WHERE p.price_per_gb IS NOT NULL), 0) AS billed_gb,
       coalesce(sum(p.gb) FILTER (WHERE p.price_per_gb IS NULL), 0)     AS unbilled_gb,
       round(coalesce(sum(p.gb * p.price_per_gb), 0), 2)                AS amount
FROM clients c
LEFT JOIN priced p ON p.client_id = c.id
GROUP BY c.id, c.name
ORDER BY c.name;
```

Ответ:

```
Астра | 20 | 0 | 37.00
Бриз | 40 | 0 | 57.00
Вега | 12.5 | 5 | 15.00
Гранит | 0 | 0 | 0.00
```

**Соединение по диапазону с пересекающимися интервалами размножает строки.**
У Бриза 10 июня под условие «день внутри интервала» попадают три версии:
незакрытый `start`, `max` и `pro`. Обычный `JOIN` тарифицирует этот день
трижды. Нужна не «любая подходящая» версия, а **одна по правилу** — это
ровно «top-1 на строку», и `LATERAL … ORDER BY … LIMIT 1` выражает его
напрямую. `DISTINCT ON (u.client_id, u.day)` с той же сортировкой — вторая
идиоматичная запись.

**Разбор Бриза по дням:** 9 июня — `start` по 2.50; 10 и 19 — `pro` (тот же
`valid_from`, что у `max`, но загружен позже) по 1.20; 20 июня `pro` уже
закончился, и действует `max` — не `start`, потому что у `max` `valid_from`
позже. Итого 25 + 12 + 12 + 8 = 57.

**Дубли в справочнике — второй источник размножения.** У `start` две
строки, действующая одна. Без `NOT t.archived` в `ON` каждый день на
`start` посчитается дважды — по 2.00 и по 2.50. Условие на *правую*
таблицу `LEFT JOIN` — в `ON`, иначе дни без тарифа потеряются.

**Полуоткрытый интервал.** Астра сменила тариф 15 июня: 14-го — старый, 15-го
— уже новый. `BETWEEN valid_from AND valid_to` отдаёт 15 июня обоим тарифам.

**Не терять ни трафик, ни клиентов.** Вега подключилась 5 июня, трафик 1
июня тарифицировать нечем — это `unbilled_gb`, а не пропажа строки (второй
`LEFT JOIN`). Гранит не потреблял ничего — внешний `LEFT JOIN` от
`clients` и `coalesce` дают ему нули.

**Что спросят дальше.** «Как не допускать пересечений?» — в SCD2 версию
закрывают в той же транзакции, где открывают новую, а базу страхует
`EXCLUDE USING gist (client_id WITH =, daterange(valid_from, valid_to) WITH
&&)`. И «почему фильтр по июню внутри CTE, а не в `WHERE` внешнего
запроса?» — там он убил бы клиентов без трафика.
