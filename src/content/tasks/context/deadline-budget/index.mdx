Обработчик последовательно ходит в три сервиса. Если отдать первому весь
дедлайн, медленный первый вызов съест время остальных, и запрос упадёт
по таймауту, так ничего и не сделав. Если поделить заранее на три,
быстрый первый вызов «сэкономит» время, которое никому не достанется.
Напишите `CallSequence`: перед каждым вызовом делить *текущий* остаток на
число оставшихся вызовов.

Что проверяют скрытые тесты:

- 900 мс на три мгновенных вызова: ≈300, ≈450 и ≈900 мс — сэкономленное
  переходит дальше;
- контексты вызовов отменены после `CallSequence`;
- зависший вызов получает только свою долю, ошибка — `DeadlineExceeded`
  с его именем, следующие не вызываются;
- доля меньше `minBudget` — `ErrNoBudget` сразу, без вызова;
- без дедлайна у `ctx` — вызовы без таймаута;
- ошибка вызова — с его именем; отменённый `ctx` — ни одного вызова.

<Reveal>

```go
func CallSequence(ctx context.Context, minBudget time.Duration, calls []Call) error {
	for i, c := range calls {
		if err := callOne(ctx, minBudget, len(calls)-i, c); err != nil {
			return err
		}
	}
	return nil
}

func callOne(ctx context.Context, minBudget time.Duration, left int, c Call) error {
	if err := ctx.Err(); err != nil {
		return fmt.Errorf("%s: %w", c.Name, context.Cause(ctx))
	}
	callCtx := ctx
	if dl, ok := ctx.Deadline(); ok {
		share := time.Until(dl) / time.Duration(left)
		if share < minBudget {
			return fmt.Errorf("%s: доля %v меньше %v: %w", c.Name, share, minBudget, ErrNoBudget)
		}
		var cancel context.CancelFunc
		callCtx, cancel = context.WithTimeout(ctx, share)
		defer cancel()
	}
	if err := c.Do(callCtx); err != nil {
		return fmt.Errorf("%s: %w", c.Name, err)
	}
	return nil
}
```

**Остаток — через `ctx.Deadline()`, а не через исходное число.** Функция
не знает, сколько времени дали запросу, и не должна знать: дедлайн мог
прийти сверху из заголовка, и часть бюджета уже потрачена. `time.Until(dl)`
перед каждым вызовом — единственный честный источник.

**Делить на оставшихся, а не на всех.** `remaining / left` автоматически
перераспределяет сэкономленное: быстрый вызов оставляет больше тем, кто
идёт после. У последнего вызова — весь остаток.

**Минимальная доля экономит зависимости.** Вызов с таймаутом 5 мс почти
наверняка упадёт, но нагрузку на зависимость создаст. Отказаться сразу —
и вызывающий быстрее получит понятную ошибку, и соседний сервис не
получит мусорный запрос. Это тот же принцип, что у gRPC: не отправлять
запрос с уже истёкшим дедлайном.

**Функция на вызов — ради `defer cancel()`.** В цикле `defer` копил бы
таймеры до конца `CallSequence`.

**Что спросят дальше:** почему не делить пропорционально ожидаемой
латентности (p99 каждой зависимости), как оставить запас на
сериализацию ответа, и что меняется, если вызовы можно делать
параллельно.
