Стриминговая выгрузка отчёта может идти час, и общий дедлайн ей не
подходит: убьёт живую выгрузку. Но если источник замолчал на 30 секунд,
соединение, скорее всего, мертво, и держать его незачем. Нужен таймаут
*простоя*: каждый прочитанный кусок продлевает срок. Так устроены
`IdleTimeout` у `http.Server` и keepalive в gRPC. Напишите
`WithIdleTimeout`.

Что проверяют скрытые тесты:

- активность каждые 20 мс при `idle` = 200 мс — контекст живёт вчетверо
  дольше порога, а после последнего `touch` отменяется примерно через
  `idle` с причиной `ErrIdle` (и `Err() == Canceled`);
- без `touch` — отмена через `idle`;
- `touch` после отмены не воскрешает контекст и не меняет причину;
- отмена родителя — причина родителя; `cancel` — `Canceled`, не
  `ErrIdle`, повторный безопасен;
- восемь горутин одновременно вызывают `touch` — без гонок и без ложной
  отмены.

<Reveal>

```go
func WithIdleTimeout(parent context.Context, idle time.Duration) (ctx context.Context, touch func(), cancel context.CancelFunc) {
	ctx, cancelCause := context.WithCancelCause(parent)
	timer := time.AfterFunc(idle, func() { cancelCause(ErrIdle) })
	stop := context.AfterFunc(ctx, func() { timer.Stop() })

	touch = func() {
		if ctx.Err() != nil {
			return
		}
		timer.Reset(idle)
	}
	cancel = func() {
		cancelCause(context.Canceled)
		stop()
		timer.Stop()
	}
	return ctx, touch, cancel
}
```

**`WithTimeout` здесь не подходит в принципе.** Дедлайн контекста
неизменяем: его нельзя сдвинуть, только создать новый дочерний
контекст — а у дочернего дедлайн не может быть позже родительского.
Поэтому скользящий срок строится вручную: обычный отменяемый контекст
плюс таймер, который его отменяет.

**`time.AfterFunc` — таймер без горутины.** Функция запустится в
отдельной горутине только при срабатывании, а `Reset` просто
перезаводит время. Альтернатива — горутина с `select` по таймеру и
каналу «активность» — работает, но это лишняя горутина на каждое
соединение и лишний канал, в который `touch` может заблокироваться.

**Гонка «сработал — продлили» безопасна.** Если таймер успел сработать
между проверкой `ctx.Err()` и `Reset`, контекст уже отменён — и отмена
необратима. `Reset` перезаведёт таймер, но его повторный
`cancelCause` ничего не изменит: первая причина остаётся. А
`context.AfterFunc` остановит таймер при любой отмене, в том числе от
родителя, чтобы он не висел впустую.

**Причина различает сценарии.** Для вызывающего `ErrIdle` значит
«соединение подвисло — можно переподключиться», а `Canceled` от
родителя — «сервер останавливается, переподключаться не надо».

**Что спросят дальше:** как совместить таймаут простоя с общим
потолком (дочерний `WithTimeout` поверх этого контекста) и почему
`touch` на каждый прочитанный байт — плохая идея: `Reset` не бесплатен,
продлевают по куску или не чаще раза в N миллисекунд.
