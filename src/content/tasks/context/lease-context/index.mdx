Одна реплика из трёх — лидер: только она запускает миграции и
планировщик. Лидерство — это аренда в etcd с TTL, которую нужно
регулярно продлевать. Если продление не удалось, лидером уже может быть
кто-то другой, и вся работа под лидерством должна немедленно
остановиться. Удобнее всего выразить это контекстом. Напишите
`WithLease`.

Что проверяют скрытые тесты:

- пока продления успешны, контекст жив, а `renew` вызывается по
  расписанию;
- `renew` вернул ошибку — контекст отменён, причина отвечает и на
  `ErrLeaseLost`, и на исходную ошибку; продлений больше нет;
- `renew` завис — через `interval` он получает таймаут, и аренда
  считается потерянной;
- отмена родителя — причина родителя, фоновая горутина вышла;
- `cancel` посреди упрямого `renew` возвращается только после его
  окончания; повторный `cancel` безопасен.

<Reveal>

```go
func WithLease(parent context.Context, interval time.Duration, renew func(context.Context) error) (context.Context, context.CancelFunc) {
	ctx, cancel := context.WithCancelCause(parent)
	done := make(chan struct{})
	go func() {
		defer close(done)
		t := time.NewTicker(interval)
		defer t.Stop()
		for {
			select {
			case <-ctx.Done():
				return
			case <-t.C:
			}
			rctx, rcancel := context.WithTimeout(ctx, interval)
			err := renew(rctx)
			rcancel()
			if err != nil {
				cancel(fmt.Errorf("%w: %w", ErrLeaseLost, err))
				return
			}
		}
	}()
	return ctx, func() {
		cancel(context.Canceled)
		<-done
	}
}
```

**Причина отмены — главное, что отличает это от `WithCancel`.** Код под
лидерством видит `ctx.Err() == Canceled` в обоих случаях — и когда
сервис штатно останавливается, и когда лидерство перехватили.
`context.Cause` позволяет различить: в первом случае выйти тихо, во
втором — записать алерт и откатить незавершённую операцию.

**Продление с таймаутом.** Зависшее хранилище не должно держать нас в
иллюзии лидерства: TTL аренды тикает на сервере независимо от нас.
Таймаут на `renew` не больше интервала (в проде — заметно меньше TTL)
превращает зависание в явную потерю.

**`cancel` ждёт горутину.** Иначе после `cancel()` продление ещё может
идти и успешно продлить аренду, которую мы уже отпустили, — другая
реплика не сможет стать лидером до следующего TTL. `<-done` в `cancel`
даёт жёсткую гарантию «после возврата — ничего». Цена — `cancel` нельзя
вызывать из самого `renew`: будет дедлок, и это записано в контракте.

**Первая причина побеждает.** `CancelCauseFunc` на уже отменённом
контексте ничего не делает, поэтому ошибка продления после штатного
`cancel` не перепишет причину на «аренда потеряна».

**Что спросят дальше:** почему одной аренды мало для безопасности
записи (процесс мог уснуть на GC после проверки) и что такое fencing
token — монотонный номер, который хранилище проверяет на каждой записи.
