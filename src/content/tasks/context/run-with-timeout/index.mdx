Напишите `RunWithTimeout`: запустить `f` с контекстом с таймаутом `d`. Если
`f` не уложилась, вернуть `DeadlineExceeded` сразу — даже если `f` контекст
игнорирует и продолжает работать.

Что проверяют скрытые тесты:

- быстрая `f` — возвращается её ошибка (или `nil`);
- у контекста, который получает `f`, есть дедлайн;
- упрямая `f`, которая спит две секунды, — `RunWithTimeout` возвращается
  через ~30 мс с `DeadlineExceeded`;
- отменённый родитель — `Canceled`.

<Reveal>

```go
func RunWithTimeout(ctx context.Context, d time.Duration, f func(context.Context) error) error {
	ctx, cancel := context.WithTimeout(ctx, d)
	defer cancel()

	done := make(chan error, 1)
	go func() { done <- f(ctx) }()

	select {
	case err := <-done:
		return err
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

**Горутина — чтобы было на что не ждать.** Вызвать `f` напрямую и
вернуться раньше неё невозможно. Запустив её в горутине, мы ждём через
`select` то, что наступит раньше: результат или дедлайн.

**Буфер на одно значение обязателен.** Если мы ушли по таймауту, `f`
когда-нибудь закончит и попытается отправить результат. Без буфера
отправка повиснет навсегда — утечка горутины на каждый таймаут.

**Честная оговорка.** `RunWithTimeout` перестаёт *ждать* `f`, но не
останавливает её. Упрямая `f` продолжит работать и держать ресурсы. В Go
нельзя убить горутину снаружи — поэтому вся система отмены построена на
сотрудничестве: функция должна сама слушать `ctx.Done()`. Эта обёртка —
для чужого кода, который вы не можете поправить, и то с пониманием, что
под нагрузкой брошенные горутины будут копиться.

</Reveal>
