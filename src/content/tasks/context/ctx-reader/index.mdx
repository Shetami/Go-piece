Сервис читает загрузку из источника, у которого нет ни дедлайнов, ни
`Close` посреди чтения, — скажем, из пайпа внешней утилиты. Клиент ушёл,
контекст отменён, а горутина обработчика висит в `Read`. Напишите
обёртку `NewReader`: её `Read` возвращается сразу по отмене контекста.

Что проверяют скрытые тесты:

- без отмены данные проходят без потерь, `io.ReadAll` работает;
- `n > 0` вместе с `io.EOF` передаются как есть;
- отмена, пока источник висит, — `Read` сразу возвращает `0` и причину
  отмены;
- когда источник потом всё-таки проснётся и что-то запишет, буфер,
  который вызывающий передал в прерванный `Read`, не изменится;
- после отмены следующие `Read` возвращают ошибку, не трогая источник;
- отменённый заранее контекст — источник не вызывается ни разу.

<Reveal>

```go
func (c *ctxReader) Read(p []byte) (int, error) {
	if c.ctx.Err() != nil {
		return 0, context.Cause(c.ctx)
	}
	buf := make([]byte, len(p))
	done := make(chan readResult, 1)
	go func() {
		n, err := c.r.Read(buf)
		done <- readResult{n, err}
	}()
	select {
	case res := <-done:
		copy(p, buf[:res.n])
		return res.n, res.err
	case <-c.ctx.Done():
		return 0, context.Cause(c.ctx)
	}
}
```

**Прервать можно только ожидание, а не сам `Read`.** Блокирующий вызов
источника никто остановить не в силах — ни контекст, ни горутина. Мы
уводим его в отдельную горутину и ждём в `select`, где вторая ветка —
отмена. Сам нижний `Read` продолжает висеть, пока источник не ответит
или не закроется.

**Главная ловушка — чей буфер.** Если отдать горутине `p` напрямую,
получится гонка: мы уже вернули управление, вызывающий переиспользует
`p` под следующий кусок, а проснувшийся источник пишет туда свои байты.
Такой баг не ловится обычными тестами и портит данные молча. Поэтому
источник пишет в собственный буфер, а в `p` копируем только при успехе.

**Буферизованный канал — чтобы не утечь.** Когда нас прервали, результат
никто не прочитает; с каналом без буфера горутина висела бы на отправке
вечно. С буфером она доотправит и завершится, как только источник
проснётся.

**После отмены источник больше не трогаем.** Висящий нижний `Read` может
всё ещё идти; второй параллельный `Read` у большинства ридеров — гонка.

**Что спросят дальше:** почему для сетевых соединений так не делают, а
ставят `conn.SetReadDeadline` (или закрывают соединение в
`context.AfterFunc`), и как избавиться от аллокации буфера на каждый
`Read` — одна долгоживущая горутина-читатель или `sync.Pool`.

</Reveal>
