Фоновый цикл в сервисе: раз в минуту пересобрать кэш, отправить
метрики, почистить просроченные сессии. Обычно его пишут как
`for range time.Tick(d) { go f() }` — и получают сразу четыре проблемы.
Напишите `Every` без них.

Что проверяют скрытые тесты:

- первый вызов — сразу, а не через `interval` (здесь он — час);
- ошибка `f` останавливает цикл и возвращается из `Every`;
- отмена посреди часового ожидания — `Every` сразу возвращает причину, и
  `f` больше не вызывается;
- вызовы `f` никогда не перекрываются;
- после вызова, который работал 20 интервалов, пропущенные тики не
  выстреливают пачкой;
- `f` получает переданный контекст.

<Reveal>

```go
func Every(ctx context.Context, interval time.Duration, f func(context.Context) error) error {
	t := time.NewTicker(interval)
	defer t.Stop()
	for n := 1; ; n++ {
		if ctx.Err() != nil {
			return context.Cause(ctx)
		}
		if err := f(ctx); err != nil {
			return fmt.Errorf("every: запуск %d: %w", n, err)
		}
		select {
		case <-t.C:
		case <-ctx.Done():
			return context.Cause(ctx)
		}
	}
}
```

**`go f()` на каждый тик — перекрытие.** Если прогон длиннее
интервала, запуски начинают наслаиваться: два пересчёта кэша пишут в
одно место, нагрузка на базу растёт ровно тогда, когда она и так
медленная. Вызов в той же горутине, что ждёт тики, исключает это по
построению.

**Тикер не копит тики.** У канала `Ticker.C` буфер на одно значение, и
лишние тики просто теряются. После долгого вызова будет ровно один
вызов «вдогонку», а не двадцать подряд. `time.After` в цикле тоже не
копит, но сдвигает расписание на длительность `f` — если нужна именно
частота, тикер честнее.

**Проверка `ctx.Err()` в начале итерации.** Если к моменту `select` готовы
и тик, и отмена, `select` выбирает случайно — и может запустить `f`
уже после отмены. Явная проверка это закрывает.

**`time.Tick` без остановки — утечка до Go 1.23.** С 1.23 сборщик
забирает неиспользуемые тикеры, но `NewTicker` + `defer Stop()` по-прежнему
яснее выражает время жизни.

**Что спросят дальше:** как добавить jitter к интервалу, чтобы сто
реплик не ходили в базу в одну секунду, и как сделать так, чтобы задачу
выполняла только одна реплика (лидерство, advisory lock).
