Необработанная паника в любой горутине завершает весь процесс — вместе
с сотней запросов, которые шли параллельно. HTTP-сервер из stdlib ловит
паники обработчиков, но горутины, которые вы запустили сами, никто не
страхует.

Напишите `RunAll` и методы `PanicError`.

Что проверяют скрытые тесты:

- все задачи успешны (и задач нет) → `nil`;
- ошибки задач собраны в порядке задач, а не завершения, и `errors.Is`
  их находит;
- паника строкой, паника рантайма (запись в `nil`-мапу) и паника ошибкой
  — процесс жив, остальные задачи доработали; каждая паника — `*PanicError`
  с индексом и значением; `errors.As` достаёт `runtime.Error`, а
  `errors.Is` — ошибку, которой паниковали;
- в стеке есть функция, в которой случилась паника;
- `panic(nil)` тоже ловится.

<Reveal>

```go
func (e *PanicError) Error() string {
	return fmt.Sprintf("задача %d: паника: %v", e.Task, e.Value)
}

func (e *PanicError) Unwrap() error {
	err, _ := e.Value.(error)
	return err
}

func RunAll(tasks ...func() error) error {
	errs := make([]error, len(tasks))
	var wg sync.WaitGroup
	for i, task := range tasks {
		wg.Add(1)
		go func() {
			defer wg.Done()
			defer func() {
				if r := recover(); r != nil {
					errs[i] = &PanicError{Task: i, Value: r, Stack: debug.Stack()}
				}
			}()
			if err := task(); err != nil {
				errs[i] = fmt.Errorf("задача %d: %w", i, err)
			}
		}()
	}
	wg.Wait()
	return errors.Join(errs...)
}
```

**`recover` — только в той же горутине.** Паника раскручивает стек своей
горутины, и отложенные функции другой горутины её не видят. `defer
recover()` в `RunAll` бесполезен: процесс упадёт раньше. Страховка —
в каждой запущенной горутине.

**Стек снимать внутри `defer`.** Отложенная функция выполняется, пока
стек паникующей горутины ещё не раскручен до конца, поэтому
`debug.Stack()` там показывает место паники — в тесте это
`chkBoomNilMap`. Снятый позже стек был бы бесполезен.

**`Unwrap` по значению паники.** Если паниковали ошибкой, она должна
остаться видимой: `errors.Is(err, ErrDiskFull)` и `errors.As(err,
&runtime.Error)` — стандартные проверки, и `PanicError` не должен их
ломать. Если значение не ошибка, `Unwrap` возвращает `nil` — цепочка
просто заканчивается.

**`panic(nil)` с Go 1.21 — не `nil`.** Раньше `recover()` возвращал `nil`
и паника «исчезала» — нельзя было отличить её от отсутствия паники.
Теперь в `recover` приходит `*runtime.PanicNilError`, и проверки `r !=
nil` достаточно.

**Что спросят дальше.** Стоит ли вообще восстанавливаться после паники
(после `nil`-мапы — да, после порчи общих данных — лучше упасть), как
отправлять такие ошибки в Sentry со стеком, и почему `errgroup` паники не
ловит.
