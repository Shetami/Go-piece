`defer f.Close()` — привычка, которая иногда теряет данные. Файл,
`bufio.Writer`, gzip, загрузка в S3 — у всех них данные окончательно
уходят только при закрытии, и именно там появляется ошибка «нет места»
или «соединение разорвано». Если её проигнорировать, функция отчитается
об успехе, а файл окажется обрезанным.

Напишите `Save`.

Что проверяют скрытые тесты:

- успех — `nil`, данные записаны, `Close` вызван один раз;
- упала запись — `Close` всё равно вызван, ошибка с префиксом `запись:`;
- упал только `Close` — ошибка с префиксом `закрытие:`;
- упали оба — видны обе, сначала запись;
- писатель принял половину данных и промолчал — это `io.ErrShortWrite`.

<Reveal>

```go
func Save(w io.WriteCloser, data []byte) (err error) {
	defer func() {
		if cerr := w.Close(); cerr != nil {
			err = errors.Join(err, fmt.Errorf("закрытие: %w", cerr))
		}
	}()
	n, werr := w.Write(data)
	if werr == nil && n < len(data) {
		werr = io.ErrShortWrite
	}
	if werr != nil {
		return fmt.Errorf("запись: %w", werr)
	}
	return nil
}
```

**Отложенная функция видит и меняет именованный результат.** `return
fmt.Errorf(…)` сначала присваивает значение `err`, потом выполняются
`defer`, и только потом функция возвращается. Поэтому в `defer` можно
дополнить уже выбранную ошибку.

**`errors.Join` не затирает.** Частая ошибка — `err = w.Close()` в
`defer`: при упавшей записи и успешном закрытии она превращает сбой в
`nil`. `Join` с `nil` возвращает вторую ошибку как есть, а с двумя
ненулевыми — обе. Одна строка покрывает все четыре случая.

**Короткая запись.** Контракт `io.Writer` требует вернуть ошибку при `n
< len(p)`, но не все реализации его соблюдают. `io.Copy` и `bufio`
проверяют это сами — и нам стоит.

**Когда ошибку Close можно игнорировать.** У читателя (`os.Open` для
чтения, тело HTTP-ответа) данные уже получены, и ошибка закрытия ничего не
меняет. У писателя — никогда.

`f.Sync()`, как сделать атомарную замену через временный файл и
`os.Rename`, и что будет, если `Close` вызвать дважды.
