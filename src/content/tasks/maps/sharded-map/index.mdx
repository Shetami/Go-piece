Одна мапа под одним мьютексом — узкое место, когда её рвут сотни горутин.
Классический приём: разбить на n шардов, у каждого своя мапа и свой
`sync.RWMutex`, шард выбирается по хэшу ключа. Реализуйте
`ShardedMap[V]`; поля — на ваше усмотрение, контракт — в заготовке.

Для хэша пригодится `hash/maphash` (`maphash.String`) или `hash/fnv`.

Что проверяют скрытые тесты:

- обычные операции при n = 0, 1 и 16;
- 40 горутин по 50 раз делают `Update(+1)` по трём ключам, а `fn`
  нарочно уступает процессор между чтением и записью — сумма должна быть
  ровно 2000;
- `Update` с `keep=false` удаляет ключ, для отсутствующего ключа `ok=false`;
- внутри `Range` вызывают `Set` и `Delete` — обход должен закончиться, а не
  зависнуть;
- `Range` останавливается, как только `fn` вернула `false`.

<Reveal>

```go
type ShardedMap[V any] struct {
	seed   maphash.Seed
	shards []*shard[V]
}

type shard[V any] struct {
	mu sync.RWMutex
	m  map[string]V
}

func (s *ShardedMap[V]) shardFor(key string) *shard[V] {
	return s.shards[maphash.String(s.seed, key)%uint64(len(s.shards))]
}

func (s *ShardedMap[V]) Update(key string, fn func(v V, ok bool) (V, bool)) {
	sh := s.shardFor(key)
	sh.mu.Lock()
	defer sh.mu.Unlock()
	old, ok := sh.m[key]
	if nv, keep := fn(old, ok); keep {
		sh.m[key] = nv
	} else {
		delete(sh.m, key)
	}
}

func (s *ShardedMap[V]) Range(fn func(key string, v V) bool) {
	type kv struct {
		k string
		v V
	}
	for _, sh := range s.shards {
		sh.mu.RLock()
		batch := make([]kv, 0, len(sh.m))
		for k, v := range sh.m {
			batch = append(batch, kv{k, v})
		}
		sh.mu.RUnlock()
		for _, p := range batch {
			if !fn(p.k, p.v) {
				return
			}
		}
	}
}
```

(Конструктор и простые методы — в эталонном решении.)

**`Update` — ради него всё и затевается.** `v, _ := m.Get(k); m.Set(k, v+1)`
— это check-then-act: каждый вызов по отдельности защищён, а пара — нет.
Между `Get` и `Set` другая горутина успевает записать своё, и её инкремент
теряется. Детектор гонок тут молчит — гонки на памяти нет, есть гонка на
логике. Чтение, вычисление и запись должны идти под **одной** блокировкой
на запись.

**Range без блокировки во время колбэка.** Если держать `RLock` шарда и
звать `fn`, то `Set` из `fn` попросит `Lock` того же шарда — и будет ждать,
пока отпустят `RLock`, который держит та же горутина. `RWMutex` не
реентерабелен: вечный дедлок. Решение — снять копию шарда под `RLock` и
звать `fn` без блокировок. Цена — слабая согласованность: `Range` видит
каждый шард на свой момент времени, а не всю мапу разом.

**Хэш и число шардов.** `maphash` со случайным сидом защищает от подбора
ключей, которые все лягут в один шард (hash flooding). Число шардов обычно
берут степенью двойки и `& (n-1)` вместо `%` — но и `%` работает при любом n.
`n = 0` без `max(n, 1)` — паника деления на ноль.

**`Len` не атомарен.** Шарды считаются по очереди, и сумма — это «примерно
сейчас». Точный `Len` потребовал бы взять все блокировки сразу, в одном и
том же порядке, чтобы не словить дедлок.

**Что спросят дальше.** Чем это лучше `sync.Map` (та хороша для «пишем
редко, читаем часто» и непересекающихся ключей по горутинам), и почему у
`shard` иногда добавляют паддинг до 64 байт — ложное разделение кэш-линий
между мьютексами соседних шардов.
