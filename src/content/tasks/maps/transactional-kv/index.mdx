Одна из самых частых задач на live-coding: хранилище ключ-значение с
транзакциями, которые вкладываются друг в друга, как `SAVEPOINT` в базе.
Реализуйте `Store`; поля и конструктор — на ваше усмотрение, точная
семантика каждой операции — в заготовке.

Что проверяют скрытые тесты:

- `Rollback` восстанавливает ключ, который менялся в транзакции дважды,
  удалённый ключ и отсутствие нового ключа; `Count` сходится и внутри
  транзакции, и после отката;
- `Commit` вложенной транзакции, затем `Rollback` внешней — откатывается
  всё, до состояния перед внешним `Begin`;
- откат только внутренней транзакции не трогает изменения внешней;
- `ErrNoTx` для `Commit` и `Rollback` без транзакции;
- пустая строка как значение, удаление отсутствующего ключа;
- 2000 коротких транзакций на хранилище в 100 000 ключей — откат не
  должен копировать всё хранилище.

<Reveal>

```go
type Store struct {
	data   map[string]string
	counts map[string]int
	undo   []map[string]prevVal
}

type prevVal struct {
	val     string
	existed bool
}

func (s *Store) remember(k string) {
	if len(s.undo) == 0 {
		return
	}
	log := s.undo[len(s.undo)-1]
	if _, ok := log[k]; ok {
		return
	}
	v, ok := s.data[k]
	log[k] = prevVal{v, ok}
}

func (s *Store) Rollback() error {
	if len(s.undo) == 0 {
		return ErrNoTx
	}
	log := s.undo[len(s.undo)-1]
	s.undo = s.undo[:len(s.undo)-1]
	for k, p := range log {
		s.apply(k, p.val, p.existed)
	}
	return nil
}

func (s *Store) Commit() error {
	if len(s.undo) == 0 {
		return ErrNoTx
	}
	log := s.undo[len(s.undo)-1]
	s.undo = s.undo[:len(s.undo)-1]
	if len(s.undo) == 0 {
		return nil
	}
	parent := s.undo[len(s.undo)-1]
	for k, p := range log {
		if _, ok := parent[k]; !ok {
			parent[k] = p
		}
	}
	return nil
}
```

(`apply`, который меняет `data` и `counts`, и простые методы — в эталонном
решении.)

**Журнал отмены вместо копии.** Самое простое решение — на `Begin`
копировать всю мапу, на `Rollback` возвращать копию. Это O(размер
хранилища) на каждую транзакцию: тест с 100 000 ключей это видит. Здесь
изменения пишутся сразу в `data`, а транзакция хранит только «что было до
меня» для затронутых ключей — откат стоит O(изменённых ключей).

**Помнить только первое изменение.** `Set a=2`, потом `Set a=3` в одной
транзакции: откатывать надо к `1`, а не к `2`. Поэтому `remember` пишет
ключ в журнал один раз. Отсутствие ключа — тоже состояние (`existed:
false`): без него откат не удалит ключ, созданный в транзакции.

**Слияние журналов при `Commit` — главная ловушка.** Внешняя транзакция
поменяла `a` с `1` на `2`, внутренняя — с `2` на `3` и закоммитилась.
Если при слиянии перезаписать запись родителя (`parent[k] = p`), в журнале
внешней окажется «до меня было `2`», и её откат вернёт `2` вместо `1`.
Родителю переходят только ключи, которых он ещё не трогал.

**`Count` за O(1) — вторая мапа.** Счётчик «значение → сколько ключей»
меняется в одном месте, в `apply`, — и при обычной записи, и при откате.
Если откат пишет в `data` напрямую, мимо `apply`, счётчики разъезжаются.
Обнулившиеся значения удаляем, чтобы мапа не росла.

**Что спросят дальше.** Альтернатива журналу — слои: каждая транзакция
держит мапу своих изменений с надгробиями для удалений, `Get` ищет сверху
вниз. `Rollback` тогда O(1), зато `Get` — O(глубины), а `Count` сложнее.
И как это соотносится с настоящей базой: undo-лог — это подход Oracle и
MySQL, а Postgres хранит версии строк прямо в таблице (MVCC).
