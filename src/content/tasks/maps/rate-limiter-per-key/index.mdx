API-шлюзу нужно ограничить каждого клиента: не больше `rate` запросов в
секунду в среднем, с допустимым всплеском до `burst`. Реализуйте `Limiter`
— по ведру токенов на ключ. Поля — на ваше усмотрение, правила — в заготовке.

Время берётся только из `now`: тесты двигают часы вручную.

Что проверяют скрытые тесты:

- новый ключ пропускает ровно `burst` запросов; ключи не мешают друг другу;
- после часа простоя ведро снова `burst`, а не 3600;
- `rate = 2`, `burst = 2`, запросы раз в 300 мс — за 6 секунд пропускается около 13, а не
  заметно меньше;
- `Cleanup` удаляет полное ведро и не трогает пустое — иначе клиент
  обходит лимит;
- 50 горутин одновременно бьют в один ключ с `burst = 10` — пропущено ровно
  10.

<Reveal>

```go
type Limiter struct {
	mu      sync.Mutex
	rate    float64
	burst   float64
	now     func() time.Time
	buckets map[string]*tokenBucket
}

type tokenBucket struct {
	tokens float64
	last   time.Time
}

func (l *Limiter) refill(b *tokenBucket, t time.Time) {
	if el := t.Sub(b.last).Seconds(); el > 0 {
		b.tokens = min(l.burst, b.tokens+el*l.rate)
	}
	b.last = t
}

func (l *Limiter) Allow(key string) bool {
	l.mu.Lock()
	defer l.mu.Unlock()
	t := l.now()
	b, ok := l.buckets[key]
	if !ok {
		b = &tokenBucket{tokens: l.burst, last: t}
		l.buckets[key] = b
	}
	l.refill(b, t)
	if b.tokens < 1 {
		return false
	}
	b.tokens--
	return true
}

func (l *Limiter) Cleanup() int {
	l.mu.Lock()
	defer l.mu.Unlock()
	t := l.now()
	n := 0
	for k, b := range l.buckets {
		l.refill(b, t)
		if b.tokens >= l.burst {
			delete(l.buckets, k)
			n++
		}
	}
	return n
}
```

**Ленивое пополнение вместо тикера.** Никакой горутины, которая раз в
секунду доливает все вёдра: токены досчитываются в момент обращения по
прошедшему времени. Так миллион ключей не стоит ничего, пока к ним не
обращаются.

**Дробные токены.** Классическая ошибка — хранить целые токены и
пополнять на `int(elapsed * rate)`, сдвигая `last` на каждом вызове. При
запросах раз в 300 мс и `rate = 2` каждый раз доливается `int(0.6) = 0` —
и ведро не пополняется никогда. Либо храните `float64`, либо сдвигайте
`last` только на время, за которое начислены целые токены.

**Потолок `min(burst, …)`.** Без него клиент, молчавший час, получает 3600
токенов и одним залпом обрушивает бэкенд — ровно то, от чего лимитер
защищает.

**Чистка по полноте ведра.** Ключи клиентов копятся бесконечно — это утечка.
Удалить можно только ведро, которое уже снова полно: новый ключ стартует
с полным ведром, так что для клиента ничего не меняется. Удалить «давно
созданное» или просто пустое ведро — значит подарить клиенту свежий `burst`.

**Мьютекс на всю мапу.** Проверка «есть токен?» и списание — одна
операция; без блокировки 50 горутин увидят один и тот же токен. На
больших нагрузках мапу шардируют, как в задаче про шардированную мапу. В
проде есть готовый `golang.org/x/time/rate`, а распределённый лимит
делают в Redis скриптом на Lua — спросят, почему там нужна атомарность.
