Реализуйте `LRU`: кэш на `capacity` записей. Когда места нет, вытесняется
запись, к которой дольше всего не обращались. Обращение — это и `Get`, и
`Put`. Поля структуры выбирайте сами, конструктор тоже можно менять.

Что проверяют скрытые тесты:

- `Get` находит положенное и не находит отсутствующее;
- вытесняется именно самая давняя по обращению запись, а не по вставке;
- `Put` существующего ключа обновляет значение и тоже освежает запись;
- `Len` не превышает ёмкость на тысяче вставок.

<Reveal>

```go
type LRU struct {
	capacity int
	order    *list.List
	items    map[string]*list.Element
}

func (c *LRU) Get(key string) (int, bool) {
	el, ok := c.items[key]
	if !ok {
		return 0, false
	}
	c.order.MoveToFront(el)
	return el.Value.(*entry).value, true
}
```

(`Put` — в эталонном решении.)

**Две структуры, потому что каждая умеет своё.** Мапа находит запись по
ключу за O(1), но порядка не знает. Двусвязный список хранит порядок
обращений и умеет переставить узел в начало или вынуть хвост за O(1), но не
умеет искать. Мапа хранит указатели на узлы списка — и обе операции
становятся O(1).

**Ключ в узле списка.** При вытеснении мы достаём узел из хвоста, и надо
удалить запись и из мапы. Для этого в узле хранится ключ — иначе пришлось бы
искать его перебором.

**`container/list`** хранит значения как `any`, отсюда приведения
`el.Value.(*entry)`. Можно написать свой двусвязный список на дженериках — это
частая просьба «а теперь без `container/list`».

**Что спросят следом.** Потокобезопасность: мьютекс вокруг всех методов,
причём и `Get` пишет (переставляет узел), так что `RWMutex` не поможет. И
почему в высоконагруженных кэшах LRU часто заменяют на приближения (CLOCK,
шардирование по ключу): один мьютекс на весь кэш становится узким местом.

</Reveal>
