Не каждая паника должна превращаться в ошибку: иногда процесс и правда
должен упасть, но сначала — оставить в логе понятную запись. Напишите
`LogPanic`.

Что проверяют скрытые тесты:

- без паники `fn` выполнена, лог пуст;
- паника строкой — одна запись со значением, дальше летит та же строка;
- паника рантайма (запись в `nil`-мапу) — дальше летит `runtime.Error`, а в
  логе есть стек с функцией, **где** упало;
- `panic(nil)` тоже логируется и летит дальше.

<Reveal>

```go
func LogPanic(logf func(msg string), fn func()) {
	defer func() {
		if r := recover(); r != nil {
			logf(fmt.Sprintf("паника: %v\n%s", r, debug.Stack()))
			panic(r)
		}
	}()
	fn()
}
```

**`panic(r)`, а не `panic(fmt.Sprint(r))`.** Выше по стеку может стоять
обработчик, который смотрит на тип значения: `http.ErrAbortHandler`,
свой `mustPanic`, `runtime.Error`. Превратив значение в строку, вы
сломаете их все.

**Стек — в отложенной функции.** Пока выполняются `defer`, кадры
паникующей функции ещё не сняты, поэтому `debug.Stack()` показывает
`chkBrokenHandler`. Повторная паника напечатает стек уже от места
`panic(r)` — поэтому исходный и надо сохранить до неё.

**`panic(nil)`.** С Go 1.21 `recover` в этом случае возвращает
`*runtime.PanicNilError`, а не `nil`, так что проверка `r != nil`
работает. В старых версиях такая паника была невидима для `recover`.

**Что спросят следом.** Чем это отличается от `recover` без повторной
паники (процесс продолжит работу в неизвестном состоянии) и почему
`net/http` сам ловит паники обработчиков, а горутины, запущенные из
обработчика, — нет.

</Reveal>
