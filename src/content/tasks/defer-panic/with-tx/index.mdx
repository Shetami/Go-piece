Реализуйте `WithTx`. Сигнатуру можно поменять, если сохранить параметры и
тип результата.

Что проверяют скрытые тесты:

- `fn` успешна — вызван только `Commit`, результат — `nil`;
- `fn` вернула ошибку — только `Rollback`, наружу — ошибка `fn`;
- `Commit` вернул ошибку — она возвращается;
- `fn` запаниковала — вызван `Rollback`, а паника **продолжает лететь** с
  тем же значением. Проглатывать её нельзя.

<Reveal>

```go
func WithTx(tx Tx, fn func() error) (err error) {
	defer func() {
		if r := recover(); r != nil {
			_ = tx.Rollback()
			panic(r)
		}
	}()

	if err := fn(); err != nil {
		_ = tx.Rollback()
		return err
	}
	return tx.Commit()
}
```

**recover — чтобы откатить, а не чтобы спасти.** Паника означает, что
программа в неизвестном состоянии. Проглотить её и вернуть ошибку —
значит скрыть баг. Но оставлять транзакцию открытой тоже нельзя: она будет
держать блокировки, пока соединение не закроется. Поэтому: перехватили,
откатили, `panic(r)` — снова.

**Почему не `defer tx.Rollback()` и всё.** Это популярный приём с
`database/sql`: `Rollback` после успешного `Commit` просто возвращает
`sql.ErrTxDone`, и его игнорируют. Он проще и тоже переживает панику. Но
здесь в тестах проверяется точная последовательность вызовов, а для своего
интерфейса лишний `Rollback` после `Commit` может быть ошибкой.

**Ошибка отката.** В ветке ошибки её можно добавить через
`errors.Join(err, rbErr)` — тогда вызывающий узнает, что откат тоже не
удался. В ветке паники её вернуть некуда — остаётся залогировать.

**Что спросят следом.** Повторы транзакции при `serialization failure`:
`WithTx` в цикле, если ошибка — конфликт сериализации. Это частая обёртка
для PostgreSQL на уровне `SERIALIZABLE`.

</Reveal>
