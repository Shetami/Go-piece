Напишите тела `Must` и `Catch`. Вместе они позволяют писать цепочку
вызовов без `if err != nil` на каждом шаге, а на границе получить обычную
ошибку.

Что проверяют скрытые тесты:

- `Must(parse("42"))` → 42;
- `Catch` без паники → `nil`, код внутри отработал целиком;
- неудачный `Must` внутри `Catch` → `Catch` возвращает исходную ошибку
  (`errors.Is` находит сентинел), код после `Must` не выполняется;
- `panic("чужая")` внутри `Catch` пролетает наружу;
- `panic(err)` без `Must` — тоже чужая паника, `Catch` её не ловит.

<Reveal>

```go
type mustPanic struct{ err error }

func Must[T any](v T, err error) T {
	if err != nil {
		panic(mustPanic{err})
	}
	return v
}

func Catch(f func()) (err error) {
	defer func() {
		r := recover()
		if r == nil {
			return
		}
		mp, ok := r.(mustPanic)
		if !ok {
			panic(r)
		}
		err = mp.err
	}()
	f()
	return nil
}
```

**Свой тип значения паники — метка «это наша».** Если `Must` паниковал бы
самой ошибкой, `Catch` не смог бы отличить её от `panic(err)`, брошенного
кем-то ещё, и проглотил бы чужой сбой. Неэкспортируемый тип
`mustPanic` не может создать никто, кроме `Must`.

**Чужое — `panic(r)` дальше.** Повторная паника с тем же значением — единственный способ «не заметить» перехваченное. Стек в сообщении будет
уже от этого места, это цена такого приёма.

**Именованный результат `err`** — отложенная функция может менять
результат, только если у него есть имя.

**Где так делают.** `encoding/json` и `text/template` внутри используют
ровно эту схему: глубокая рекурсия паникует своим типом, публичная
функция на границе превращает панику в ошибку. Наружу паники из
библиотеки не утекают никогда.

</Reveal>
