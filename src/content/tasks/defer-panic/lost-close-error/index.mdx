`Close` возвращает ошибку: при сбросе буфера кончилось место. `save`
перехватывает её в `defer` и кладёт в `err`. Программа печатает:

```
ошибка сохранения: <nil>
```

Отметьте строку, в которой заложена поломка.

<Reveal>

Сломано в строке 17: `func save(f *File) error` — результат не
именованный.

**`return err` копирует значение в момент `return`.** У функции с безымянным
результатом есть скрытая ячейка для возвращаемого значения. `return err`
записывает туда текущее значение `err` — `nil`, потому что `Write` удался.
Потом срабатывает `defer`, присваивает ошибку `Close` в *локальную*
переменную `err` — а ячейку результата уже никто не трогает. Наружу уходит
`nil`.

Код в `defer` выглядит правильно и даже аккуратно проверяет `err == nil`,
чтобы не затереть ошибку записи. Он просто пишет не туда.

**Как правильно** — назвать результат:

```go
func save(f *File) (err error) {
	defer func() {
		if cerr := f.Close(); cerr != nil && err == nil {
			err = cerr
		}
	}()
	...
}
```

Теперь `err` — это и есть ячейка результата, и `defer` меняет то, что уйдёт
вызывающему.

**Почему это важно в жизни.** Для файлов на запись ошибка `Close` — часто
единственная ошибка, которую вы увидите: данные буферизуются, и на диск
они уходят при закрытии. `defer f.Close()` без проверки молча теряет
записанное. Для чтения ошибку `Close` игнорировать можно.

С Go 1.20 есть `errors.Join`, и тогда можно не выбирать: `err = errors.Join(err, f.Close())`.

</Reveal>
