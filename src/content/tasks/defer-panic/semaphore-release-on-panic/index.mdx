Ограничитель одновременных запросов к базе: не больше `n` сразу,
остальные ждут. Типичная авария: одна паника (или ранний `return`) — и
слот не вернулся. Через неделю лимит 10 превращается в 0, и сервис стоит.
Реализуйте `Limiter`.

Что проверяют скрытые тесты:

- из 30 горутин одновременно работают не больше 3 (и не по одной);
- после пяти паник и пяти ошибок (паника летит дальше, ошибка
  возвращается) слоты свободны;
- ожидание слота прерывается дедлайном `ctx`, `fn` не вызывается, а слот
  после этого не «застревает»;
- с уже отменённым `ctx` `fn` не вызывается ни разу из 50, даже если
  слоты свободны.

<Reveal>

```go
type Limiter struct {
	slots chan struct{}
}

func NewLimiter(n int) *Limiter {
	return &Limiter{slots: make(chan struct{}, n)}
}

func (l *Limiter) Do(ctx context.Context, fn func(ctx context.Context) error) error {
	if err := ctx.Err(); err != nil {
		return err
	}
	select {
	case l.slots <- struct{}{}:
	case <-ctx.Done():
		return ctx.Err()
	}
	defer func() { <-l.slots }()
	return fn(ctx)
}
```

**`defer` освобождения — сразу после захвата.** Не раньше (иначе при
отмене ожидания освободим чужой слот — и лимит превысится) и не позже
(любой код между захватом и `defer` может запаниковать). Вызов
`<-l.slots` в конце функции без `defer` пропускается и паникой, и
ранним `return`.

**`select` выбирает случайно.** Если слот свободен **и** `ctx` уже
отменён, готовы обе ветки, и Go выберет любую. Без предварительной
проверки `ctx.Err()` примерно половина вызовов с отменённым контекстом
выполнит `fn`. Тест с 50 вызовами это ловит.

**Канал как семафор.** Отправка занимает слот, получение освобождает; ёмкость
буфера — лимит. `golang.org/x/sync/semaphore` делает то же с весами и
очередью FIFO, но для одинаковых задач канала достаточно.

**Что спросят следом.** Чем это отличается от пула воркеров (здесь
горутины создаёт вызывающий), как сделать `TryDo` без ожидания и
как отдавать метрики очереди (сколько ждут слот) для алертов о насыщении.
