Функция `counter` возвращает `count int` — результат **именованный**. Внутри
три отложенных вызова в цикле и ещё один, объявленный до цикла.

Напишите весь вывод программы, строка в строку, вместе с порядком.

<Reveal>

Разбирать надо три отдельные вещи, и обычно спотыкаются на второй.

**Аргументы `defer` вычисляются сразу, тело — потом.** Строка
`defer fmt.Println("defer", i)` на каждой итерации *вычисляет* `i` и
запоминает значение. Поэтому в очередь попадают три готовых вызова: с `0`,
`1` и `2`. Изменение `i` после этого на них уже не влияет — и переход Go 1.22
на новую переменную цикла на каждой итерации здесь ничего не меняет: значение
было скопировано в момент `defer`, а не прочитано в момент вызова.

**Отложенные вызовы исполняются в обратном порядке.** Это стек, а не очередь.
Последним объявлен `defer` с `i == 2`, он же сработает первым:

```
defer 2
defer 1
defer 0
```

А `func() { count *= 2 }()` объявлен раньше всех, значит сработает последним —
после всех трёх `Println`.

**`return count + 1` — это не одна операция, а две.** Сначала выражение
вычисляется и присваивается именованному результату (`count = 3 + 1 = 4`),
и только потом запускаются отложенные вызовы. Они видят `count` и могут его
менять: `count *= 2` превращает `4` в `8`, и наружу уходит именно `8`.

Будь результат безымянным (`func counter() int`), тот же `defer` не смог бы
до него дотянуться — возвращаемое значение уже лежало бы в недоступной
временной ячейке, и ответ был бы `4`.

Итого:

```
defer 2
defer 1
defer 0
итог: 8
```

**Где это встречается по-настоящему.** Именно на этом механизме работает
перехват паники с подменой результата:

```go
func parse(s string) (n int, err error) {
	defer func() {
		if r := recover(); r != nil {
			err = fmt.Errorf("parse: %v", r)
		}
	}()
	return mustParse(s), nil
}
```

Без именованного `err` записать ошибку из `defer` было бы некуда.

</Reveal>
