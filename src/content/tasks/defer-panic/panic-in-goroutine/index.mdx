Три задачи обрабатываются параллельно, одна из них паникует. В `main`
есть `defer` с `recover`, но программа падает:

```
panic: сбой в задаче 1
```

Почините: упавшая задача должна превратиться в строку с причиной, а
остальные — отработать. Ожидаемый вывод:

```
задача 0: ок
задача 1: сбой в задаче 1
задача 2: ок
```

<Reveal>

**`recover` работает только в горутине, где случилась паника.** Паника
раскручивает стек своей горутины, вызывая её отложенные функции. У
горутины, запущенной через `wg.Go`, стек свой, и отложенного `recover` в
нём нет. `defer` в `main` живёт в другом стеке, и до него паника не
доходит.

Раскрутив свою горутину до конца и не найдя `recover`, паника завершает
**весь процесс**. Не горутину — процесс. Одна непойманная паника в любом
обработчике роняет весь сервер.

**Как чинят** — `recover` внутри горутины, обычно в обёртке:

```go
func safeProcess(id int) (res string) {
	defer func() {
		if r := recover(); r != nil {
			res = fmt.Sprint("задача ", id, ": ", r)
		}
	}()
	return process(id)
}
```

Именованный результат нужен, чтобы `defer` мог подменить то, что вернётся.

**Как это устроено в библиотеках.** `net/http` перехватывает панику в
каждом обработчике — поэтому упавший запрос не роняет сервер. А
`errgroup` и пулы воркеров этого по умолчанию не делают: каждую
горутину, которую вы запускаете сами, защищаете тоже сами.

</Reveal>
