Интернет-магазин. Категории образуют дерево произвольной глубины:
`Электроника → Аксессуары → Чехлы`. Товар привязан к любой категории, не
обязательно к листу.

Нужен отчёт для категорийных менеджеров: **в каждой корневой категории —
два лучших товара по чистой выручке за I квартал 2024 года.**

Правила подсчёта:

- учитываются заказы, созданные с 1 января по 31 марта 2024 года
  включительно (`created_at` — метка времени, заказы идут круглые сутки);
- статус заказа — `paid` или `shipped`; отменённые и неоплаченные не в счёт;
- заказы тестовых покупателей (`customers.is_test`) не в счёт;
- выручка позиции — `qty × price` из `order_items`: цена в каталоге
  (`products.list_price`) с тех пор могла измениться;
- чистая выручка — выручка минус возвраты. Возврат уменьшает позицию на
  `refunds.qty × price` этой позиции, когда бы он ни случился; одну позицию
  могут возвращать несколькими возвратами;
- товар относится ко всем категориям выше по дереву, вплоть до корня.

Места считаются по убыванию чистой выручки внутри корневой категории. Товары
с одинаковой выручкой делят место, и места идут без пропусков: 1, 2, 2, 3.
В отчёт попадают места 1 и 2 — поэтому строк в категории может быть больше
двух.

`share_pct` — доля товара в чистой выручке всей корневой категории (всех её
товаров, а не только попавших в отчёт), в процентах, `round(…, 1)`.

- колонки: `root_category`, `place`, `product`, `net_revenue`, `share_pct`;
- порядок: `root_category`, `place`, `product`.

<Reveal>

```sql
WITH RECURSIVE tree AS (
  SELECT id, id AS root_id
  FROM categories
  WHERE parent_id IS NULL
  UNION ALL
  SELECT c.id, t.root_id
  FROM categories c
  JOIN tree t ON c.parent_id = t.id
),
good_orders AS (
  SELECT o.id
  FROM orders o
  JOIN customers c ON c.id = o.customer_id
  WHERE NOT c.is_test
    AND o.status IN ('paid', 'shipped')
    AND o.created_at >= '2024-01-01'
    AND o.created_at <  '2024-04-01'
),
refunded AS (
  SELECT order_id, product_id, sum(qty) AS qty
  FROM refunds
  GROUP BY order_id, product_id
),
product_net AS (
  SELECT oi.product_id,
         sum((oi.qty - coalesce(r.qty, 0)) * oi.price) AS net_revenue
  FROM order_items oi
  JOIN good_orders g ON g.id = oi.order_id
  LEFT JOIN refunded r ON r.order_id = oi.order_id AND r.product_id = oi.product_id
  GROUP BY oi.product_id
),
ranked AS (
  SELECT root.name AS root_category,
         p.name    AS product,
         pn.net_revenue,
         dense_rank() OVER (PARTITION BY t.root_id ORDER BY pn.net_revenue DESC) AS place,
         round(100.0 * pn.net_revenue / sum(pn.net_revenue) OVER (PARTITION BY t.root_id), 1) AS share_pct
  FROM product_net pn
  JOIN products p      ON p.id = pn.product_id
  JOIN tree t          ON t.id = p.category_id
  JOIN categories root ON root.id = t.root_id
)
SELECT root_category, place, product, net_revenue, share_pct
FROM ranked
WHERE place <= 2
ORDER BY root_category, place, product;
```

Ответ:

```
Дом         | 1 | Робот-пылесос | 20000  | 34.5
Дом         | 2 | Плед          | 15000  | 25.9
Дом         | 2 | Чайник        | 15000  | 25.9
Электроника | 1 | Бук Air       | 178000 | 56.7
Электроника | 2 | Фон X         | 95000  | 30.3
```

Задачу удобно решать слоями — каждый CTE отвечает на один вопрос, и каждый
можно проверить отдельно.

**1. Дерево → «категория — её корень».** Рекурсивный CTE стартует с корней
(`root_id = id`) и спускается вниз, протаскивая `root_id` через все уровни.
Одного `JOIN categories parent ON parent.id = c.parent_id` мало: `Чехлы`
лежат на третьем уровне, и один шаг вверх приводит в `Аксессуары`, а не в
`Электронику`. Заодно сюда попадает сам корень — `Робот-пылесос` привязан
прямо к `Дому` и тоже участвует.

**2. Какие заказы считаются.** Три фильтра, у каждого своя ловушка:

- `created_at <= '2024-03-31'` потеряет заказ в 23:30 последнего дня —
  строка `'2024-03-31'` превращается в полночь. Полуоткрытый интервал
  `>= начало AND < следующий день` надёжен для любых типов;
- тестовый заказ `QA-бота` на 250 000 вывел бы `Фон X` на первое место;
- заказ 8 от 1 апреля 00:10 и заказ 9 от 31 декабря — за границами.

**3. Возвраты сначала агрегируются, потом присоединяются.** `Фон Mini`
возвращали дважды по одной штуке. Прямой `LEFT JOIN refunds` размножит
позицию заказа на две строки: выручка посчитается дважды (174 000 вместо
87 000), и `Фон Mini` с 116 000 обгонит `Фон X`. Предварительный `GROUP BY` по
ключу позиции даёт ровно одну строку возвратов на позицию — соединение
становится «один к одному».

Возврат `Фон Mini` от 15 апреля тоже учитывается: условие привязывает возврат
к заказу, а не к кварталу.

**4. Ранжирование и доля — окна по одному разбиению.** `dense_rank` даёт
1, 2, 2, 3 — это и есть «делят место, без пропусков». `rank` дал бы 1, 2, 2, 4,
а `row_number` потерял бы `Чайник` или `Плед` произвольным образом.

Доля считается окном `sum(...) OVER (PARTITION BY root_id)` **до** фильтра
`place <= 2`: `WHERE` выполняется раньше оконных функций того же уровня,
поэтому ранжирование и фильтр по нему разнесены по разным уровням запроса.
Отфильтруй сначала — и знаменатель будет суммой только лидеров.

**`100.0 *` вместо `100 *`** — иначе деление целых обнулит долю.

**Что спросят дальше на собеседовании.** «А если товар перенесут в другую
категорию — отчёт за прошлый квартал поменяется?» Да: дерево берётся
текущее. Для исторической точности категорию фиксируют в строке заказа или
ведут историю изменений справочника (SCD 2).
