HR готовит отчёт по руководителям **на 1 июня 2024 года**.

Сотрудник работает на эту дату, если `hired_at <= '2024-06-01'` и он либо не
уволен, либо `fired_at >= '2024-06-01'` (`fired_at` — последний рабочий день).
Кто не работает на дату, тот в отчёте не существует — ни как руководитель, ни
как подчинённый.

Оклады хранятся историей: строка в `salaries` действует с `valid_from` до
следующей строки этого же сотрудника. Оклад на дату — строка с самым поздним
`valid_from`, не позже 1 июня. Повышения, запланированные на будущее, уже
лежат в таблице.

Для каждого работающего сотрудника, у которого есть хотя бы один работающий
прямой подчинённый:

- `manager` — имя;
- `direct_reports` — сколько у него прямых подчинённых;
- `team_size` — сколько человек под ним на всех уровнях (сам руководитель не
  считается);
- `team_payroll` — сумма окладов всех этих людей на дату;
- `depth` — сколько уровней под ним: 1 — только прямые подчинённые.

Порядок: `team_size` по убыванию, при равенстве — по `manager`.

<Reveal>

```sql
WITH RECURSIVE active AS (
  SELECT id, name, manager_id
  FROM employees
  WHERE hired_at <= date '2024-06-01'
    AND (fired_at IS NULL OR fired_at >= date '2024-06-01')
),
current_salary AS (
  SELECT DISTINCT ON (employee_id) employee_id, amount
  FROM salaries
  WHERE valid_from <= date '2024-06-01'
  ORDER BY employee_id, valid_from DESC
),
-- Все пары «начальник — подчинённый на любом уровне» и расстояние между ними
chain AS (
  SELECT manager_id AS boss_id, id AS emp_id, 1 AS depth
  FROM active
  WHERE manager_id IS NOT NULL
  UNION ALL
  SELECT c.boss_id, a.id, c.depth + 1
  FROM chain c
  JOIN active a ON a.manager_id = c.emp_id
)
SELECT b.name AS manager,
       count(*) FILTER (WHERE c.depth = 1) AS direct_reports,
       count(*)                            AS team_size,
       sum(s.amount)                       AS team_payroll,
       max(c.depth)                        AS depth
FROM chain c
JOIN active b ON b.id = c.boss_id
LEFT JOIN current_salary s ON s.employee_id = c.emp_id
GROUP BY b.id, b.name
ORDER BY team_size DESC, manager;
```

Ответ:

```
Ольга  | 2 | 9 | 1830 | 4
Пётр   | 2 | 5 | 900  | 3
Тимур  | 2 | 3 | 480  | 2
Роман  | 1 | 2 | 310  | 2
Ульяна | 1 | 1 | 120  | 1
Циля   | 1 | 1 | 110  | 1
```

**Главная идея — транзитивное замыкание.** Обычный рекурсивный обход «от
Ольги вниз» отвечает на вопрос про одного руководителя. Здесь нужен ответ про
всех сразу, поэтому рекурсия строит **все пары** «начальник — подчинённый на
любом уровне»:

- старт: каждый сотрудник со своим прямым начальником, `depth = 1`;
- шаг: если `boss → emp` уже есть, а у `emp` есть подчинённый `a`, то
  `boss → a` на уровень глубже.

Пара `Ольга → Чен` появляется на четвёртой итерации: Ольга → Пётр → Тимур →
Ульяна → Чен. После этого все метрики — обычная группировка по `boss_id`:
`count(*)` — размер команды, `max(depth)` — глубина,
`count(*) FILTER (WHERE depth = 1)` — прямые подчинённые. Строки с
`depth = 1` есть у любого, кто попал в `chain` как начальник, — отсюда и
условие «хотя бы один прямой подчинённый» выполняется само.

**Фильтр по активности — до рекурсии.** Рекурсия идёт по `active`, а не по
`employees`: уволенная Хлоя и Шура, который выйдет 15 июня, не попадают ни в
цепочки, ни в `JOIN active b`. Если отфильтровать уже готовые пары, пришлось
бы проверять активность обоих концов — и промежуточных звеньев тоже.

Отдельный вопрос для собеседования: а если бы уволили руководителя, а его
подчинённых не переназначили? Тогда фильтр до рекурсии оборвал бы ветку, и
люди «потерялись» бы из команды верхнего начальника. Правильный ответ зависит
от бизнеса — стоит спросить, а не угадывать.

**Оклад на дату — `DISTINCT ON`.** Из всех строк не позже 1 июня берётся по
одной на сотрудника — первая после сортировки по `valid_from DESC`. Ловушки
в данных:

- Пётр получит 350 только 1 июля — на дату у него 300;
- Ульяне подняли оклад 31 мая — уже 200;
- у Шуры оклад начинается 15 июня, но его и так нет среди работающих.

Переносимая замена `DISTINCT ON` — `row_number() OVER (PARTITION BY
employee_id ORDER BY valid_from DESC) = 1` или коррелированный подзапрос с
`max(valid_from)`.

**Без фильтра по дате** `JOIN salaries` размножил бы каждого сотрудника на
число строк его истории — и `team_size`, и `team_payroll` выросли бы.

**`LEFT JOIN current_salary`** — страховка: сотрудник без оклада на дату не
должен выпадать из численности команды.
