Фитнес-приложение показывает в профиле «рекорд серии» — самое длинное число
**дней подряд**, в каждый из которых была хотя бы одна тренировка.

Пользователи живут в разных часовых поясах, а `done_at` хранится как
`timestamptz`. **День тренировки — дата по местному времени пользователя**
(`users.tz`), а не по UTC и не по часовому поясу сервера: пробежка в 01:30
ночи по Москве — это тренировка за новый день, даже если в UTC ещё вчера.

Для **каждого** пользователя:

- колонки: `user_name`, `longest_streak` — длина самой длинной серии в днях
  (0, если тренировок нет), `streak_start` — местная дата начала этой серии
  (`date`); если серий максимальной длины несколько — самая ранняя; `NULL`,
  если тренировок нет;
- порядок: `longest_streak` по убыванию, затем `user_name`.

<Reveal>

```sql
WITH days AS (
  SELECT DISTINCT w.user_id, (w.done_at AT TIME ZONE u.tz)::date AS day
  FROM workouts w
  JOIN users u ON u.id = w.user_id
),
islands AS (
  SELECT user_id, day,
         day - row_number() OVER (PARTITION BY user_id ORDER BY day)::int AS grp
  FROM days
),
streaks AS (
  SELECT user_id, min(day) AS started_on, count(*) AS len
  FROM islands
  GROUP BY user_id, grp
),
best AS (
  SELECT DISTINCT ON (user_id) user_id, len, started_on
  FROM streaks
  ORDER BY user_id, len DESC, started_on
)
SELECT u.name AS user_name,
       coalesce(b.len, 0) AS longest_streak,
       b.started_on AS streak_start
FROM users u
LEFT JOIN best b ON b.user_id = u.id
ORDER BY longest_streak DESC, user_name;
```

Ответ:

```
Боря | 3 | 2024-03-02
Аня  | 2 | 2024-03-02
Вера | 2 | 2024-03-01
Дина | 1 | 2024-03-10
Гоша | 0 | NULL
```

**Сначала — местная дата.** `timestamptz AT TIME ZONE 'Europe/Moscow'`
возвращает `timestamp` — «что показывали часы в Москве», и только его
можно резать до даты. Просто `done_at::date` берёт часовой пояс **сессии**
базы: результат зависит от настроек сервера и в любом случае не совпадает
с поясом пользователя. У Ани и Бори по UTC тренировки идут четыре дня
подряд — 1, 2, 3 и 4 марта, у Веры по UTC серий нет вовсе, а по местному
времени картина другая:

- Аня (UTC+3): 22:30 UTC 1 марта — это уже 2-е, а 21:30 UTC 4 марта — уже
  5-е. Дни 2, 2, 3, 5 — серия из двух;
- Боря (UTC+7): дни 2, 2, 3, 4 — серия из трёх, начало 2 марта;
- Вера (UTC−5): 03:00 UTC 3 марта — это вечер 2-го по Нью-Йорку. Дни 1, 2, 5,
  6 — две серии по два дня, берётся ранняя.

**Острова: «дата минус номер».** Внутри серии дата и `row_number` растут на
единицу одновременно, поэтому разность постоянна; на разрыве дата прыгает
сильнее номера, и разность меняется. Приём работает, только если каждый
день встречается **один раз** — отсюда `DISTINCT` в `days`. У Дины три
тренировки 10 марта: без `DISTINCT` номера 1, 2, 3 при одной дате дадут три
разных «острова» по одному дню, а у соседних дней номера съедут и серия
развалится.

**Лучшая серия с ничьей — `DISTINCT ON`.** `ORDER BY user_id, len DESC,
started_on` ставит первой самую длинную и самую раннюю серию, `DISTINCT ON
(user_id)` оставляет её одну. Альтернатива — `row_number()` с тем же
порядком и фильтр `= 1`. `max(len)` и `min(started_on)` по отдельности, как
в заготовке, склеят длину одной серии с началом другой.

**Гоша без тренировок** остаётся в отчёте через `LEFT JOIN` от `users`.

**Что спросят дальше.** Как считать **текущую** серию (заканчивается
сегодня или вчера по местному времени — иначе 0) и как хранить её
инкрементально, не пересчитывая всю историю: поле `streak` и `last_day` у
пользователя, обновляемые при каждой тренировке с учётом его пояса.
