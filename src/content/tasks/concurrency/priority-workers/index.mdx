Обработчик уведомлений: письма сброса пароля нельзя ставить в очередь за
десятью тысячами маркетинговых рассылок. Задачи приходят в двух каналах,
и воркеры должны отдавать предпочтение срочным. Реализуйте `RunPriority`
по контракту из заготовки.

Что проверяют скрытые тесты:

- один воркер, в обеих очередях по десять задач: все срочные выполняются
  раньше любой обычной;
- срочная очередь закрыта с самого начала — обычные всё равно выполняются
  все, без паник;
- `RunPriority` не возвращается, пока открыта хотя бы одна очередь;
- при отмене новые задачи не начинаются, начатые доделываются до
  возврата, горутин не остаётся.

<Reveal>

```go
func worker(ctx context.Context, high, low <-chan func()) {
	for high != nil || low != nil {
		if ctx.Err() != nil {
			return
		}
		select {
		case task, ok := <-high:
			if !ok {
				high = nil
				continue
			}
			task()
			continue
		default:
		}
		select {
		case task, ok := <-high:
			if !ok {
				high = nil
				continue
			}
			task()
		case task, ok := <-low:
			if !ok {
				low = nil
				continue
			}
			task()
		case <-ctx.Done():
			return
		}
	}
}
```

`RunPriority` запускает `workers` таких воркеров, ждёт их через
`WaitGroup` и возвращает `ctx.Err()`.

**У `select` нет приоритетов.** Если готовы несколько веток, выбирается
случайная, равновероятно, и порядок веток в коде ничего не значит. Приоритет
делают двумя `select`: сначала неблокирующий только по `high`, и лишь если
там пусто — общий, который ждёт всё. В общем `select` `high` тоже есть:
если срочная задача придёт, пока воркер ждёт, она не должна ждать обычную.

**Закрытый канал читается всегда — и выигрывает `select`.** Чтение из
закрытого канала мгновенно возвращает нулевое значение: для `func()` это
`nil`, и `task()` паникует. А если проверять `ok` и просто продолжать
цикл, воркер будет крутиться на закрытом `high` и жечь CPU. Решение —
`high = nil`: чтение из nil-канала блокируется навсегда, и `select` просто
перестаёт видеть эту ветку.

**Выход — когда обе очереди стали nil.** Условие цикла `high != nil ||
low != nil`: закрытие одной очереди не повод останавливаться.

**Отмена проверяется перед каждой задачей.** Буфер полон, и `select` с
готовыми задачами может раз за разом выбирать задачу, а не `ctx.Done()`.
Явная проверка `ctx.Err()` в начале итерации останавливает воркера сразу.
Начатая задача доделывается: прерывать её — дело самой задачи и её
контекста.

**Что спросят дальше.** Голодание: при постоянном потоке срочных задач
обычные не выполнятся никогда. Лечат взвешенным выбором (например, 1
обычная на 10 срочных) или отдельными воркерами для каждой очереди. И
когда вместо этого нужна настоящая очередь с приоритетами
(`container/heap`) — если уровней больше двух.
