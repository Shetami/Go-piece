Симуляция по шагам, параллельные итерации численного метода, нагрузочный
тест, где все клиенты стартуют одновременно, — везде нужен барьер: никто
не начинает фазу `k+1`, пока все не закончили фазу `k`. `WaitGroup` для
этого не подходит — его нельзя переиспользовать, пока кто-то ещё ждёт.
Реализуйте `Barrier` по контракту из заготовки.

Что проверяют скрытые тесты:

- пять горутин проходят сто раундов подряд, и никто не проходит барьер
  раунда, пока в него не пришли все; барьер не зависает, даже когда быстрые
  горутины приходят в следующий раунд раньше, чем медленные проснулись;
- в каждом раунде `true` получает ровно одна горутина;
- барьер на одного не ждёт никогда;
- ушедший по отмене контекста больше не засчитан в текущем поколении.

<Reveal>

```go
type Barrier struct {
	n     int
	mu    sync.Mutex
	count int
	gen   chan struct{}
}

func (b *Barrier) Wait(ctx context.Context) (bool, error) {
	b.mu.Lock()
	gen := b.gen
	b.count++
	if b.count == b.n {
		close(gen)
		b.gen = make(chan struct{})
		b.count = 0
		b.mu.Unlock()
		return true, nil
	}
	b.mu.Unlock()

	select {
	case <-gen:
		return false, nil
	case <-ctx.Done():
		b.mu.Lock()
		defer b.mu.Unlock()
		select {
		case <-gen:
			return false, nil
		default:
		}
		b.count--
		return false, ctx.Err()
	}
}
```

**Ключ к многоразовости — поколение.** Наивный барьер со счётчиком и
`sync.Cond` ждёт условия «счётчик дошёл до n». Последний сбрасывает
счётчик в 0 и делает `Broadcast`. Но пока спящие просыпаются, быстрая
горутина уже пришла в следующий раунд и увеличила счётчик. Проснувшиеся
видят не то, что ждали, и засыпают снова — дедлок. Или наоборот, проходят
чужой раунд. Здесь каждая горутина запоминает канал **своего** поколения
и ждёт именно его. Новое поколение получает новый канал, и старое уже
никак не спутать с новым.

**Закрытие канала — широковещательное пробуждение.** Один `close(gen)`
будит всех ждущих поколения, сколько бы их ни было. Всё, что участники
сделали до `Wait`, видно всем после выхода: happens-before от закрытия
канала к чтению из него.

**Уход по отмене — под мьютексом и с проверкой.** Если поколение
заполнилось в тот же момент, когда сработал `ctx.Done()`, горутина уже
прошла, и уменьшать `count` нельзя: он принадлежит следующему поколению.
Поэтому под мьютексом ещё раз смотрим на `gen`.

**Что спросят дальше.** Как сделать «сломанный» барьер как в Java
(`BrokenBarrierException`): если один ушёл, освободить всех остальных с
ошибкой, иначе они ждут участника, который уже не придёт. Действие
барьера (`barrierAction`) — ровно для этого и возвращается `true` одной
горутине. И чем барьер отличается от `errgroup`: там все ждут конца, а не
общую точку посреди работы.
