Обработчик событий: «создан заказ», «оплачен», «отменён» для одного
заказа должны примениться строго по порядку, а заказы разных клиентов
обрабатываются параллельно. Kafka решает это партициями, а внутри процесса
то же самое делают исполнителем с упорядочиванием по ключу. Реализуйте
`KeyedExecutor` по контракту из заготовки.

Что проверяют скрытые тесты:

- задачи одного ключа выполняются в порядке `Submit` и никогда не
  пересекаются во времени;
- долгая задача одного ключа не мешает задачам другого;
- `Submit` сотни задач на занятый ключ возвращается сразу;
- после тысячи разовых ключей не остаётся ни записей (`Keys() == 0`), ни
  горутин.

<Reveal>

```go
type KeyedExecutor struct {
	mu     sync.Mutex
	queues map[string][]func()
	wg     sync.WaitGroup
}

func (e *KeyedExecutor) Submit(key string, task func()) {
	e.mu.Lock()
	defer e.mu.Unlock()
	e.wg.Add(1)
	if q, busy := e.queues[key]; busy {
		e.queues[key] = append(q, task)
		return
	}
	e.queues[key] = nil
	go e.run(key, task)
}

func (e *KeyedExecutor) run(key string, task func()) {
	for {
		task()
		e.mu.Lock()
		q := e.queues[key]
		if len(q) == 0 {
			delete(e.queues, key)
			e.mu.Unlock()
			e.wg.Done()
			return
		}
		task = q[0]
		q[0] = nil
		e.queues[key] = q[1:]
		e.mu.Unlock()
		e.wg.Done()
	}
}
```

**Горутина живёт, пока у ключа есть работа.** Наличие ключа в карте
означает «по нему уже работает горутина». Первая задача ключа запускает
горутину, следующие просто встают в очередь. Горутина разбирает очередь и,
когда она пуста, удаляет ключ и выходит. Ни пула фиксированного размера,
ни горутины на ключ навсегда.

**Самая тонкая гонка — между «очередь пуста» и «удалить ключ».** Если
горутина проверит очередь, отпустит мьютекс и только потом удалит ключ,
`Submit` между этими моментами положит задачу в очередь, которую уже
никто не разбирает. Задача потеряна, `Wait` висит вечно. Проверка и
удаление — одна критическая секция с тем же мьютексом, что и в `Submit`.

**Почему не шардинг «ключ → hash % N воркеров».** Это тоже сохраняет
порядок, но один медленный ключ блокирует все ключи своего шарда
(head-of-line blocking), а занятость воркеров неравномерна. Здесь медленный
ключ тормозит только себя. Цена — неограниченное число горутин при
неограниченном числе активных ключей. В проде добавляют общий семафор на
выполнение задач.

**Мелочи, которые спросят.** `q[0] = nil` — чтобы выполненные замыкания
(и всё, что они захватили) не жили в массиве очереди. `wg.Add` — в
`Submit`, до запуска горутины, иначе `Wait` может проскочить. А `wg.Done`
— после удаления ключа, а не сразу после `task()`: иначе последний `Done`
отпустит `Wait`, пока запись ключа ещё в карте, и `Keys()` сразу после
`Wait` иногда вернёт 1 вместо 0.

**Что дальше.** Ограничить длину очереди ключа (обратное давление или
отказ), восстановление после паники задачи (иначе горутина ключа умрёт, а
ключ останется «занятым» навсегда) и как это соотносится с партициями и
consumer group в Kafka.
