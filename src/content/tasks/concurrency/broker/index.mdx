Допишите `Broker`: поля, `Subscribe` и `Publish`.

Что проверяют скрытые тесты:

- сообщение получают все подписчики, `Publish` возвращает их число;
- без подписчиков — 0;
- отписка закрывает канал, повторная отписка безопасна, после неё
  сообщения не приходят;
- подписчик с полным буфером не блокирует `Publish`: лишние сообщения для
  него выбрасываются, остальные получают всё;
- полсотни горутин одновременно подписываются, публикуют и отписываются —
  без паник и зависаний.

<Reveal>

```go
type Broker struct {
	mu   sync.Mutex
	subs map[chan string]struct{}
}

func (b *Broker) Subscribe(buf int) (<-chan string, func()) {
	ch := make(chan string, buf)
	b.mu.Lock()
	b.subs[ch] = struct{}{}
	b.mu.Unlock()

	var once sync.Once
	return ch, func() {
		once.Do(func() {
			b.mu.Lock()
			delete(b.subs, ch)
			close(ch)
			b.mu.Unlock()
		})
	}
}

func (b *Broker) Publish(msg string) int {
	b.mu.Lock()
	defer b.mu.Unlock()
	n := 0
	for ch := range b.subs {
		select {
		case ch <- msg:
			n++
		default:
		}
	}
	return n
}
```

**Главная гонка — между отправкой и закрытием.** Если `unsubscribe`
закроет канал, пока `Publish` в него пишет, — `send on closed channel`.
Поэтому закрытие и удаление из мапы идут под тем же мьютексом, под которым
`Publish` обходит подписчиков: пока идёт рассылка, закрыть канал нельзя.

**Держать мьютекс во время отправки можно только потому, что отправка
неблокирующая.** С блокирующей `ch <- msg` один зависший подписчик держал
бы мьютекс вечно — и остановил бы и рассылку, и все подписки.

**`sync.Once` делает отписку идемпотентной** — без него второй вызов
закрыл бы закрытый канал.

**Выбрасывать — осознанный выбор.** Альтернативы — блокироваться (медленный
тормозит всех) или копить без предела (память). Для метрик и уведомлений
потеря лучше; для заказов нужна настоящая очередь.
