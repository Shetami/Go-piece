Горячая перезагрузка конфига: источник публикует новую версию, десяток
компонентов на неё подписан. Если компонент занят и прочитал не сразу,
ему не нужны все двадцать промежуточных версий — только последняя. А
источник не должен ждать медленного подписчика. Реализуйте `Latest[T]`
по контракту из заготовки.

Чем это отличается от брокера сообщений: там медленный подписчик теряет
**новые** сообщения, а здесь — **старые** и всегда получает самое свежее.

Что проверяют скрытые тесты:

- тысяча `Set` при наблюдателе, который ничего не читает, не блокируется;
- новый наблюдатель сразу получает текущее значение; без нового `Set`
  значение не повторяется; наблюдатель пустого `Latest` ничего не получает;
- медленный читатель после тысячи `Set` получает несколько значений по
  возрастанию, без повторов, и последним — `1000`;
- после отмены контекста каналы закрываются, а горутины наблюдателей
  завершаются, даже если застряли на отправке.

<Reveal>

```go
type Latest[T any] struct {
	mu      sync.Mutex
	val     T
	ver     int
	changed chan struct{}
}

func (l *Latest[T]) Set(v T) {
	l.mu.Lock()
	l.val = v
	l.ver++
	close(l.changed)
	l.changed = make(chan struct{})
	l.mu.Unlock()
}

func (l *Latest[T]) Watch(ctx context.Context) <-chan T {
	out := make(chan T)
	go func() {
		defer close(out)
		sent := 0
		for {
			l.mu.Lock()
			val, ver, changed := l.val, l.ver, l.changed
			l.mu.Unlock()

			if ver == sent {
				select {
				case <-changed:
					continue
				case <-ctx.Done():
					return
				}
			}
			select {
			case out <- val:
				sent = ver
			case <-changed:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}
```

**`Set` не знает о наблюдателях.** Он только меняет значение и закрывает
канал `changed`. Закрытие мгновенно и будит всех, кто ждёт на этом канале,
сколько бы их ни было. Никаких отправок из `Set` — значит, и блокироваться
ему не на чем. Новый канал для следующего изменения создаётся под тем же
мьютексом.

**Версия вместо сравнения значений.** Наблюдатель помнит номер версии,
которую уже отправил. Это решает и «не повторять одно и то же», и «пустой
`Latest` ничего не шлёт» (версия 0), и работает для типов, которые нельзя
сравнить через `==`.

**Ждать читателя — и одновременно следить за изменениями.** Если
наблюдатель застрял на `out <- val`, а пришло новое значение, отправлять
старое бессмысленно. Ветка `<-changed` в том же `select` бросает
устаревшую отправку и идёт за свежим. Без неё медленный читатель сначала
получил бы устаревшее значение.

**Буфер канала на одно значение — ловушка.** Популярный приём «канал с
буфером 1, при переполнении вычитать старое и положить новое» ломается,
когда вычитывают двое: Set и читатель. Можно потерять последнее значение
или получить их не по порядку. Своя горутина на наблюдателя с версией
проще доказать.

**Что спросят дальше.** Как сделать без горутины на наблюдателя: вернуть
методы `Get() (T, version)` и `Changed(version) <-chan struct{}` и дать
читателю ждать самому. Так устроены watch-механизмы etcd и Kubernetes
informers. И почему для конфигов часто хватает `atomic.Pointer[Config]`, если
уведомления не нужны.
