Классика, которую любят просить «распараллелить»: сортировка слиянием.
Наивное «`go` на каждую половину» на миллионе элементов запускает сотни
тысяч горутин. Напишите `SortParallel` по контракту из заготовки.

Что проверяют скрытые тесты:

- результат отсортирован на размерах от 0 до 1000, включая границу 16;
- сортировка устойчивая: равные ключи идут в исходном порядке;
- входной слайс не меняется;
- одновременно сравнивают не больше `maxPar` горутин, и параллельность
  реально есть;
- `maxPar = 0` не приводит к зависанию.

<Reveal>

```go
func SortParallel[T any](s []T, maxPar int, cmp func(a, b T) int) []T {
	out := slices.Clone(s)
	if len(out) < 2 {
		return out
	}
	buf := make([]T, len(out))
	sem := make(chan struct{}, max(maxPar-1, 0))
	mergeSort(out, buf, sem, cmp)
	return out
}

func mergeSort[T any](s, buf []T, sem chan struct{}, cmp func(a, b T) int) {
	if len(s) < 16 {
		slices.SortStableFunc(s, cmp)
		return
	}
	mid := len(s) / 2
	select {
	case sem <- struct{}{}:
		done := make(chan struct{})
		go func() {
			defer close(done)
			defer func() { <-sem }()
			mergeSort(s[:mid], buf[:mid], sem, cmp)
		}()
		mergeSort(s[mid:], buf[mid:], sem, cmp)
		<-done
	default:
		mergeSort(s[:mid], buf[:mid], sem, cmp)
		mergeSort(s[mid:], buf[mid:], sem, cmp)
	}
	merge(s, buf, mid, cmp)
}

func merge[T any](s, buf []T, mid int, cmp func(a, b T) int) {
	copy(buf, s)
	i, j, k := 0, mid, 0
	for i < mid && j < len(s) {
		if cmp(buf[j], buf[i]) < 0 {
			s[k] = buf[j]
			j++
		} else {
			s[k] = buf[i]
			i++
		}
		k++
	}
	k += copy(s[k:], buf[i:mid])
	copy(s[k:], buf[j:len(s)])
}
```

**Семафор — неблокирующий, через `select` с `default`.** Горутина-родитель,
которая ждёт слот, сама занимает слот и ждёт детей. Если все слоты заняты
родителями, а дети ждут слотов — классический дедлок. Правило для
рекурсивного параллелизма: «есть свободный слот — отдай половину новой
горутине, нет — сделай сам». При `maxPar = 1` буфер семафора нулевой, и
`default` срабатывает всегда — получается обычная последовательная
сортировка.

**Считаем и вызывающую горутину.** Слотов `maxPar-1`: родитель, который
запустил горутину, продолжает сортировать правую половину сам. Он тоже
вызывает `cmp`, и его надо учитывать.

**Устойчивость — в одном знаке.** При равенстве берём элемент из левой
половины: `cmp(right, left) < 0`, а не `<= 0`. Порог `< 16` сортируем
`SortStableFunc`, а не `SortFunc` — нестабильный базовый случай испортил бы
всё.

**Половины не пересекаются — гонок нет.** Горутины пишут в `s[:mid]` и
`s[mid:]` и в соответствующие куски `buf`. Разные элементы — разные
переменные. Слияние начинается только после `<-done`, а это
happens-before.

**Что спросят дальше.** Почему порог нужен (горутина на 3 элемента дороже
самих сравнений) и как его выбрать. Почему ускорение ограничено: последнее
слияние всегда последовательное и проходит весь массив. И когда параллельная
сортировка вообще выгодна — дорогой `cmp` или миллионы элементов; на
десятке тысяч `slices.SortFunc` обычно быстрее.
