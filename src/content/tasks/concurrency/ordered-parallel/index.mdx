Напишите тело `OrderedMap`.

Что проверяют скрытые тесты:

- результаты идут в порядке входа, даже когда ранние значения считаются
  дольше поздних;
- 16 задач по 50 мс с 8 воркерами укладываются в 400 мс — работа идёт
  параллельно;
- одновременно работает не больше `workers` вызовов `f`;
- пустой закрытый вход → выход закрывается сразу.

<Reveal>

```go
func OrderedMap(in <-chan int, workers int, f func(int) int) <-chan int {
	out := make(chan int)
	pending := make(chan chan int, max(workers-1, 0))

	go func() {
		defer close(pending)
		for v := range in {
			res := make(chan int, 1)
			pending <- res
			go func() { res <- f(v) }()
		}
	}()

	go func() {
		defer close(out)
		for res := range pending {
			out <- <-res
		}
	}()
	return out
}
```

**На каждое значение — канал-«обещание» результата.** Обещания встают в
очередь `pending` в порядке входа. Второй этап забирает их строго по
очереди и ждёт каждое: даже если пятый результат готов раньше первого, он
полежит в своём буфере.

**Ёмкость `pending` — это и есть лимит.** Горутина с `f` стартует только
после того, как её обещание встало в очередь. Живых обещаний не больше
`workers - 1` в буфере плюс одно, которое уже забрал второй этап и ждёт.
Значит, одновременно вычисляются не больше `workers` значений — отдельный
семафор не нужен. Ёмкость `workers` дала бы на одного больше: обещание,
которое ждёт второй этап, в буфере уже не лежит, — ровно на это и
проверяет тест.

**Буфер 1 у каждого обещания** позволяет горутине с `f` завершиться сразу,
не дожидаясь своей очереди на выдачу.

**Цена порядка — head-of-line blocking.** Одно медленное значение держит
все готовые за ним. Если порядок не нужен, обычный пул воркеров отдаёт
результаты быстрее.
