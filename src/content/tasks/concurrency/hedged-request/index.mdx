Хвост задержки часто даёт одна тормозящая реплика. Приём из статьи Google
«The Tail at Scale»: если ответа нет дольше обычного, отправить тот же
запрос ещё раз и взять того, кто ответит первым. Реализуйте `Hedged` по
контракту из заготовки.

Чем это отличается от «запустить всё сразу и взять первый»: запросы
запускаются **по очереди с задержкой**, чтобы в хорошем случае не удваивать
нагрузку.

Что проверяют скрытые тесты:

- первый ответ пришёл быстро — вторая попытка не запускается вовсе;
- первая попытка зависла — через `delay` стартует вторая, её ответ
  возвращается, а зависшая получает отмену контекста;
- попытка сразу упала — следующая стартует немедленно, без `delay`;
- упали все — в ошибке все причины и в порядке номеров попыток, хотя
  приходят они в обратном порядке;
- внешняя отмена возвращает управление сразу, даже если попытки не слушают
  контекст, и когда они всё-таки закончатся, ни одна горутина не повиснет.

```go
func Hedged[T any](ctx context.Context, attempts int, delay time.Duration,
	call func(ctx context.Context, i int) (T, error)) (T, error) {
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	type result struct {
		i   int
		v   T
		err error
	}
	results := make(chan result, attempts)
	errs := make([]error, attempts)
	launched, finished := 0, 0

	timer := time.NewTimer(delay)
	defer timer.Stop()
	launch := func() {
		i := launched
		launched++
		go func() {
			v, err := call(ctx, i)
			results <- result{i, v, err}
		}()
		if !timer.Stop() {
			select {
			case <-timer.C:
			default:
			}
		}
		timer.Reset(delay)
	}
	launch()

	var zero T
	for {
		var hedge <-chan time.Time
		if launched < attempts {
			hedge = timer.C
		}
		select {
		case <-hedge:
			launch()
		case r := <-results:
			finished++
			if r.err == nil {
				return r.v, nil
			}
			errs[r.i] = r.err
			if finished == attempts {
				return zero, errors.Join(errs...)
			}
			if launched < attempts {
				launch()
			}
		case <-ctx.Done():
			return zero, ctx.Err()
		}
	}
}
```

**Буфер канала результатов — на все попытки.** Это главная защита от
утечки. Функция возвращается после первого успеха, и больше никто канал не
читает. С небуферизованным каналом каждая опоздавшая попытка навсегда
застрянет на `results <- …`. С буфером `attempts` отправка никогда не
блокируется.

**`defer cancel()` — отмена для проигравших.** Производный контекст
отменяется при любом выходе, и медленные реплики бросают работу, а не
держат соединения. Это вежливость, а не гарантия: попытка, которая не
слушает `ctx`, доработает до конца, поэтому и нужен буфер.

**Один таймер и nil-канал.** Когда попытки кончились, `hedge == nil`, и
ветка таймера выключена. При каждом запуске таймер перезапускается, в том
числе после досрочного запуска из-за ошибки: следующая страховка через
полный `delay` от последнего запуска. Пара `Stop` + неблокирующее чтение
корректна и со старой семантикой таймеров, и с новой, из Go 1.23.

**Ошибки — по индексу, а не `append`.** Порядок завершения случаен, и
`append` дал бы плавающий текст ошибки. Слот `errs[i]` у каждой попытки
свой, `errors.Join` пропускает `nil`.

**Что спросят дальше.** Как выбрать `delay` (обычно p95 по живой
статистике, а не константа), почему страховать можно только идемпотентные
запросы и как ограничить долю страховок (бюджет, например не больше 5%
запросов), чтобы при общей деградации они не удвоили нагрузку и не добили
сервис.
