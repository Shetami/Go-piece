Напишите тело `ParallelMap`. Она применяет `f` к каждому элементу и возвращает
результаты **в том же порядке**, что и вход, запуская при этом не больше
`workers` горутин одновременно.

Что проверяют скрытые тесты:

- **порядок** — результат соответствует входу поэлементно;
- **параллелизм** — восемь элементов по 100 мс на четырёх воркерах укладываются
  заметно быстрее, чем последовательные 800 мс;
- **предел** — при `workers = 3` одновременно не работает больше трёх горутин
  (и больше одной — иначе это не параллелизм);
- пустой вход не роняет программу.

<Reveal>

```go
func ParallelMap(items []int, workers int, f func(int) int) []int {
	out := make([]int, len(items))
	if len(items) == 0 {
		return out
	}
	if workers < 1 {
		workers = 1
	}

	tasks := make(chan int)

	var wg sync.WaitGroup
	wg.Add(workers)
	for w := 0; w < workers; w++ {
		go func() {
			defer wg.Done()
			for i := range tasks {
				out[i] = f(items[i])
			}
		}()
	}

	for i := range items {
		tasks <- i
	}
	close(tasks)
	wg.Wait()

	return out
}
```

**Главная идея: порядок держится сам собой.** По каналу ходят не значения, а
**индексы**. Каждый воркер пишет результат в `out[i]` — в свою ячейку, которую
больше никто не трогает. Ни сортировать, ни собирать результаты в мапу не надо.

И да, запись в общий слайс из нескольких горутин здесь **не** гонка: гонка — это
доступ к одной и той же ячейке памяти, а у нас каждый индекс достаётся ровно
одному воркеру. `go build -race` на этом коде молчит. Сам заголовок слайса
никто не меняет — `out` создан до запуска горутин и дальше только читается.

**Три ошибки, которые делают здесь чаще всего.**

**Горутина на каждый элемент.** `for i := range items { go ... }` — и никакого
предела параллелизма нет: на миллионе элементов вы запустите миллион горутин.
Аргумент `workers` существует ровно для того, чтобы этого не случилось; пул
фиксированного размера, который разбирает задачи из канала, — стандартный
способ такой предел задать.

**Собирать результаты в канал и потом раскладывать.** Работает, но требует
передавать пару «индекс + значение» и лишний проход. Запись по индексу проще и
дешевле.

**`wg.Add(1)` внутри горутины.** Тогда `wg.Wait()` может добежать раньше, чем
горутина успеет зарегистрироваться, и функция вернёт недосчитанный результат.
`Add` всегда вызывают до `go`, в той горутине, которая потом будет ждать.

**Про закрытие и порядок действий.** Раздатчик работает в той же горутине, что
и `ParallelMap`: он блокируется на `tasks <- i`, пока воркеры разбирают. Это
нормально — здесь нам не нужно возвращать управление раньше времени. `close`
после раздачи завершает `range` во всех воркерах, `wg.Wait()` дожидается их, и
только после этого `out` можно читать. Закрыть канал раньше — потерять задачи,
не закрыть вовсе — навсегда повесить воркеров на `range`, а вместе с ними и
`Wait`.

**Чего в этой версии нет и о чём спросят.** Отмены: функция не принимает
`context.Context`, поэтому прервать её нельзя. В настоящем коде сигнатура была
бы `ParallelMap(ctx, ...)`, раздатчик выбирал бы между `tasks <- i` и
`<-ctx.Done()`, а воркеры проверяли контекст перед каждым вызовом `f`. И ошибок:
если `f` может вернуть `error`, дальше идёт разговор про `errgroup` из
`golang.org/x/sync` — она умеет и ограничивать параллелизм (`SetLimit`), и
отменять контекст по первой ошибке, и возвращать её наружу. Строго говоря, вся
эта задача — ручная реализация того, что `errgroup` даёт из коробки; спрашивают
её ровно затем, чтобы увидеть, понимаете ли вы, что там внутри.

**И про панику.** Если `f` паникует, падает весь процесс: `recover` в `main` не
ловит панику из чужой горутины. В пуле, который работает с чужим кодом, тело
воркера обычно оборачивают в `defer func() { if r := recover(); ... }()` —
[см. отдельную задачу про recover](/practice/defer-panic/recover-too-deep/).
