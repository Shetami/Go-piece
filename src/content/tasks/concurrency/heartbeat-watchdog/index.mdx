Общий таймаут на миграцию данных не поставишь: она законно идёт час. Но
если она минуту не продвинулась, значит, зависла. Решение — сердцебиение:
работа периодически вызывает `beat()`, а сторож перезапускает таймер.
Реализуйте `Supervise` по контракту из заготовки.

Что проверяют скрытые тесты:

- работа идёт дольше `timeout`, но регулярно бьётся — её не трогают;
- работа замолчала — ей отменяют контекст, `Supervise` возвращает
  `ErrStalled` (а не то, что вернула работа после отмены), и только после
  того, как работа действительно завершилась;
- собственная ошибка работы и отмена внешнего контекста доходят наружу;
- сотня `beat()` подряд и вызовы `beat()` после возврата `Supervise` не
  блокируются, горутин не остаётся.

```go
func Supervise(ctx context.Context, timeout time.Duration,
	work func(ctx context.Context, beat func()) error) error {
	ctx2, cancel := context.WithCancel(ctx)
	defer cancel()

	beats := make(chan struct{}, 1)
	beat := func() {
		select {
		case beats <- struct{}{}:
		default:
		}
	}

	done := make(chan error, 1)
	go func() { done <- work(ctx2, beat) }()

	timer := time.NewTimer(timeout)
	defer timer.Stop()
	for {
		select {
		case <-beats:
			if !timer.Stop() {
				select {
				case <-timer.C:
				default:
				}
			}
			timer.Reset(timeout)
		case err := <-done:
			return err
		case <-timer.C:
			cancel()
			<-done
			return ErrStalled
		case <-ctx.Done():
			cancel()
			<-done
			return ctx.Err()
		}
	}
}
```

**`beat` — неблокирующая отправка в буфер на один.** С небуферизованным
каналом работа ждала бы, пока сторож прочитает, а после возврата
`Supervise` зависла бы навсегда — это утечка. С буфером 1 и `default`
частые сердцебиения схлопываются в одно («было хоть одно с прошлой
проверки»), а лишние просто выбрасываются. Ровно так устроен heartbeat в
книге «Concurrency in Go».

**Перезапуск таймера.** `Stop` + неблокирующее чтение `timer.C` + `Reset`
корректно и со старыми таймерами, и с новыми из Go 1.23. Без чтения на
старых версиях в канале мог остаться «протухший» тик, и сторож убил бы
живую работу сразу после сердцебиения. Альтернатива — тикер с проверкой
«когда было последнее сердцебиение», но тогда точность — до периода тикера.

**`ErrStalled`, а не то, что вернула работа.** После отмены работа обычно
возвращает `context.Canceled`, и это ничего не говорит о причине. Причину
знает только сторож.

**Дождаться работы, даже зависшей.** `<-done` после `cancel()`: иначе
после возврата `Supervise` работа продолжит жить, писать в базу, держать
ресурсы. Если работа не слушает контекст, `Supervise` будет ждать — это
честнее, чем тихая утечка. На практике добавляют второй, жёсткий таймаут и
алерт.

**Что спросят дальше.** Перезапуск зависшей работы с backoff (supervisor
tree как в Erlang), сердцебиение с прогрессом (`beat(n)` — сколько
обработано, чтобы ловить «бьётся, но не двигается») и как это связано с
liveness-пробой в Kubernetes.
