`firstN` берёт первые три числа из генератора. Результаты правильные, но
после трёх вызовов в программе висят лишние горутины:

```
[0 1 2]
[0 1 2]
[0 1 2]
горутин: 4
```

Должна остаться одна — `main`. Почините. Ожидаемый вывод:

```
[0 1 2]
[0 1 2]
[0 1 2]
горутин: 1
```

<Reveal>

**Производитель не знает, что его больше не слушают.** `firstN` делает
`break` и уходит. Горутина генератора в этот момент стоит на `ch <- i` — и
будет стоять вечно: читателя нет и не будет. Сборщик мусора её не
тронет: заблокированная горутина жива, и всё, на что она ссылается, тоже.
Каждый вызов `firstN` — плюс одна вечная горутина.

**Как чинят** — дать производителю способ узнать об уходе потребителя:

```go
select {
case ch <- i:
case <-ctx.Done():
	return
}
```

А потребитель отменяет контекст, когда заканчивает: `defer cancel()`.

**Правило конвейеров.** Каждая горутина, которая пишет в канал, должна
слушать и сигнал остановки. Иначе любой потребитель, который бросил
читать раньше конца — по ошибке, по таймауту, по `break`, — оставляет за
собой утечку. На Go 1.23+ генераторы часто пишут итераторами
(`iter.Seq`) без горутин вовсе: там `break` просто возвращает `false` из
`yield`, и утекать нечему.

</Reveal>
