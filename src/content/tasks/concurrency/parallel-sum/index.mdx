Напишите `ParallelSum`: разбить `nums` на `parts` примерно равных частей,
посчитать каждую в своей горутине и сложить результаты.

Что проверяют скрытые тесты:

- правильная сумма при разном числе частей — от 1 до 1000;
- длина не делится на `parts` нацело: 5 чисел на 2 части — хвост не
  теряется;
- частей больше, чем чисел; `parts = 0`; пустой вход.

<Reveal>

```go
func ParallelSum(nums []int, parts int) int {
	parts = max(1, min(parts, len(nums)))
	if len(nums) == 0 {
		return 0
	}
	sums := make([]int, parts)
	size := (len(nums) + parts - 1) / parts
	var wg sync.WaitGroup
	for p := range parts {
		lo := min(p*size, len(nums))
		hi := min(lo+size, len(nums))
		wg.Go(func() {
			for _, n := range nums[lo:hi] {
				sums[p] += n
			}
		})
	}
	wg.Wait()
	...
}
```

**Размер части с округлением вверх.** `len / parts` при 5 числах и 2
частях даст 2 — и пятое число никуда не попадёт. `(len + parts - 1) / parts`
даёт 3, а `min(lo+size, len)` обрезает последнюю часть. Остаётся
тонкость: при 10 числах на 4 части размер 3, и частей получится 4 —
`[0:3] [3:6] [6:9] [9:10]`. Но бывает и так, что последние части пустые
(10 чисел на 9 частей: размер 2, шестая часть начиналась бы с индекса 10,
а седьмая — с 12, за концом слайса). Поэтому начало части тоже
ограничивают длиной: `lo := min(p*size, len(nums))`. Пустой диапазон
`[10:10]` просто ничего не прибавит, а `nums[12:10]` — паника.

**Ячейка на горутину.** Каждая горутина пишет в `sums[p]` — разные ячейки,
гонки нет, мьютекс не нужен. Общая переменная с мьютексом тоже работает, но
горутины толкались бы за блокировку.

**Имеет ли это смысл.** Для сложения чисел — почти никогда: память
читается быстрее, чем горутины создаются, и узкое место — пропускная
способность памяти, а не процессор. Сама схема (разбить — посчитать —
собрать) — основа любой параллельной обработки, и на собеседовании её
спрашивают именно как схему. Следом часто спрашивают про false sharing:
соседние ячейки `sums` лежат в одной кэш-линии, и параллельные записи в
них мешают друг другу.

</Reveal>
