Так работают продюсер Kafka, запись метрик и массовые `INSERT`: ждать
полную пачку при низкой нагрузке — слишком долго, отправлять по одному при
высокой — слишком дорого. Реализуйте `Batcher[T]` по контракту из заготовки.

Что проверяют скрытые тесты:

- пачки по размеру, остаток уходит при `Close`, и `Close` возвращается
  только после последнего `flush`;
- неполная пачка уходит через `maxWait`, но не раньше;
- срок считается от первого элемента **текущей** пачки: пачка, начатая
  вскоре после отправки предыдущей, не уходит досрочно;
- `flush` может хранить полученные слайсы — их содержимое не должно
  меняться задним числом;
- двадцать горутин вызывают `Add`, пока идёт `Close`: без паник, ни один
  принятый элемент не потерян, `Add` после `Close` — `ErrClosed`, повторный
  `Close` безопасен, фоновая горутина завершается.

<Reveal>

```go
func (b *Batcher[T]) Add(item T) error {
	b.mu.Lock()
	defer b.mu.Unlock()
	if b.closed {
		return ErrClosed
	}
	b.in <- item
	return nil
}

func (b *Batcher[T]) Close() {
	b.mu.Lock()
	if !b.closed {
		b.closed = true
		close(b.in)
	}
	b.mu.Unlock()
	<-b.done
}

func (b *Batcher[T]) loop() {
	defer close(b.done)
	var batch []T
	var timer *time.Timer
	var timeout <-chan time.Time

	send := func() {
		if timer != nil {
			timer.Stop()
		}
		timeout = nil
		b.flush(batch)
		batch = nil
	}

	for {
		select {
		case item, ok := <-b.in:
			if !ok {
				if len(batch) > 0 {
					send()
				}
				return
			}
			if len(batch) == 0 {
				timer = time.NewTimer(b.maxWait)
				timeout = timer.C
			}
			batch = append(batch, item)
			if len(batch) >= b.maxSize {
				send()
			}
		case <-timeout:
			send()
		}
	}
}
```

**Пачкой владеет одна горутина.** Всё состояние — `batch`, таймер — живёт
в `loop` и никуда не утекает, поэтому мьютекс для него не нужен. Снаружи
только канал `in`. Это «владелец» из лекции про общее состояние.

**Nil-канал выключает ветку `select`.** Пока пачка пуста, `timeout == nil`, и
чтение из него никогда не выбирается. Таймер заводится на первом элементе
пачки и останавливается при любой отправке. Самая частая ошибка — тикер на
весь срок жизни или таймер, который забыли остановить при отправке по
размеру. Тогда он срабатывает посреди следующей пачки, и она уходит
досрочно.

**`batch = nil`, а не `batch[:0]`.** Второй вариант переиспользует массив,
и следующая пачка молча перезапишет данные, которые `flush` сохранил
(или ещё отправляет в фоне). Экономия одной аллокации не стоит такого бага.

**Закрытие канала против отправки в него.** Если `Close` закроет `in`,
пока другая горутина в `Add` в него отправляет, будет `send on closed
channel`. Отправка и закрытие идут под одним мьютексом, флаг `closed`
проверяется там же. Держать мьютекс во время отправки безопасно: `loop`
его не берёт и рано или поздно прочитает канал.

**Что спросят дальше.** `Add` сейчас ждёт, пока идёт `flush`, — это
естественное обратное давление. Если нужно не блокировать, ставят буфер у
`in` или отдельную горутину отправки с очередью пачек. Ещё вопросы: ретраи
неудачного `flush`, `Close(ctx)` с дедлайном и тесты без реального времени
через подменяемые часы.
