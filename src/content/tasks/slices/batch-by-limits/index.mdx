Напишите тело `Batches`. Так продюсер Kafka или клиент bulk-API в
Elasticsearch режет поток: у брокера есть лимит и на число записей в
запросе, и на размер тела.

Что проверяют скрытые тесты:

- пачка закрывается и по количеству, и по байтам; ровно `maxBytes` байт
  ещё помещаются;
- сообщения нулевой длины тоже считаются в `maxCount`;
- сообщение длиннее `maxBytes` — первым, в середине, два подряд — уходит
  отдельной пачкой, и перед ним не появляется пустая пачка;
- пустой вход — ноль пачек;
- пачки — подслайсы `msgs`, а `append` к пачке не затирает следующую;
- нулевые лимиты — паника.

<Reveal>

```go
func Batches(msgs [][]byte, maxCount, maxBytes int) [][][]byte {
	if maxCount <= 0 || maxBytes <= 0 {
		panic("Batches: лимиты должны быть положительными")
	}
	var out [][][]byte
	start, size := 0, 0
	for i, m := range msgs {
		if i > start && (i-start == maxCount || size+len(m) > maxBytes) {
			out = append(out, msgs[start:i:i])
			start, size = i, 0
		}
		size += len(m)
	}
	if start < len(msgs) {
		out = append(out, msgs[start:len(msgs):len(msgs)])
	}
	return out
}
```

**Решение «закрыть пачку» принимается перед добавлением.** Для каждого
сообщения спрашиваем: поместится ли оно в текущую пачку? Если нет —
закрываем текущую и начинаем новую с него. Так пачка никогда не
превышает лимит, и не нужно ничего «откатывать».

**`i > start` — защита от пустых пачек.** Огромное сообщение не
помещается никуда. Без этой проверки перед ним закрылась бы пустая пачка,
а его самого положили бы в новую. С проверкой оно просто становится
единственным в своей пачке, а следующее сообщение закроет её по байтам.
Выбрасывать такое сообщение молча нельзя — это потеря данных; решение
«отдельная пачка» пусть принимает вызывающий или брокер.

**Подслайсы с обрезанной вместимостью.** Копировать сообщения незачем —
пачка это просто окно `msgs[start:i]`. Но `append` к такому окну пишет в
`msgs[i]` — следующую пачку. Третий индекс `msgs[start:i:i]` это
исключает.

**Что спросят дальше.** Добавить лимит по времени (это уже каналы и
таймер); учитывать накладные расходы протокола на каждое сообщение; что
делать, если одно сообщение больше максимального размера запроса брокера
— отдельная очередь ошибок вместо бесконечных ретраев.
