Реализуйте `KeyedMutex`. Задача из прода: вебхуки платёжки по одному
заказу приходят пачкой и параллельно, и их нужно обрабатывать строго по
одному на заказ, при этом разные заказы — одновременно. Ключей
неограниченно много, так что держать мьютекс на каждый вечно нельзя.
Контракт — в doc-комментариях.

Что проверяют скрытые тесты (с детектором гонок):

- двенадцать горутин по 300 раз захватывают три ключа: на каждом ключе
  никогда не бывает двоих, и после всех `unlock` записей не остаётся;
- пока держат ключ `a`, ключ `b` захватывается сразу, а второй `Lock(a)`
  ждёт; двойной `unlock` ничего не ломает.

<Reveal>

```go
type keyLock struct {
	mu   sync.Mutex
	refs int
}

type KeyedMutex struct {
	mu    sync.Mutex
	locks map[string]*keyLock
}

func (m *KeyedMutex) Lock(key string) func() {
	m.mu.Lock()
	if m.locks == nil {
		m.locks = make(map[string]*keyLock)
	}
	l, ok := m.locks[key]
	if !ok {
		l = &keyLock{}
		m.locks[key] = l
	}
	l.refs++
	m.mu.Unlock()

	l.mu.Lock()

	return sync.OnceFunc(func() {
		l.mu.Unlock()
		m.mu.Lock()
		l.refs--
		if l.refs == 0 {
			delete(m.locks, key)
		}
		m.mu.Unlock()
	})
}
```

**Считать нужно и ждущих, а не только держателя.** Наивная уборка —
«при `unlock` удалить запись о ключе» — ломает взаимоисключение. Горутина
B взяла из мапы мьютекс ключа и ждёт на нём. A отпускает и удаляет запись.
Приходит C, не находит запись, создаёт *новый* мьютекс и сразу его
захватывает. B тем временем получает старый — теперь в секции двое
(первый тест). Счётчик `refs` увеличивается под общим мьютексом ещё до
ожидания, поэтому запись живёт, пока на неё хоть кто-то рассчитывает.

**Два уровня блокировки.** Общий мьютекс держится наносекунды — найти
запись и поправить счётчик. Ожидание ключа идёт на его собственном
мьютексе, уже после `Unlock` общего. Если ждать ключ под общим
мьютексом, блокировка одного заказа остановит все остальные — и
получится дедлок: держатель не сможет отпустить ключ, потому что
`unlock` тоже берёт общий мьютекс.

**`sync.OnceFunc` (Go 1.21)** делает `unlock` идемпотентным. Без него
двойной вызов разблокирует чужой захват и уведёт `refs` в минус. Удобно
вернуть функцию, а не заставлять вызывающего передавать ключ второй раз:
`defer km.Lock(orderID)()`.

**Что спросят дальше.** Это работает в одном процессе. Если сервис
запущен в нескольких репликах, вебхуки по одному заказу попадут на
разные поды — нужна распределённая блокировка (Redis `SET NX PX`,
`SELECT ... FOR UPDATE` в базе) или маршрутизация по ключу, чтобы все
события заказа шли в одну партицию Kafka и один обработчик.
