Слотов десять. Сто горутин пытаются занять слот. Счётчик — `atomic.Int64`,
`-race` молчит. Программа печатает

```
выдано слотов: 100 из 10
```

Отметьте строку, в которой заложена поломка.

<Reveal>

Сломано в строке 16: `if active.Load() < limit` — проверка отдельно от
захвата.

**Атомарная каждая операция, но не их сочетание.** `Load` атомарен, `Add`
атомарен, а «прочитать, проверить, увеличить» — три шага, между которыми
может пройти что угодно. Сто горутин одновременно читают `0`, все видят
«меньше десяти», все проходят проверку, и потом все делают `Add`. Пауза
между проверкой и захватом лишь делает окно шире — в реальном коде там
логирование, запрос прав, что угодно.

Детектор гонок это не ловит: гонка данных — это неатомарный доступ к
памяти, а здесь каждый доступ атомарный. Это гонка *логическая*
(race condition), check-then-act. Её никакой инструмент не найдёт.

**Как правильно** — сделать проверку и захват одной операцией:

```go
for {
	cur := active.Load()
	if cur >= limit {
		return false
	}
	if active.CompareAndSwap(cur, cur+1) {
		return true
	}
}
```

Если между чтением и записью кто-то успел изменить значение, CAS не
сработает, и цикл перечитает. Проще, когда можно: взять мьютекс на всю
проверку, или семафор — буферизованный канал на `limit` мест, или
`golang.org/x/sync/semaphore`.

</Reveal>
