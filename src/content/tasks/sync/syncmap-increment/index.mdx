Тысяча горутин увеличивают счётчик в `sync.Map`. `-race` молчит, а
программа печатает число меньше тысячи — каждый раз разное.

Почините. Ожидаемый вывод:

```
просмотров: 1000
```

<Reveal>

**`sync.Map` защищает каждую операцию, но не их последовательность.**
`LoadOrStore` атомарен, `Store` атомарен. Но «прочитать значение, прибавить
один, записать» — это две операции, и между ними другие горутины успевают
сделать то же самое. Две горутины читают 41, обе записывают 42 — один
просмотр потерян. Гонки *данных* нет, поэтому детектор молчит. Есть
логическая гонка: check-then-act.

**Как чинят** — сделать само значение атомарным:

```go
v, _ := hits.LoadOrStore("/", new(atomic.Int64))
v.(*atomic.Int64).Add(1)
```

`LoadOrStore` гарантирует, что счётчик на ключ создастся ровно один раз, а
дальше все горутины увеличивают один и тот же `atomic.Int64`. Лишний
`new(atomic.Int64)` на каждом вызове — мелкая плата; если важно, сначала
пробуют `Load`, а `LoadOrStore` зовут только при промахе.

**Другой путь** — обычная мапа под `sync.Mutex`, внутри которого
`m[k]++`. Для счётчиков с небольшим числом ключей это часто и быстрее, и
понятнее. `sync.Map` выигрывает, когда ключи в основном только читаются
или каждая горутина работает со своими ключами.

Также есть `CompareAndSwap` у самой `sync.Map` (Go 1.20): цикл «прочитал,
посчитал, CAS» решает задачу без атомиков внутри, но пишется длиннее.

</Reveal>
