Реализуйте `Pool` — пул соединений, как в `database/sql` или клиенте
Redis: открытых соединений не больше `max`, простаивающие
переиспользуются, а когда всё занято — `Get` ждёт с уважением к
контексту. Контракт — в doc-комментариях.

Что проверяют скрытые тесты (с детектором гонок):

- возвращённое соединение переиспользуется, причём последнее
  возвращённое выдаётся первым;
- при исчерпанном пуле `Get` с таймаутом получает `DeadlineExceeded`, а
  ждущий без таймаута просыпается от `Put`;
- в пуле на одно соединение его выбрасывают через `Discard` — ждущий
  `Get` получает новое;
- три неудачных `dial` подряд, потом удачный;
- двенадцать горутин с короткими таймаутами, `Put` и `Discard` вперемешку
  на пуле из трёх: одновременно выдано не больше трёх, никто не завис.

```go
type Pool struct {
	dial func() (*Conn, error)
	max  int

	mu      sync.Mutex
	idle    []*Conn
	open    int
	waiters []chan struct{}
}

func (p *Pool) Get(ctx context.Context) (*Conn, error) {
	for {
		p.mu.Lock()
		if n := len(p.idle); n > 0 {
			c := p.idle[n-1]
			p.idle = p.idle[:n-1]
			p.mu.Unlock()
			return c, nil
		}
		if p.open < p.max {
			p.open++
			p.mu.Unlock()
			c, err := p.dial()
			if err != nil {
				p.release()
				return nil, err
			}
			return c, nil
		}
		ch := make(chan struct{}, 1)
		p.waiters = append(p.waiters, ch)
		p.mu.Unlock()

		select {
		case <-ch:
		case <-ctx.Done():
			p.mu.Lock()
			removed := p.removeWaiter(ch)
			p.mu.Unlock()
			if !removed {
				p.wakeOne()
			}
			return nil, ctx.Err()
		}
	}
}

func (p *Pool) Put(c *Conn) {
	p.mu.Lock()
	p.idle = append(p.idle, c)
	p.wakeLocked()
	p.mu.Unlock()
}

func (p *Pool) Discard(c *Conn) { p.release() }

func (p *Pool) release() {
	p.mu.Lock()
	p.open--
	p.wakeLocked()
	p.mu.Unlock()
}
```

**Ждут двух разных событий — и будить нужно на оба.** Ждущему `Get`
подходит и возвращённое соединение (`Put`), и освободившееся место
(`Discard`, неудачный `dial`). Забыть побудку в `Discard` — классика: в
пуле на одно соединение оно сломалось, место свободно, а ждущий спит
вечно (третий тест). Любое изменение, после которого ждущий может
продвинуться, должно его будить.

**`dial` без мьютекса, но с бронью.** Открытие соединения — сетевой
вызов на миллисекунды. Под мьютексом оно остановило бы и `Put`, и
раздачу простаивающих. Поэтому место бронируется (`open++`) под
мьютексом, а `dial` идёт после `Unlock`. Если `dial` упал, бронь
возвращается — иначе каждая ошибка сети навсегда съедает место в пуле
(четвёртый тест).

**Сигнал, пришедший отменённому.** Ждущего разбудили, и в тот же момент
истёк его контекст — `select` выбрал `ctx.Done()`. Если просто уйти,
сигнал пропадёт, а место или соединение достанутся никому. Поэтому,
уходя по отмене, ждущий проверяет, стоит ли он ещё в очереди; если его
уже убрали (значит, сигнал был отправлен ему), он передаёт побудку
следующему.

**Канал на каждого ждущего вместо `sync.Cond`**, потому что `Cond` не
умеет ждать контекст. Очередь ждущих — FIFO: так никто не голодает.
Канал с буфером 1 позволяет будить под мьютексом, не блокируясь.

**LIFO для простаивающих.** Последнее возвращённое соединение — самое
«тёплое»: TCP-окно разогнано, сервер точно не закрыл его по idle-таймауту.
А редко используемые остаются в хвосте и закрываются по `MaxIdleTime`.
Что спросят дальше: проверку соединения при выдаче, `MaxIdleConns` и
фоновое закрытие простаивающих — всё это есть в `database/sql`.
