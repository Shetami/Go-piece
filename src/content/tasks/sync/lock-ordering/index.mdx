Тысяча переводов с `a` на `b` и тысяча обратно. Балансы должны остаться по
сто. Программа зависает и падает:

```
fatal error: all goroutines are asleep - deadlock!
```

Почините. Ожидаемый вывод:

```
100 100
```

<Reveal>

**Два мьютекса, взятые в разном порядке, — классический дедлок.** Перевод
`a → b` берёт сначала `a.mu`, потом `b.mu`. Встречный `b → a` — сначала
`b.mu`, потом `a.mu`. Если они стартуют одновременно, первый держит `a` и
ждёт `b`, второй держит `b` и ждёт `a`. Никто не отпустит своё первым.

С тысячей встречных переводов это происходит почти наверняка. С двумя —
иногда. Отсюда слава «плавающего» дедлока.

**Как чинят** — глобальный порядок захвата. Все, кто берёт несколько
мьютексов, берут их в одном и том же порядке — например, по возрастанию
`id`:

```go
first, second := from, to
if second.id < first.id {
	first, second = second, first
}
first.mu.Lock()
second.mu.Lock()
```

Направление перевода влияет только на то, откуда списывать, но не на
порядок блокировок. Циклическое ожидание становится невозможным.

**Другие варианты.** Один общий мьютекс на все счета (просто, но все
переводы идут строго по очереди). Или `TryLock` с откатом и повтором —
в Go он есть с 1.18, но документация честно предупреждает, что правильных
применений у него мало. То же правило упорядоченного захвата работает и в
базах данных: `SELECT ... FOR UPDATE ... ORDER BY id`.

</Reveal>
