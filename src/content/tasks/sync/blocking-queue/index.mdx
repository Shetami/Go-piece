Реализуйте `Queue` — ограниченную блокирующую очередь на `sync.Mutex` и
`sync.Cond`, без каналов. Это классика live-coding: на ней видно,
понимаете ли вы `Wait` в цикле, `Signal` против `Broadcast` и потерянные
побудки. Контракт — в doc-комментариях.

Что проверяют скрытые тесты (с детектором гонок):

- порядок FIFO; `Put` в полную очередь ждёт, пока освободится место;
- три `Take` ждут на пустой очереди, три `Put` — на полной; `Close` (дважды)
  будит всех: первые получают `false`, вторые — `ErrClosed`;
- после `Close` оставшиеся элементы ещё можно забрать;
- четыре производителя и четыре потребителя гоняют 4000 элементов через
  очередь на два места — ни один не потерян, никто не завис.

<Reveal>

```go
type Queue[T any] struct {
	mu       sync.Mutex
	notEmpty *sync.Cond
	notFull  *sync.Cond
	buf      []T
	head, n  int
	closed   bool
}

func (q *Queue[T]) Put(v T) error {
	q.mu.Lock()
	defer q.mu.Unlock()
	for q.n == len(q.buf) && !q.closed {
		q.notFull.Wait()
	}
	if q.closed {
		return ErrClosed
	}
	q.buf[(q.head+q.n)%len(q.buf)] = v
	q.n++
	q.notEmpty.Signal()
	return nil
}

func (q *Queue[T]) Take() (T, bool) {
	q.mu.Lock()
	defer q.mu.Unlock()
	for q.n == 0 && !q.closed {
		q.notEmpty.Wait()
	}
	var zero T
	if q.n == 0 {
		return zero, false
	}
	v := q.buf[q.head]
	q.buf[q.head] = zero
	q.head = (q.head + 1) % len(q.buf)
	q.n--
	q.notFull.Signal()
	return v, true
}

func (q *Queue[T]) Close() {
	q.mu.Lock()
	defer q.mu.Unlock()
	q.closed = true
	q.notEmpty.Broadcast()
	q.notFull.Broadcast()
}
```

**Два условия, а не одно.** Если и производители, и потребители ждут на
одном `Cond`, то `Signal` после `Put` может разбудить *производителя*:
тот видит, что очередь всё ещё полна, и снова засыпает — а потребитель,
которому предназначался сигнал, спит дальше. Побудка потеряна, и при
малой ёмкости всё виснет (последний тест). С одним `Cond` работает только
`Broadcast` на каждое изменение — корректно, но будит всех ради одного.

**`for`, а не `if`, вокруг `Wait`.** Между сигналом и пробуждением
другой потребитель мог успеть забрать элемент, а ещё бывают ложные
пробуждения — после `Wait` условие обязательно перепроверяется.

**Закрытие — это тоже условие ожидания.** `closed` входит в условие
цикла в обоих методах, иначе ждущий на пустой очереди не заметит
`Close`. И тут нужен именно `Broadcast`: проснуться должны все, а не один.
`Put` проверяет `closed` раньше места — положить в закрытую очередь нельзя
даже при свободном месте. `Take`, наоборот, сначала отдаёт остаток: так
при остановке сервиса не теряются уже принятые задачи.

**Кольцевой буфер и обнуление слота.** `buf = buf[1:]` сдвигал бы окно
по массиву, и `append` периодически копировал бы его заново; кольцо
работает на месте. Обнулить отданный слот нужно, чтобы очередь не
удерживала от сборщика мусора большие объекты, которые давно забрали.

**Что спросят дальше.** Как добавить `Put` с контекстом? `sync.Cond` не
умеет ждать `ctx.Done()` — будить всех через `context.AfterFunc` (см.
задачу про ожидание версии) или переписать на каналах. Именно поэтому в
Go такую очередь чаще всего и пишут как буферизованный канал.
