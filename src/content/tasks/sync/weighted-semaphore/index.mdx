Реализуйте `Weighted` — семафор с весами, как
`golang.org/x/sync/semaphore`. Пример из прода: сервис обрабатывает
загруженные файлы и не должен держать в памяти больше 1 ГБ, так что
файл на 300 МБ занимает 300 единиц, а на 2 МБ — две. Контракт — в
doc-комментариях.

Что проверяют скрытые тесты (с детектором гонок):

- занято 8 из 10, ждёт запрос на 5: `TryAcquire(2)` и `Acquire(1)` не
  проходят вперёд него, хотя места им хватает; после `Release` проходят оба;
- занято 5 из 10, первым в очереди ждёт запрос на 10, за ним — на 3;
  первый отменяют — второй должен пройти сразу;
- запрос больше ёмкости и лишний `Release`;
- десять горутин с короткими таймаутами: одновременно занято не больше
  ёмкости, и в конце ни одна единица не потеряна.

```go
type Weighted struct {
	size    int64
	mu      sync.Mutex
	cur     int64
	waiters list.List
}

func (s *Weighted) Acquire(ctx context.Context, n int64) error {
	if n > s.size {
		return ErrTooLarge
	}
	s.mu.Lock()
	if s.size-s.cur >= n && s.waiters.Len() == 0 {
		s.cur += n
		s.mu.Unlock()
		return nil
	}
	w := &waiter{n: n, ready: make(chan struct{})}
	elem := s.waiters.PushBack(w)
	s.mu.Unlock()

	select {
	case <-w.ready:
		return nil
	case <-ctx.Done():
		s.mu.Lock()
		defer s.mu.Unlock()
		select {
		case <-w.ready:
			s.cur -= n
			s.notifyLocked()
		default:
			front := s.waiters.Front() == elem
			s.waiters.Remove(elem)
			if front {
				s.notifyLocked()
			}
		}
		return ctx.Err()
	}
}

func (s *Weighted) Release(n int64) {
	s.mu.Lock()
	defer s.mu.Unlock()
	if n > s.cur {
		panic("semaphore: released more than held")
	}
	s.cur -= n
	s.notifyLocked()
}

func (s *Weighted) notifyLocked() {
	for {
		e := s.waiters.Front()
		if e == nil {
			return
		}
		w := e.Value.(*waiter)
		if s.size-s.cur < w.n {
			return
		}
		s.cur += w.n
		s.waiters.Remove(e)
		close(w.ready)
	}
}
```

**FIFO ради больших запросов.** Если пускать всех, кому хватает места,
то при постоянном потоке мелких задач свободных единиц никогда не станет
10 разом, и большая задача будет ждать вечно. Поэтому и быстрый путь, и
`TryAcquire` смотрят не только на свободное место, но и на пустоту
очереди, а раздача в `notifyLocked` останавливается на первом, кому не
хватает.

**Отмена первого в очереди должна будить следующих.** Первый ждал 10
единиц и загораживал очередь; свободно 5, за ним стоит запрос на 3.
Если отменённый просто уйдёт из списка, запрос на 3 будет спать до
ближайшего `Release`, которого может и не быть (второй тест).
`x/sync/semaphore` делает то же самое: при отмене первого ждущего
вызывает раздачу заново.

**Гонка «выдали и отменили одновременно».** `Release` мог закрыть
`ready` в тот же момент, когда сработал `ctx.Done()`, и `select` выбрал
отмену. Под мьютексом проверяем `ready` ещё раз: если единицы уже
выданы, возвращаем их — иначе они потеряны навсегда, и семафор тихо
сжимается (последний тест).

**Ожидание на своём канале, а не на `sync.Cond`.** У каждого ждущего
свой канал, который закрывается при выдаче: это позволяет ждать в
`select` вместе с контекстом и будить конкретного ждущего, а не всех.
`container/list` даёт удаление из середины очереди за O(1).

**`n > size` — сразу ошибка.** Такой запрос не выполнится никогда, но,
встав первым в очередь, он навсегда заблокирует всех за собой. В
`x/sync/semaphore` в этом случае `Acquire` ждёт отмены контекста — ещё
один вопрос, который стоит обсудить.
