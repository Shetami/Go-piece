Реализуйте `Limiter` — ограничение частоты запросов по алгоритму token
bucket, с отдельным ведром на каждого клиента. Такое стоит в
middleware почти любого публичного API. Контракт — в doc-комментарии к
типу; время берите только из `now`.

Что проверяют скрытые тесты (с детектором гонок):

- новый клиент получает ровно `burst`, клиенты не делят вёдра, после
  долгого простоя — снова не больше `burst`;
- запросы каждые 500 мс при скорости 1 токен в секунду;
- часы переводят на минуту назад, потом вперёд;
- `Cleanup` удаляет только полностью пополнившиеся вёдра;
- 400 одновременных запросов одного клиента при замороженных часах.

<Reveal>

```go
type bucket struct {
	tokens float64
	last   time.Time
}

func (l *Limiter) refill(b *bucket, now time.Time) {
	if elapsed := now.Sub(b.last); elapsed > 0 {
		b.tokens = min(l.burst, b.tokens+elapsed.Seconds()*l.rate)
		b.last = now
	}
}

func (l *Limiter) Allow(key string) bool {
	now := l.now()
	l.mu.Lock()
	defer l.mu.Unlock()
	b, ok := l.buckets[key]
	if !ok {
		b = &bucket{tokens: l.burst, last: now}
		l.buckets[key] = b
	}
	l.refill(b, now)
	if b.tokens < 1 {
		return false
	}
	b.tokens--
	return true
}

func (l *Limiter) Cleanup() int {
	now := l.now()
	l.mu.Lock()
	defer l.mu.Unlock()
	n := 0
	for k, b := range l.buckets {
		l.refill(b, now)
		if b.tokens >= l.burst {
			delete(l.buckets, k)
			n++
		}
	}
	return n
}
```

**Никакого тикера — ленивое пополнение.** Доливать токены фоновой
горутиной в каждое ведро — O(клиентов) работы каждую секунду. Вместо
этого ведро помнит время последнего обновления, и при обращении мы
досчитываем, сколько накапало: `elapsed × rate`, но не больше `burst`.

**Дробные токены.** Если хранить `int` и округлять вниз, то при
запросах каждые 500 мс и скорости 1/с каждый раз накапывает 0,5 → 0, а
`last` сдвигается — токены не накопятся никогда, и клиент заблокирован
навечно (второй тест). Либо `float64`, либо двигать `last` только на
время, соответствующее целым выданным токенам.

**Часы назад.** Настенное время может прыгнуть назад (NTP, ручной перевод),
и тогда `elapsed` отрицательный: токены уйдут в минус или, если сдвинуть
`last` в прошлое, следующий вызов насчитает лишнее. Поэтому при
`elapsed <= 0` ведро не трогаем. (У `time.Now()` в Go есть монотонная
составляющая, и `Sub` между двумя его результатами назад не идёт, но
подменённые часы или время из заголовка запроса — идут.)

**Одна блокировка на «пополнить — проверить — списать».** Если проверка
и списание разнесены, две горутины одного клиента увидят один и тот же
последний токен и обе пройдут — лимит нарушен (последний тест). Для
очень горячих ключей мьютекс шардируют по хешу ключа, как в
шардированном счётчике.

**Уборка.** Без `Cleanup` мапа растёт на каждый IP, который хоть раз
пришёл, — при сканировании портов это миллионы записей. Полное ведро
неотличимо от нового, поэтому его можно удалить без потери состояния.
Что спросят дальше: на нескольких репликах лимит должен быть общим —
тогда ведро живёт в Redis и обновляется Lua-скриптом атомарно, а для
одного процесса готовый вариант — `golang.org/x/time/rate`.
