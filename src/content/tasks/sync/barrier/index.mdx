Допишите `Barrier`: поля, конструктор и `Wait`. Так синхронизируют фазы
вычисления: никто не начинает шаг `k+1`, пока все не закончили шаг `k`.

Что проверяют скрытые тесты:

- пока пришли двое из трёх, не проходит никто; третий открывает барьер
  для всех;
- четыре горутины проходят пятьдесят кругов подряд, и за барьером каждого
  круга видно, что отметились все четверо;
- барьер на одного участника пропускает сразу.

<Reveal>

```go
type Barrier struct {
	mu      sync.Mutex
	cond    *sync.Cond
	n       int
	arrived int
	round   int
}

func (b *Barrier) Wait() {
	b.mu.Lock()
	defer b.mu.Unlock()

	round := b.round
	b.arrived++
	if b.arrived == b.n {
		b.arrived = 0
		b.round++
		b.cond.Broadcast()
		return
	}
	for round == b.round {
		b.cond.Wait()
	}
}
```

**Вся сложность — в многоразовости.** Однократный барьер ждал бы условия
«собрались все»: `for b.arrived < b.n { Wait() }`. Но последний пришедший
тут же обнуляет счётчик для следующего круга, и проснувшиеся увидят
`arrived == 0` — снова заснут, навсегда.

**Номер круга решает это.** Каждый запоминает, в каком круге пришёл, и
ждёт, пока круг сменится. Сменить его может только последний участник
этого круга. Быстрая горутина, которая уже прошла и пришла в следующий
круг, увеличивает `arrived` для *нового* круга и не путает ожидающих.

**`for`, а не `if`, вокруг `Wait`** — как всегда с `sync.Cond`.

**Каналом тоже можно:** канал на каждый круг, последний его закрывает, а
ожидающие читают. Закрытие канала — широковещательный сигнал, как
`Broadcast`.

</Reveal>
