Реализуйте `Registry` — реестр «ключ → значение» с подпиской на
изменения, как watch в etcd или Consul для адресов сервисов и
фичефлагов. Подписчику важно не каждое промежуточное значение, а
актуальное: если он отстал, старые уведомления заменяются новым.
Контракт — в doc-комментариях.

Что проверяют скрытые тесты (с детектором гонок):

- подписка на ключ, у которого уже есть значение; уведомления только
  своего ключа; двойной `cancel` закрывает канал и убирает подписку;
- подписчик не читает канал, а в ключ сто раз пишут: `Set` не
  блокируется, подписчик потом получает ровно последнее значение;
- четыре горутины непрерывно пишут в ключ, а подписки открываются и
  отменяются из двух горутин одновременно — без паник.

<Reveal>

```go
type Registry struct {
	mu       sync.RWMutex
	values   map[string]string
	watchers map[string]map[*watcher]struct{}
}

func (r *Registry) Set(key, value string) {
	r.mu.Lock()
	defer r.mu.Unlock()
	r.values[key] = value
	for w := range r.watchers[key] {
		offerLatest(w.ch, value)
	}
}

func offerLatest(ch chan string, v string) {
	select {
	case <-ch:
	default:
	}
	ch <- v
}

func (r *Registry) Watch(key string) (<-chan string, func()) {
	w := &watcher{ch: make(chan string, 1)}
	r.mu.Lock()
	if r.watchers[key] == nil {
		r.watchers[key] = make(map[*watcher]struct{})
	}
	r.watchers[key][w] = struct{}{}
	if v, ok := r.values[key]; ok {
		w.ch <- v
	}
	r.mu.Unlock()

	cancel := func() {
		r.mu.Lock()
		defer r.mu.Unlock()
		if _, ok := r.watchers[key][w]; !ok {
			return
		}
		delete(r.watchers[key], w)
		if len(r.watchers[key]) == 0 {
			delete(r.watchers, key)
		}
		close(w.ch)
	}
	return w.ch, cancel
}
```

**Канал на одно место + «выбросить старое, положить новое».** Это не
очередь событий, а ящик с последним значением. Отправка никогда не
блокируется: если в ящике лежит непрочитанное, оно уже неактуально —
его вынимаем и кладём новое. Так делают watch-механизмы: клиенту нужен
текущий адрес базы, а не история всех промежуточных. Сравните с брокером
сообщений, где каждое сообщение важно, и лишнее для медленного
подписчика выбрасывается целиком.

**Почему `offerLatest` безопасна только под `Lock`.** Между «вынуть» и
«положить» не должно быть другого писателя: два `Set` одновременно могли
бы оба вынуть, потом оба положить — второй `ch <- v` заблокируется
навсегда, или старое значение ляжет поверх нового. Поэтому `Set` берёт
полную блокировку, а `RLock` остаётся только у `Get`, которых
большинство.

**Закрытие канала — под той же блокировкой, что и отправка.** Если
`cancel` закроет канал без мьютекса, `Set`, который уже нашёл этого
подписчика в мапе, отправит в закрытый канал — паника `send on closed
channel` (третий тест). А проверка «ещё подписан?» под мьютексом делает
`cancel` идемпотентным без отдельного `sync.Once`.

**Уборка пустых множеств.** Если не удалять `watchers[key]`, когда
подписок не осталось, мапа растёт на каждый ключ, на который хоть раз
подписывались, — медленная утечка памяти в долгоживущем процессе.

**Что спросят дальше.** Как узнать, сколько значений пропустил
подписчик? Отправлять не строку, а пару «значение + ревизия», как etcd.
И как подписаться на префикс (`/services/`): хранить подписки в дереве
или проверять `strings.HasPrefix` при каждом `Set`.
