Напишите тело `Filter`. Она возвращает новый слайс из тех элементов, для
которых `keep` вернула `true`.

Что проверяют скрытые тесты:

- отбор работает для чисел, строк и структур;
- порядок сохраняется;
- исходный слайс не меняется;
- на `nil`-входе и когда ничего не подошло — пустой результат, без паники.

<Reveal>

```go
func Filter[T any](items []T, keep func(T) bool) []T {
	out := make([]T, 0, len(items))
	for _, item := range items {
		if keep(item) {
			out = append(out, item)
		}
	}
	return out
}
```

**Ограничение — `any`, и это важно.** Соблазн написать `comparable` или
`constraints.Ordered` велик, но мы не сравниваем элементы между собой и не
сортируем их: всё решение принимает переданная функция. Лишнее ограничение
только сузит круг типов, с которыми функция работает. Правило простое: в
ограничение попадает ровно то, что вы с типом делаете внутри.

**`make([]T, 0, len(items))` против `var out []T`.** Оба варианта правильные.
Первый заранее берёт память под худший случай и избавляет `append` от
перевыделений — за счёт того, что при жёстком фильтре память тратится зря.
Второй экономен, но может несколько раз перевыделить массив. Для библиотечной
функции обычно берут первый: `append` растёт с копированием, и это заметнее,
чем разовый перебор памяти.

**Есть и содержательная разница:** `make(...)` возвращает пустой, но не
`nil`-слайс, а `var out []T` при пустом результате вернёт `nil`. Для `len`,
`range` и `append` это одно и то же, а вот `encoding/json` кодирует `nil` как
`null`, а пустой слайс — как `[]`. Поэтому в тестах здесь проверяется `len`, а
не сравнение с `nil`: спорить о такой мелочи в задаче незачем, но знать о ней
стоит.

**Почему исходный слайс не страдает.** Мы пишем только в свежий `out`. Если бы
вы решили фильтровать «на месте» — популярный приём `items[:0]`:

```go
out := items[:0]        // тот же массив, длина ноль
for _, item := range items {
	if keep(item) { out = append(out, item) }
}
```

— то результат был бы верным, но исходный слайс оказался бы затёрт: `out`
пишет в тот же массив. Это законный приём, когда вы владеете слайсом и хотите
ноль выделений, но для функции-утилиты он опасен ровно так же, как история
[из задачи про Split](/practice/slices/shared-array-append/). Тест про
неизменность входа стоит именно здесь.

**Что спросят следом.** Почему у Go нет `Map` в стандартной библиотеке в том же
виде (до Go 1.27 у методов не могло быть своих параметров типа, поэтому
цепочки `.Filter().Map()` было не построить — только отдельные функции, и
стандартная библиотека так и осталась набором функций); что лежит в
`slices` начиная с 1.21 (`slices.DeleteFunc`, `slices.IndexFunc`,
`slices.ContainsFunc` — половина нужного уже есть); и во что дженерики
обходятся на исполнении — компилятор генерирует код не на каждый тип, а на
каждую «форму» (GC shape), так что все указательные типы делят одну
реализацию и ходят через словарь.

</Reveal>
