Допишите `TopK`. Сценарий — «десять самых медленных запросов за сутки»
или «топ страниц по хитам» из лога в миллионы строк, который читается
итератором и в память целиком не влезает.

Что проверяют скрытые тесты:

- обычный топ с повторами, `k` больше длины, `k = 0` → `nil`, обратный
  `less` даёт `k` наименьших;
- из равных побеждают встреченные раньше, и в ответе они идут в порядке
  появления;
- 200 случайных наборов сверяются со стабильной сортировкой;
- топ-10 из миллиона чисел выделяет меньше мегабайта: поток нельзя
  собирать в слайс.

<Reveal>

```go
type ranked[T any] struct {
	v   T
	idx int
}

type worstFirst[T any] struct {
	items []ranked[T]
	less  func(a, b T) bool
}

func (h *worstFirst[T]) worse(a, b ranked[T]) bool {
	if h.less(a.v, b.v) {
		return true
	}
	if h.less(b.v, a.v) {
		return false
	}
	return a.idx > b.idx
}

// Len, Less (через worse), Swap, Push, Pop — для container/heap.

func TopK[T any](seq iter.Seq[T], k int, less func(a, b T) bool) []T {
	if k <= 0 {
		return nil
	}
	h := &worstFirst[T]{items: make([]ranked[T], 0, k), less: less}
	i := 0
	for v := range seq {
		cur := ranked[T]{v, i}
		i++
		if len(h.items) < k {
			h.items = append(h.items, cur)
			if len(h.items) == k {
				heap.Init(h)
			}
			continue
		}
		if less(h.items[0].v, v) {
			h.items[0] = cur
			heap.Fix(h, 0)
		}
	}
	slices.SortFunc(h.items, func(a, b ranked[T]) int {
		switch {
		case h.worse(b, a):
			return -1
		case h.worse(a, b):
			return 1
		}
		return 0
	})
	out := make([]T, len(h.items))
	for j, r := range h.items {
		out[j] = r.v
	}
	return out
}
```

**Для топа наибольших нужна куча на минимум.** В корне лежит худший из
отобранных — тот, кого первым вытеснят. Каждый новый элемент
сравнивается только с корнем: не лучше — пропускаем за `O(1)`, лучше —
заменяем корень и погружаем за `O(log k)`. Итого `O(n log k)` времени и
`O(k)` памяти, а сортировка всего потока — `O(n log n)` и `O(n)`.

**Стабильность — через номер элемента.** Куча нестабильна, поэтому
«раньше встреченный лучше» записано явно в `worse`. Новый элемент всегда
встречен позже всех отобранных, значит, при равенстве с корнем он хуже,
и заменять надо только строго большим. Если заменять при `!less(v, top)`,
ничьи достанутся последним.

**`heap.Fix` вместо `Pop` + `Push`.** `Push` принимает `any`, и каждый
вызов упаковывал бы элемент в интерфейс — лишнее выделение памяти на
элемент потока. Замена корня на месте и `Fix` ничего не выделяют, поэтому
тест на память проходит.

**`iter.Seq` на входе — не формальность.** Со слайсом на входе память
уже потрачена до вызова. С итератором данные текут через функцию по
одному, и `O(k)` становится реальной границей.

**Что спросят дальше:** как считать топ по частоте, когда ключей слишком
много для мапы (Count-Min Sketch и Space-Saving), как слить топы с
нескольких шардов (топ из объединения их топов) и когда проще
`slices.SortFunc` и срез (маленькие `n`).
