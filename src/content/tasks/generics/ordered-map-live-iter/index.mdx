Допишите `OrderedMap`. Такая структура нужна, когда порядок важен:
заголовки HTTP в порядке добавления, поля JSON в стабильном порядке,
очередь задач с поиском по id. Обычная мапа в Go обходится в случайном
порядке. При этом со встроенной мапой можно удалять ключи прямо в
`range`, и от своей структуры ждут того же.

Что проверяют скрытые тесты:

- порядок вставки, обновление не двигает ключ, удалённый и снова
  добавленный ключ встаёт в конец, удаление всех ключей и новая вставка;
- в обходе удаляется текущий ключ и следующий — выдаются ровно
  `0, 2, 4, 6, 8`;
- в обходе удаляется хвост, на котором стоит итератор, и дописываются
  два новых ключа — они тоже выдаются;
- 4000 случайных операций сверяются с моделью на слайсе;
- 200 000 `Set` и удаление всех, кроме последнего, — быстрее секунды.

```go
type omEntry[K comparable, V any] struct {
	key        K
	val        V
	prev, next *omEntry[K, V]
	deleted    bool
}

type OrderedMap[K comparable, V any] struct {
	idx  map[K]*omEntry[K, V]
	root omEntry[K, V]
	tail *omEntry[K, V]
}

func (m *OrderedMap[K, V]) last() *omEntry[K, V] {
	if m.tail == nil {
		return &m.root
	}
	return m.tail
}

func (m *OrderedMap[K, V]) Set(k K, v V) {
	if e, ok := m.idx[k]; ok {
		e.val = v
		return
	}
	if m.idx == nil {
		m.idx = make(map[K]*omEntry[K, V])
	}
	t := m.last()
	e := &omEntry[K, V]{key: k, val: v, prev: t}
	t.next = e
	m.tail = e
	m.idx[k] = e
}

func (m *OrderedMap[K, V]) Delete(k K) bool {
	e, ok := m.idx[k]
	if !ok {
		return false
	}
	delete(m.idx, k)
	e.deleted = true
	e.prev.next = e.next
	if e.next != nil {
		e.next.prev = e.prev
	} else {
		m.tail = e.prev
		if m.tail == &m.root {
			m.tail = nil
		}
	}
	return true
}

func (m *OrderedMap[K, V]) All() iter.Seq2[K, V] {
	return func(yield func(K, V) bool) {
		for nd := m.root.next; nd != nil; {
			if !yield(nd.key, nd.val) {
				return
			}
			for nd.deleted {
				nd = nd.prev
			}
			nd = nd.next
		}
	}
}
```

**Мапа для поиска, список для порядка.** Мапа ведёт от ключа к узлу
списка, поэтому `Delete` вырезает узел за `O(1)`. Если хранить порядок в
слайсе ключей, удаление превращается в поиск и сдвиг, `O(n)`, и тест на
200 000 удалений это покажет. Параметры `K comparable` и `V any` переходят
и в тип узла: `omEntry[K, V]` ссылается сам на себя.

**Страж вместо проверок на `nil`.** `root` — фиктивный узел перед первым
элементом. У каждого настоящего узла есть `prev`, и вырезание не
различает «первый или нет». Страж лежит внутри структуры, поэтому её
нельзя копировать после использования: указатели смотрят на `root`
оригинала.

**Живой обход — главная сложность.** Наивный вариант запоминает
`next := nd.next` до `yield`, но тогда удаление следующего ключа внутри
тела цикла не заметно, и удалённый ключ всё равно выдаётся. Брать
`nd.next` после `yield` тоже неверно: если текущий узел удалён, его `next`
устарел. Пример — удалили хвост и дописали новые: у вырезанного хвоста
`next == nil`, и обход закончится раньше. Поэтому удалённый узел не
обнуляет свои ссылки, а итератор отступает по `prev` до ближайшего живого
узла и идёт от него.

**Почему это корректно.** Между живым предком и текущим узлом все узлы
удалены и уже выданы. Значит, `next` живого предка — первый живой узел,
который ещё не выдавали, включая дописанные только что. Каждый живой ключ
выдаётся ровно один раз.

**Что спросят дальше:** как сделать из этого LRU (`MoveToBack` при
чтении, вытеснение с головы), как поддержать обход в обратную сторону и
почему `container/list` для этого неудобен (элементы в `any`, нет
дженериков, а удалённый элемент обнуляет свои ссылки, так что живой обход
на нём не построить).
