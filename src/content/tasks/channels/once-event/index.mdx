Напишите `Event`. Такой примитив нужен, когда много горутин ждут одного
момента: прогрев кэша закончился, конфиг загружен, пора принимать трафик.
Отправка значения в канал разбудит только одного получателя — нужен другой
приём.

Что проверяют скрытые тесты:

- пять горутин ждут в `Wait`; до `Fire` не просыпается никто, после —
  все пять, а `Done()` закрыт и всегда один и тот же;
- десять горутин одновременно зовут `Fire` — никто не паникует;
- отмена контекста возвращает из `Wait` ошибку `context.Canceled`;
- если событие уже наступило, `Wait` с отменённым контекстом возвращает
  `nil` — всегда, а не через раз.

<Reveal>

```go
type Event struct {
	once sync.Once
	done chan struct{}
}

func NewEvent() *Event { return &Event{done: make(chan struct{})} }

func (e *Event) Fire() { e.once.Do(func() { close(e.done) }) }

func (e *Event) Done() <-chan struct{} { return e.done }

func (e *Event) Wait(ctx context.Context) error {
	select {
	case <-e.done:
		return nil
	default:
	}
	select {
	case <-e.done:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}
```

**Закрытие канала — это broadcast.** Чтение из закрытого канала не
блокируется никогда, поэтому `close` будит всех текущих получателей и
пропускает всех будущих. Именно так устроен `ctx.Done()`.

**Второй `close` паникует.** Флаг `fired bool` без синхронизации — гонка
(две горутины увидят `false` и обе закроют). `sync.Once` решает это
одной строкой; вариант с мьютексом и флагом тоже корректен.

**Два `select` подряд — не опечатка.** Если готовы обе ветки — и событие,
и отмена, — `select` выбирает случайно, и `Wait` через раз возвращал бы
`context.Canceled` для давно наступившего события. Неблокирующая проверка
с `default` задаёт приоритет.

**Что спросят дальше:** как сделать событие многоразовым («сбросить» и
ждать снова) — тогда канал придётся заменять новым под мьютексом, и
ожидающий должен брать канал до проверки условия. Это уже `sync.Cond` на
каналах.
