Напишите `Prioritize`. В `select` нет приоритетов: из готовых веток он
выбирает случайно. Строгий приоритет («сначала вычерпать срочные») тоже
плох: под постоянным потоком срочных обычные не обработаются никогда.
Так в планировщиках и брокерах делают взвешенный приоритет — на каждые
`burst` срочных одно обычное, если оно есть.

Что проверяют скрытые тесты:

- в high готово `h0..h9`, в low — `l0 l1 l2`, `burst = 3` → ровно
  `h0 h1 h2 l0 h3 h4 h5 l1 h6 h7 h8 l2 h9`, двадцать раз подряд;
- high открыт, но пуст — значения low (включая пустую строку) приходят
  сразу; после отмены выход закрывается;
- high закрыт с самого начала — low читается до конца, потом выход закрыт;
- отмена, пока значение ждёт отправки, закрывает выход и не оставляет
  горутин.

```go
func Prioritize[T any](ctx context.Context, high, low <-chan T, burst int) <-chan T {
	out := make(chan T)
	go func() {
		defer close(out)
		streak := 0
		for high != nil || low != nil {
			var v T
			got := false
			if streak >= burst && low != nil {
				select {
				case x, ok := <-low:
					if !ok {
						low = nil
						continue
					}
					v, got, streak = x, true, 0
				default:
				}
			}
			if !got && high != nil {
				select {
				case x, ok := <-high:
					if !ok {
						high = nil
						continue
					}
					v, got = x, true
					streak++
				default:
				}
			}
			if !got {
				select {
				case x, ok := <-high:
					if !ok {
						high = nil
						continue
					}
					v = x
					streak++
				case x, ok := <-low:
					if !ok {
						low = nil
						continue
					}
					v, streak = x, 0
				case <-ctx.Done():
					return
				}
			}
			select {
			case out <- v:
			case <-ctx.Done():
				return
			}
		}
	}()
	return out
}
```

**Приоритет в Go — это порядок нескольких `select`.** Неблокирующий
`select` с `default` проверяет один канал, не дожидаясь его; цепочка
таких проверок задаёт порядок. Только когда не готово ничего, нужен
общий блокирующий `select` — и там случайность уже не важна: готово
будет одно.

**Защита от голодания — счётчик серии.** После `burst` значений из high
первым проверяется low. Если в low пусто, ждать его нельзя — это
затормозило бы срочные. Счётчик при этом не сбрасывается, и low
проверяется снова на следующем шаге.

**Закрытый вход — в `nil`.** Закрытый канал всегда готов, и без
обнуления `select` бесконечно выбирал бы его ветку. `nil`-канал не готов
никогда, ветка выключена, а условие цикла `high != nil || low != nil`
закрывает выход, когда кончились оба.

**`continue` после закрытия** — чтобы не отправить наружу нулевое
значение от закрытого канала. Что спросят дальше: как обобщить на N
уровней (веса, как в weighted round-robin) и почему в очередях с
приоритетом всё равно нужен лимит на размер каждой очереди.
