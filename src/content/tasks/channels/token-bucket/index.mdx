Напишите `Bucket`. Token bucket — стандартный ограничитель: разрешает
всплеск до `capacity` запросов, а в среднем — не больше скорости
пополнения. Здесь его ёмкость — буфер канала, а часы приходят снаружи:
в проде это `ticker.C`, а в тестах — обычный канал, который тикает, когда
скажет тест. Так ограничитель тестируется без `time.Sleep` и без
мигающих тестов.

Что проверяют скрытые тесты:

- новое ведро на 3 выдаёт ровно три токена;
- десять тиков в полное ведро — горутина пополнения забирает каждый тик
  без задержки, а токенов по-прежнему два, а не двенадцать; два тика в
  пустое ведро — два токена;
- `Wait` на пустом ведре по дедлайну — `DeadlineExceeded`, а после тика —
  получает токен;
- двадцать горутин на ведро из пяти — ровно пять `Allow` успешны;
- двойной `Stop` возвращается, закрытый `refill` тоже останавливает
  горутину пополнения.

```go
type Bucket struct {
	tokens chan struct{}
	stop   chan struct{}
	done   chan struct{}
	once   sync.Once
}

func NewBucket(capacity int, refill <-chan time.Time) *Bucket {
	b := &Bucket{
		tokens: make(chan struct{}, capacity),
		stop:   make(chan struct{}),
		done:   make(chan struct{}),
	}
	for range capacity {
		b.tokens <- struct{}{}
	}
	go func() {
		defer close(b.done)
		for {
			select {
			case _, ok := <-refill:
				if !ok {
					return
				}
				select {
				case b.tokens <- struct{}{}:
				default:
				}
			case <-b.stop:
				return
			}
		}
	}()
	return b
}

func (b *Bucket) Allow() bool {
	select {
	case <-b.tokens:
		return true
	default:
		return false
	}
}

func (b *Bucket) Wait(ctx context.Context) error {
	select {
	case <-b.tokens:
		return nil
	case <-ctx.Done():
		return ctx.Err()
	}
}

func (b *Bucket) Stop() {
	b.once.Do(func() { close(b.stop) })
	<-b.done
}
```

**Буфер канала — ведро, `len` — число токенов.** Взять токен — прочитать
из канала, положить — отправить. Ограничение ёмкости, ожидание и
потокобезопасность канал даёт сам, и `Wait` с контекстом — это один
`select`.

**Пополнение в полное ведро — неблокирующее.** Обычное
`b.tokens <- struct{}{}` на полном ведре заблокирует горутину пополнения.
С настоящим тикером это незаметно (тикер просто выбросит тики), но
дальше горутина не слышит `stop`, и `Stop` висит вечно. Лишний токен
должен пропасть — в этом и смысл потолка.

**Закрытый канал читается всегда.** Если не проверять `ok`, цикл после
закрытия `refill` крутится на 100% CPU, «пополняя» ведро без остановки.

**Часы снаружи — ради тестов.** Тест сам решает, когда тикнуть, и
проверяет точные числа. Что спросят дальше: почему тикер на каждый
токен плох при высокой скорости (1000 rps — тысяча пробуждений в секунду;
лучше считать токены по прошедшему времени, как `x/time/rate`) и как
сделать лимит на каждого клиента — мапа ведер с вытеснением неактивных.
