Напишите `DelayQueue[T]`. Такая очередь стоит за повторами с backoff
(«повторить через 30 секунд»), напоминаниями, истечением резервов и TTL.
Потребитель ждёт, пока созреет самый ранний элемент, — но пока он ждёт,
может прийти элемент, который созреет раньше.

Что проверяют скрытые тесты:

- элементы с задержками 30, 10, 20 и 20 мс выходят по времени
  готовности, равные — в порядке `Put`;
- элемент с задержкой 50 мс не выдаётся раньше срока;
- `Pop` уже ждёт элемент «через час», и тут кладут элемент «через 10 мс» —
  он приходит вовремя, а не через час;
- три потребителя ждут на пустой очереди, приходят три готовых элемента —
  каждый получает свой;
- `Pop` по дедлайну возвращает `DeadlineExceeded`, а элемент остаётся в
  очереди.

<Reveal>

```go
type DelayQueue[T any] struct {
	mu      sync.Mutex
	items   delayHeap[T] // container/heap по (at, seq)
	seq     uint64
	changed chan struct{}
}

func (q *DelayQueue[T]) Put(v T, delay time.Duration) {
	q.mu.Lock()
	defer q.mu.Unlock()
	q.seq++
	heap.Push(&q.items, delayItem[T]{v: v, at: time.Now().Add(delay), seq: q.seq})
	close(q.changed)
	q.changed = make(chan struct{})
}

func (q *DelayQueue[T]) Pop(ctx context.Context) (T, error) {
	for {
		q.mu.Lock()
		changed := q.changed
		var wait <-chan time.Time
		var timer *time.Timer
		if len(q.items) > 0 {
			d := time.Until(q.items[0].at)
			if d <= 0 {
				it := heap.Pop(&q.items).(delayItem[T])
				q.mu.Unlock()
				return it.v, nil
			}
			timer = time.NewTimer(d)
			wait = timer.C
		}
		q.mu.Unlock()
		select {
		case <-wait:
		case <-changed:
		case <-ctx.Done():
			if timer != nil {
				timer.Stop()
			}
			var zero T
			return zero, ctx.Err()
		}
		if timer != nil {
			timer.Stop()
		}
	}
}
```

**Куча по времени готовности, `seq` — для равных.** Голова кучи — самый
ранний элемент, `Pop` смотрит только на неё. Без `seq` элементы с
одинаковым временем выходили бы в порядке, который зависит от устройства
кучи, а не от порядка добавления.

**Ждать — не `time.Sleep(d)`.** Потребитель, уснувший до головы «через
час», не заметит нового элемента «через 10 мс». Поэтому ожидание — `select`
на таймер головы *и* на сигнал «очередь изменилась», после которого
ожидание пересчитывается.

**Сигнал — закрытием канала, а не отправкой.** Отправка в канал с буфером
на один будит одного потребителя: трое ждут, пришли три элемента, а
проснулся один — двое спят, хотя работа есть. Закрытие будит всех, а
лишние просто пересчитают ожидание и снова уснут. Канал берётся под тем
же замком, под которым смотрели на кучу, — иначе `Put` между «посмотрел»
и «начал ждать» потеряется.

**Пустая очередь — `nil`-таймер.** Если элементов нет, `wait` остаётся
`nil` и ветка выключена: ждём только `Put` или отмену. Что спросят
дальше: как сделать очередь устойчивой к перезапуску (хранить в Redis
sorted set с score = время или в Postgres с `SKIP LOCKED`) и что делать
с тысячами потребителей — будить всех на каждый `Put` дорого, и тогда
заводят одну горутину-диспетчер, которая раздаёт созревшие элементы в
обычный канал.
