Напишите `Watchdog`. Так следят за зависшими потребителями, за
соединениями, по которым давно ничего не приходило (idle timeout), за
долгой задачей, которая должна регулярно отчитываться о прогрессе.

Что проверяют скрытые тесты:

- kick каждые 10 мс при `timeout` 60 мс — двадцать раз подряд сторож
  молчит; kicks прекратились — приходит `ErrIdle`;
- без единого kick — `ErrIdle` через `timeout` от старта;
- закрытые kicks — `nil`, отмена контекста — `context.Canceled`;
- в канале результата ровно одно значение, потом он закрыт;
- если результат никто не читает, горутины сторожа всё равно завершаются.

<Reveal>

```go
func Watchdog(ctx context.Context, timeout time.Duration, kicks <-chan struct{}) <-chan error {
	res := make(chan error, 1)
	go func() {
		defer close(res)
		timer := time.NewTimer(timeout)
		defer timer.Stop()
		for {
			select {
			case _, ok := <-kicks:
				if !ok {
					res <- nil
					return
				}
				timer.Reset(timeout)
			case <-timer.C:
				res <- ErrIdle
				return
			case <-ctx.Done():
				res <- ctx.Err()
				return
			}
		}
	}()
	return res
}
```

**Таймер нужно перезаводить.** `deadline := time.After(timeout)` один раз
перед циклом — это «общий таймаут на всё», а не «таймаут тишины»: сторож
сработает через `timeout` от старта, как бы часто его ни пинали. Первый
тест ловит именно это.

**`Reset` в Go 1.23+ и раньше.** С 1.23 каналы таймеров не буферизованы,
и `Reset` гарантирует, что старое срабатывание не придёт после. В старых
версиях сработавший таймер успевал положить значение в `timer.C`, и перед
`Reset` его надо было вычерпать (`if !timer.Stop() { <-timer.C }`) — на
собеседовании об этом любят спросить. `time.After` на каждой итерации
тоже работает, но плодит по таймеру на каждый kick.

**Буфер на один — чтобы не утечь.** Без буфера `res <- ErrIdle` ждёт
читателя, и если вызывающий уже ушёл (например, по своему контексту),
горутина висит вечно. С буфером она кладёт результат и завершается, а
`close` после значения даёт читателю и значение, и конец.

**Что спросят дальше:** как сделать сторож «с предупреждением» (первый
таймаут — лог, второй — перезапуск) и почему для сетевого соединения
лучше `SetReadDeadline`, чем отдельная горутина со своим таймером.
