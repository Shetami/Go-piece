Напишите `Batch`. Так копят записи для пакетной вставки в базу или
отправки в брокер: не ждать бесконечно, пока наберётся пачка, но и не
слать по одной.

Что проверяют скрытые тесты:

- 7 значений при `size = 3` — пачки `[1 2 3] [4 5 6] [7]`, последняя — при
  закрытии входа;
- если пачка не набралась, она уходит через `maxWait` после **первого**
  элемента пачки, и отсчёт начинается заново со следующей пачки;
- пустые пачки не отправляются ни по таймеру, ни при закрытии.

<Reveal>

```go
var batch []int
var timer <-chan time.Time

for {
	select {
	case v, ok := <-in:
		if !ok {
			flush()
			return
		}
		if len(batch) == 0 {
			timer = time.After(maxWait)
		}
		batch = append(batch, v)
		if len(batch) == size {
			flush()
		}
	case <-timer:
		flush()
	}
}
```

**Таймер от первого элемента, а не тикер.** `time.Ticker` срабатывал бы
по расписанию независимо от данных: пачка, начатая за миллисекунду до тика,
уходила бы почти пустой, а пустые тики пришлось бы фильтровать. Таймер,
заведённый на первом элементе, даёт ровно «не дольше `maxWait` с момента,
как появились данные».

**`nil`-канал выключает ветку.** Пока пачка пуста, `timer == nil`, и
`case <-timer` никогда не сработает. `flush` обнуляет таймер — старый,
если он ещё не сработал, просто забывается (с Go 1.23 такие таймеры
собирает сборщик мусора).

**`batch = nil` после отправки.** Отданный слайс теперь принадлежит
потребителю. Если бы мы переиспользовали его (`batch = batch[:0]`),
следующие `append` писали бы в массив, который потребитель, может быть,
ещё читает.

</Reveal>
