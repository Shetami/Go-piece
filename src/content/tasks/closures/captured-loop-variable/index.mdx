`makeHandlers` собирает три функции и возвращает их. Каждая печатает `i` —
переменную цикла. Вызывают их уже после того, как цикл закончился.

Напишите весь вывод программы.

<Reveal>

```
0 1 2
x = 12
```

**Замыкание захватывает переменную, а не её значение.** Пока функция жива,
жива и переменная — компилятор видит, что она «убегает» из кадра, и размещает
её в куче. Вопрос только в том, **сколько переменных** создаёт цикл.

**До Go 1.22** переменная цикла была одна на весь цикл. Все три замыкания
захватывали её же, и после цикла она равнялась `3`. Вывод был:

```
3 3 3
```

Это была, пожалуй, самая известная ошибка в языке: её ловили линтеры, про неё
писали в каждом гайде, а обходили так:

```go
for i := 0; i < 3; i++ {
	i := i // своя копия на итерацию
	handlers = append(handlers, func() { fmt.Print(i, " ") })
}
```

**Начиная с Go 1.22** переменная создаётся заново на каждой итерации. Каждое
замыкание захватывает свою — и вывод стал `0 1 2`. Костыль `i := i` больше не
нужен, хотя и не мешает.

Поведение привязано к `go`-директиве в `go.mod`: модуль с `go 1.21` соберётся
по старым правилам даже новым компилятором. Так что на собеседовании правильный
ответ — «зависит от версии», и дальше обе.

Вторая часть задачи про то же с другой стороны: `inc` захватывает `x`, и оба
вызова меняют **ту самую** переменную, а не копию. Отсюда `x = 12`.

**Чего здесь нарочно нет.** Горутин. Если бы вместо `handlers` запускались
`go func()`, вывод перестал бы быть предсказуемым: порядок выполнения горутин
не определён, и `0 1 2` могло бы выйти как `2 0 1`. Смена правил в 1.22 чинит
захват, но не делает порядок горутин определённым — это разные вещи, и их
часто путают.

</Reveal>
