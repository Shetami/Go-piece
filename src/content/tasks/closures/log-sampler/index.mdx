Упала база — и каждый запрос пишет в лог одну и ту же ошибку, тысячи строк
в секунду. Логгер тормозит, диск и счёт за хранение логов растут. Сэмплер
пропускает первые `first` одинаковых сообщений за окно, а дальше — только
каждое `thereafter`-е. Так устроен sampling в `zap`.

Напишите `NewSampler`. Ключ — текст сообщения, окно у каждого ключа своё и
начинается с его первого сообщения.

Что проверяют скрытые тесты:

- `first = 2, thereafter = 3`: из 11 сообщений проходят 1, 2, 5, 8, 11;
- `thereafter = 0`: после первых `first` не проходит ничего, и ничего не
  падает;
- у разных ключей свои счётчики и свои окна; сообщение ровно через `tick`
  после начала окна открывает новое;
- 100 горутин с одним ключом при `first = 10`: проходят ровно 10.

<Reveal>

```go
func NewSampler(first, thereafter int, tick time.Duration) (allow func(key string, now time.Time) bool) {
	type window struct {
		start time.Time
		n     int
	}
	var (
		mu sync.Mutex
		ws = make(map[string]*window)
	)
	return func(key string, now time.Time) bool {
		mu.Lock()
		defer mu.Unlock()
		w := ws[key]
		if w == nil || !now.Before(w.start.Add(tick)) {
			w = &window{start: now}
			ws[key] = w
		}
		w.n++
		if w.n <= first {
			return true
		}
		return thereafter > 0 && (w.n-first)%thereafter == 0
	}
}
```

**Мапа в замыкании — это приватный объект.** Мьютекс и окна объявлены в
`NewSampler`, снаружи есть только `allow`. Два сэмплера (для разных
логгеров) не делят ничего. Тип `window` объявлен прямо в функции — он
никому больше не нужен.

**Своё окно у ключа.** Если держать одно общее окно на все ключи, редкая
ошибка, пришедшая в конце окна, попадёт в уже сброшенный счётчик, но
отсчёт её окна начнётся не с неё. Тест с ключом `b` проверяет, что окно
отсчитывается от первого сообщения именно этого ключа.

**Граница окна — полуинтервал.** `!now.Before(start+tick)` означает
`now >= start+tick`. Сообщение ровно в конце окна открывает новое. Условие
`now.After(...)` оставило бы его в старом.

**`% 0` — паника.** «После первых — больше ни одного» — частая настройка, и
наивное `(n-first)%thereafter == 0` роняет сервис при первом же всплеске
ошибок. То есть ровно тогда, когда логи нужнее всего.

**Что спросят дальше:** мапа растёт на каждый уникальный текст — нужна
очистка просроченных окон или ограничение числа ключей (в `zap` это
фиксированная хеш-таблица счётчиков, коллизии допустимы), и как не
потерять информацию: вести счётчик отброшенных сообщений и писать его при
закрытии окна.
