Внешний API отдаёт список постранично: запрос с курсором возвращает
элементы и курсор следующей страницы, пустой `Next` — конец. Вызывающему
коду страницы не интересны, ему нужен просто поток элементов:

```go
for user, err := range All(ctx, client.ListUsers) {
	if err != nil {
		return err
	}
	process(user)
}
```

Напишите `All`. Ошибки идут в том же потоке, парой `(нулевое значение,
ошибка)`, — так устроены итераторы в стиле `iter.Seq2[T, error]`.

Что проверяют скрытые тесты:

- три страницы, средняя из которых пустая, но с `Next`, — все элементы по
  порядку, ровно три запроса;
- `break` на последнем элементе первой страницы — второй страницы никто
  не запрашивал и паники нет;
- один и тот же результат `All` обходят дважды — оба раза все элементы с
  самого начала;
- `Fetch` вернул ошибку на второй странице — сначала элементы первой,
  потом ровно одна ошибка, из которой `errors.Is` достаёт исходную, а в
  тексте есть курсор; больше запросов нет;
- сервер по ошибке снова вернул курсор, по которому уже ходили, —
  элементы, одна ошибка `ErrCursorLoop` и никакого бесконечного цикла;
- контекст отменили посреди обхода — следующий запрос не уходит,
  приходит `context.Canceled`.

<Reveal>

```go
func All[T any](ctx context.Context, fetch Fetch[T]) iter.Seq2[T, error] {
	return func(yield func(T, error) bool) {
		var zero T
		cursor := ""
		seen := make(map[string]bool)
		for {
			if err := ctx.Err(); err != nil {
				yield(zero, err)
				return
			}
			if seen[cursor] {
				yield(zero, fmt.Errorf("%w: %q", ErrCursorLoop, cursor))
				return
			}
			seen[cursor] = true

			page, err := fetch(ctx, cursor)
			if err != nil {
				yield(zero, fmt.Errorf("страница %q: %w", cursor, err))
				return
			}
			for _, it := range page.Items {
				if !yield(it, nil) {
					return
				}
			}
			if page.Next == "" {
				return
			}
			cursor = page.Next
		}
	}
}
```

**Где живёт состояние — главный вопрос задачи про замыкания.** `All`
возвращает функцию, и курсор с множеством `seen` можно объявить в двух
местах: в теле `All` или в теле возвращённой функции. В первом случае их
захватывают *все* обходы результата: второй `range` начнёт с курсора, на
котором кончил первый (то есть с пустого `Next`), и тут же закончится, а
`seen` уже помнит все курсоры. Состояние одного обхода объявляют внутри
функции-итератора — тогда каждый `range` получает свои переменные.

**Ленивость — это `return` сразу после `yield(…) == false`.** Потребитель
сделал `break`, и `yield` вернул `false`: дальше нельзя ни вызывать
`yield` (рантайм запаникует: итерация продолжилась после выхода из тела
цикла), ни запрашивать страницы. Наивное «сначала собрать всё в слайс,
потом отдать» ломает и ленивость, и память на миллионе записей.

**Пустая страница — не конец.** Конец обозначает только пустой `Next`.
Серверы с фильтрацией на своей стороне нередко отдают пустую страницу
посреди выдачи; обход, который на ней останавливается, молча теряет
данные.

**Защита от зацикленного сервера.** Баг на той стороне, и курсор
повторился — без `seen` клиент будет крутиться вечно, долбя API. Множество
просмотренных курсоров стоит копейки по сравнению с одним запросом.

**Ошибка — один раз и с контекстом.** `%w` сохраняет исходную ошибку для
`errors.Is` (`503` можно ретраить, `401` — нет), а курсор в тексте
покажет, на какой странице всё сломалось. После ошибки итератор
заканчивается: продолжать с того же курсора — забота вызывающего, у него
для этого есть ретраи.

**Что спросят дальше.** Как добавить ретраи на временные ошибки внутрь
`All` и не сломать ленивость; как запрашивать следующую страницу заранее,
пока потребитель обрабатывает текущую (фоновая горутина и её остановка
при `break` — тот же `stop`, что у `iter.Pull`); и почему `ctx` не
хранят в структуре клиента, а передают в каждый вызов.
