Классика live-coding: ограничить частоту запросов к внешнему API. Токен-бакет
вмещает `burst` токенов и пополняется со скоростью `rate` токенов в секунду;
каждый запрос забирает один токен, нет токена — отказ. Всё состояние —
сколько токенов и когда пересчитывали — живёт в замыкании.

Время приходит из `now`, чтобы тесты могли его двигать. Таймеров и фоновых
горутин не нужно: токены досчитываются лениво, в момент вызова.

Что проверяют скрытые тесты:

- полный бакет на старте: из пяти вызовов подряд проходят `burst`;
- через секунду при `rate = 1` проходит ровно один, а после часа простоя —
  снова не больше `burst`;
- при `rate = 2` и вызовах каждые 250 мс пропускается каждый второй: доли
  токена копятся между вызовами, даже когда целого токена ещё нет;
- часы ушли назад и вернулись — токенов не прибавилось;
- 100 горутин одновременно при `burst = 10`: проходят ровно 10.

<Reveal>

```go
func NewLimiter(rate float64, burst int, now func() time.Time) (allow func() bool) {
	var (
		mu     sync.Mutex
		tokens = float64(burst)
		last   = now()
	)
	return func() bool {
		mu.Lock()
		defer mu.Unlock()
		t := now()
		if elapsed := t.Sub(last); elapsed > 0 {
			tokens = min(float64(burst), tokens+elapsed.Seconds()*rate)
		}
		if t.After(last) {
			last = t
		}
		if tokens < 1 {
			return false
		}
		tokens--
		return true
	}
}
```

**Ленивое пополнение.** Бакет не тикает сам: при каждом вызове считаем,
сколько прошло с прошлого раза, и добавляем `elapsed × rate`. Это дешевле
любого `time.Ticker` и не требует горутины, которую потом надо
останавливать.

**Главная ловушка — дроби.** Если хранить токены целыми и при этом
сдвигать `last` на каждом вызове, то при частых вызовах каждый раз
набегает `0.5` токена, округляется до нуля — и теряется. Бакет перестаёт
пополняться ровно тогда, когда нагрузка высокая. Решений два: хранить
`float64`, как здесь, или сдвигать `last` только на время, «оплаченное»
целыми токенами.

**Потолок и старт.** `min(burst, …)` — иначе после ночи простоя клиент
получит миллион запросов разом. Изначально бакет полон — так ведёт себя
`golang.org/x/time/rate`, и это то, чего ждут от burst.

**Часы назад.** Настенное время прыгает (NTP, ручная правка). Отрицательный
`elapsed` не должен ни отнимать токены, ни сдвигать `last` назад — иначе
возврат часов в прежнюю точку засчитается как прошедшее время. Поэтому в
Go для интервалов используют монотонные часы: `time.Now()` их содержит, и
`Sub` между двумя `Now()` от прыжков защищён.

**Мьютекс на всё тело.** Прочитать токены, пересчитать, уменьшить —
одна критическая секция. Атомик на счётчике не спасёт: между проверкой и
уменьшением влезет другая горутина. Дальше спросят про лимитер на ключ
(мапа бакетов и вытеснение старых) и про распределённый вариант — тот же
алгоритм в Redis-скрипте.
