Отправка прогресса загрузки в UI, пересчёт метрик по событиям, запись
позиции курсора — нужно не чаще раза в `interval`, при этом первое событие
пропустить сразу, а последнее не потерять. Это throttle с leading и
trailing вызовами. Время сообщают `call` и `tick`, чтобы его можно было
двигать в тестах.

Напишите `NewThrottle` по контракту в заготовке.

Что проверяют скрытые тесты:

- `call(1)`, `call(2)`, `call(3)` подряд → `f(1)` сразу, `f(3)` по `tick`
  через интервал; следующий интервал отсчитывается от этого отложенного
  вызова;
- отложенное значение, которое не успели отправить, а интервал уже
  истёк и пришёл новый `call`, выбрасывается — `f` вызывается один раз,
  с новым значением;
- отложенная пустая строка — тоже значение;
- `f` сама вызывает `call` — без дедлока;
- 50 горутин вызывают `call` одновременно: `f` вызвана один раз сразу и
  ещё один — по `tick`.

```go
func NewThrottle[T any](interval time.Duration, f func(T)) (call func(v T, now time.Time), tick func(now time.Time)) {
	var (
		mu      sync.Mutex
		fired   bool
		last    time.Time
		pending bool
		pval    T
	)
	ready := func(now time.Time) bool {
		return !fired || now.Sub(last) >= interval
	}
	fire := func(now time.Time) {
		fired, last = true, now
		pending = false
		var zero T
		pval = zero
	}
	call = func(v T, now time.Time) {
		mu.Lock()
		if !ready(now) {
			pending, pval = true, v
			mu.Unlock()
			return
		}
		fire(now)
		mu.Unlock()
		f(v)
	}
	tick = func(now time.Time) {
		mu.Lock()
		if !pending || !ready(now) {
			mu.Unlock()
			return
		}
		v := pval
		fire(now)
		mu.Unlock()
		f(v)
	}
	return call, tick
}
```

**Четыре замыкания над одним состоянием.** `call` и `tick` — внешние,
`ready` и `fire` — внутренние помощники, которые избавляют от
дублирования. Все четыре видят одни и те же переменные. Помощники
вызываются только под замком, это договорённость внутри функции.

**`f` — строго после `Unlock`.** `sync.Mutex` в Go нереентерабельный. Если
`f` сама вызовет `call` (запланирует следующую порцию), а мы держим замок,
горутина заблокируется на самой себе навсегда. Поэтому под замком мы
решаем, что делать, и отмечаем вызов (`fire`). Сам `f` вызываем после.
Отметка до вызова важна: вложенный `call` уже видит новый `last` и
правильно откладывается.

**Отложенный вызов — тоже вызов.** Если отсчитывать интервал только от
leading-вызовов, после trailing-вызова в момент 100 мс следующий `call` в
150 мс пройдёт сразу — и получится два вызова за 50 мс.

**Устаревшее значение.** Если интервал истёк, а `tick` так и не пришёл,
новый `call` важнее старого отложенного. Отправить оба — нарушить лимит,
отправить старое — показать пользователю прошлое. `fire` сбрасывает
`pending`, и старое значение просто исчезает.

**Что спросят дальше:** как сделать то же на реальных таймерах
(`time.AfterFunc` на trailing-вызов и его `Stop` при leading-вызове), и
почему здесь флаг `fired`, а не `last.IsZero()` — нулевое время вполне
может прийти от тестовых часов.
