Складской журнал хранит движения: `qty > 0` — приход, `qty < 0` — расход.
Для сверки с инвентаризацией нужен остаток каждого товара на конец
каждого дня с 1 по 5 августа 2024.

- остаток на конец дня = сумма всех движений товара с начала времён
  по этот день включительно;
- нужны все товары из `products` и все пять дней, даже без движений;
- движения после 5 августа не влияют.

Колонки: `sku`, `day` (тип `date`), `balance`.

Порядок: по `sku`, затем по `day`.

Что проверяют скрытые тесты: движения до начала периода, в `23:59` и в
полночь после периода, дни без движений (остаток переносится), товар без
движений вовсе.

<Reveal>

```sql
WITH opening AS (
  SELECT sku, sum(qty) AS qty
  FROM stock_moves
  WHERE moved_at < '2024-08-01'
  GROUP BY sku
),
daily AS (
  SELECT sku, moved_at::date AS day, sum(qty) AS delta
  FROM stock_moves
  WHERE moved_at >= '2024-08-01' AND moved_at < '2024-08-06'
  GROUP BY sku, moved_at::date
),
grid AS (
  SELECT p.sku, d.day::date AS day
  FROM products p
  CROSS JOIN generate_series(date '2024-08-01', date '2024-08-05', interval '1 day') AS d(day)
)
SELECT g.sku, g.day,
       coalesce(o.qty, 0)
         + sum(coalesce(dl.delta, 0)) OVER (PARTITION BY g.sku ORDER BY g.day) AS balance
FROM grid g
LEFT JOIN daily dl  ON dl.sku = g.sku AND dl.day = g.day
LEFT JOIN opening o ON o.sku = g.sku
ORDER BY g.sku, g.day;
```

Ответ:

```
BOLT | 2024-08-01 | 80
BOLT | 2024-08-02 | 80
BOLT | 2024-08-03 | 30
BOLT | 2024-08-04 | 30
BOLT | 2024-08-05 | 30
NUT | 2024-08-01 | 5
NUT | 2024-08-02 | 5
NUT | 2024-08-03 | 5
NUT | 2024-08-04 | 25
NUT | 2024-08-05 | 25
WASHER | 2024-08-01 | 0
WASHER | 2024-08-02 | 0
WASHER | 2024-08-03 | 0
WASHER | 2024-08-04 | 0
WASHER | 2024-08-05 | 0
```

**Остаток — нарастающий итог, но начинается не с нуля.** Всё, что было до
1 августа, сворачивается в `opening` — входящий остаток. Если считать
только движения периода, `BOLT` начнёт 1 августа с −20 вместо 80, а `NUT` —
с нуля вместо 5.

**Дни без движений — через сетку.** Нарастающий итог по одним лишь
движениям даёт строки только в дни, когда что-то происходило. Сетка
`products × generate_series` + `LEFT JOIN` дневных сумм + `coalesce(delta, 0)`
делают так, что остаток «переносится» на пустые дни сам собой: окно
складывает нули.

**Сначала агрегат, потом окно.** В `daily` несколько движений за день
сворачиваются в одну дельту, иначе соединение с сеткой размножило бы
строки. `sum(…) OVER (PARTITION BY sku ORDER BY day)` — рамка по умолчанию
`RANGE UNBOUNDED PRECEDING … CURRENT ROW`, и так как день в разделе
уникален, это ровно «с начала по сегодня».

**Альтернатива без окон** — треугольное соединение: к каждой клетке сетки
все движения `moved_at < day + 1` и `sum`. Короче, но на длинной истории
это O(дни × движения); окно проходит данные один раз.

**Что спросят дальше.** В проде этот запрос не гоняют по всей истории:
хранят ежедневные снимки остатков (или ежемесячные) и досчитывают от
последнего снимка — ровно та же схема «входящий остаток + движения».
