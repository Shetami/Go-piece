Каталог магазина — дерево категорий произвольной глубины. Товар может лежать
в любой категории, не только в листе (универсальный чехол — прямо в
«Телефонах»). Для страницы аналитики нужна выручка **каждой** категории
вместе со всеми её подкатегориями.

- `revenue` — сумма `qty * price` продаж всех товаров поддерева; если продаж
  нет — `0`;
- `products` — сколько товаров лежит в поддереве (проданных и нет);
- в отчёт попадают все категории, даже совсем пустые.

- колонки: `name`, `revenue`, `products`;
- порядок: по `revenue` по убыванию, затем по `name`.

Что проверяют скрытые данные: четыре уровня вложенности, товар в
нелистовой категории, товар без продаж, категорию без товаров, товар с
несколькими продажами.

<Reveal>

```sql
WITH RECURSIVE subtree AS (
  SELECT id AS root_id, id
  FROM categories

  UNION ALL

  SELECT s.root_id, c.id
  FROM subtree s
  JOIN categories c ON c.parent_id = s.id
),
product_revenue AS (
  SELECT p.id, p.category_id, coalesce(sum(s.qty * s.price), 0) AS revenue
  FROM products p
  LEFT JOIN sales s ON s.product_id = p.id
  GROUP BY p.id, p.category_id
)
SELECT c.name,
       coalesce(sum(pr.revenue), 0) AS revenue,
       count(pr.id)                 AS products
FROM categories c
JOIN subtree t               ON t.root_id = c.id
LEFT JOIN product_revenue pr ON pr.category_id = t.id
GROUP BY c.id, c.name
ORDER BY revenue DESC, c.name;
```

Ответ:

```
Электроника | 306500.00 | 6
Телефоны | 226500.00 | 5
Смартфоны | 224000.00 | 3
Складные | 90000.00 | 1
Ноутбуки | 80000.00 | 1
Дом | 7900.00 | 2
Кухня | 7900.00 | 2
Кнопочные | 0 | 1
Текстиль | 0 | 0
```

**Таблица замыкания за один рекурсивный CTE.** Рекурсия стартует не с
одного корня, а со *всех* категорий сразу: пара `(root_id, id)` значит «`id`
лежит в поддереве `root_id`». Каждая категория — в своём поддереве, поэтому
товары нелистовой категории (чехол в «Телефонах») попадают и в неё, и во
всех предков.

**Сначала свернуть продажи, потом соединять.** Если соединить категории,
замыкание, товары и продажи одним махом и считать `count(p.id)`, «Смартфон
A» с двумя продажами посчитается дважды. Предагрегация `product_revenue`
даёт ровно одну строку на товар — и сумма, и количество становятся честными.
Та же беда с двойным счётом возникает и на уровне выручки, если перепутать
порядок соединений.

**Пустые ветки.** «Текстиль» без товаров и «Кнопочные» с непроданным
товаром должны остаться с нулём, а не пропасть и не показать `NULL`. Отсюда
`LEFT JOIN` к товарам и `coalesce` на обоих уровнях. Заготовка теряет и их, и
всю выручку дочерних категорий у родителя.

**Что спросят дальше.** «Каталог меняется редко, а отчёт строят часто — что
сделать?» — хранить замыкание (или `ltree`-путь) в отдельной таблице и
обновлять его триггером при переносе категории, вместо рекурсии на каждый
запрос.
