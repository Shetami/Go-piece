Финансам нужна выручка по дням за период **с 2024-02-26 по 2024-03-03
включительно** — по строке на каждый день периода, даже если продаж не было.

- считаются только `status = 'paid'`;
- день заказа — дата `created_at`;
- `running` — нарастающая выручка с начала периода; заказы до и после
  периода в неё не входят;
- календарь соберите рекурсивным CTE (`generate_series` тоже даст верный
  ответ, но на собеседовании часто просят без него).

- колонки: `day` (дата), `orders`, `revenue` (0, если продаж не было),
  `running`;
- порядок: по `day`.

Что проверяют скрытые данные: 29 февраля, заказы в `23:59:59` и в
`00:00:00` на границах периода, дни без продаж подряд, отменённый заказ.

<Reveal>

```sql
WITH RECURSIVE calendar AS (
  SELECT date '2024-02-26' AS day
  UNION ALL
  SELECT (day + 1)::date
  FROM calendar
  WHERE day < date '2024-03-03'
),
daily AS (
  SELECT created_at::date AS day, count(*) AS orders, sum(amount) AS revenue
  FROM orders
  WHERE status = 'paid'
    AND created_at >= date '2024-02-26'
    AND created_at <  date '2024-03-04'
  GROUP BY created_at::date
)
SELECT c.day,
       coalesce(d.orders, 0)  AS orders,
       coalesce(d.revenue, 0) AS revenue,
       sum(coalesce(d.revenue, 0)) OVER (ORDER BY c.day) AS running
FROM calendar c
LEFT JOIN daily d ON d.day = c.day
ORDER BY c.day;
```

Ответ:

```
2024-02-26 | 2 | 350.00 | 350.00
2024-02-27 | 0 | 0 | 350.00
2024-02-28 | 0 | 0 | 350.00
2024-02-29 | 2 | 500.00 | 850.00
2024-03-01 | 1 | 50.00 | 900.00
2024-03-02 | 0 | 0 | 900.00
2024-03-03 | 1 | 300.00 | 1200.00
```

**Дни без продаж берутся из календаря, а не из данных.** Группировка по
`orders` просто не знает о 27, 28 февраля и 2 марта. Рекурсивный CTE
генерирует даты шаг за шагом, пока не дойдёт до конца периода; `date + 1`
сам знает про високосный год, и 29 февраля появляется без подсказок.

**`BETWEEN '2024-02-26' AND '2024-03-03'` теряет последний день.** Строка
превращается в `2024-03-03 00:00:00`, и заказ в `23:59:59` за бортом.
Полуоткрытый интервал `>= начало AND < следующий день` не зависит от
точности времени и дружит с индексом по `created_at` — в отличие от
`created_at::date BETWEEN …`.

**Сначала свернуть, потом присоединить.** Предагрегат `daily` — одна строка
на день. Если сделать `LEFT JOIN orders` к календарю и поставить `status =
'paid'` в `WHERE`, пустые дни исчезнут снова: у них `status` — `NULL`.

**Нарастающий итог — по календарю.** Окно идёт по уже дополненным дням,
поэтому в «пустые» дни `running` не пропадает, а стоит на месте. Заказ 25
февраля в `23:59:59` в итог не попадает: он отсечён ещё до окна. Спросят
дальше: «а в часовом поясе клиента?» — `created_at AT TIME ZONE …` до
приведения к дате, и граница суток сдвигается.
