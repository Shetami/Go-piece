Маркетинг хочет дослать кампанию `7` тем, кто её ещё не получил. В `sends`
лежат все отправки всех кампаний. Если подписчика удалили по запросу,
строку об отправке оставляют для статистики, но `subscriber_id` в ней
обнуляют.

Найдите активных подписчиков (`unsubscribed_at` пуст), которым кампанию `7`
ещё ни разу не отправляли.

- колонка: `email`;
- порядок: по `email`.

Что проверяют скрытые данные: отправки других кампаний, повторную отправку
одному и тому же человеку, отписавшихся и строки отправок без получателя.

<Reveal>

```sql
SELECT s.email
FROM subscribers s
WHERE s.unsubscribed_at IS NULL
  AND NOT EXISTS (
    SELECT 1
    FROM sends x
    WHERE x.campaign_id = 7
      AND x.subscriber_id = s.id
  )
ORDER BY s.email;
```

Ответ:

```
boris@example.com
dina@example.com
egor@example.com
```

**`NOT IN` + `NULL` = пустой ответ.** `id NOT IN (1, NULL, 3)` раскрывается в
`id <> 1 AND id <> NULL AND id <> 3`. Среднее слагаемое — `UNKNOWN`, и всё
выражение не бывает истинным ни для одной строки. Запрос из заготовки не
падает и не ругается — он просто возвращает ноль строк, и рассылка «уже всем
ушла».

**`NOT EXISTS` к `NULL` равнодушен.** Для каждого подписчика он спрашивает
«есть ли строка отправки с моим id» — строка с пустым `subscriber_id` не
совпадёт ни с кем и ничего не испортит. Если очень хочется `NOT IN`, в
подзапрос обязательно добавляют `AND subscriber_id IS NOT NULL`, но об этом
легко забыть при следующей правке.

**Фильтр по кампании — внутри подзапроса.** Боря и Дина получали кампанию `5`
— это не повод исключать их из досылки `7`. А повторная отправка Вере ничего
не ломает: `EXISTS` останавливается на первом совпадении и дублей не
порождает, в отличие от `LEFT JOIN … WHERE x.id IS NULL` с неаккуратным
условием соединения.

**Что спросят дальше.** «Какой индекс нужен?» — составной
`sends (campaign_id, subscriber_id)`: планировщик превратит `NOT EXISTS` в
hash anti join или в проход по индексу.

</Reveal>
