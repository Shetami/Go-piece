short: Горутина, ждущая канал, которого никто не тронет. Не падает и не пишет в лог — просто остаётся в памяти до конца программы.
aliases: [goroutine leak, утечка горутин]
category: состояние
related: [deadlock, channel, chan-buffer, gopark]
source: runtime/proc.go — checkdead видит только полную блокировку
---

[Deadlock](/glossary/deadlock/) рантайм обнаруживает: если спят **все** горутины, `checkdead` роняет программу. Но если спят не все — а на сервере всегда работает хоть кто-то, — забытая горутина просто висит. Ни паники, ни ошибки, ни всплеска нагрузки: только память, которая не вернётся.

Классический пример — отменённый запрос:

```go
func search(ctx context.Context) (Result, error) {
    ch := make(chan Result)          // небуферизованный!
    go func() { ch <- doWork() }()   // некому забрать, если мы ушли по таймауту
    select {
    case r := <-ch:
        return r, nil
    case <-ctx.Done():
        return Result{}, ctx.Err()   // горутина остаётся в chan send навсегда
    }
}
```

Лечится одним символом — `make(chan Result, 1)`: отправка завершится даже без получателя, значение полежит в буфере и уедет вместе с каналом к сборщику.

Общее правило: **у каждой отправки должен быть гарантированный получатель**. Отсюда буфер ровно на число ожидаемых результатов, `context` с отменой и принцип «кто запустил горутину, тот отвечает за её завершение».

Как увидеть:

- `runtime.NumGoroutine()` в метриках. График, который только растёт, — это она.
- `/debug/pprof/goroutine?debug=1` — стеки всех горутин с причиной ожидания: `chan send`, `chan receive`, `select`. Сразу видно и сколько их, и откуда они.
- `go test -race` тут не поможет: утечка — не гонка. Зато помогает `goleak` от Uber, который проверяет в конце теста, что лишних горутин не осталось.
