Правило Java-клиента, на которое равняются остальные:

```
partition = toPositive(murmur2(keyBytes)) % numPartitions
```

**С ключом** одно и то же значение ключа всегда попадает в одну партицию — а значит, сообщения одного пользователя, заказа, счёта читаются строго по порядку и одним потребителем группы. Ради этого ключ обычно и задают.

**Без ключа** — липкий партиционер (KIP-480, с Kafka 3.3 — адаптивный, KIP-794): все сообщения идут в одну партицию, пока её пакет не уйдёт, потом переключаются на другую. Так пакеты крупнее, чем при раскладке по кругу.

Три практических следствия:

- **Горячий ключ — горячая партиция.** 60% трафика от одного клиента означает 60% нагрузки на одну партицию и на одного потребителя в группе. Лишние потребители не помогут.
- **Число партиций — часть функции.** Добавили партиции — ключи переехали, порядок на стыке нарушен.
- **Разные клиенты — разные хеши.** В Go это ловушка: `sarama` по умолчанию хеширует FNV-1a, `confluent-kafka-go` (librdkafka) — CRC32 (`partitioner=consistent_random`), а `segmentio/kafka-go` по умолчанию вообще раскладывает по кругу, не глядя на ключ. С Java совместим `franz-go`. Если в топик пишут сервисы на разных языках, партиционер надо выровнять явно: в kafka-go — `kafka.Murmur2Balancer`, в librdkafka — `partitioner=murmur2_random`, в sarama — свой murmur2 через `NewCustomHashPartitioner`.
