Подготовленный запрос (`PREPARE`, или протокол расширенных запросов, которым пользуется pgx) разбирается один раз и выполняется много раз с разными параметрами. Первые пять выполнений PostgreSQL строит **частный план** под конкретные значения. Потом строит **общий план**, не глядя на значения, и если по оценке он не сильно дороже среднего частного — дальше использует его всегда.

Для равномерных данных это экономит время планирования. Для неравномерных — ловушка. `WHERE status = $1`: `'done'` — 95% строк, нужен полный просмотр; `'pending'` — 0,1%, нужен индекс. Общий план один на всех и для какого-то из значений будет плохим.

pgx по умолчанию (`QueryExecModeCacheStatement`) готовит и кэширует каждый запрос на соединении — поэтому запрос может быть быстрым в `psql` и медленным из приложения.

Что делать:

- `plan_cache_mode = force_custom_plan` — для роли или для сессии, где такие запросы;
- `EXPLAIN (ANALYZE) EXECUTE ...` после шести выполнений `PREPARE`, чтобы увидеть общий план;
- для редких значений — частичный индекс или отдельный запрос с литералом.
