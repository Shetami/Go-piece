Чаще всего используется **корзина токенов**: токены накапливаются с постоянной скоростью до некоторого запаса, каждый запрос забирает один, а если корзина пуста — отказ. Скорость задаёт средний поток, запас — допустимый всплеск. В Go это `golang.org/x/time/rate`:

```go
lim := rate.NewLimiter(rate.Limit(200), 50) // 200 запросов в секунду, всплеск до 50

func handler(w http.ResponseWriter, r *http.Request) {
    if !lim.Allow() {
        w.Header().Set("Retry-After", "1")
        http.Error(w, "too many requests", http.StatusTooManyRequests)
        return
    }
    …
}
```

Чем отличается от [сброса нагрузки](/glossary/load-shedding/): ограничитель решает заранее и по правилу («не больше стольких в секунду»), а сброс — по факту перегрузки («очередь полна, отказываю»). В жизни используют оба: первое — против всплесков и слишком активных клиентов, второе — против перегрузки как таковой.

Практические детали:

- **лимит на клиента, а не только общий**: иначе один клиент выберет всю квоту;
- **ограничитель распределённый**, если реплик много: считать в Redis или делить квоту между репликами;
- **отказывать дёшево**: проверка лимита должна быть до тяжёлой работы, в идеале на границе (API-шлюз, прокси);
- **говорить клиенту правду**: 429 и `Retry-After`, чтобы он знал, когда повторять;
- **разные лимиты для разного**: запись обычно дороже чтения, а фоновые задачи должны уступать живым пользователям.
