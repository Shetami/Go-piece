`selectgo` работает в три прохода.

1. **Опрос.** Обойти все case в случайном порядке и проверить, кто готов прямо сейчас. Нашёлся готовый — выполнить его и выйти. Не нашёлся, но есть `default` — уйти в него.
2. **Постановка в очередь.** Завести по [sudog](/glossary/sudog/) на каждый case и положить их в `sendq`/`recvq` соответствующих каналов. Потом [gopark](/glossary/gopark/) — один раз, не по разу на канал.
3. **Пробуждение.** Кто-то выполнил встречную операцию на одном из каналов. Рантайм снимает горутину со всех остальных очередей и сообщает, какой case сработал.

Отсюда всё практически важное:

- **Ожидание бесплатно.** select на десяти каналах стоит столько же, сколько ожидание одного: десять постановок в очередь и один сон. Никакого опроса и ноль процессорного времени.
- **Выбор случаен.** Если готовы несколько case, выбирается случайный — это требование спецификации, а не деталь реализации. Иначе первый case в тексте программы навсегда заглушил бы остальные.
- **Порядок в исходнике ничего не значит.** Приоритета у case нет. Если он нужен, его делают руками: вложенный select с `default`.
- **`default` превращает ожидание в попытку.** «Забери, если есть», «отправь, если влезет». Но `for { select { … default: } }` без паузы — это активное ожидание, которое жжёт ядро целиком.
- **nil-канал выключает case.** См. [nil-канал](/glossary/nil-channel/).

Блокировки всех каналов select берёт в порядке их адресов (`lockorder`) — иначе два select-а на одних и тех же каналах могли бы заблокировать друг друга.

Пустой `select {}` без case блокируется навсегда и в одиночной программе даёт `deadlock`.
