Баланс 100. T1 читает 100 и хочет прибавить 50. T2 читает 100 и хочет прибавить 30. T1 пишет 150, T2 пишет 130. Одно пополнение пропало, ошибок нет.

Это самая частая аномалия в реальном коде, потому что шаблон «прочитать в приложении — посчитать — записать» встречается повсюду. Способы защиты:

1. **Считать в базе**: `UPDATE accounts SET balance = balance + 30 WHERE id = $1`. Второй UPDATE дождётся первого и [перепроверит](/glossary/eval-plan-qual/) свежую версию. Лучший вариант, если логика укладывается в SQL.
2. **Блокировать при чтении**: `SELECT … FOR UPDATE`. Вторая транзакция будет ждать уже на чтении и прочитает свежее значение. Цена — ожидание.
3. **Проверять версию** (оптимистичная блокировка): `UPDATE … SET balance = $new, version = version + 1 WHERE id = $1 AND version = $read`. Если затронуто 0 строк — кто-то успел раньше, повторить.
4. **REPEATABLE READ или SERIALIZABLE**: вторая транзакция получит [ошибку сериализации](/glossary/serialization-failure/) вместо тихой потери. Приложение должно повторить.

Чего делать не нужно — полагаться на то, что «у нас мало параллельных запросов». Двойной клик по кнопке — это уже два параллельных запроса.
