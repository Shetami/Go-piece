Обычный `SELECT ... FOR UPDATE` на занятой строке ждёт, пока её отпустят. Десять воркеров, которые берут «первую свободную задачу», выстраиваются в очередь к одной и той же строке. `SKIP LOCKED` меняет поведение: занятые строки просто пропускаются, и каждый воркер получает свою задачу.

```sql
BEGIN;
SELECT id, payload FROM jobs
WHERE status = 'pending' AND run_at <= now()
ORDER BY id
LIMIT 10
FOR UPDATE SKIP LOCKED;
-- обработать, затем
UPDATE jobs SET status = 'done' WHERE id = ANY($1);
COMMIT;
```

Если воркер упал, транзакция откатится, блокировки снимутся, и задачи достанутся другим. Главное преимущество перед отдельным брокером — задача ставится в той же транзакции, что и бизнес-данные: нет проблемы двойной записи.

Пределы:

- **тысячи задач в секунду** — нормально; десятки тысяч требуют аккуратности, дальше лучше брокер;
- **мёртвые строки** — каждая обработанная задача оставляет мёртвые версии, таблице очереди нужен агрессивный автовакуум, а выполненные задачи стоит удалять или секционировать;
- **долгая обработка внутри транзакции** держит соединение и горизонт очистки. Долгие задачи лучше помечать как «взята до такого-то времени» и коммитить сразу, а не держать транзакцию.
