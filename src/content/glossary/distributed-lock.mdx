Простейшая блокировка на Redis:

```go
token := uuid.NewString()
ok, err := rdb.SetNX(ctx, "lock:report", token, 10*time.Second).Result()
// ok == false — блокировку держит кто-то другой
```

`NX` — только если ключа нет, TTL — чтобы упавший владелец не держал её вечно. Освобождать — Lua-скриптом «удалить, если значение всё ещё мой токен». Простой `DEL` снимет чужую блокировку, если своя уже истекла.

Главная проблема — **TTL**. Владелец может заснуть дольше срока аренды: пауза GC, своп, остановленная виртуальная машина, повисший сетевой вызов. Блокировка истекает, её берёт другой, а первый просыпается и продолжает работать, уверенный, что она его. Проверка «ещё моя?» перед записью не помогает — пауза может случиться сразу после неё.

Лечится только на стороне защищаемого ресурса: вместе с блокировкой выдаётся монотонно растущий **токен ограждения** (fencing token), каждая запись несёт его, и хранилище отвергает запись со старым токеном. Сам Redis такой токен не даёт; его можно вести счётчиком (`INCR`) или взять ревизию из etcd/ZooKeeper.

Есть и вторая проблема: репликация Redis асинхронная. Если ведущий упал сразу после `SET NX`, новый ведущий может блокировки не знать. Redlock (большинство из N независимых Redis) закрывает это, но не проблему пауз.

Практическое правило: блокировка в Redis хороша **для эффективности** — чтобы два воркера не делали одну и ту же дорогую работу. Если двойное выполнение портит данные, нужна [идемпотентность](/glossary/idempotency-key/), ограничение в базе или токен ограждения.
