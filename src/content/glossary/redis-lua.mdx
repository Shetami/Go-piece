Одна команда Redis атомарна. Когда нужно несколько — есть три инструмента.

**MULTI/EXEC.** Команды ставятся в очередь и при `EXEC` выполняются подряд, ничего не вклинивается. Но это не транзакция в смысле SQL: **отката нет**. Если команда упала при исполнении (например, `INCR` по строке `"abc"`), остальные всё равно применятся. И внутри нельзя прочитать значение и решить, что делать дальше: ответы придут только после `EXEC`.

**WATCH.** Оптимистичная блокировка: `WATCH key`, прочитать, посчитать, `MULTI … EXEC`. Если кто-то изменил `key` после `WATCH`, `EXEC` вернёт nil — нужно повторить. В go-redis — `rdb.Watch(ctx, fn, keys...)` и `redis.TxFailedErr`.

**Lua.** Скрипт исполняется на сервере целиком, как одна команда: читать, ветвиться и писать можно атомарно и за один круг по сети.

```go
var release = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
end
return 0`)

release.Run(ctx, rdb, []string{"lock:report"}, token)
```

`Run` сначала пробует `EVALSHA` по хэшу и отправляет текст скрипта только если сервер его ещё не знает.

Скрипт занимает единственный поток Redis, пока работает. Долгий скрипт — такая же проблема, как `KEYS *`: после порога (`busy-reply-threshold`, 5 секунд) остальные клиенты получают `BUSY`, а убить скрипт, который уже что-то записал, можно только остановкой сервера. Все ключи скрипт должен получать в `KEYS`, а не собирать сам, — иначе он не будет работать в кластере.
