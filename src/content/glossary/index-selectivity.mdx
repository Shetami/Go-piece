`WHERE id = 42` отбирает одну строку из миллиона — селективность 0,0001%, индекс незаменим. `WHERE status = 'active'`, когда активны 70% строк, — индекс только мешает: чтобы достать 700 тысяч строк по одной, пришлось бы прыгать по страницам таблицы вразнобой, а читать её подряд намного дешевле.

Планировщик не знает селективность точно — он её оценивает по статистике, которую собирает `ANALYZE` (и автовакуум): доля NULL, число различных значений, самые частые значения и гистограмма распределения. Видно её в `pg_stats`.

Отсюда типичные проблемы:

- **Устаревшая статистика.** Таблицу только что залили, `ANALYZE` не прошёл — планировщик думает, что строк десять, и выбирает вложенные циклы.
- **Коррелированные колонки.** `city = 'Москва' AND region = 'Москва'` — планировщик перемножит вероятности, будто колонки независимы, и ошибётся в разы. Лечится `CREATE STATISTICS`.
- **Перекос.** Одно значение встречается в 90% строк, остальные редки. Для редких индекс хорош, для частого — нет, и параметризованный запрос может получить план, неудачный для половины значений.

Проверять оценки — в [EXPLAIN ANALYZE](/glossary/explain/): расхождение `rows` (оценка) и `actual rows` в десятки раз почти всегда объясняет плохой план.
