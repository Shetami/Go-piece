Проблема, которую он решает, называется **двойной записью**: сервис сначала пишет в свою базу, а потом отправляет событие в брокер. Это два разных хранилища и две разные операции, общей транзакции у них нет. Упал процесс между ними, недоступен брокер — данные есть, события нет. Поменять порядок не помогает: тогда бывает событие о том, чего не случилось.

Outbox устроен просто:

```sql
BEGIN;
INSERT INTO orders (id, user_id, total) VALUES (…);
INSERT INTO outbox (aggregate_id, type, payload) VALUES (…);
COMMIT;
```

Обе строки попадают в базу вместе. Дальше отдельный процесс (relay) читает неотправленные строки и публикует их в брокер:

```sql
SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED;
```

`SKIP LOCKED` позволяет запускать несколько отправщиков. Альтернатива опросу — читать журнал базы: Debezium подписывается на WAL PostgreSQL ([логическая репликация](/glossary/logical-replication/)) и публикует изменения сам.

Что нужно помнить:

- **доставка получается «хотя бы один раз»**: между публикацией и отметкой `sent_at` сервис может упасть, и строка уедет ещё раз. Значит, потребителю нужен [ключ идемпотентности](/glossary/idempotency-key/);
- **появляется задержка**: событие ждёт отправщика. Частый опрос уменьшает её, но нагружает базу;
- **таблицу надо чистить**, иначе она станет самой большой в базе;
- **порядок сохраняется только в пределах ключа** — если он важен, публикуйте с ключом партиции.
