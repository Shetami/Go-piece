Отдельной таблицы блокировок строк в PostgreSQL нет — иначе UPDATE миллиона строк потребовал бы миллион записей в памяти. Блокировка записана в самой строке: в [xmax](/glossary/xmin-xmax/) лежит номер транзакции, которая её держит.

Второй писатель находит строку, видит в xmax идущую транзакцию и ждёт **её конца** — не строки, а всей транзакции, через блокировку на её xid. Когда та закончится:

- откатилась — строка свободна, можно менять;
- закоммитилась — на READ COMMITTED UPDATE [перепроверяет](/glossary/eval-plan-qual/) свежую версию, на REPEATABLE READ получает [ошибку сериализации](/glossary/serialization-failure/).

Читатели в этой очереди не стоят никогда: обычный SELECT читает версию по своему снимку.

`SELECT … FOR UPDATE` берёт ту же блокировку без изменения. Варианты:

- `FOR NO KEY UPDATE` — слабее, не мешает вставке ссылающихся строк по внешнему ключу; UPDATE неключевых колонок берёт именно её.
- `FOR SHARE` — разделяемая: несколько транзакций могут держать её вместе, но никто не может изменить строку.
- `NOWAIT` — ошибка вместо ожидания; `SKIP LOCKED` — пропустить занятые строки. С `SKIP LOCKED` из таблицы получается очередь задач: каждый обработчик берёт свою строку, не мешая другим.
