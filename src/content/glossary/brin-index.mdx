Журнал событий пишется по времени: вчерашние строки лежат в начале таблицы, сегодняшние — в конце. Значит, для каждого куска таблицы (по умолчанию 128 страниц, 1 МБ) можно запомнить только минимальное и максимальное время — и запрос за сегодня прочитает только куски, чей диапазон пересекается с сегодняшним.

```sql
CREATE INDEX events_created_brin ON events USING brin (created_at);
```

B-дерево на миллиард строк занимает десятки гигабайт, BRIN — мегабайты. Вставка почти бесплатна.

Условие одно, но жёсткое: **физический порядок строк должен соответствовать значениям** (корреляция близка к 1 — видно в `pg_stats.correlation`). Если строки перемешаны — UPDATE переносят версии в другие страницы, данные грузились вразнобой, — у каждого куска диапазон будет «от начала времён до сегодня», и индекс не отсеет ничего.

BRIN не находит отдельную строку — он отсеивает куски, а внутри кусков идёт полное чтение (Bitmap Heap Scan с перепроверкой). Для «найди заказ по id» он не годится; для «сумма за вчера по таблице в два терабайта» — идеален.
