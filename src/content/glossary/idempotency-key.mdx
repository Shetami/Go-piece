Брокеры и сети дают доставку [хотя бы один раз](/glossary/delivery-semantics/): повтор возможен всегда. Значит, обработчик должен давать одинаковый результат и на первую доставку, и на десятую. Самый надёжный способ — уникальная строка в той же базе, куда пишется результат:

```go
tx, _ := db.BeginTx(ctx, nil)
defer tx.Rollback()

// Ключ и эффект операции пишутся в одной транзакции.
res, err := tx.ExecContext(ctx,
    `INSERT INTO processed_events (key) VALUES ($1) ON CONFLICT DO NOTHING`, event.Key)
if n, _ := res.RowsAffected(); n == 0 {
    return nil // это повтор: работу уже делали
}
if _, err := tx.ExecContext(ctx, `UPDATE accounts SET balance = balance - $1 WHERE id = $2`, …); err != nil {
    return err
}
return tx.Commit()
```

Важные детали:

- **проверить и потом сделать — не одно и то же.** Если сначала посмотреть «нет ли ключа», а потом работать, два одновременных дубля пройдут оба. Ключ должен захватываться записью с уникальным индексом;
- **эффект и ключ — в одной транзакции.** Иначе можно записать ключ и упасть до работы;
- **ключ приходит снаружи.** Его задаёт отправитель: `Idempotency-Key` в HTTP, идентификатор сообщения в брокере, id операции в запросе;
- **хранить не вечно**: обычно дни или недели, дальше чистить;
- **естественная идемпотентность лучше**. `UPDATE … SET status='paid'` можно повторять без ключей, а `balance = balance - 100` — нельзя.
