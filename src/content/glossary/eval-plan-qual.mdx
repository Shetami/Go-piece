UPDATE нашёл строку по своему снимку, но её держит другая транзакция. Он ждёт. Та закоммитила — теперь есть более новая версия, которую снимок оператора не видит.

На READ COMMITTED PostgreSQL не отказывается, а идёт по цепочке версий к последней, проверяет на ней условие `WHERE` и, если оно всё ещё верно, выполняет изменение над ней. Для `SET balance = balance + 30` это значит: прибавка ляжет поверх чужого изменения, ничего не потеряется.

Две тонкости:

- **Оператор видит базу «наполовину по новому».** Остальные строки — по снимку начала оператора, а эту — по свежей версии. Для сложных запросов с соединениями это может дать странные результаты.
- **Не спасает значения, посчитанные в приложении.** `SET balance = 130`, где 130 = прочитанные ранее 100 + 30, запишется как есть и затрёт чужое изменение. Перепроверяется условие, а не происхождение числа.

На REPEATABLE READ и SERIALIZABLE перепроверки нет: там это [ошибка сериализации](/glossary/serialization-failure/).
