Если нагрузка выше ёмкости, кто-то всё равно не получит ответа. Вопрос только в том, как:

- **без предела очереди** все ждут всё дольше, пока не начнут уходить по таймауту. Сервис при этом обрабатывает запросы, которых уже никто не ждёт;
- **с пределом** лишние сразу получают 503. Остальные обслуживаются с нормальной задержкой, и клиент может сразу пойти на другую реплику.

Длину очереди выбирают из допустимого ожидания: по [закону Литтла](/glossary/littles-law/) очередь в N запросов при ёмкости μ — это N/μ ожидания. Если клиенты ждут 1 секунду, а сервис делает 200 запросов в секунду, очередь длиннее 200 бессмысленна.

В Go простейший вариант — семафор на канале:

```go
select {
case sem <- struct{}{}:
    defer func() { <-sem }()
    handle(w, r)
default:
    http.Error(w, "overloaded", http.StatusServiceUnavailable)
}
```

Более тонкие варианты сбрасывают сначала менее важное (фоновые задачи, повторы, запросы без авторизации) или решают по времени ожидания, а не по длине очереди, как CoDel.
