PromQL — язык запросов Prometheus. Его же, с небольшими расширениями, понимают VictoriaMetrics, Mimir, Thanos и Grafana. На нём пишут дашборды, алерты и разбирают инциденты, и почти каждая ошибка в нём выглядит правдоподобно: график рисуется, число есть — но это не то число. Эта лекция — о том, что именно считает каждая конструкция и где она обманывает.

## Что возвращает запрос

Запрос из одного имени метрики возвращает **мгновенный вектор** — по одной точке, последнему значению, для каждого подходящего ряда:

```
http_requests_total{job="api", status=~"5.."}
```

Фигурные скобки — фильтры по меткам: `=` и `!=` — точное совпадение, `=~` и `!~` — регулярное выражение. Регулярка всегда привязана к началу и концу строки: `status=~"5.."` совпадёт с `503`, но не с `1503`.

Добавьте в конец окно — и получится **диапазонный вектор**: для каждого ряда все точки за последние 5 минут.

```
http_requests_total{job="api"}[5m]
```

Нарисовать диапазонный вектор нельзя — это набор точек, а не одна. Его обязательно превращают обратно в мгновенный функцией, которая что-то считает по окну: `rate`, `increase`, `max_over_time`, `avg_over_time`.

Когда Grafana рисует график за сутки, она выполняет запрос не один раз, а в каждой точке графика с шагом `step` (например, раз в минуту). Каждая точка графика — это отдельный мгновенный запрос «как если бы сейчас было 14:37». Это важно понимать, когда окно и шаг не согласованы.

## rate: скорость счётчика

<RateWindow />

Значение счётчика само по себе ничего не говорит. Вопрос «сколько запросов в секунду» — это <Term id="promql-rate">rate</Term>:

```
rate(http_requests_total{job="api"}[5m])
```

`rate` берёт точки за окно, находит рост с учётом сбросов (падение значения — это перезапуск пода, и рост после него прибавляется) и делит на длительность окна. Получается **средняя** скорость в секунду за последние 5 минут.

Рядом живут ещё две функции:

- **`increase(x[1h])`** — рост за окно, а не скорость: `rate × длительность окна`. «Сколько ошибок за последний час».
- **`irate(x[5m])`** — скорость по **двум последним** точкам окна. Реагирует мгновенно, но дёргается, и на графике за сутки с шагом в минуту показывает случайную выборку из пиков. Годится для оперативного графика за последние минуты и не годится для алертов.

Точки собираются раз в 15 секунд, и первая точка окна почти никогда не лежит ровно на его начале, а последняя — на конце. Prometheus считает рост между первой и последней точкой и растягивает его на всё окно, предполагая, что скорость была той же. Отсюда дробные значения у целочисленного счётчика.

Это нормально и не мешает графикам и алертам. Но из этого следует важное: `increase` и `rate` — оценки, а не учёт. Если нужно точное число событий — например, платежей — его берут из базы, а не из Prometheus.
</Predict>

### Каким делать окно

У окна две крайности.

**Слишком короткое** — пустота. Для скорости нужны минимум две точки в окне. При сборе раз в 15 секунд окно `[15s]` чаще всего содержит одну точку, и `rate` возвращает пустой результат — на графике дыры. Один пропущенный сбор — и `[30s]` тоже пусто. Правило: окно не меньше **четырёх интервалов сбора**, при 15 секундах — `[1m]`, надёжнее `[2m]`.

**Слишком длинное** — сглаживание. `rate(x[1h])` покажет всплеск ошибок, который длился 5 минут, как невысокий горб, растянутый на час. Для алертов это задержка срабатывания, для графиков — потеря деталей.

В Grafana вместо ручного окна используют переменную `$__rate_interval`: она учитывает и интервал сбора, и шаг графика, так что окно никогда не становится меньше шага и точки не проскакивают. Жёстко прописанное `[1m]` на графике за неделю с шагом 10 минут берёт по одной минуте из каждых десяти — 90% данных просто не участвуют.

## Агрегация: sum после rate

У `api` тридцать подов, и `rate(http_requests_total[5m])` возвращает скорость по каждому ряду каждого пода. Для дашборда нужно одно число или разбивка по маршрутам:

```
sum(rate(http_requests_total{job="api"}[5m]))                     # всего
sum by (route) (rate(http_requests_total{job="api"}[5m]))         # по маршрутам
sum without (pod, instance) (rate(http_requests_total[5m]))       # всё, кроме подов
```

`by` оставляет только перечисленные метки, `without` — все, кроме перечисленных. Кроме `sum` есть `avg`, `min`, `max`, `count`, `topk`, `bottomk`, `quantile`.

После перезапуска счётчик пода начинается с нуля, и сумма падает — скажем, с 5 000 000 до 4 830 000. `rate` видит уменьшение и, как любое уменьшение счётчика, считает его сбросом: «счётчик обнулился и снова вырос до 4 830 000». Этот рост попадает в скорость — на графике появляется пик в тысячи раз выше настоящего трафика. На алерте по такой метрике дежурного будят ни за что.

Правильный порядок — **сначала `rate` по каждому ряду, потом `sum`**: `sum(rate(http_requests_total[5m]))`. Сброс одного пода обрабатывается в его собственном ряду, а сумма скоростей корректна. То же для `increase` и для гистограмм: сначала `rate` бакетов, потом `sum by (le)`.

### Ещё несколько правил

- **`rate` — только для счётчиков.** Для gauge, который может уменьшаться (размер очереди, память), `rate` примет любое уменьшение за сброс. Для изменения gauge есть `delta(x[5m])` и `deriv(x[5m])`.
- **Среднее от gauge за окно** — `avg_over_time`, максимум — `max_over_time`. `max_over_time(go_goroutines[1h])` покажет пик за час, даже если график с крупным шагом его сгладил.
- **`avg` врёт так же, как всегда.** Средняя загрузка процессора по подам в 40% может означать, что три пода упёрлись в лимит, а остальные стоят. Для ресурсов смотрят `max` или `topk`.

## Деление рядов и сопоставление меток

Доля ошибок — это деление одного вектора на другой:

```
sum by (route) (rate(http_requests_total{status=~"5.."}[5m]))
  /
sum by (route) (rate(http_requests_total[5m]))
```

Бинарная операция между векторами сопоставляет ряды **по одинаковому набору меток**. Слева после `sum by (route)` остались только ряды с меткой `route`, справа — тоже, и ряды с одинаковым `route` делятся друг на друга.

<Predict

    'Ошибку: разное число рядов слева и справа',
  ]}
  answer={1}
>
Слева — ряды с `status="500"`, `status="503"`. Справа — все ряды, в том числе те же самые с `status="500"`. Сопоставление идёт по полному набору меток, и ряд `{route="/orders", status="500", pod="a"}` слева находит справа ровно себя. Результат — `1` для каждого ряда с ошибками, а ряды с `status="200"` в результат не попадают вовсе: слева им нет пары.

Поэтому метку, по которой делится выборка, убирают: либо агрегацией (`sum by (route)` с обеих сторон), либо явно — `ignoring(status)` в операторе. Общее правило: если результат деления пустой или странно ровный, первым делом сравните наборы меток слева и справа.
</Predict>

Иногда нужно сопоставить ряды с разными наборами меток: например, приложить к потреблению памяти контейнера его лимит из `kube-state-metrics`, или к метрике пода — метку `node` из `kube_pod_info`. Для этого есть `on(...)` — сопоставлять только по перечисленным меткам — и `group_left(...)` — разрешить многим рядам слева соответствовать одному справа и скопировать его метки:

```
# память контейнера относительно его лимита
sum by (namespace, pod, container) (container_memory_working_set_bytes{container!=""})
  /
sum by (namespace, pod, container) (kube_pod_container_resource_limits{resource="memory"})

# приложить имя узла к каждой метрике пода
rate(http_requests_total[5m])
  * on (namespace, pod) group_left (node)
kube_pod_info
```

Второй приём работает потому, что `kube_pod_info` — это «информационная» метрика: её значение всегда 1, а полезное — в метках. Умножение на единицу ничего не меняет, кроме набора меток.

### Когда рядов нет

Счётчик ошибок, в который ни разу не писали, не существует: ряд с `status="500"` появится только при первой ошибке. Запрос «ошибки / все» до этого момента возвращает пустоту, а не ноль, и алерт на `> 0.01` просто не с чем сравнить. Это одна из причин заранее инициализировать ряды нулями в коде сервиса — об этом в следующей лекции. На уровне запроса пустоту можно заменить нулём:

```
sum(rate(http_requests_total{status=~"5.."}[5m])) or vector(0)
```

А чтобы узнать, что ряда нет совсем — например, экспортер перестал отдавать метрику, — есть `absent(up{job="payments"})`: возвращает 1, когда ни одного подходящего ряда нет.

## Гистограммы в запросах

Из гистограммы получают три вещи.

**Перцентиль:**

```
histogram_quantile(0.99,
  sum by (le, route) (rate(http_request_duration_seconds_bucket{job="api"}[5m])))
```

Порядок тот же: `rate` каждого бакета, `sum` по подам **с сохранением `le`** — без этой метки `histogram_quantile` не знает, где какой бакет, и возвращает пустоту. Сумма бакетов по подам — это распределение всех запросов сервиса, и перцентиль по нему честный, в отличие от среднего перцентилей подов.

**Доля запросов быстрее порога** — точная, без интерполяции, если порог совпадает с границей бакета:

```
sum(rate(http_request_duration_seconds_bucket{le="0.3"}[5m]))
  /
sum(rate(http_request_duration_seconds_count[5m]))
```

Это лучший способ задавать цели по задержке: «99% запросов быстрее 300 мс» — это доля, а не перцентиль. Долю можно честно усреднять по времени и складывать, а на ней же строится алерт по <Term id="slo-error-budget">SLO</Term>.

**Средняя длительность** — сумма, делённая на число:

```
sum(rate(http_request_duration_seconds_sum[5m])) / sum(rate(http_request_duration_seconds_count[5m]))
```

Среднее прячет хвост, но полезно рядом с перцентилем: когда растёт p99, а среднее стоит, — проблема у небольшой доли запросов; растут оба — у всех.

У `histogram_quantile` есть неприятная особенность: если перцентиль попадает в последний бакет `+Inf`, функция возвращает границу предпоследнего. При бакетах до 10 секунд p99 «10 секунд» на графике на самом деле означает «10 секунд или сколько угодно больше». Если важен хвост, последний конечный бакет ставят за пределами таймаута.

## Время: offset, тренды, подзапросы

**Сравнение с прошлым.** `offset` сдвигает запрос назад во времени:

```
sum(rate(http_requests_total[5m]))
  /
sum(rate(http_requests_total[5m] offset 1w))
```

Отношение к тому же времени неделю назад убирает суточную и недельную сезонность: 0.5 в среду в 14:00 — повод разбираться, даже если абсолютное значение выглядит нормально.

**Прогноз.** `predict_linear` строит линейный тренд по окну и продлевает его:

```
# диск кончится в ближайшие 4 часа, если тренд последних 6 часов сохранится
predict_linear(node_filesystem_avail_bytes{mountpoint="/"}[6h], 4 * 3600) < 0
```

Это классический алерт на заполнение диска: он срабатывает заранее и не срабатывает на диск, который заполнен на 90%, но не растёт.

**Подзапросы.** Функции `*_over_time` принимают диапазонный вектор, а `rate(...)` возвращает мгновенный. Подзапрос вычисляет выражение в каждой точке окна с заданным шагом:

```
# максимальная пятиминутная скорость ошибок за последние сутки, с шагом в минуту
max_over_time(sum(rate(http_requests_total{status=~"5.."}[5m]))[1d:1m])
```

Подзапросы удобны, но дороги: это 1440 вычислений внутреннего выражения. Если такой запрос нужен регулярно — его место в recording rule.

## Recording rules: считать заранее

<Term id="recording-rule">Recording rule</Term> — запрос, который Prometheus выполняет сам по расписанию и записывает результат как новый ряд:

```yaml
groups:
  - name: http
    interval: 30s
    rules:
      - record: job_route:http_requests:rate5m
        expr: sum by (job, route) (rate(http_requests_total[5m]))
      - record: job:http_request_errors:ratio_rate5m
        expr: |
          sum by (job) (rate(http_requests_total{status=~"5.."}[5m]))
            /
          sum by (job) (rate(http_requests_total[5m]))
```

Зачем:

- **скорость дашбордов** — вместо свёртки 50 000 рядов на каждое открытие дашборда читается несколько десятков готовых;
- **длинные окна** — доля ошибок за 30 дней для SLO по сырым рядам считается долго, а по заранее посчитанным пятиминуткам — мгновенно;
- **одно определение** — «доля ошибок» считается одинаково на дашборде, в алерте и в отчёте;
- **агрегация перед отправкой** — в долгосрочное хранилище можно отправлять только агрегаты, а сырые ряды держать локально несколько дней.

Имя по соглашению — `уровень:метрика:операции`: `job_route:http_requests:rate5m` — «по job и route, из `http_requests`, rate за 5 минут». По имени сразу видно, из чего посчитан ряд и какие метки в нём остались.

## Запросы, которые кладут Prometheus

Каждый запрос вынимает из хранилища все ряды, подходящие под селектор, за всё окно. Стоимость — это ряды × точки, и один неосторожный запрос может съесть память сервера:

- **селектор без имени метрики**: `{job="api"}` или `{__name__=~".+"}` — все ряды всех метрик;
- **регулярка по кардинальной метке**: `{path=~".*orders.*"}` — Prometheus перебирает все значения метки;
- **долгое окно по сырым рядам**: `rate(x[30d])` по гистограмме на сотни тысяч рядов;
- **дашборд на 40 панелей с автообновлением раз в 5 секунд**, открытый у половины команды во время инцидента.

Защищаются настройками (`--query.max-samples`, таймаут запроса), recording rules и дисциплиной дашбордов. А найти, что именно раздуло базу, помогает сам PromQL:

```
# 10 метрик с наибольшим числом рядов
topk(10, count by (__name__) ({__name__=~".+"}))

# какие значения метки route дают больше всего рядов
topk(20, count by (route) (http_request_duration_seconds_bucket))
```

Первый запрос сам тяжёлый — на большом Prometheus его выполняют в спокойное время. Ту же статистику без нагрузки показывает страница `/tsdb-status` в интерфейсе Prometheus.

## Итог

- Селектор возвращает мгновенный вектор, с окном `[5m]` — диапазонный. Регулярки в фильтрах привязаны к началу и концу.
- [rate](/glossary/promql-rate/) — средняя скорость счётчика за окно с учётом сбросов, `increase` — рост, `irate` — по двум последним точкам и не для алертов. Всё это оценки с экстраполяцией.
- Окно — не меньше четырёх интервалов сбора; в Grafana — `$__rate_interval`.
- Сначала `rate`, потом `sum`. Сумма счётчиков разных подов «сбрасывается» при каждом перезапуске.
- Бинарные операции сопоставляют ряды по полному набору меток. Пустой или «ровный» результат — первым делом сравнить метки; для разных наборов — `on`, `ignoring`, `group_left`.
- Несуществующий ряд — пустота, а не ноль: `or vector(0)`, `absent()`.
- `histogram_quantile` — только с `le` в `sum by`. Цель по задержке лучше формулировать долей запросов быстрее порога.
- `offset` убирает сезонность, `predict_linear` предупреждает заранее, подзапросы дороги.
- [Recording rules](/glossary/recording-rule/) ускоряют дашборды, дают длинные окна для SLO и одно определение на всех.

Следующая лекция — о другой стороне: как сделать так, чтобы сервис на Go отдавал метрики, по которым все эти запросы вообще имеют смысл.
