В первой лекции курса было сказано: один Prometheus — одна машина, без репликации и с хранением на недели. Для одного кластера и десятка сервисов этого хватает надолго. Потом приходят вопросы, на которые один Prometheus не отвечает:

- **надёжность** — Prometheus перезапускается десять минут, пока перечитывает WAL, и всё это время нет ни графиков, ни алертов;
- **глобальный вид** — кластеров пять, в каждом свой Prometheus, а дашборд нужен по сервису целиком;
- **долгое хранение** — сравнить нагрузку с прошлым годом, спланировать мощности;
- **объём** — десятки миллионов рядов не помещаются в память одного сервера.

Эта лекция — о том, какие есть ответы и чем за них платят. Разработчику сервиса не обязательно уметь всё это разворачивать, но понимать, откуда берутся задержка данных, расхождение чисел и лимиты на кардинальность, — нужно.

## Две реплики и дедупликация

Самый простой шаг к надёжности — два одинаковых Prometheus, которые собирают одни и те же цели. Упал один — второй продолжает работать, алерты вычисляют оба, и Alertmanager склеивает дубли (для этого Prometheus и отправляет алерты во все его реплики).

С графиками сложнее. Реплики собирают данные в чуть разные моменты времени, и значения у них немного отличаются. Если Grafana смотрит в одну реплику через балансировщик, график прыгает при каждом переключении, а пока одна реплика перезапускалась, у неё дыра. Поэтому репликам дают внешнюю метку (`replica="a"` и `replica="b"`), а склеивает их слой запросов: берёт данные одной реплики и, где у неё дыра, подставляет другую. Это умеют Thanos и Mimir, а в VictoriaMetrics дубли прореживаются при записи.

## Federation

Исторически первый способ получить глобальный вид — federation: глобальный Prometheus собирает с Prometheus кластеров их эндпоинт `/federate`, указывая, какие ряды взять.

```yaml
- job_name: federate
  honor_labels: true
  metrics_path: /federate
  params:
    'match[]':
      - '{__name__=~"job:.*"}'   # только результаты recording rules
  static_configs:
    - targets: [prom-cluster-a:9090, prom-cluster-b:9090]
```

Federation подходит только для **агрегатов**: заранее посчитанных recording rules вроде `job:http_requests:rate5m`. Тянуть через неё сырые ряды — плохая идея: один ответ `/federate` на миллионы рядов собирается долго, падает по таймауту, и глобальный Prometheus упирается в те же пределы, что и локальные, только теперь в одном месте. Сейчас federation используют редко — для небольших инсталляций, где нужна сводка по нескольким кластерам.

## Remote write

Основной механизм масштабирования сегодня — **<Term id="remote-write">remote write</Term>**: Prometheus параллельно с записью в локальное хранилище отправляет каждую точку по HTTP во внешнее хранилище.

```yaml
remote_write:
  - url: https://mimir.example.com/api/v1/push
    queue_config:
      max_shards: 50
      capacity: 10000
    write_relabel_configs:
      # отправлять только то, что нужно долго хранить
      - source_labels: [__name__]
        regex: "job:.*|up|http_request_duration_seconds_bucket|http_requests_total"
        action: keep
```

Точки для отправки читаются из WAL, а не из отдельной очереди: remote write отстаёт от записи ровно настолько, насколько не успевает. Параллельные отправители (shards) Prometheus добавляет сам, если отставание растёт.

Раз хранением и запросами теперь занимается внешняя система, локальный Prometheus можно облегчить. В **агентском режиме** (`--agent`) Prometheus только собирает метрики и отправляет их: у него нет локальных запросов, правил и долгого хранения — только WAL на время отправки. Ту же роль играют `vmagent`, Grafana Alloy и коллектор OpenTelemetry.

## Три архитектуры

<ScaleArch />

### Thanos

Thanos достраивает недостающее к обычным Prometheus, не заменяя их:

- **sidecar** рядом с каждым Prometheus выгружает его двухчасовые блоки в объектное хранилище (S3, GCS) и отвечает на запросы о свежих данных из самого Prometheus;
- **store gateway** читает историю из объектного хранилища;
- **querier** принимает PromQL, опрашивает все sidecar и store gateway веером и склеивает ответ, убирая дубли реплик;
- **compactor** уплотняет блоки в хранилище и строит прореженные версии старых данных;
- **ruler** вычисляет правила по глобальным данным, а **receive** принимает remote write для тех, кто хочет push.

Сильная сторона Thanos — постепенность: к существующим Prometheus добавляются компоненты, и ничего не нужно переносить. Долгое хранение в S3 дёшево. Слабая — каждый Prometheus по-прежнему ограничен своей машиной, а запрос за свежие данные идёт веером во все кластеры и ждёт самый медленный.

### Grafana Mimir

Mimir (наследник Cortex) — распределённое хранилище, которое принимает remote write:

- **distributor** принимает точки, проверяет лимиты и раскладывает каждый ряд по хэшу на три **ingester** — это репликация;
- ingester держит свежие данные в памяти и WAL, как head в Prometheus, и выгружает блоки в объектное хранилище;
- **querier** читает свежее из ingester, историю — через **store gateway**, а **query frontend** режет долгие запросы на куски, кэширует и выполняет параллельно.

Mimir масштабируется горизонтально практически без предела и изначально многопользовательский: у каждого арендатора (команды, окружения) свои данные и свои **лимиты** — число рядов, частота точек, размер запроса. Платой — сложность: десяток компонентов, кольцо хэшей, кэши. Для небольших инсталляций есть монолитный режим, где все компоненты в одном процессе.

### VictoriaMetrics

VictoriaMetrics — отдельная реализация хранилища, совместимая с Prometheus по протоколам и почти полностью по языку. Бывает одноузловой (один бинарник) и кластерной (`vminsert`, `vmstorage`, `vmselect`). Хранит данные на своих дисках, а не в объектном хранилище, сжимает очень плотно и расходует заметно меньше памяти на ряд, чем Prometheus. Операционно — самый простой из трёх.

Язык запросов — **MetricsQL**, надмножество PromQL. И вот здесь есть ловушка.

`rate` и `increase` в MetricsQL устроены иначе: они не экстраполируют на края окна, а начало отсчёта берут из последней точки **перед** окном. Поэтому у целочисленного счётчика `increase` в VictoriaMetrics — целое число, а в Prometheus — дробное.

Для графиков разница незаметна. Но при переезде с одного хранилища на другое или при сравнении дашбордов, смотрящих в разные источники, числа расходятся, и это не ошибка. Порог алерта, подобранный на одном хранилище, на другом может вести себя чуть иначе — особенно на коротких окнах и редких событиях.

### Что выбрать

| | Prometheus + Thanos | Mimir | VictoriaMetrics |
| --- | --- | --- | --- |
| Модель | Prometheus остаются, блоки в S3 | remote write в распределённое хранилище | remote write, одноузловая или кластер |
| Масштаб одного кластера | ограничен одним Prometheus | горизонтальный | горизонтальный (кластерная версия) |
| Долгое хранение | объектное хранилище | объектное хранилище | свои диски |
| Язык | PromQL | PromQL | MetricsQL — надмножество, с отличиями в `rate` |
| Многопользовательность | ограниченная | встроенная, с лимитами | в кластерной версии |
| Сложность эксплуатации | средняя | высокая | низкая |

Для разработчика сервиса разница видна в трёх местах: где смотреть данные (один глобальный источник в Grafana вместо Prometheus каждого кластера), какие лимиты на ряды у твоей команды и почему числа в разных источниках могут чуть расходиться.

## Прореживание истории

Хранить год данных с разрешением 15 секунд дорого и бессмысленно: для графика за год нужна одна точка на несколько часов. Поэтому старые данные **прореживают** (downsampling): Thanos, например, строит версии с разрешением 5 минут для данных старше 40 часов и 1 час — для данных старше 10 дней, а сырые данные можно удалять раньше, чем прореженные.

Прореживание — не просто «каждая двадцатая точка». Для каждого интервала сохраняются минимум, максимум, сумма, число точек и рост счётчика, чтобы `rate`, `max_over_time` и `avg_over_time` по прореженным данным оставались осмысленными. Но с ограничениями:

- **окно должно быть больше разрешения**: `rate(x[5m])` по данным с разрешением в час пуст — в окне нет двух точек. Для графиков за год окна — `[3h]` и больше;
- **перцентиль из прошлого** настолько точен, насколько сохранились бакеты гистограммы. Всплеск задержки на 10 минут в часовой точке превращается в небольшую ступеньку;
- **короткие события** исчезают. Для «сколько было ошибок в тот день» лучше заранее сохранить агрегат recording rule, чем надеяться на прореженные сырые ряды.

## Лимиты и стоимость

В большой инсталляции метрики — это деньги: память ingester, диски, трафик. Поэтому появляются лимиты, и разработчику важно понимать, как они срабатывают.

**Лимиты при сборе.** Prometheus может ограничить каждую цель: `sample_limit` — число рядов с одной цели, `label_limit` — число меток на ряд.

  options={[
    'Prometheus возьмёт первые 10 000 рядов и отбросит остальные',
    'Весь сбор этой цели будет признан неудачным: не запишется ни один ряд, up станет 0, и алерты сервиса, завязанные на его метрики, замолчат',
    'Prometheus запишет всё и выдаст предупреждение в лог',
  ]}
  answer={1}
>
Превышение `sample_limit` проваливает сбор целиком — частично принятых данных не бывает. Для Prometheus это выглядит как недоступная цель: `up == 0`, все ряды сервиса помечены устаревшими. Лимит защитил Prometheus от взрыва кардинальности, но сервис стал невидимым — в том числе для своих алертов.

Поэтому такой лимит всегда идёт в паре с алертом на `up == 0` и на `scrape_samples_scraped`, приближающийся к лимиту, а у команды должно быть понятно, где посмотреть причину: `prometheus_target_scrapes_exceeded_sample_limit_total` и страница целей в интерфейсе Prometheus.
</Predict>

**Лимиты при записи.** В Mimir и кластерной VictoriaMetrics лимит на число активных рядов задан на арендатора. Превысил — новые ряды отбрасываются, а старые продолжают приниматься. Это лучше, чем падение хранилища, но выглядит странно: новая метрика после выкатки «не появляется», хотя сервис её отдаёт.

**Где режут стоимость:**

- **ненужные метрики** — большинство рядов в типичной инсталляции никто никогда не запрашивал. Их находят анализом того, что используется в дашбордах, алертах и правилах (`mimirtool analyze`, отчёты о кардинальности в Grafana и VictoriaMetrics), и отбрасывают через `metric_relabel_configs`;
- **лишние метки** — метка `pod` на бизнес-метрике, по которой никогда не смотрят в разрезе подов. Агрегация до отправки (recording rules, потоковая агрегация в `vmagent`) убирает её до того, как ряд попадёт в хранилище;
- **лишние бакеты** — 30 бакетов гистограммы там, где хватит 10, или переход на нативные гистограммы.

## Когда нужна высокая кардинальность

Иногда разрез по ID действительно нужен: «какие клиенты получили больше всего ошибок», «задержка по каждому арендатору из десяти тысяч». Метрики для этого не подходят в принципе: каждый ряд — это отдельная структура в памяти, и миллион значений метки — миллион структур независимо от того, насколько редки события.

Для таких вопросов данные хранят как **события**, а не как ряды: одна запись на запрос со всеми полями — маршрут, клиент, версия, длительность, код — в колоночном хранилище (ClickHouse, BigQuery) или в системе наблюдаемости, построенной вокруг «широких событий». Любой разрез считается запросом по событиям в момент вопроса, а не заводится заранее. Это дороже по хранению, но отвечает на вопросы, которые никто не догадался задать при проектировании метрик. Трассы и структурированные логи — частные случаи того же подхода, и о них следующие лекции.

<Callout title="А Elasticsearch для метрик?">
Elasticsearch и OpenSearch умеют хранить метрики — у Elasticsearch есть специальный режим индексов для временных рядов. Это удобно, если в компании уже всё в Elastic, но экосистема дашбордов, алертов и экспортеров построена вокруг Prometheus и PromQL, а специализированные хранилища временных рядов сжимают метрики в разы плотнее. Обычная расстановка — метрики в Prometheus-совместимом хранилище, логи в Elasticsearch или Loki.
</Callout>

## Итог

- Надёжность — две одинаковые реплики Prometheus; склеивает их слой запросов по метке `replica`.
- Federation — только для агрегатов из recording rules; для сырых рядов она не масштабируется.
- [Remote write](/glossary/remote-write/) отправляет точки из WAL во внешнее хранилище. WAL живёт пару часов — дольше хранилище лежать не должно. Отставание отправки — отдельный алерт. Агентский режим — только сбор и отправка.
- [Thanos](/glossary/long-term-metrics-storage/) добавляет к Prometheus глобальный запрос и S3; Mimir — распределённое многопользовательское хранилище с лимитами; VictoriaMetrics — самое простое в эксплуатации и экономное, но `rate` и `increase` в MetricsQL считаются без экстраполяции.
- Прореженные данные требуют окон больше разрешения и теряют короткие события.
- `sample_limit` проваливает сбор целиком — сервис становится невидим. Лимиты на арендатора молча отбрасывают новые ряды.
- Стоимость режут, удаляя неиспользуемые метрики, лишние метки и бакеты.
- Разрез по ID — это не метрики, а события: колоночные хранилища, трассы, структурированные логи.
