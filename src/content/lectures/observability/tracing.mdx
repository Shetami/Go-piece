Метрики показывают, что p99 оформления заказа вырос до секунды. Логи сервиса заказов чистые: ошибок нет. Сервисов в цепочке восемь, у каждого свои метрики, и у всех задержка немного выросла — кто из них причина, а кто просто ждёт следующего? Это вопрос, на который ни метрики, ни логи отдельных сервисов не отвечают. Отвечает трасса: путь одного конкретного запроса через все сервисы с точным временем каждого шага.

## Трасса и спан

<TraceWaterfall />

**Трасса** — это дерево операций одного запроса, объединённых общим ID трассы. Каждая операция — <Term id="trace-span">спан</Term>: у него есть имя, время начала и конца, ID родительского спана и атрибуты.

| Поле спана | Что это | Пример |
| --- | --- | --- |
| имя | тип операции, без переменных частей | `GET /orders/{id}`, `SELECT orders`, `send order.created` |
| kind | роль: сервер, клиент, продюсер, потребитель, внутренний | `SERVER` для входящего HTTP |
| атрибуты | подробности операции | `http.route`, `http.response.status_code`, `db.system`, `order.id` |
| события | отметки времени внутри спана | «повтор №2», исключение со стеком |
| статус | успех или ошибка | `Error: payment declined` |
| ссылки | связи с другими трассами | обработка пачки сообщений, пришедших из разных трасс |

Спан — не метрика, и правила кардинальности для атрибутов у него мягче: `order.id` или `user.id` в атрибуте спана — нормально и полезно, по ним потом ищут. А вот **имя** спана должно быть шаблоном: бэкенды трасс строят по именам списки операций и агрегаты, и `GET /orders/123` вместо `GET /orders/{id}` создаёт миллион «операций».

Кроме атрибутов спанов, у трассы есть **ресурс** — атрибуты процесса, который её записал: `service.name`, `service.version`, `k8s.pod.name`, `deployment.environment`. Они общие для всех спанов сервиса и задаются один раз при старте.

## Распространение контекста

Чтобы спаны разных сервисов сложились в одну трассу, каждый сервис должен узнать ID трассы и ID родительского спана от вызывающего. Для этого есть стандарт W3C Trace Context — заголовок <Term id="trace-context">traceparent</Term>:

```
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             │  └───────── ID трассы ──────────┘ └── ID спана ──┘ └ флаги: 01 — выбрана
             └ версия
```

Сервис читает заголовок из входящего запроса, создаёт свой спан ребёнком указанного и кладёт в исходящие вызовы свой `traceparent` — уже со своим ID спана. Флаг `01` — решение о выборке: записывать эту трассу или нет. Оно принимается один раз в начале и едет вместе с контекстом, поэтому все сервисы одной трассы решают одинаково.

Рядом живёт **baggage** — заголовок с произвольными парами «ключ-значение», которые передаются по всей цепочке: `tenant=acme`. Удобно, но осторожно: baggage уходит во все нижележащие вызовы, в том числе во внешние API, и не должен содержать ничего секретного. И каждый байт в нём едет в каждом запросе.

Контекст должен пересекать не только HTTP. В gRPC это метаданные, в Kafka — заголовки сообщения. Если хоть одно звено его не передаёт, трасса распадается на куски, и самое интересное — «что было после того, как событие ушло в Kafka» — теряется.

## OpenTelemetry в Go

OpenTelemetry — стандарт и набор SDK для всех трёх сигналов. Для трасс в Go нужны три вещи: провайдер, который создаёт спаны и отправляет их; пропагатор, который читает и пишет `traceparent`; и инструментация библиотек.

```go
func setupTracing(ctx context.Context) (shutdown func(context.Context) error, err error) {
    // Адрес — из OTEL_EXPORTER_OTLP_ENDPOINT, обычно коллектор на том же узле.
    exp, err := otlptracegrpc.New(ctx)
    if err != nil {
        return nil, err
    }
    res, err := resource.New(ctx,
        resource.WithFromEnv(), // OTEL_SERVICE_NAME, OTEL_RESOURCE_ATTRIBUTES
        resource.WithAttributes(attribute.String("service.version", buildVersion)),
    )
    if err != nil {
        return nil, err
    }
    tp := sdktrace.NewTracerProvider(
        sdktrace.WithBatcher(exp), // спаны уходят пачками в фоне, а не на каждый End()
        sdktrace.WithResource(res),
        sdktrace.WithSampler(sdktrace.ParentBased(sdktrace.TraceIDRatioBased(0.1))),
    )
    otel.SetTracerProvider(tp)
    otel.SetTextMapPropagator(propagation.NewCompositeTextMapPropagator(
        propagation.TraceContext{}, propagation.Baggage{},
    ))
    return tp.Shutdown, nil // вызвать при остановке, иначе последняя пачка спанов пропадёт
}
```

### Инструментация

Большую часть спанов пишут готовые обёртки — сервер, клиенты, драйверы:

```go
// Входящий HTTP: спан на каждый запрос, traceparent читается из заголовков.
mux := http.NewServeMux()
mux.Handle(routed("GET /orders/{id}", getOrder))
mux.Handle(routed("POST /orders", createOrder))
srv := &http.Server{Handler: otelhttp.NewHandler(mux, "http.server")}

// Имя спана и http.route — из шаблона маршрута, а не из пути.
func routed(pattern string, h http.HandlerFunc) (string, http.Handler) {
    return pattern, http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        span := trace.SpanFromContext(r.Context())
        span.SetName(pattern)
        span.SetAttributes(attribute.String("http.route", pattern))
        h(w, r)
    })
}

// Исходящий HTTP: спан-клиент и traceparent в заголовках.
client := &http.Client{Transport: otelhttp.NewTransport(http.DefaultTransport)}

// PostgreSQL через pgx: спан на каждый запрос.
cfg.ConnConfig.Tracer = otelpgx.NewTracer()

// gRPC.
grpcSrv := grpc.NewServer(grpc.StatsHandler(otelgrpc.NewServerHandler()))
```

Обёртка клиента не угадывает родителя: он берётся из контекста запроса. Поэтому исходящие вызовы — только с контекстом: `http.NewRequestWithContext(ctx, ...)`, `pool.Query(ctx, ...)`. Запрос с `context.Background()` начинает новую, отдельную трассу.

Свои спаны добавляют вокруг значимых шагов — там, где на разборе захочется увидеть время отдельно. Не вокруг каждой функции: трасса из пятисот спанов по 3 микросекунды не читается.

```go
var tracer = otel.Tracer("orders")

func (s *Service) reserveStock(ctx context.Context, items []Item) error {
    ctx, span := tracer.Start(ctx, "reserve stock",
        trace.WithAttributes(attribute.Int("items.count", len(items))))
    defer span.End()

    if err := s.stock.Reserve(ctx, items); err != nil {
        span.RecordError(err)
        span.SetStatus(codes.Error, "reserve failed")
        return fmt.Errorf("reserve stock: %w", err)
    }
    return nil
}
```

### Через Kafka

Для Kafka контекст кладут в заголовки сообщения. OpenTelemetry работает с любым носителем через интерфейс `TextMapCarrier`, так что для заголовков достаточно маленького адаптера:

```go
type headersCarrier struct{ rec *kgo.Record }

func (c headersCarrier) Get(key string) string {
    for _, h := range c.rec.Headers {
        if h.Key == key {
            return string(h.Value)
        }
    }
    return ""
}

func (c headersCarrier) Set(key, val string) {
    c.rec.Headers = append(c.rec.Headers, kgo.RecordHeader{Key: key, Value: []byte(val)})
}

func (c headersCarrier) Keys() []string {
    keys := make([]string, len(c.rec.Headers))
    for i, h := range c.rec.Headers {
        keys[i] = h.Key
    }
    return keys
}

// продюсер
otel.GetTextMapPropagator().Inject(ctx, headersCarrier{rec})

// потребитель
ctx := otel.GetTextMapPropagator().Extract(context.Background(), headersCarrier{rec})
ctx, span := tracer.Start(ctx, "process order.created", trace.WithSpanKind(trace.SpanKindConsumer))
defer span.End()
```

У многих клиентов это уже есть готовым: например, для franz-go — плагин `kotel`. Есть и вопрос выбора: делать обработку сообщения **ребёнком** спана продюсера или отдельной трассой **со ссылкой** на него. Ребёнок удобен, когда обработка — продолжение того же запроса. Ссылка — когда обработка идёт через минуты или обрабатывается пачка сообщений из сотни разных трасс: у спана один родитель, а ссылок может быть сколько угодно.

## Выборка

Трасса на каждый запрос — это объём, сравнимый с логами. Поэтому трассы выбирают, и способ выборки определяет, что вы увидите во время разбора.

**В начале** (head sampling) решение принимает первый сервис, когда трасса ещё только началась: `TraceIDRatioBased(0.1)` — сохранить 10%. Это дёшево: невыбранные трассы не записываются нигде. Но решение принимается вслепую — ещё неизвестно, будет ли запрос медленным или ошибочным. Если ошибок 0,1% запросов, а сохраняется 1% трасс, то трасс с ошибками сохранится одна из ста тысяч запросов.

**В конце** (tail sampling) все спаны отправляются в коллектор, он ждёт, пока трасса завершится, и решает по её содержимому: сохранить все трассы с ошибками, все медленнее порога и 5% остальных. Сохраняется именно интересное, но вся телеметрия проходит через коллектор, а он держит в памяти все незавершённые трассы.

<Term id="trace-sampling">Выборка</Term> должна быть согласована по всей цепочке — иначе трассы рвутся.

## Коллектор OpenTelemetry

Между сервисами и хранилищами почти всегда ставят <Term id="otel-collector">коллектор OpenTelemetry</Term> — программу-конвейер из трёх частей: приёмники, обработчики и отправители.

```yaml
receivers:
  otlp:
    protocols:
      grpc: { endpoint: 0.0.0.0:4317 }

processors:
  memory_limiter: { check_interval: 1s, limit_percentage: 80 }
  k8sattributes: {}              # добавить под, узел, деплоймент по IP отправителя
  tail_sampling:
    decision_wait: 10s           # сколько ждать завершения трассы
    policies:
      - { name: errors, type: status_code, status_code: { status_codes: [ERROR] } }
      - { name: slow,   type: latency,     latency: { threshold_ms: 1000 } }
      - { name: rest,   type: probabilistic, probabilistic: { sampling_percentage: 5 } }
  batch: {}

exporters:
  otlp/tempo: { endpoint: tempo:4317, tls: { insecure: true } }

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [memory_limiter, k8sattributes, tail_sampling, batch]
      exporters: [otlp/tempo]
```

Коллектор развязывает сервисы и хранилища так же, как агент логов: сервис отправляет OTLP на локальный адрес и не знает, куда данные едут дальше. Сменить бэкенд, добавить второй, отфильтровать персональные данные из атрибутов — это правка конфигурации коллектора, а не выкатка сотни сервисов.

Обычная схема — два уровня: **агент** на каждом узле (DaemonSet) принимает данные от подов и добавляет метаданные Kubernetes, **шлюз** — отдельный масштабируемый сервис — делает выборку в конце и отправляет в хранилища. Для выборки в конце есть важное условие: все спаны одной трассы должны попасть в **один** экземпляр шлюза, иначе каждый увидит только часть трассы. Поэтому агенты раскладывают спаны по экземплярам шлюза по хэшу ID трассы (экспортер `loadbalancing`).

## Хранилища и поиск трасс

| Хранилище | Как устроено | Как ищут |
| --- | --- | --- |
| Jaeger | классика; версия 2 построена на коллекторе OpenTelemetry, хранит в Elasticsearch, OpenSearch, Cassandra | по сервису, операции, атрибутам и длительности |
| Grafana Tempo | хранит трассы в объектном хранилище, индексирует минимум — дёшево | TraceQL; от метрик — через exemplars, от логов — по `trace_id` |
| Elastic APM | трассы как документы в Elasticsearch | KQL, ES\|QL, общий интерфейс с логами |

TraceQL в Tempo ищет по структуре трассы, а не только по отдельным спанам:

```
{ resource.service.name = "orders" && span.http.route = "POST /orders" && duration > 1s }

# трассы, где медленный заказ сопровождался ошибкой у провайдера
{ resource.service.name = "orders" && duration > 1s } >> { resource.service.name = "payments" && status = error }
```

### Метрики из спанов

Коллектор умеет считать RED прямо из проходящих спанов (коннектор `spanmetrics`) и строить граф вызовов между сервисами (`servicegraph`). Это удобно для сервисов, которые сами метрики не пишут. Но есть условие: считать нужно **до** выборки. Метрики, посчитанные по 5% сохранённых трасс, где выборка к тому же предпочитает ошибки и медленные запросы, покажут и частоту, и долю ошибок, и задержку неправильно.

## Три сигнала вместе

Каждый из сигналов по отдельности отвечает на часть вопроса. Ценность — в переходах между ними, и эти переходы нужно подготовить заранее:

- **метрика → трасса**: <Term id="exemplar">exemplars</Term> на гистограммах задержки. Точка на графике p99 открывает трассу одного из медленных запросов;
- **трасса → логи**: `trace_id` в каждой строке лога. Из спана — все логи этого запроса во всех сервисах;
- **лог → трасса**: тот же `trace_id` в строке — ссылка на трассу;
- **общие атрибуты ресурса**: `service.name`, `service.version`, `k8s.pod.name` одинаково называются в метриках, логах и трассах — можно сузить любой сигнал до той же версии или пода.

Разбор инцидента тогда выглядит так. Алерт по расходу бюджета ошибок оформления заказа: доля ошибок 2%. Дашборд: рост начался в 14:02, в 14:01 выкатили `payments` 3.4; задержка выросла только у маршрута `POST /orders`. Exemplar на графике задержки — трасса: 790 мс из 1000 — спан вызова провайдера, со статусом ошибки на повторе. Логи этой трассы в `payments`: `provider timeout after 800ms, retrying`. В новой версии таймаут к провайдеру уменьшили с 2 секунд до 800 мс, а провайдер в это время отвечает за секунду. Откат — и бюджет ошибок перестаёт гореть.

Каждый шаг — один клик, если сигналы связаны, и полчаса поисков, если нет.

## Итог

- Трасса — дерево [спанов](/glossary/trace-span/) с общим ID. Имя спана — шаблон без переменных частей, а ID и подробности — в атрибутах, им там место.
- [traceparent](/glossary/trace-context/) несёт ID трассы, ID родителя и решение о выборке через все сервисы: HTTP, gRPC, заголовки Kafka. Baggage уходит во все вызовы — ничего секретного.
- В Go: провайдер с пачечной отправкой и `Shutdown` при остановке, пропагатор W3C, готовые обёртки `otelhttp`, `otelgrpc`, `otelpgx`. Контекст передаётся в каждый исходящий вызов.
- `context.Background()` в фоновой горутине начинает новую трассу; `context.WithoutCancel` сохраняет трассу без отмены.
- Обработка сообщения — ребёнок спана продюсера или отдельная трасса со ссылкой, если она отложена или пачечная.
- [Выборка](/glossary/trace-sampling/) в начале дешёвая, но слепая; в конце сохраняет ошибки и медленные. Все сервисы, кроме входных, — `ParentBased`.
- [Коллектор](/glossary/otel-collector/) развязывает сервисы и хранилища. Для выборки в конце все спаны трассы должны попасть в один экземпляр.
- Метрики из спанов считают до выборки.
- Переходы между сигналами — exemplars, `trace_id` в логах, общие атрибуты ресурса — готовят заранее.

Этой лекцией курс заканчивается. Если свести его к одной мысли: наблюдаемость — это не инструменты, а заранее подготовленные ответы. Метрики с ограниченными метками и правильными типами, алерты на симптомы с понятным действием, логи с полями и `trace_id`, трассы с согласованной выборкой — всё это делается в спокойное время, чтобы во время аварии путь от алерта до причины занимал минуты.
