Метрика говорит, что доля ошибок оформления заказа выросла до 3%. Какие это ошибки, у каких клиентов, с каким текстом от платёжного провайдера — метрика не скажет и не должна: всё, что уникально для события, в метки класть нельзя. Это работа логов. Лог — запись об отдельном событии со всеми подробностями, и именно поэтому логи — самый дорогой сигнал: их объём растёт вместе с трафиком.

Эта лекция — о трёх вещах: как писать логи из Go, чтобы их можно было искать; как они доезжают до хранилища и где теряются; и как устроен Elasticsearch — самое распространённое хранилище логов, — чтобы понимать его ограничения.

## Структурированные логи

Строка `payment failed for order 123: provider timeout after 5s` удобна человеку и неудобна всему остальному. Чтобы найти все ошибки провайдера `stripe` на маршруте оформления, нужны регулярные выражения, которые сломаются при первом изменении формулировки. <Term id="structured-logging">Структурированный лог</Term> — это запись из полей:

```json
{"time":"2026-09-25T14:03:11.482Z","level":"ERROR","msg":"payment failed",
 "service":"orders","order_id":"123","provider":"stripe","err":"provider timeout after 5s",
 "trace_id":"4bf92f3577b34da6a3ce929d0e0e4736","span_id":"00f067aa0ba902b7"}
```

Сообщение `msg` постоянное — это тип события. Всё переменное — в полях, и по ним можно искать и считать: `provider: stripe and level: ERROR`.

В Go для этого есть стандартный `log/slog`:

```go
var level slog.LevelVar // Info по умолчанию; можно менять на лету

func newLogger() *slog.Logger {
    h := slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: &level})
    return slog.New(traceHandler{h}).With("service", "orders", "version", buildVersion)
}

// traceHandler добавляет ID трассы и спана из контекста в каждую запись.
type traceHandler struct{ slog.Handler }

func (h traceHandler) Handle(ctx context.Context, r slog.Record) error {
    if sc := trace.SpanContextFromContext(ctx); sc.IsValid() {
        r.AddAttrs(
            slog.String("trace_id", sc.TraceID().String()),
            slog.String("span_id", sc.SpanID().String()),
        )
    }
    return h.Handler.Handle(ctx, r)
}

// Без этих двух методов logger.With(...) вернёт внутренний обработчик, и trace_id пропадёт.
func (h traceHandler) WithAttrs(as []slog.Attr) slog.Handler { return traceHandler{h.Handler.WithAttrs(as)} }
func (h traceHandler) WithGroup(name string) slog.Handler     { return traceHandler{h.Handler.WithGroup(name)} }
```

И при записи — всегда варианты с контекстом, иначе обработчик не узнает трассу:

```go
logger.ErrorContext(ctx, "payment failed",
    "order_id", order.ID,
    "provider", provider,
    "amount_cents", order.Amount,
    "err", err,
)
```

`trace_id` в каждой строке — это мост между сигналами: из трассы медленного запроса можно открыть все его логи, а из строки с ошибкой — всю трассу.

### Что и когда писать

**Успешный запрос не пишет ничего** — для него есть метрики. Строка `request handled` на каждый запрос — это сотни гигабайт в сутки, в которых ничего не ищут. Если нужен журнал доступа, его пишет балансировщик или ingress.

**Уровни по делу.** `ERROR` — нужно внимание человека: операция не выполнена. `WARN` — нештатное, но обработанное: повтор удался, сработал запасной путь. `INFO` — редкие значимые события: старт, смена конфигурации, ребаланс. `DEBUG` — выключен в проде и включается на время разбора через `LevelVar`:

```go
admin.HandleFunc("PUT /loglevel", func(w http.ResponseWriter, r *http.Request) {
    if err := level.UnmarshalText([]byte(r.URL.Query().Get("level"))); err != nil {
        http.Error(w, err.Error(), http.StatusBadRequest)
    }
})
```

**Секреты и персональные данные — никогда.** Токены, пароли, номера карт, полные тела запросов. Лог уезжает в систему, куда доступ есть у многих, и хранится неделями. В `slog` защиту можно встроить в сам тип:

```go
type Token string

func (Token) LogValue() slog.Value { return slog.StringValue("[скрыто]") }
```

**Одинаковые ошибки — выборочно.** Когда падает зависимость, каждый запрос порождает одну и ту же ошибку. Десять тысяч одинаковых строк в секунду ничего не добавляют к первой сотне, зато кладут систему доставки. Выборку делают в обработчике: первые N одинаковых сообщений в секунду пишутся, остальные считаются и выводятся одной строкой «ещё 9 812 таких же». В `slog` это пишется своим обработчиком, в `zap` — встроено.

## Путь строки

<LogPipeline />

Сервис пишет логи в stdout — и всё. Среда контейнеров складывает вывод в файлы на узле (`/var/log/containers/…`), а агент, запущенный на каждом узле как DaemonSet (Fluent Bit, Vector, Filebeat, коллектор OpenTelemetry), читает эти файлы, разбирает JSON, добавляет метаданные Kubernetes — пространство имён, под, контейнер, метки — и отправляет дальше. В больших инсталляциях между агентами и хранилищем ставят буфер — Kafka, — чтобы пики не упирались в скорость индексации.

Почему не отправлять логи из сервиса прямо в хранилище? Потому что тогда хранилище логов становится зависимостью сервиса: оно тормозит — тормозит сервис, оно лежит — сервис копит логи в памяти или теряет их. С агентом сервис не знает о хранилище вовсе.

Но у цепочки есть места, где строки теряются, и все они срабатывают во время аварий, когда логов больше всего.

Ротация на узле ничего не знает о том, дочитал ли агент файл. При 30 МБ в минуту пять файлов по 10 МБ сменяются меньше чем за две минуты, и если агент отстал больше, начало аварии — самая ценная часть для разбора — исчезает.

Что с этим делают:

- **меньше логов на ошибку** — выборка одинаковых ошибок в самом сервисе. Это самое действенное;
- **буфер на диске у агента** — Fluent Bit и Vector умеют копить очередь на диске узла, а не только в памяти;
- **буфер перед хранилищем** — Kafka принимает быстрее, чем Elasticsearch индексирует;
- **метрики самого агента** — отставание чтения, размер буфера, отброшенные записи. Потерю логов нужно видеть так же, как потерю метрик.
</Predict>

Ещё одна потеря — отказ хранилища принять документ. О ней ниже, в разделе о маппинге.

## Как устроен Elasticsearch

Elasticsearch — распределённая поисковая система поверх библиотеки Lucene. Для логов он хорош тем, что умеет быстро искать по словам в тексте и считать агрегаты по полям в огромных объёмах. Чтобы пользоваться им без сюрпризов, нужно понимать четыре вещи: шарды, инвертированный индекс, путь записи и маппинг.

### Индексы и шарды

Данные хранятся в **индексах** — это что-то вроде таблицы, только с гибкой схемой. Каждый индекс разбит на <Term id="elasticsearch-shard">шарды</Term> — независимые части, каждая из которых — отдельный индекс Lucene. У каждого первичного шарда есть реплики на других узлах. Документ попадает в шард по хэшу своего ID, а поиск идёт по всем шардам индекса параллельно, и результаты сливаются — это тот же [веерный запрос](/glossary/scatter-gather/), что и в шардированной базе.

Число первичных шардов задаётся при создании индекса и потом не меняется. Поэтому логи не пишут в один вечный индекс: создают новый по размеру или по времени, а старые удаляют целиком — это быстрее, чем удалять документы. Об этом — в разделе о жизненном цикле.

### Инвертированный индекс

Чтобы найти все строки со словом `timeout` среди миллиардов, Elasticsearch не просматривает их. При записи он разбивает текст на слова (токены) и строит <Term id="inverted-index">инвертированный индекс</Term>: для каждого слова — список документов, где оно встречается.

```
"connection refused by upstream"  → токены: connection, refused, by, upstream
"upstream timeout"                → токены: upstream, timeout

индекс:  connection → [1]      refused → [1]      upstream → [1, 2]      timeout → [2]
```

Поиск `upstream AND timeout` — это пересечение двух списков, а не чтение текста. Отсюда и ограничения:

- **ищутся слова, а не подстроки.** `refus` не найдёт `refused` — такого токена нет. Запрос `*timeout*` с подстановкой в начале перебирает весь словарь и работает медленно;
- **разбиение на токены зависит от анализатора.** Стандартный делит по пробелам и знакам препинания и приводит к нижнему регистру: `OrderService.Charge` может стать одним токеном или двумя, в зависимости от настроек;
- **для агрегаций инвертированный индекс не годится.** Для подсчётов, сортировки и группировки у точных полей есть отдельное колоночное хранилище — doc values.

### Путь записи

<EsWritePath />

Документ при записи попадает в буфер индексации в памяти и в журнал **translog**. По умолчанию translog сбрасывается на диск до ответа клиенту — это гарантирует, что принятый документ переживёт падение узла.

Но искать его ещё нельзя. Раз в секунду происходит <Term id="es-refresh">refresh</Term>: содержимое буфера становится новым небольшим **сегментом** Lucene — неизменяемой частью индекса в кэше файловой системы, — и документ становится виден поиску. Поэтому Elasticsearch называют системой «почти реального времени»: между записью и появлением в поиске до секунды.

Реже происходит **flush**: сегменты сбрасываются на диск коммитом Lucene, и translog можно обрезать. В фоне идёт **слияние**: мелкие сегменты склеиваются в крупные, а документы, помеченные удалёнными, при этом вычищаются. Сегменты неизменяемы, поэтому «изменить документ» — это пометить старую версию удалённой и записать новую.

Для логов из этого следуют две настройки. `refresh_interval` можно увеличить до 10–30 секунд: логи редко ищут в ту же секунду, а каждый refresh — это новый мелкий сегмент и работа для слияния. И массовая запись — только через `_bulk`: тысячи документов одним запросом, а не по одному.

### Маппинг

Маппинг — это схема индекса: какого типа каждое поле и как его индексировать. Два типа для строк важнее всего:

| Тип | Как индексируется | Для чего |
| --- | --- | --- |
| `text` | разбивается на токены анализатором | полнотекстовый поиск по сообщениям и ошибкам |
| `keyword` | целиком, как одно значение | точные фильтры, агрегации, сортировка: `service`, `level`, `trace_id`, `route` |

Если маппинг не задан, Elasticsearch выводит его сам по первому документу с новым полем (**динамический маппинг**): строка становится `text` с подполем `.keyword`, число — `long`, объект — вложенными полями. Это удобно для начала и опасно в проде.

Вторая беда динамического маппинга — **взрыв полей**. Если в лог попадает словарь с произвольными ключами (заголовки запроса, параметры, `map[string]any` с ID в ключах), каждый новый ключ — новое поле в маппинге. Маппинг хранится в состоянии кластера и рассылается на все узлы, и после тысячи полей (`index.mapping.total_fields.limit`) документы с новыми полями начинают отвергаться.

Явный шаблон решает обе проблемы:

```json
PUT _index_template/logs-app
{
  "index_patterns": ["logs-app-*"],
  "data_stream": {},
  "template": {
    "settings": {
      "index.refresh_interval": "10s",
      "index.lifecycle.name": "logs-app"
    },
    "mappings": {
      "dynamic": false,
      "properties": {
        "@timestamp": { "type": "date" },
        "level":      { "type": "keyword" },
        "service":    { "type": "keyword" },
        "trace_id":   { "type": "keyword" },
        "msg":        { "type": "text" },
        "err":        { "type": "text" },
        "http": {
          "properties": {
            "route":       { "type": "keyword" },
            "status":      { "type": "short" },
            "duration_ms": { "type": "float" }
          }
        },
        "attrs": { "type": "flattened" }
      }
    }
  }
}
```

`"dynamic": false` означает: неизвестные поля хранятся в исходном документе, но не индексируются — документ не отвергается, а маппинг не растёт. Тип `flattened` индексирует весь объект `attrs` как одно поле: по его ключам можно искать точные значения, но без взрыва маппинга.

### Жизненный цикл и число шардов

Логи пишут в **data stream** — поток, за которым стоит цепочка скрытых индексов. Новые документы идут в текущий индекс, а политика <Term id="index-lifecycle">жизненного цикла (ILM)</Term> решает, когда начать новый и что делать со старыми:

```json
PUT _ilm/policy/logs-app
{
  "policy": {
    "phases": {
      "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" } } },
      "warm":   { "min_age": "3d",  "actions": { "forcemerge": { "max_num_segments": 1 } } },
      "delete": { "min_age": "30d", "actions": { "delete": {} } }
    }
  }
}
```

**Hot** — текущий индекс на быстрых дисках, сюда идёт запись. **Rollover** — начать новый индекс, когда шард дорос до 50 ГБ или прошли сутки. **Warm** — индексы только для чтения на дешёвых узлах, сегменты слиты в один. **Cold/frozen** — ещё дешевле, в том числе с данными в объектном хранилище. **Delete** — удаление целым индексом.

Главная ошибка здесь — **слишком много мелких шардов**. Каждый шард — это открытый индекс Lucene с памятью под структуры, файлами и записью в состоянии кластера. Индекс на каждый сервис на каждый день по пять шардов с репликой — сто сервисов за месяц дают 30 000 шардов, большинство по сотне мегабайт. Кластер тратит память и время мастера на учёт, а не на данные. Ориентир — шарды по 10–50 ГБ и rollover по размеру, а не только по дате.

### Поиск

В Kibana логи ищут на KQL:

```
service: "orders" and level: "ERROR" and not http.status: 404
err: "connection refused" and http.route: "POST /orders"
trace_id: "4bf92f3577b34da6a3ce929d0e0e4736"
```

Для подсчётов удобнее ES|QL — конвейерный язык запросов:

```
FROM logs-app-*
| WHERE level == "ERROR" AND @timestamp > NOW() - 1 hour
| STATS errors = COUNT(*) BY service, http.route
| SORT errors DESC
| LIMIT 20
```

Несколько правил, которые делают поиск быстрым:

- **сначала время.** Самый дешёвый фильтр — интервал: он отсекает целые индексы data stream, не заглядывая в них;
- **точные поля — фильтром.** Условия по `keyword`-полям не считают релевантность и кэшируются;
- **без подстановки в начале.** `*timeout` перебирает словарь, `timeout` — ищет токен;
- **глубокая пагинация не работает.** `from + size` ограничены 10 000 документов; для выгрузки — `search_after` с point in time.

<Callout title="Elasticsearch и OpenSearch">
В 2021 году Elastic сменил лицензию на несвободную, и AWS выпустил форк — OpenSearch, на основе Elasticsearch 7.10. С 2024 года Elasticsearch снова доступен под открытой лицензией AGPL. API у них во многом общие, но за годы разошлись: у Elasticsearch — ES|QL и свои режимы индексов, у OpenSearch — свой язык PPL и плагины. Всё, что в этой лекции об устройстве — шарды, сегменты, refresh, маппинг, — одинаково верно для обоих.
</Callout>

## Loki: индексировать только метки

Elasticsearch индексирует каждое слово каждой строки. Это даёт быстрый поиск, но стоит дорого: индекс сравним по размеру с данными, а индексирование ест процессор. <Term id="loki">Loki</Term> от Grafana Labs устроен противоположно: он индексирует только **метки потока** — как в Prometheus, — а сами строки хранит сжатыми кусками в объектном хранилище. Поиск по тексту — это перебор кусков нужных потоков за нужный интервал.

Запросы на LogQL выглядят как смесь PromQL и `grep`:

```
{namespace="prod", app="orders"} |= "timeout" | json | status >= 500

# метрика из логов: ошибки в секунду по маршрутам
sum by (route) (rate({app="orders"} | json | level="error" [5m]))
```

Сначала селектор потоков по меткам — это быстро и точно. Потом фильтры по тексту и разбор полей — это перебор, и его скорость зависит от того, сколько строк отобрал селектор.

Отсюда та же ловушка, что в Prometheus: <Term id="metric-cardinality">кардинальность</Term> меток. Метки потока — это `namespace`, `app`, `level`, может быть `pod`. `trace_id` или `user_id` в метках создают по потоку на каждое значение, и Loki начинает тонуть в крошечных кусках. Такие поля ищут фильтром по содержимому, а для частых — используют structured metadata.

| | Elasticsearch / OpenSearch | Loki | ClickHouse |
| --- | --- | --- | --- |
| Что индексирует | каждое слово и поле | только метки потока | колонки, разреженный первичный индекс |
| Поиск по тексту | быстрый, по токенам | перебор отобранных потоков | перебор колонки, быстрый на колонках |
| Агрегации по полям | быстрые по `keyword` | за счёт разбора строк при запросе | самые быстрые |
| Стоимость хранения | высокая: индекс + реплики | низкая: сжатые куски в S3 | низкая: сильное сжатие колонок |
| Схема | маппинг, конфликты типов | почти нет | таблица, нужно проектировать |

Правило выбора: много полнотекстового поиска по разным полям и есть команда, которая умеет обслуживать кластер, — Elasticsearch или OpenSearch. Логи в основном смотрят по сервису и времени, а бюджет важен — Loki. Логи — это данные для аналитики с агрегатами по многим полям — ClickHouse.

## Итог

- [Структурированный лог](/glossary/structured-logging/): постоянное сообщение и переменные поля. `slog` с JSON, `trace_id` в каждой строке через свой обработчик, варианты `…Context` при записи.
- Успешные запросы — в метриках, а не в логах. Ошибку логируют один раз — там, где её обрабатывают. Одинаковые ошибки — с выборкой. Секреты — через `LogValuer`.
- Сервис пишет в stdout, доставкой занимается агент на узле. Строки теряются при ротации файлов, переполнении буферов и отказе маппинга — и именно во время аварий.
- Elasticsearch делит индекс на [шарды](/glossary/elasticsearch-shard/), ищет по [инвертированному индексу](/glossary/inverted-index/) — слова, а не подстроки — и показывает документ после [refresh](/glossary/es-refresh/), а сохранность обеспечивает translog.
- [Маппинг](/glossary/es-mapping/) фиксирует тип поля первым документом. Конфликт типов молча выбрасывает логи, произвольные ключи раздувают маппинг. Явный шаблон, `dynamic: false`, `flattened`, общая схема полей.
- Data streams и [ILM](/glossary/index-lifecycle/): rollover по размеру, удаление целыми индексами, шарды по 10–50 ГБ, а не тысячи мелких.
- [Loki](/glossary/loki/) индексирует только метки — дешевле, но поиск по тексту — перебор. Высококардинальные поля — не в метки.

Логи отвечают, что случилось с отдельным событием. Остался последний вопрос — где в цепочке из десятка сервисов ушло время одного запроса. Это трассы.
