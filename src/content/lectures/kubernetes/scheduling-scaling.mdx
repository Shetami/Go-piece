До сих пор мы считали, что поды «как-то» оказываются на узлах, а их число задано в манифесте. В этой лекции разберём обе вещи всерьёз. Где окажется под — определяет, переживёт ли сервис падение узла или целой зоны. Сколько подов — определяет, выдержит ли он вечерний пик и не будете ли вы платить за пустые машины ночью.

## Как планировщик выбирает узел

<Term id="kube-scheduler">Планировщик</Term> берёт поды без узла по одному и для каждого делает два шага.

<SchedulerFilter />

**Фильтрация.** Отбросить узлы, на которые под поставить нельзя:

- не хватает свободных **requests** по CPU или памяти (помните из прошлой лекции — считается заказанное, а не использованное);
- на узле есть **taint**, который под не терпит;
- не выполнено обязательное **правило размещения**;
- нужный поду **том** не может быть подключён к этому узлу — например, диск в другой зоне.

**Оценка.** Оставшиеся узлы получают баллы: насколько свободен узел, есть ли на нём уже образ, насколько ровно лягут реплики по зонам и узлам, выполнены ли желательные правила. Под достаётся узлу с лучшим баллом.

Результат — просто имя узла в поле `spec.nodeName`. Если ни один узел не прошёл фильтр, под остаётся в `Pending`, а в событиях появляется причина — очень подробная:

```
$ kubectl describe pod api-7d9c8b6f5-x2kqp
Events:
  Warning  FailedScheduling  0/5 nodes are available: 2 Insufficient memory,
           2 node(s) had untolerated taint {dedicated: gpu}, 1 node(s) didn't
           match pod topology spread constraints.
```

Это первое, что стоит читать, когда под «завис». Планировщик всегда говорит, почему.

## Taints и tolerations: не пускать

Иногда узлы нужно держать для особой работы: узлы с GPU дорогие, и обычным сервисам там делать нечего. Для этого на узел ставят <Term id="taints-tolerations">taint</Term> — отметку, которая отталкивает поды:

```sh
kubectl taint nodes gpu-1 dedicated=gpu:NoSchedule
```

Теперь на `gpu-1` попадут только поды с подходящим toleration:

```yaml
spec:
  tolerations:
    - {key: dedicated, operator: Equal, value: gpu, effect: NoSchedule}
```

Важно: toleration **разрешает** поду стоять на таком узле, но не **отправляет** его туда. Под с toleration может спокойно оказаться на обычном узле. Чтобы GPU-задачи шли именно на GPU-узлы, нужны оба механизма: taint не пускает чужих, а affinity — о ней ниже — тянет своих.

Kubernetes и сам ставит taint-ы. Когда узел перестаёт отвечать, он получает taint `node.kubernetes.io/unreachable` с эффектом `NoExecute` — «выселить тех, кто не терпит». По умолчанию каждый под терпит его 300 секунд. Поэтому поды с умершего узла уезжают на другие не сразу, а **через пять минут**. Для сервисов, которым это долго, `tolerationSeconds` можно уменьшить — но осторожно: сетевой сбой на полминуты не должен приводить к переезду всего подряд.

## Affinity и распределение: куда тянуть

<Term id="node-affinity">Правила размещения</Term> бывают нескольких видов:

- **nodeAffinity** (или простой `nodeSelector`) — на какие узлы можно: с SSD, в определённой зоне, с архитектурой arm64;
- **podAffinity** — ставить рядом с определёнными подами: например, кэш поближе к приложению;
- **podAntiAffinity** — ставить подальше от определённых подов: две реплики базы — не на одном узле;
- **topologySpreadConstraints** — распределять реплики ровно по зонам или узлам.

Каждое правило бывает обязательным (`required…`, не выполнено — под `Pending`) или желательным (`preferred…`, влияет только на баллы).

У планировщика есть встроенное желательное распределение по зонам и узлам, но оно лишь одно из слагаемых балла. Если в зоне A просто больше свободных ресурсов, или две другие зоны заняты, или поды создавались в момент, когда узлы других зон были недоступны, — все три реплики вполне могут оказаться в одной зоне. А после нескольких выкаток и переездов раскладка меняется непредсказуемо.

Если зона A упадёт, сервис пропадёт целиком минимум на время, пока поды пересоздадутся в других зонах. А для этого там ещё должно найтись место.

Гарантировать распределение можно только явно — через topologySpreadConstraints.

Рецепт, полезный почти любому сервису с несколькими репликами:

```yaml
spec:
  topologySpreadConstraints:
    - maxSkew: 1                                  # разница между зонами — не больше одного пода
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: ScheduleAnyway            # желательно; DoNotSchedule — обязательно
      labelSelector: {matchLabels: {app: api}}
    - maxSkew: 1
      topologyKey: kubernetes.io/hostname          # и по узлам тоже
      whenUnsatisfiable: ScheduleAnyway
      labelSelector: {matchLabels: {app: api}}
```

`ScheduleAnyway` — разумный выбор по умолчанию: если идеального распределения не добиться, под всё равно запустится. `DoNotSchedule` строже, но может оставить поды в `Pending`, если в одной из зон кончится место.

## Приоритеты: кого подвинуть

Когда места нет, планировщик может освободить его, выселив менее важные поды. Важность задаётся `PriorityClass`:

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata: {name: critical-service}
value: 100000
description: Сервисы на пути платежа
```

Под с `priorityClassName: critical-service`, которому не хватило места, может вытеснить поды с меньшим приоритетом. Полезно, чтобы пакетная обработка не мешала пользовательским сервисам. Опасно, если раздать высокий приоритет всем — тогда он ничего не значит.

## HPA: сколько нужно подов

Нагрузка меняется: днём больше, ночью меньше, в распродажу — в разы больше. Держать ёмкость под пик круглосуточно дорого. **Horizontal Pod Autoscaler** (HPA) меняет число реплик по метрике — это <Term id="autoscaling">автомасштабирование</Term>:

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: {name: api}
spec:
  scaleTargetRef: {apiVersion: apps/v1, kind: Deployment, name: api}
  minReplicas: 3
  maxReplicas: 30
  metrics:
    - type: Resource
      resource:
        name: cpu
        target: {type: Utilization, averageUtilization: 60}   # 60% от requests
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300   # уменьшать не раньше, чем через 5 минут стабильно низкой нагрузки
```

Формула у HPA простая:

```
нужно реплик = ⌈ сейчас реплик × текущая метрика / целевая метрика ⌉
```

Четыре реплики загружены на 90% при цели 60% — нужно ⌈4 × 90 / 60⌉ = 6. Обратите внимание: процент считается **от requests**. Если requests занижены, «загрузка» будет больше 100%, и формула всё равно работает — но цифры на графиках будут вводить в заблуждение.

Для сервиса, который в основном ждёт, CPU — плохой показатель нагрузки. Горутина, ожидающая ответа базы, процессор не тратит. Вдвое больше запросов — это вдвое больше ожидающих горутин и, возможно, очередь за соединениями пула, но загрузка процессора вырастет совсем немного. HPA этого не заметит.

К тому же, если узкое место — база, добавление реплик сервиса не поможет, а может и навредить: каждая новая реплика откроет ещё пул соединений к той же базе.

Масштабироваться нужно по метрике, которая отражает насыщение именно этого сервиса: числу запросов в работе на под, длине очереди, для консьюмеров — отставанию группы в Kafka. HPA умеет работать с такими метриками через адаптер Prometheus или KEDA.
</Predict>

HPA по собственной метрике — например, по числу запросов в работе на под, которое сервис отдаёт в Prometheus:

```yaml
metrics:
  - type: Pods
    pods:
      metric: {name: http_requests_in_flight}
      target: {type: AverageValue, averageValue: "20"}
```

Для консьюмеров очередей удобнее **KEDA**: он масштабирует по отставанию группы в Kafka, длине очереди в RabbitMQ или SQS и умеет опускать число реплик до нуля, когда работы нет.

И главное, что нужно помнить про любое автомасштабирование: **оно реагирует с задержкой**. Метрика усредняется за десятки секунд, новый под нужно запланировать, скачать образ, запустить, дождаться readiness. В лучшем случае — полминуты, при необходимости добавить узел — несколько минут. Всё это время нагрузку держат старые реплики. Поэтому:

- цель ставят с запасом — 50–70%, а не 90%;
- `minReplicas` — не меньше, чем нужно, чтобы пережить падение одного пода в пиковый час;
- на известные пики масштабируются заранее, по расписанию;
- быстрый старт — маленький образ, отсутствие долгого прогрева — прямо влияет на скорость реакции.

## Когда подам не хватает узлов

HPA добавляет поды, но узлы от этого не появляются. Если места нет, новые поды висят в `Pending`. Здесь вступает **автомасштабирование кластера** — Cluster Autoscaler или Karpenter:

- видит поды в `Pending` из-за нехватки ресурсов и добавляет узлы, на которые они встанут;
- видит недогруженные узлы, чьи поды поместятся на других, и удаляет их, предварительно выселив поды.

Karpenter (AWS, и не только) сам подбирает тип машины под ожидающие поды, Cluster Autoscaler работает с заранее описанными группами узлов. Для обоих главное входное данное — **requests**: они решают, «поместится» ли под, опираясь на заказы. Неправильные requests — неправильные решения о числе узлов.

## Узлы уходят: PodDisruptionBudget

Автомасштабирование кластера удаляет узлы. Обновление версии Kubernetes заменяет их все по очереди. Облачный провайдер перезапускает машины для обслуживания. Каждый раз поды с узла выселяются — через `kubectl drain` или его аналог.

<Term id="k8s-eviction">Плановое выселение</Term> идёт через Eviction API, и его можно ограничить. <Term id="pod-disruption-budget">PodDisruptionBudget</Term> говорит: «сколько подов этого приложения можно выселить одновременно»:

```yaml
apiVersion: policy/v1
kind: PodDisruptionBudget
metadata: {name: api}
spec:
  maxUnavailable: 1
  selector:
    matchLabels: {app: api}
```

Теперь, если под `api` уже выселяется и новый ещё не готов, Eviction API откажет в выселении следующего. `drain` подождёт и повторит.

  options={[

`minAvailable: 2` при двух репликах означает «ни один под нельзя выселить никогда». Eviction API будет отказывать при каждой попытке, и `drain` застрянет навсегда. Выселение не создаёт новую реплику заранее — оно сначала убирает старую, а Deployment потом создаёт замену. Значит, бюджет в ноль недоступных подов делает выселение невозможным в принципе.

Это классическая ошибка, из-за которой команда платформы приходит с вопросом «почему ваш сервис блокирует обновление кластера». Правильный бюджет всегда оставляет возможность выселить хотя бы один под: `maxUnavailable: 1` или `minAvailable` меньше числа реплик. А для сервиса из одной реплики PDB бессмыслен — нужно либо больше реплик, либо смириться с коротким простоем.
</Predict>

И помните, от чего PDB **не** защищает: от внезапной смерти узла, от OOMKilled, от удаления пода руками и от выкатки Deployment (её темп задаёт `maxUnavailable` в стратегии). Он работает только с добровольными выселениями.

## Что из этого следует для сервиса на Go

- **Читайте события `FailedScheduling`** — планировщик всегда пишет, почему под не встал.
- **Раскладывайте реплики по зонам и узлам** через topologySpreadConstraints. По умолчанию это не гарантировано.
- **Не меньше трёх реплик** для сервисов, которые должны пережить падение зоны, и `minReplicas` в HPA соответственно.
- **HPA по метрике насыщения**: CPU — для вычислительных сервисов, запросы в работе или отставание очереди — для всех, кто в основном ждёт.
- **Быстрый старт** ускоряет реакцию на нагрузку: маленький образ, прогрев за секунды, readiness сразу после него.
- **PDB с `maxUnavailable: 1`** для каждого сервиса с несколькими репликами; никогда — бюджет, запрещающий выселение вовсе.
- **Мягкая остановка обязательна**: при автомасштабировании поды выселяются постоянно, и каждый раз это остановка по SIGTERM.

## Итог

- [Планировщик](/glossary/kube-scheduler/) фильтрует узлы по requests, taint-ам, правилам и томам, затем оценивает оставшиеся. Причину `Pending` он пишет в события.
- [Taints](/glossary/taints-tolerations/) не пускают поды на узлы, tolerations разрешают; [affinity и распределение](/glossary/node-affinity/) тянут поды к нужным узлам и раскладывают реплики по зонам.
- HPA считает нужное число реплик по метрике относительно цели. [Автомасштабирование](/glossary/autoscaling/) запаздывает, поэтому цель ставят с запасом, а метрику выбирают по реальному узкому месту.
- Cluster Autoscaler и Karpenter добавляют и убирают узлы, ориентируясь на requests и поды в `Pending`.
- [PodDisruptionBudget](/glossary/pod-disruption-budget/) ограничивает плановые выселения, но бюджет без права выселить хотя бы один под блокирует обслуживание кластера.

Остался последний, самый практический шаг: что делать, когда что-то из всего этого не работает. Следующая лекция — отладка: как по симптому быстро найти причину.
