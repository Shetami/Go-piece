Один и тот же образ должен работать и в staging, и в продакшене — с разными адресами баз, разными уровнями логирования и, конечно, разными паролями. Значит, всё, что отличается между окружениями, должно приходить снаружи. Kubernetes даёт для этого ConfigMap и Secret. А для тех редких сервисов, которым нужно хранить данные на диске, — постоянные тома и StatefulSet. Разберём и то, и другое, и заодно контроллеры для работы, которая не должна крутиться вечно.

## ConfigMap: настройки

<Term id="k8s-configmap" /> — объект с парами ключ-значение или целыми файлами:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: api-config
data:
  LOG_LEVEL: info
  HTTP_TIMEOUT: 5s
  features.yaml: |
    new_checkout: true
    recommendations: false
```

Подать его в под можно двумя способами — и у них разное поведение, которое стоит понимать.

**Переменными окружения:**

```yaml
containers:
  - name: api
    envFrom:
      - configMapRef: {name: api-config}   # все ключи сразу
    env:
      - name: TIMEOUT
        valueFrom:
          configMapKeyRef: {name: api-config, key: HTTP_TIMEOUT}
```

**Файлами в томе:**

```yaml
containers:
  - name: api
    volumeMounts:
      - {name: config, mountPath: /etc/api}
volumes:
  - name: config
    configMap: {name: api-config}   # каждый ключ станет файлом: /etc/api/features.yaml
```

Переменные окружения процесса задаются один раз — при его запуске. Kubernetes не может поменять их у работающего процесса, и изменение ConfigMap само по себе поды не перезапускает: шаблон пода в Deployment ведь не поменялся — он ссылается на ConfigMap по имени, а имя то же.

Новое значение увидят только поды, созданные после изменения. А значит, после следующей выкатки или случайного перезапуска часть подов будет работать с `debug`, часть — с `info`. Это худший вариант: конфигурация кластера разная, и никто этого не видит.
</Predict>

Как с этим жить:

- **Перезапускать поды после изменения конфигурации.** Руками — `kubectl rollout restart deployment/api`. Автоматически — положив хэш конфигурации в аннотацию шаблона пода: изменилась конфигурация — изменился шаблон — Deployment плавно заменил поды. Helm и Kustomize умеют это из коробки; Kustomize, например, добавляет хэш прямо к имени ConfigMap (`api-config-7g2k9h`), и ссылка в Deployment меняется сама.
- **Или читать файлы и перечитывать их.** Файлы в томе kubelet обновляет сам, с задержкой до минуты. Но приложение должно заметить изменение — следить за файлом или перечитывать его периодически:

```go
// Перечитываем файл раз в 30 секунд. Kubernetes подменяет его атомарно —
// через симлинк — поэтому наполовину записанный файл мы не увидим.
func watchFeatures(ctx context.Context, path string, cur *atomic.Pointer[Features]) {
	t := time.NewTicker(30 * time.Second)
	defer t.Stop()
	for {
		select {
		case <-ctx.Done():
			return
		case <-t.C:
			f, err := loadFeatures(path)
			if err != nil {
				log.Printf("конфигурация не перечитана, работаем со старой: %v", err)
				continue
			}
			cur.Store(f)
		}
	}
}
```

Для большинства настроек перезапуск через хэш проще и надёжнее: конфигурация меняется так же плавно, как при выкатке, а если новая сломана — выкатка остановится на первом поде. Перечитывание на лету имеет смысл для того, что меняют часто: флагов функций, лимитов.

И ещё одна деталь: при монтировании ConfigMap через `subPath` (чтобы положить один файл в существующий каталог) файл **не обновляется** вовсе.

## Secret: пароли — и почему это не сейф

<Term id="k8s-secret">Secret</Term> устроен как ConfigMap, но предназначен для паролей, токенов и ключей:

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: api-db
type: Opaque
stringData:                  # можно писать открытым текстом, в data окажется base64
  DATABASE_URL: postgres://api:s3cr3t@postgres:5432/app
```

Посмотрите на него через `kubectl get secret api-db -o yaml` — значение будет в base64. Многие думают, что это защита. Нет: `base64 -d` раскодирует его за миллисекунду. base64 здесь нужен, чтобы хранить бинарные данные (ключи, сертификаты), а не чтобы прятать.

Что на самом деле защищает секреты:

- **права доступа.** Право читать секреты в namespace — это доступ ко всем паролям в нём. Менее очевидно: право **создавать поды** в namespace — тоже, потому что под может смонтировать любой секрет своего namespace. Раздавайте эти права через <Term id="k8s-rbac">RBAC</Term> осознанно;
- **шифрование в etcd.** По умолчанию секреты лежат в etcd как есть. Шифрование включается настройкой API-сервера или ключом из облачного KMS; в управляемых кластерах обычно включено, но стоит проверить;
- **секреты не лежат в git открытым текстом.** Манифест с `stringData` в репозитории — это пароль в репозитории.

Для последнего пункта есть несколько подходов:

- **External Secrets Operator** — в git лежит только ссылка «возьми ключ `prod/api/db` из Vault / AWS Secrets Manager / GCP Secret Manager», а оператор создаёт Secret в кластере и обновляет его при ротации;
- **Sealed Secrets** — в git лежит зашифрованный секрет, расшифровать который может только контроллер в кластере;
- **SOPS** — файлы шифруются ключом из KMS, расшифровываются при деплое.

Файлы или переменные окружения? Для секретов — лучше **файлы**. Переменные окружения попадают в дампы процессов, в вывод отладочных инструментов, в ошибки, которые логируют «всё окружение», и не обновляются при ротации. Секрет, смонтированный файлом, лежит в памяти (tmpfs), не на диске узла, и обновляется сам.

## Тома: где хранить файлы

Файловая система контейнера исчезает вместе с ним — даже при перезапуске контейнера в том же поде. Если нужны файлы, которые переживут хотя бы это, нужен том. Томов много видов, и важно выбрать по времени жизни:

| том | живёт | для чего |
| --- | --- | --- |
| `emptyDir` | пока жив под | временные файлы, кэш, обмен файлами между контейнерами пода |
| `configMap`, `secret` | пока жив под | настройки и пароли в виде файлов |
| `persistentVolumeClaim` | независимо от пода | данные, которые должны пережить под: базы, очереди |
| `hostPath` | пока жив узел | каталог узла — почти никогда не нужен приложениям и опасен |

Для постоянных данных используется цепочка из трёх объектов:

- <Term id="persistent-volume-claim">PersistentVolumeClaim (PVC)</Term> — заявка: «нужен диск на 20 Gi, подключаемый к одному узлу»;
- **PersistentVolume (PV)** — сам диск: облачный том, NFS, локальный SSD;
- **StorageClass** — рецепт, как создать диск под заявку: какой тип облачного диска, какая скорость, удалять ли его вместе с заявкой.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata: {name: uploads}
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: fast-ssd
  resources:
    requests: {storage: 20Gi}
```

Вы создаёте PVC, драйвер хранилища (CSI) видит его и создаёт в облаке настоящий диск, а Kubernetes связывает их. Под ссылается на PVC — и где бы он ни запустился, диск подключат к его узлу.

Главное ограничение — **режим доступа**. Облачные блочные диски почти всегда `ReadWriteOnce`: подключены к одному узлу за раз. Значит, **Deployment с несколькими репликами не может делить такой диск** — поды на разных узлах его не получат. А ещё облачный диск живёт в одной зоне доступности, и под с ним можно поставить только в эту зону. Если нужен общий доступ из многих подов — `ReadWriteMany` на сетевой файловой системе (NFS, EFS), но для Go-сервиса почти всегда правильнее объектное хранилище вроде S3.

## StatefulSet: поды с идентичностью

Поды Deployment одинаковы и взаимозаменяемы. Для базы данных или брокера так не годится: у каждой реплики свои данные, и важно, какая из них какая. Для таких приложений есть <Term id="k8s-statefulset" />:

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata: {name: db}
spec:
  serviceName: db            # headless Service, дающий подам DNS-имена
  replicas: 3
  selector:
    matchLabels: {app: db}
  template:
    metadata:
      labels: {app: db}
    spec:
      containers:
        - name: postgres
          image: postgres:17
          volumeMounts: [{name: data, mountPath: /var/lib/postgresql/data}]
  volumeClaimTemplates:      # у каждого пода — свой PVC
    - metadata: {name: data}
      spec:
        accessModes: [ReadWriteOnce]
        resources: {requests: {storage: 100Gi}}
```

Что StatefulSet гарантирует:

- **постоянные имена**: `db-0`, `db-1`, `db-2`. Пересозданный `db-0` снова называется `db-0`;
- **постоянные диски**: у каждого пода свой PVC (`data-db-0`, `data-db-1`…), и пересозданный под получает именно свой;
- **постоянные адреса**: через <Term id="headless-service">headless Service</Term> — `db-0.db.prod.svc.cluster.local`. Можно обратиться к конкретной реплике;
- **порядок**: поды создаются по одному, начиная с `db-0`, и каждый следующий — только когда предыдущий готов. Удаляются и обновляются в обратном порядке.

StatefulSet гарантирует, что под с одним именем существует **не больше одного**. А недоступный узел — это не мёртвый узел. Возможно, он просто потерял связь с управляющим слоем, а `db-0` на нём продолжает работать и писать в свой диск. Если создать второй `db-0` с тем же диском, два процесса запишут в одни данные.

Поэтому под на недоступном узле зависает в `Terminating` или `Unknown`, и замена не создаётся, пока Kubernetes не убедится, что старый точно мёртв: узел удалён из кластера, вернулся и подтвердил остановку, или администратор явно пометил его выключенным (taint `node.kubernetes.io/out-of-service`) либо удалил под принудительно.

Deployment так не осторожничает — его поды взаимозаменяемы, и лишний под ничего не испортит. Для StatefulSet осторожность — это защита данных. Высокую доступность базы должна обеспечивать сама база — репликацией и переключением на реплику, — а не Kubernetes.
</Predict>

Это важная мысль: **StatefulSet не делает из приложения кластер**. Он даёт стабильные имена и диски, но не знает, кто ведущий, не настраивает репликацию и не переключает. Эту работу делают операторы — контроллеры, написанные для конкретной системы: CloudNativePG или Zalando Postgres Operator для PostgreSQL, Strimzi для Kafka. А многие команды и вовсе держат базы вне Kubernetes — в управляемых облачных сервисах — и в кластере запускают только сервисы без состояния. Для начала это самый спокойный путь.

## Job и CronJob: работа, которая заканчивается

Deployment держит поды вечно. Но бывает работа с концом: миграция, пересчёт, выгрузка отчёта. Для неё есть <Term id="k8s-job">Job</Term>: он запускает под и считает дело сделанным, когда тот завершился с кодом 0. Упал — запустит заново, до `backoffLimit` раз.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata: {name: nightly-report}
spec:
  schedule: "0 3 * * *"          # каждый день в 03:00
  timeZone: Europe/Moscow
  concurrencyPolicy: Forbid      # не запускать, если прошлый ещё идёт
  jobTemplate:
    spec:
      backoffLimit: 2
      activeDeadlineSeconds: 3600
      ttlSecondsAfterFinished: 86400
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: report
              image: registry.example.com/report:2.1.0
```

CronJob создаёт Job-ы по расписанию. Самое важное здесь — `concurrencyPolicy`: если отчёт вдруг стал выполняться дольше суток, с `Allow` (по умолчанию) запуски начнут накладываться друг на друга.

И общее правило для всего, что запускают Job-ы: **задача должна быть идемпотентной**. Kubernetes не обещает ровно один запуск. Под может упасть посреди работы и начаться заново, узел может пропасть — и Job запустит замену, хотя старый под, возможно, доработал. Пересчёт, запущенный дважды, не должен удвоить результат.

## DaemonSet: по поду на каждый узел

<Term id="k8s-daemonset" /> держит ровно один под на каждом узле: появился узел — появился под. Это инструмент для инфраструктуры: сборщики логов и метрик, сетевые плагины, драйверы дисков. Своему сервису на Go он почти никогда не нужен: число реплик сервиса определяется нагрузкой, а не числом узлов. Но знать о нём стоит — в `kubectl get pods -A` вы увидите много его подов.

## Что из этого следует для сервиса на Go

- **Вся конфигурация — снаружи.** Образ один на все окружения; всё, что отличается, — из ConfigMap и Secret.
- **Изменение конфигурации = выкатка.** Хэш в аннотации шаблона, и конфигурация меняется так же плавно и так же откатывается, как код.
- **Секреты — файлами и не в git.** External Secrets или Sealed Secrets, шифрование etcd, аккуратные права.
- **Состояние — вне пода.** База, очередь, S3. Если без диска никак — StatefulSet и PVC, но помните про зоны и режимы доступа.
- **Базы данных — лучше управляемые** или через зрелый оператор. StatefulSet сам по себе репликацию и переключение не делает.
- **Периодическая работа — CronJob с `concurrencyPolicy: Forbid`** и идемпотентной логикой. Не `time.Ticker` в одной из реплик сервиса: при трёх репликах задача выполнится трижды.

## Итог

- [ConfigMap](/glossary/k8s-configmap/) подаёт настройки переменными окружения или файлами. Переменные не обновляются у работающих подов; файлы обновляются, но приложение должно их перечитать.
- [Secret](/glossary/k8s-secret/) — не шифрование. Защищают его права доступа, шифрование etcd и внешние хранилища секретов.
- [PVC](/glossary/persistent-volume-claim/) — заявка на диск, который живёт независимо от пода. Облачные диски обычно подключаются к одному узлу и живут в одной зоне.
- [StatefulSet](/glossary/k8s-statefulset/) даёт подам постоянные имена, диски и адреса и никогда не запускает два пода с одним именем. Кластер из приложения он не делает.
- [Job и CronJob](/glossary/k8s-job/) — для работы с концом; задача должна переживать повторный запуск. [DaemonSet](/glossary/k8s-daemonset/) — по поду на узел, для инфраструктуры.

Осталась одна большая тема: как кластер решает, куда поставить под, и как он растёт и сжимается вместе с нагрузкой. Об этом — следующая лекция.
