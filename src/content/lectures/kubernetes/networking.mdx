Поды одноразовые: при каждой выкатке, каждом переезде у них новые IP-адреса. А клиентам нужен постоянный адрес. Эту задачу решает Service — и то, как он её решает, объясняет несколько неочевидных вещей: почему нельзя пингнуть адрес сервиса, почему gRPC-сервис грузит один под из десяти и почему «сервис не отвечает», хотя все поды работают.

## Сетевая модель

Kubernetes требует от сети трёх вещей:

- **у каждого пода свой IP-адрес**, общий для всех его контейнеров;
- **любой под может достучаться до любого другого пода по его IP** — на том же узле или на другом, без трансляции адресов;
- **узлы видят поды, а поды — узлы** тоже напрямую.

Как это достигается — дело CNI-плагина: Calico, Cilium, Flannel или облачного плагина, который выдаёт подам адреса прямо из сети облака. Для приложения результат одинаковый: кластер выглядит как одна плоская сеть, где у каждого пода свой адрес.

Это удобно, но на адрес пода по-прежнему нельзя полагаться: он меняется при каждой замене пода. Нужна прослойка.

## Service: постоянный адрес

<Term id="k8s-service">Service</Term> выбирает поды по меткам и даёт им общий постоянный адрес:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: api
  namespace: prod
spec:
  selector: {app: api}      # все поды с этой меткой
  ports:
    - name: http
      port: 80              # порт сервиса
      targetPort: http      # порт контейнера — можно по имени из пода
```

Service получает два адреса:

- **ClusterIP** — виртуальный IP вроде `10.96.14.2`, который не меняется, пока существует Service;
- **DNS-имя** — `api.prod.svc.cluster.local`. Из того же namespace достаточно `api`, из соседнего — `api.prod`.

В коде это выглядит обыденно:

```go
resp, err := client.Get("http://api.prod/v1/users/42") // Service api в namespace prod, порт 80
```

Какие поды стоят за сервисом прямо сейчас, записано в объекте <Term id="endpoint-slice">EndpointSlice</Term>. Его ведёт контроллер: смотрит на поды, подходящие под селектор, и записывает их адреса с отметкой, готов ли каждый. Именно сюда смотрят, когда «сервис не отвечает»:

```sh
kubectl get endpointslices -n prod -l kubernetes.io/service-name=api
```

Пустой список — это почти всегда одно из двух: селектор сервиса не совпадает с метками подов (опечатка) или ни один под не прошёл readiness-пробу.

## Как запрос доходит до пода

<ServicePath />

Вот что происходит, когда под делает запрос на `http://api.prod`:

1. **DNS.** Программа спрашивает CoreDNS — DNS-сервер кластера, который сам работает подами. Он отвечает ClusterIP сервиса.
2. **Подмена адреса.** Программа открывает TCP-соединение на ClusterIP. Пакет не уходит в сеть с этим адресом: его перехватывает ядро узла, на котором работает клиент, выбирает один из готовых подов и подменяет адрес назначения на IP этого пода.
3. **Доставка.** Дальше пакет идёт как обычно — напрямую в под, по плоской сети.

Правила для шага 2 пишет <Term id="kube-proxy" />. Несмотря на название, он не прокси: через него не проходит ни байта трафика. Он следит за Service-ами и EndpointSlice-ами и переписывает правила iptables, IPVS или nftables на своём узле. Работу делает ядро.

Отсюда два следствия.

**ClusterIP нельзя пингнуть.** За ним нет ни машины, ни интерфейса — только правила для конкретных портов. `ping 10.96.14.2` молчит, и это нормально. Проверять сервис нужно запросом на его порт.

**Под выбирается один раз на соединение.** Ядро делает выбор, когда открывается TCP-соединение, и дальше все пакеты этого соединения идут в тот же под. Для коротких соединений это хорошая балансировка. А вот для долгих…

## Долгие соединения и gRPC

  ]}
  answer={1}

gRPC работает поверх HTTP/2 и отправляет все запросы через одно долгое TCP-соединение. Каждый под A открыл одно соединение — kube-proxy выбрал для него под B — и дальше тысячи запросов в секунду идут по этому соединению в тот же под. Два клиента — два соединения — два загруженных пода B. Остальные восемь получают трафик, только если соединение порвётся.

Хуже того, новые поды, добавленные автомасштабированием, не получат ничего: существующие соединения к ним не переоткроются. HPA добавляет поды, а нагрузка на старые не падает.

То же, в меньшей степени, случается и с HTTP/1.1: `http.Client` в Go держит соединения открытыми (keep-alive) и переиспользует их. При небольшом числе клиентов нагрузка распределяется заметно неровно.
</Predict>

Корень проблемы в том, что балансировщик на уровне соединений (L4) не видит отдельных запросов. Решений три.

**Балансировка на клиенте.** Клиент сам узнаёт адреса всех подов и раскидывает запросы между ними. Для этого нужен <Term id="headless-service">headless Service</Term> — сервис без ClusterIP, чей DNS отдаёт адреса всех готовых подов сразу:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: b-headless
spec:
  clusterIP: None          # вот что делает его headless
  selector: {app: b}
  ports: [{name: grpc, port: 9090}]
```

```go
conn, err := grpc.NewClient(
	"dns:///b-headless.prod.svc.cluster.local:9090",
	grpc.WithDefaultServiceConfig(`{"loadBalancingConfig": [{"round_robin":{}}]}`),
	grpc.WithTransportCredentials(insecure.NewCredentials()),
)
```

Клиент откроет соединение к каждому поду и будет раздавать запросы по кругу. Нюанс: DNS-резолвер gRPC перечитывает адреса не постоянно, а при разрыве соединений. Чтобы клиенты узнавали о новых подах, на сервере ставят `MaxConnectionAge` — сервер периодически мягко закрывает соединения, и клиенты переподключаются, заново спрашивая DNS:

```go
srv := grpc.NewServer(grpc.KeepaliveParams(keepalive.ServerParameters{
	MaxConnectionAge:      5 * time.Minute,
	MaxConnectionAgeGrace: 30 * time.Second,
}))
```

**Балансировщик L7.** Прокси, который понимает HTTP/2 и раздаёт отдельные запросы, — Envoy, ingress-контроллер, service mesh (Istio, Linkerd). Mesh ставит sidecar-прокси рядом с каждым подом и решает задачу для всех сервисов сразу — но ценой ещё одного компонента, который нужно понимать и обслуживать.

**Ограничить время жизни соединений** — тот же `MaxConnectionAge` и без headless-сервиса. Грубо, но уже лучше: соединения периодически перераспределяются.

## DNS: одна настройка, которая стоит знать

Внутри пода в `/etc/resolv.conf` записано примерно такое:

```
search prod.svc.cluster.local svc.cluster.local cluster.local
options ndots:5
```

`ndots:5` означает: если в имени меньше пяти точек, сначала попробовать его с каждым суффиксом из `search`. Запрос на `api.stripe.com` (две точки) превращается в серию: `api.stripe.com.prod.svc.cluster.local`, `api.stripe.com.svc.cluster.local`, `api.stripe.com.cluster.local` — и только потом `api.stripe.com`. Каждый — отдельный запрос в CoreDNS, да ещё и по два (A и AAAA).

Для сервиса, который много ходит во внешние API, это заметная задержка и нагрузка на DNS. Лечится точкой в конце имени (`api.stripe.com.` — полное имя, суффиксы не пробуются) или настройкой пода:

```yaml
spec:
  dnsConfig:
    options: [{name: ndots, value: "2"}]
```

## Типы Service

Всё, о чём говорили выше, — тип `ClusterIP`, адрес внутри кластера. Есть ещё три:

- **NodePort** — вдобавок открывает порт из диапазона 30000–32767 на каждом узле. Пришло на `<любой узел>:31080` — ушло в под. Сам по себе используется редко, чаще как строительный блок.
- **LoadBalancer** — вдобавок просит облако создать внешний балансировщик, который смотрит на этот сервис. Один сервис — один облачный балансировщик и один внешний IP. Для десятка HTTP-сервисов это дорого и неудобно.
- **ExternalName** — просто DNS-псевдоним: `postgres` → `mydb.abc123.eu-west-1.rds.amazonaws.com`. Удобно, чтобы код обращался к внешней базе по «внутреннему» имени.

## Вход снаружи: Ingress и Gateway API

Для HTTP-трафика снаружи обычно заводят одну точку входа, которая разбирает запросы по доменам и путям. Это <Term id="k8s-ingress">Ingress</Term>:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: public
spec:
  ingressClassName: nginx
  tls:
    - hosts: [api.example.com]
      secretName: api-example-com-tls
  rules:
    - host: api.example.com
      http:
        paths:
          - path: /v1
            pathType: Prefix
            backend: {service: {name: api, port: {name: http}}}
```

Важно понимать: объект Ingress — это только описание. Работает **ingress-контроллер** — обычный Deployment с прокси (nginx, Envoy, Traefik), стоящий за одним Service типа LoadBalancer. Он читает все Ingress-ы в кластере и настраивает себя. Если контроллер не установлен, Ingress-ы просто лежат в API и ничего не делают.

У Ingress бедная модель: хост, путь, TLS. Всё остальное — таймауты, лимиты, канареечные выкатки — задавалось аннотациями, у каждого контроллера своими. Поэтому появился его преемник — **Gateway API**:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: api
spec:
  parentRefs: [{name: public-gateway, namespace: infra}]
  hostnames: [api.example.com]
  rules:
    - matches: [{path: {type: PathPrefix, value: /v1}}]
      backendRefs:
        - {name: api, port: 80, weight: 90}
        - {name: api-canary, port: 80, weight: 10}   # 10% трафика — на новую версию
```

Он разделяет роли: команда платформы описывает `Gateway` — точку входа, порты, сертификаты; команда сервиса пишет свои `HTTPRoute` или `GRPCRoute`. Разделение трафика по весам, заголовкам, gRPC-методам — это поля, а не аннотации. Новые кластеры стоит начинать сразу с Gateway API. Тем более что самый популярный контроллер Ingress, ingress-nginx, сообщество Kubernetes сняло с поддержки.

<Callout title="Таймауты ingress и мягкая остановка">
Ingress-контроллер — ещё одно место, которое узнаёт о смерти пода с задержкой. Поэтому пауза перед остановкой из прошлой лекции нужна и здесь. А ещё у контроллера свои таймауты: у nginx по умолчанию 60 секунд на ответ. Запрос, который ваш сервис обрабатывает 90 секунд, клиент никогда не дождётся — он получит 504 от ingress, хотя сервис честно доработает.
</Callout>

## NetworkPolicy: закрыть лишнее

По умолчанию в кластере **разрешено всё**: любой под может соединиться с любым другим, в любом namespace. Взломали один сервис — получили сетевой доступ к базам всех остальных.

<Term id="network-policy">NetworkPolicy</Term> — это файрвол на уровне подов. Обычная схема — запретить всё входящее, а потом разрешать точечно:

```yaml
# 1. В namespace prod по умолчанию никто ни к кому не ходит
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: default-deny-ingress, namespace: prod}
spec:
  podSelector: {}          # все поды namespace
  policyTypes: [Ingress]
---
# 2. К подам api можно только с ingress-контроллера и только на порт 8080
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: {name: api-from-ingress, namespace: prod}
spec:
  podSelector: {matchLabels: {app: api}}
  ingress:
    - from:
        - namespaceSelector: {matchLabels: {kubernetes.io/metadata.name: ingress-nginx}}
      ports: [{port: 8080}]
```

Две вещи, о которых стоит помнить:

- **политики исполняет CNI-плагин.** Calico и Cilium исполняют, Flannel — нет: объекты создаются, но ничего не блокируют. Проверьте, прежде чем полагаться;
- **ограничивая исходящий трафик, разрешите DNS.** Политика на `Egress` без разрешения UDP и TCP на порт 53 до CoreDNS ломает разрешение имён, и всё падает с загадочными ошибками.

## Что из этого следует для сервиса на Go

- **Обращайтесь к сервисам по DNS-имени**, никогда по IP пода. Внутри namespace — короткое имя, между namespace — `имя.namespace`.
- **gRPC между сервисами — через headless Service и `round_robin`**, плюс `MaxConnectionAge` на сервере. Или через mesh, если он уже есть.
- **`http.Client` — один на приложение, с таймаутом.** Переиспользуйте соединения, но помните, что долгоживущие keep-alive-соединения к небольшому числу подов дают перекос нагрузки. `IdleConnTimeout` ограничивает их жизнь.
- **Внешние имена — с точкой в конце** или `ndots` поменьше, если во внешние API ходите много.
- **Таймауты сервиса меньше таймаутов ingress**, иначе клиент уйдёт раньше, чем вы ответите.
- **Default-deny NetworkPolicy** в продакшен-namespace и явные разрешения для каждого сервиса.

## Итог

- В кластере плоская сеть: у каждого пода свой IP, и все поды видят друг друга напрямую.
- [Service](/glossary/k8s-service/) даёт группе подов постоянный виртуальный IP и DNS-имя. Кто за ним стоит — видно в [EndpointSlice](/glossary/endpoint-slice/); туда попадают только готовые поды.
- [kube-proxy](/glossary/kube-proxy/) не прокси, а программист правил ядра. Под выбирается один раз на TCP-соединение.
- Поэтому долгие соединения — gRPC, HTTP/2, keep-alive — балансируются плохо. Решение — [headless Service](/glossary/headless-service/) и балансировка на клиенте, L7-прокси или mesh.
- Снаружи трафик приходит через [Ingress или Gateway API](/glossary/k8s-ingress/) — описание маршрутов, которое исполняет отдельный контроллер.
- По умолчанию сеть открыта; [NetworkPolicy](/glossary/network-policy/) закрывает её, если CNI-плагин её поддерживает.

Мы научились запускать, обновлять и находить поды. Но пока не сказали ни слова о том, сколько им можно есть. В следующей лекции — requests и limits: почему под с загрузкой 30% тормозит, почему он внезапно умирает с кодом 137 и что Go-программе нужно знать о своём контейнере.
