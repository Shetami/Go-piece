Написать систему — половина работы. Вторая половина — годами менять её, не останавливая: добавлять поля, переименовывать сущности, менять формат событий, переезжать с одной базы на другую. И всё это пока по системе идут запросы, а в топиках лежат сообщения, записанные прошлой версией кода.

Главная мысль лекции простая, и из неё следует всё остальное: **в каждый момент времени в системе живёт больше одной версии всего**. Две версии кода во время выкатки. Старые строки в базе и новые. Старые сообщения в топике и новые. Мобильные клиенты, которые обновятся через полгода. Любое изменение должно быть совместимо со всем, что может с ним встретиться.

## Две версии одновременно

<Term id="rolling-update">Выкатка</Term> в Kubernetes заменяет поды по одному. Несколько минут часть запросов обслуживает старый код, часть — новый. А если новый код оказался сломан, откат возвращает старый — к той схеме базы, которую успел поменять новый.

Отсюда правило для миграций схемы: **схема должна работать и с текущей версией кода, и с предыдущей**. На практике это значит, что миграцию выполняют до выкатки кода, и она только добавляет — ничего не удаляет и не переименовывает из того, что использует работающий код.

Переименование действительно мгновенное — и именно поэтому опасное. Сразу после миграции старые поды, которые ещё обслуживают трафик, выполняют `SELECT name FROM users` и получают `column "name" does not exist`. Выкатка десяти подов идёт несколько минут, и все эти минуты часть запросов падает.

Хуже того: если в новом коде найдётся баг и выкатку откатят, старый код вернётся к схеме, в которой колонки `name` уже нет, — и сломается полностью. Изменение, которое ломает совместимость в одну сторону, превращает откат из спасения в аварию.
</Predict>

## Переименование в шесть шагов

Безопасный способ — <Term id="expand-contract">расширение и сжатие</Term>. Вместо одного изменения — несколько, каждое совместимо с соседними версиями кода.

<ExpandContract />

1. **Расширить.** Миграция добавляет `full_name`. Старый код её не замечает.
2. **Двойная запись.** Новый код пишет и в `name`, и в `full_name`, читает по-прежнему `name`.
3. **Заполнить.** Отдельная задача переносит `name` в `full_name` для старых строк.
4. **Читать новое.** Код читает `full_name`, но всё ещё пишет в обе колонки — откат на шаг назад безопасен.
5. **Перестать писать** в `name`.
6. **Сжать.** Миграция удаляет `name`, когда старого кода, который её использует, точно нигде нет.

Шесть выкаток вместо одной. Поэтому переименование делают, только когда без него действительно нельзя, а для удобства чтения хватает псевдонима в коде. Но когда нужно поменять тип колонки, разделить одну таблицу на две или перенести поле в другой сервис — схема та же.

## Даже добавить — не всегда безопасно

Кажется, что добавление колонки совместимо всегда. Не совсем.

`RowToStructByName` в pgx возвращает ошибку, если в результате есть колонка, для которой в структуре нет поля. `SELECT *` после миграции возвращает на одну колонку больше, чем знает старый код, — и все чтения заказов в старых подах падают. Есть вариант `RowToStructByNameLax`, который такое допускает, но надёжнее не использовать `SELECT *` в коде вовсе: явный список колонок делает запрос независимым от того, что добавили в таблицу.

Та же проблема бывает в обратную сторону: колонку добавили с `NOT NULL` без значения по умолчанию, а старый код делает `INSERT` без неё — и все вставки в старых подах падают. Новая колонка должна быть необязательной или иметь умолчание, пока весь код не начнёт её заполнять.
</Predict>

Удаление — зеркальная история. Сначала выкатывается код, который колонку не использует нигде: ни в запросах, ни в структурах, ни в ORM, которая может кэшировать список колонок. Потом — через выкатку или две — миграция, которая её удаляет. Удалять колонку в том же релизе, где из кода убрали последнее обращение, нельзя: во время выкатки старые поды ещё работают.

## Заполнить данные на живой таблице

Третий шаг схемы — <Term id="backfill">бэкфилл</Term>: перенести данные для миллионов старых строк. Один `UPDATE users SET full_name = name` на большой таблице — это часы блокировок, гигабайты WAL, отстающие реплики и таблица, раздутая вдвое. Бэкфилл делают отдельной задачей, пачками:

```go
// Прогресс хранится в базе: задачу можно остановить и продолжить.
last, err := loadProgress(ctx, "users_full_name")
if err != nil {
    return err
}
for {
    var maxID *int64 // NULL — пачка пуста, таблица пройдена
    err := pool.QueryRow(ctx, `
        WITH batch AS (
            SELECT id FROM users WHERE id > $1 ORDER BY id LIMIT 5000
        ), upd AS (
            UPDATE users u SET full_name = u.name
            FROM batch
            WHERE u.id = batch.id
              AND u.full_name IS NULL -- не затирать то, что уже записал новый код
        )
        SELECT max(id) FROM batch`, last).Scan(&maxID)
    if err != nil {
        return err
    }
    if maxID == nil {
        return nil
    }
    last = *maxID
    if err := saveProgress(ctx, "users_full_name", last); err != nil {
        return err
    }
    time.Sleep(throttle(ctx)) // пауза по отставанию реплик
}
```

Детали меняются от задачи к задаче, но четыре свойства нужны всегда: короткие транзакции, пауза, сохранённый прогресс и условие, которое не перезаписывает свежие данные.

## Контракты API

С базой проще, чем с API: схему базы вы меняете сами, а клиентов API — нет. Мобильное приложение, выпущенное год назад, всё ещё у кого-то установлено и всё ещё вызывает ваш API. Внешний партнёр обновит интеграцию, когда у него дойдут руки.

Для API и событий действуют правила <Term id="schema-compatibility">совместимости</Term>:

- добавлять можно только **необязательное**. Новое обязательное поле в запросе ломает всех старых клиентов;
- удалять и переименовывать нельзя, пока старые клиенты живы. Переименование — это удаление плюс добавление;
- **новое значение в enum — ломающее изменение**, хотя выглядит как добавление. Клиент с `switch` без ветки `default` не знает, что делать со статусом `partially_refunded`;
- менять смысл поля нельзя никогда. `amount` в рублях, ставший `amount` в копейках, — это авария, которую не поймает ни один валидатор.

Go помогает с первым пунктом: `encoding/json` по умолчанию игнорирует незнакомые поля, так что добавление полей в ответ не ломает клиентов на Go. `DisallowUnknownFields` делает клиента хрупким — его стоит применять к входящим запросам, а не к ответам зависимостей. В protobuf поле определяется номером, а не именем. Номер удалённого поля помечают `reserved`: иначе через год кто-нибудь займёт его новым полем, и старые клиенты прочитают его с чужим смыслом.

Когда ломающее изменение неизбежно — новая версия API рядом со старой (`/v2/orders`), метрики использования старой и её удаление, когда трафик на ней упал до нуля.

Топик — это не труба, а журнал. В нём лежат сообщения, записанные старой версией, и потребитель их прочитает: после ребаланса с незакоммиченного оффсета, после отката, при переигрывании с начала, при запуске нового потребителя с `earliest`. Все эти сообщения должны разбираться новым кодом — всё время retention, а для компактифицированных топиков — всегда.

Правильный путь — то же расширение: добавить `money` рядом с `price`, какое-то время писать оба, научить потребителей читать оба формата, и только потом перестать писать `price`. Реестр схем с режимом совместимости `BACKWARD` не дал бы зарегистрировать ломающую схему вовсе — ошибку поймал бы CI, а не прод.

И ещё одно следствие: потребители разных команд обновляются в разном темпе. Продюсер не может «выкатиться одновременно» со всеми потребителями, которых он даже не знает. Поэтому для событий обычно требуют совместимости в обе стороны: новые потребители читают старые события, старые потребители — новые.

## Выкатить не значит включить

<Term id="feature-flag">Флаг функциональности</Term> разделяет два события, которые обычно происходят одновременно: код доставлен и функция включена.

```go
if flags.Enabled(ctx, "checkout.new-pricing", user.ID) {
    price, err = pricingV2.Calculate(ctx, cart)
} else {
    price, err = pricing.Calculate(ctx, cart)
}
```

Что это даёт:

- **постепенное включение** — 1% пользователей, потом 10%, потом все, и между шагами — взгляд на метрики ошибок и задержки;
- **выключение за секунды** — без отката выкатки, без ожидания сборки и пайплайна;
- **аварийные выключатели** — постоянные флаги для дорогих функций: при перегрузке выключить рекомендации, а не уронить оформление заказа. Это инструмент <Term id="graceful-degradation">деградации</Term>.

Цена — долг. Каждый временный флаг — две ветки кода, и комбинации десятков флагов никто не тестирует. У флага выпуска должен быть владелец и срок, после которого флаг и старая ветка удаляются.

## Переезд на другое хранилище

Самое большое изменение — перенос данных в другое хранилище: из монолитной базы в базу сервиса, из PostgreSQL в Cassandra, из одного кластера в другой. Остановить систему на время переноса нельзя, поэтому переезд делают тем же расширением, только крупнее:

1. **Двойная запись.** Код пишет и в старое, и в новое. Источник правды — старое; ошибка записи в новое логируется, но не ломает запрос.
2. **Перенос истории** — бэкфилл из старого в новое.
3. **Теневое чтение.** Код читает из обоих, отдаёт результат старого, а расхождения пишет в метрики. Это главный шаг: он показывает, что новое хранилище возвращает то же самое, на реальном трафике.
4. **Переключение чтения** — под флагом, по процентам.
5. **Смена источника правды** — теперь основная запись в новое.
6. **Отключение старого.**

Двойная запись в два хранилища не атомарна: одна запись может пройти, а вторая — нет. Это та же проблема, что и запись в базу с отправкой события, — её разбирает лекция о <Term id="transactional-outbox">согласованности между сервисами</Term>. На время переезда с расхождениями живут, но их считают, чинят сверкой и не переключаются, пока теневое чтение не покажет, что расхождений нет.

## Откат

Последнее — про путь назад. Откатить код легко, откатить данные почти невозможно. Миграция, которая удалила колонку, не откатывается — данных уже нет. Поэтому:

- миграции делают **только вперёд**: «откатная» миграция, которая заново создаёт удалённую колонку, возвращает схему, но не данные;
- откат кода должен быть безопасен всегда, и это проверяется до выкатки: совместим ли предыдущий релиз с новой схемой;
- необратимые шаги — удаление колонок, таблиц, старых форматов — отделяют от остальных изменений и делают, когда в откате уже точно не будет нужды;
- если откат невозможен, чинят вперёд: быстрый исправляющий релиз, а до него — флаг, который выключает сломанное.

## Итог

- Во время выкатки и отката работают две версии кода сразу. Схема должна быть совместима с обеими — миграция перед выкаткой, и только добавляет.
- Ломающие изменения делают через [расширение и сжатие](/glossary/expand-contract/): добавить новое, писать в оба, [заполнить](/glossary/backfill/), читать новое, перестать писать старое, удалить.
- Даже добавление колонки ломает `SELECT *` со строгим сканированием в структуру и `INSERT` без новой `NOT NULL`-колонки. Явный список колонок и необязательные новые колонки.
- В API и событиях добавляют только необязательное. Новое значение enum — ломающее изменение. Номера полей protobuf не используют повторно. [Совместимость](/glossary/schema-compatibility/) событий проверяет реестр схем.
- Старые события живут в топике всё время retention, и новый код обязан их читать.
- [Флаг](/glossary/feature-flag/) разделяет выкатку и включение: проценты, быстрое выключение, аварийные выключатели. Временные флаги удаляют по сроку.
- Переезд хранилища — двойная запись, перенос истории, теневое чтение, переключение по флагу.
- Данные не откатываются. Миграции — только вперёд, необратимые шаги — отдельно и в последнюю очередь.
