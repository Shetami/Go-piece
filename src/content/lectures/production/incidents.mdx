Предыдущие лекции курса разбирали механизмы по одному: пул соединений, очередь блокировок, ребаланс, idle-таймаут. В проде они редко ломаются по одному. Инцидент, который действительно трудно разобрать, почти всегда складывается из двух-трёх вещей, каждая из которых по отдельности безобидна: проба живости плюс холодный кэш, блокировка с TTL плюс пауза процесса, выкатка плюс TTL кэша.

Эта лекция — разборы таких случаев. Они собирательные: детали изменены, но каждый сценарий многократно встречается в реальных постмортемах. У каждого одна и та же структура:

- **симптом** — что увидели на дашбордах и от пользователей;
- **первая гипотеза** — что проверили сначала и почему это оказалось не то;
- **причина** — что было на самом деле и почему такое вообще возможно;
- **как выходили** — что сделали срочно, чтобы остановить ущерб;
- **что поменяли** — что сделали, чтобы это не повторилось.

Первая гипотеза здесь важна не меньше ответа. Именно она съедает первый час инцидента, и научиться её отбрасывать — половина навыка.

## Пики ровно раз в час

**Симптом.** После обычной выкатки у сервиса каталога появились всплески задержки: p99 подскакивает с 40 мс до 1,5 секунды на 10–20 секунд, и так ровно раз в час. Нагрузка на базу в эти секунды вырастает в восемь раз. Время пиков сдвинуто относительно начала часа — 14:07, 15:07, 16:07.

**Первая гипотеза.** Cron-задача: что-то запускается раз в час и нагружает базу. Проверили расписания — ничего на :07 нет. Пики начались после выкатки, но в изменениях нет ничего про расписание.

**Причина.** Выкатка закончилась в 13:07. Все 40 подов стартовали в одну и ту же минуту с пустым локальным кэшем и заполнили его в одну и ту же минуту. TTL записей — ровно час. Ровно через час все записи на всех подах истекают одновременно, и все поды одновременно идут в базу.

До выкатки поды перезапускались в разное время — после падений, при переездах между узлами, — и истечения были размазаны по часу. Выкатка их синхронизировала. Система, у которой есть одинаковый период и общий момент старта, превращает равномерную нагрузку в пики. Механизм описан в разделе про [одновременное истечение](/lectures/system-design/caching/) — здесь тот же эффект, только синхронизирующим событием стала выкатка, а не массовая запись.

Та же ловушка встречается в других местах:

- `time.NewTicker(time.Minute)` на всех подах, стартовавших вместе, — фоновые задачи бьют в зависимость синхронно;
- мобильные клиенты, которые обновляют данные «каждые 15 минут от начала часа», или токены, выданные всем при старте и истекающие одновременно;
- cron `0 * * * *` у десяти разных команд — все считают, что «в начале часа» база свободна.

**Как выходили.** Перезапустили поды по одному с интервалом в полторы минуты — это размазало истечения по часу. Пики пропали до следующей выкатки.

**Что поменяли.** Добавили случайный разброс везде, где есть период:

```go
// TTL с разбросом ±10%: записи, созданные одновременно, истекают в разное время.
func jitter(d time.Duration) time.Duration {
    return d - d/10 + time.Duration(rand.Int64N(int64(d/5)))
}

cache.Set(key, value, jitter(time.Hour))
```

Фоновые циклы начинают со случайной задержки, cron-задачи ставят на случайную минуту, а горячие ключи обновляют заранее в фоне (<Term id="stale-while-revalidate">stale-while-revalidate</Term>), чтобы истечение вообще не приводило к запросу в базу на пути пользователя. Периодичность в метриках с периодом, равным какому-то TTL или интервалу в конфиге, — теперь первое, что проверяют.

## Пустая корзина на час

**Симптом.** Поддержка получает жалобы: у части пользователей пустая корзина. Через час сами собой всё возвращается. Ошибок в логах нет, 5xx нет, все метрики зелёные.

**Первая гипотеза.** Потеря данных в сервисе корзины. Проверили базу — все корзины на месте. Проверили репликацию — отставания нет.

**Причина.** За час до жалоб у сервиса корзины была минута деградации: часть запросов упиралась в таймаут. BFF — сервис, собирающий страницу для фронтенда, — вызывал корзину через функцию, которая выглядела так:

```go
func (c *Client) GetCart(ctx context.Context, userID string) Cart {
    cart, err := c.fetch(ctx, userID)
    if err != nil {
        c.log.Warn("cart fetch failed", "err", err)
        return Cart{} // не ломать страницу — показать пустую корзину
    }
    return cart
}
```

Само по себе это разумная <Term id="graceful-degradation">деградация</Term>: лучше страница без корзины, чем страница с ошибкой. Но выше по стеку стоял кэш с TTL в час, и он получил от `GetCart` обычное значение — пустую корзину. Для кэша это не отличается от настоящей пустой корзины. Минута сбоя превратилась в час неверных данных, и ни одна метрика ошибок этого не увидела: с точки зрения всех сервисов запросы были успешны.

Корень — в типе. Функция стёрла разницу между «корзина пустая» и «я не знаю, что в корзине». Как только эти два состояния выглядят одинаково, любой код выше — кэш, агрегатор, расчёт суммы — будет обращаться с незнанием как с фактом.

Родственные случаи:

- CDN или кэш на балансировщике закэшировали ответ 502 или страницу-заглушку;
- поиск по индексу вернул пустой результат во время переиндексации, и он закэширован как «ничего не найдено»;
- значение по умолчанию из конфигурации при недоступном сервисе конфигурации (например, лимит `0` вместо реального) сохранено как настоящее.

**Как выходили.** Сбросили кэш корзин. Для этого пришлось срочно писать скрипт: механизма инвалидации по префиксу не было.

**Что поменяли.**

- Функции клиентов возвращают ошибку, а решение о заглушке принимается там, где собирается ответ пользователю, — выше кэша. В кэш попадают только настоящие данные:

  ```go
  cart, err := carts.GetCart(ctx, userID) // ошибка не прячется
  if err != nil {
      page.Cart = nil        // шаблон покажет «корзина временно недоступна»
      page.Degraded = true   // и этот ответ не кэшируется
  }
  ```

- Кэш не сохраняет ответы, помеченные как деградированные. Если отрицательные результаты кэшировать нужно — например, «товар не найден», — у них отдельный короткий TTL в секунды, а не час.
- Счётчик деградированных ответов стал метрикой с алертом. Ответ-заглушка — это частичный отказ, и он должен быть виден как отказ.
- У ключей кэша появилась версия (`cart:v3:{user}`): смена версии в конфиге мгновенно делает все старые записи недостижимыми, без скриптов.

## Один узел Redis на 100%

**Симптом.** В Redis Cluster шесть мастеров. Один из них загружен на 100% процессора, остальные — на 8–12%. Задержка команд к этому узлу — десятки миллисекунд, и от неё растёт p99 всех сервисов, которые ходят в Redis, даже тех, кто этот узел почти не использует.

**Первая гипотеза.** Перекос слотов: на узле оказалось больше данных. Проверили — памяти и ключей на всех узлах примерно поровну. Добавили седьмой мастер и перенесли на него часть слотов с горячего узла. Не помогло: процессор горячего узла не изменился.

**Причина.** Горячий ключ. На каждый запрос каждого сервиса читался один ключ — `feature_flags`, хэш с конфигурацией функций. 60 тысяч чтений в секунду одного ключа. Ключ живёт в одном <Term id="redis-hash-slot">слоте</Term>, слот — на одном узле, а Redis выполняет команды в <Term id="redis-event-loop">одном потоке</Term>. Шардирование делит ключи, но не может разделить один ключ, поэтому добавление узлов ничего не дало. Та же проблема, что и с <Term id="hot-partition">горячей партицией</Term>: у распределения нагрузки по ключу есть предел, равный мощности одного шарда.

А почему страдали остальные: клиенты держат ограниченный пул соединений к каждому узлу, и медленный узел увеличивает время жизни команд в конвейере. Сервисы, которые делали `MGET` по ключам в разных слотах, ждали самого медленного узла.

Найти такой ключ помогает `redis-cli --hotkeys` — но только при политике вытеснения на основе LFU (`maxmemory-policy allkeys-lfu`), потому что он читает счётчики частоты обращений. Без этого остаётся `MONITOR` на несколько секунд (сам по себе заметно нагружает узел) или метрики на стороне клиента с префиксом ключа в метке — префиксом, а не самим ключом, иначе [кардинальность](/glossary/metric-cardinality/) метрики уронит Prometheus.

**Как выходили.** Добавили в сервисы локальный кэш флагов в памяти процесса на 5 секунд. Чтения из Redis упали с 60 тысяч до сотни в секунду (по одному на под раз в 5 секунд), узел остыл за минуту.

**Что поменяли.** Для горячих ключей есть три приёма, в порядке предпочтения:

1. **Кэш в процессе** с коротким TTL и <Term id="singleflight">singleflight</Term>, чтобы при истечении в Redis шёл один запрос с пода, а не сотня. Подходит для всего, что можно читать с опозданием на секунды: конфигурация, флаги, справочники.
2. **Копии ключа.** Значение пишется в N ключей (`flags:{0}` … `flags:{7}`) — фигурные скобки задают хэш-тег, и копии попадают в разные слоты. Читатель выбирает копию случайно. Запись дороже в N раз, чтение распределяется по узлам.
3. **Кэширование на стороне клиента** средствами самого Redis (`CLIENT TRACKING`, протокол RESP3): сервер запоминает, какие ключи читал клиент, и присылает уведомление об их изменении. Нужен клиент, который это поддерживает — например, rueidis.

И отдельное правило: данные, которые нужны на каждый запрос, не читают из сети на каждый запрос. Если значение одинаково для всех пользователей и меняется раз в минуты, его место — в памяти процесса.

## Больше ядер — медленнее

**Симптом.** Сервис перенесли с 8-ядерных узлов на 32-ядерные и увеличили лимит процессора пода в четыре раза. Пропускная способность пода вместо ожидаемого роста в 3–4 раза выросла на 20%, а p99 стал хуже. Загрузка процессора — около 40%, упора в CPU нет.

**Первая гипотеза.** <Term id="cpu-throttling">Троттлинг</Term> или неправильный <Term id="gomaxprocs">GOMAXPROCS</Term>. Проверили: троттлинга нет, `GOMAXPROCS` равен 32, как и должно быть. Профиль процессора ничего подозрительного не показывает — горячих функций нет, время размазано.

**Причина.** Конкуренция за мьютекс. В сервисе был кэш в памяти — обычная `map` под одним `sync.Mutex`, к которому обращался каждый запрос. На 8 ядрах критическая секция в 200 наносекунд почти не мешала. На 32 ядрах горутины начали выстраиваться в очередь к мьютексу.

Профиль процессора этого не показывает: ожидающая горутина не тратит процессор, она припаркована. Поэтому и загрузка 40% — большую часть времени горутины ждут. Видно это только в профиле мьютексов, который по умолчанию выключен:

```go
runtime.SetMutexProfileFraction(100) // каждое сотое событие конкуренции
// затем: go tool pprof http://host:6060/debug/pprof/mutex
```

В профиле почти всё время ожидания — в одной строке `cache.mu.Lock()`.

У мьютекса Go есть ещё одна особенность, которая делает эффект нелинейным. Если горутина ждёт мьютекс дольше миллисекунды, <Term id="mutex">мьютекс</Term> переходит в режим голодания: он передаётся строго по очереди, первому ожидающему, а новые горутины не могут перехватить его, даже если он свободен прямо сейчас. Это честно, но дорого: каждая передача — это пробуждение и переключение горутины. Пропускная способность мьютекса в режиме голодания падает, очередь растёт, и система застревает в этом режиме.

**Как выходили.** Откатились на 8-ядерные узлы и увеличили число подов — горизонтальное масштабирование не упирается в общий мьютекс.

**Что поменяли.** Кэш разбили на шарды, у каждого — своя `map` и свой мьютекс:

```go
type shard struct {
    mu sync.Mutex
    m  map[string]Item
    _  [48]byte // 8 (mu) + 8 (m) + 48 = 64: один шард — одна кэш-линия
}

var seed = maphash.MakeSeed()

type Cache struct{ shards [64]shard }

func (c *Cache) shard(key string) *shard {
    return &c.shards[maphash.String(seed, key)%64]
}
```

64 независимых мьютекса почти не конкурируют между собой. Заполнитель в конце структуры нужен, чтобы соседние шарды не оказались в одной 64-байтной кэш-линии: иначе ядра, работающие с разными шардами, всё равно мешают друг другу — это называют ложным разделением (false sharing).

Другие частые источники той же проблемы: общий счётчик метрик под мьютексом (лечится атомиками или счётчиком на шард), логгер с синхронной записью в один `io.Writer` под блокировкой, `sync.Pool`, которым пользуются неправильно, самописный пул объектов на канале. Правило: всё, к чему обращается **каждый** запрос, на многоядерной машине становится узким местом, если к нему нужна общая блокировка. Смотреть нужно не только на профиль процессора, но и на профили мьютексов и блокировок (`/debug/pprof/mutex`, `/debug/pprof/block`).

## OOM без виноватого

**Симптом.** Раз в сутки-двое один из подов сервиса отчётов погибает с <Term id="oom-killed">OOMKilled</Term>. Время всегда разное. В метриках памяти перед падением — не плавный рост, как при утечке, а вертикальный скачок с 300 МБ до лимита в 2 ГБ за несколько секунд.

**Первая гипотеза.** Утечка памяти. Сняли профиль кучи с живых подов — ничего подозрительного, куча стабильна. Подняли лимит до 4 ГБ — поды стали падать реже, но всё равно падают.

**Причина.** Один запрос. Клиент с самой большой историей раз в сутки выгружал все свои заказы за всё время. Обработчик делал так:

```go
rows, _ := db.QueryContext(ctx, `SELECT ... FROM orders WHERE tenant_id = $1`, tenant)
var orders []Order
for rows.Next() { /* ... */ orders = append(orders, o) } // 2 млн строк в памяти
json.NewEncoder(w).Encode(orders)
```

Два миллиона структур в срезе, плюс удвоения ёмкости при `append`, плюс сериализация. Для остальных клиентов — тысячи строк и мегабайты. Для одного — гигабайты.

Главный вопрос этого инцидента — почему виноватого не было видно в логах. Строка в журнале запросов пишется, когда запрос завершается: там есть код ответа и длительность. Запрос, убивший процесс, не завершился никогда. Ядро убивает процесс сигналом `SIGKILL`, `defer` не выполняются, буферизованные логи теряются. В логах остаются только запросы, которые успели закончиться — то есть все, кроме нужного.

**Как нашли.** Сопоставили время падений с логами балансировщика: там запрос тоже записывается по завершении, но балансировщик-то жив, и он записал ответ 502 после разрыва соединения. У всех падений в предшествующие секунды был один и тот же `GET /export` одного клиента.

**Как выходили.** Временно ограничили экспорт периодом в 90 дней.

**Что поменяли.**

- Экспорт идёт потоком: строка из базы сразу пишется в ответ, память не зависит от объёма данных.

  ```go
  enc := json.NewEncoder(w)
  for rows.Next() {
      var o Order
      if err := rows.Scan(/* ... */); err != nil { /* ... */ }
      if err := enc.Encode(o); err != nil { return } // клиент ушёл
  }
  ```

  Для совсем больших выгрузок — асинхронная задача, которая пишет файл в объектное хранилище и присылает ссылку.

- У каждого запроса к базе, который отдаётся пользователю, есть жёсткий `LIMIT`, у каждого списка в API — максимальный размер страницы и <Term id="keyset-pagination">курсорная пагинация</Term>. Размер ввода тоже ограничен: `http.MaxBytesReader` и предел числа элементов в запросе.
- Тяжёлые эндпоинты вынесли в отдельный деплоймент — <Term id="bulkhead">переборку</Term>: теперь OOM экспорта не убивает обычные запросы, которые обслуживал тот же под.
- Для дорогих эндпоинтов лог пишется **в начале** запроса тоже, а `GOMEMLIMIT` выставлен ниже лимита контейнера — сборщик начинает работать активнее до того, как придёт ядро.

Урок шире этого случая: сервис со множеством клиентов обслуживает распределение, у которого длинный хвост. Нагрузочный тест со «средним клиентом» его не видит. Тестировать нужно и на самом большом клиенте, а лучше — ставить пределы, которые не зависят от размера клиента.

## 401 только с одного узла

**Симптом.** Около 0,5% запросов получают 401 «token is not valid yet». Повтор обычно проходит. Токены выдаёт сервис авторизации, проверяют — все сервисы. Разбивка по подам показала: все ошибки — у подов на двух узлах кластера из тридцати.

**Первая гипотеза.** Проблема в выдаче токенов или ротации ключей подписи. Но тогда ошибки были бы на всех узлах.

**Причина.** Часы. На двух узлах перестала работать синхронизация времени — после обновления образа узла сломалась конфигурация chrony, — и их часы за неделю ушли назад на 4 секунды. Токен, выданный сервисом авторизации, содержит поле `iat` и `nbf` — «действителен начиная с» — со временем выдачи. Сервис на отстающем узле проверяет `nbf` по своим часам и видит токен из будущего. Ошибка возникает только у токенов моложе 4 секунд — а это как раз свежевыданные токены, первый запрос после входа.

Часы на разных машинах никогда не совпадают точно. При работающей синхронизации расхождение — миллисекунды, без неё — секунды в сутки. Всё, что сравнивает время, записанное на одной машине, со временем другой машины, ломается от этого:

- проверка сроков действия токенов, подписанных ссылок, сертификатов;
- «последняя запись побеждает» по отметке времени — запись с отстающего узла проиграет более ранней записи с правильного узла, и обновление потеряется;
- сортировка событий из разных сервисов по времени — в логах причина окажется после следствия;
- таймауты блокировок и аренд, выраженные как момент истечения, а не как длительность.

Внутри одного процесса Go защищает от части этого: `time.Now()` содержит показания монотонных часов, и `time.Since`, `t.Sub(u)` используют именно их — переводы системных часов на длительности не влияют. Но монотонные показания не переживают сериализацию: время, записанное в JSON, базу или заголовок, — это всегда показания обычных часов той машины, где его записали.

**Как выходили.** Выселили поды с двух узлов (`kubectl drain`) и починили синхронизацию.

**Что поменяли.**

- Проверка токенов допускает расхождение: в golang-jwt это `jwt.WithLeeway(30 * time.Second)`. Допуск в десятки секунд — стандартная практика, он не ослабляет безопасность заметно.
- Появился алерт на смещение часов узла: node_exporter отдаёт `node_timex_offset_seconds` и `node_timex_sync_status`. Смещение больше 100 мс или потеря синхронизации — предупреждение.
- Порядок событий между машинами определяется не отметкой времени, а версией: номер версии строки, оффсет в Kafka, последовательность из базы.

## Двойное выполнение под блокировкой

**Симптом.** Ежечасная задача начисления процентов по вкладам запускается на всех подах, но выполняется одним — под распределённой блокировкой в Redis с TTL в 60 секунд. Обычно задача занимает 10 секунд. Однажды часть клиентов получила проценты дважды.

**Первая гипотеза.** Ошибка в блокировке: два пода одновременно получили `SET lock NX`. Проверили код — `SET NX PX` атомарен, два клиента не могут получить его одновременно.

**Причина.** Два пода получили блокировку не одновременно, а по очереди. Под A взял блокировку и начал работу. В середине задачи его процесс остановился на 70 секунд: узел был перегружен, и под попал под жёсткий троттлинг (в других версиях этой истории — долгая пауза сборки мусора в JVM, живая миграция виртуальной машины, `SIGSTOP` отладчиком, сетевая изоляция). Через 60 секунд TTL истёк, и блокировку взял под B. Он начислил проценты. Потом процесс A проснулся — и продолжил с того места, где остановился, уверенный, что блокировка всё ещё у него.

Проверка «блокировка ещё моя?» перед записью не спасает: между проверкой и записью процесс может остановиться снова. Это принципиальное свойство <Term id="distributed-lock">распределённой блокировки</Term> с арендой: держатель не может знать, что аренда ещё действует, в момент, когда его запись доходит до хранилища. Подробно механизм и вокруг него — Redlock — разобран в [лекции о Redis](/lectures/databases/redis/).

**Как выходили.** Нашли двойные начисления по журналу операций и откатили компенсирующими проводками.

**Что поменяли.** Защиту перенесли туда, где происходит запись.

- **Токен ограждения.** При каждом взятии блокировки выдаётся номер, который только растёт (`INCR` в Redis рядом с блокировкой, или последовательность в базе). Хранилище принимает запись, только если номер не меньше последнего, который оно видело:

  ```sql
  UPDATE jobs SET last_fence = $2, finished_at = now()
  WHERE name = 'interest' AND last_fence < $2;
  -- 0 строк → кто-то с более свежим токеном уже работал, выходим
  ```

  Проснувшийся под A с токеном 41 получит отказ, потому что B уже записал 42.

- **Идемпотентность операции.** Главное исправление — не блокировка, а уникальное ограничение: `UNIQUE (account_id, period)` в таблице начислений. Второе начисление за тот же период база просто не примет. Блокировка остаётся как оптимизация — чтобы поды не делали лишнюю работу, — но корректность от неё больше не зависит.

Общее правило: распределённая блокировка годится, чтобы **уменьшить** дублирование работы, но не чтобы **гарантировать** его отсутствие. Если двойное выполнение недопустимо, гарантию даёт хранилище — ограничение уникальности, условная запись, транзакция, — а не блокировка рядом с ним.

## База поднялась за минуту, сервис лежал час

Самый дорогой тип инцидента — когда причина давно устранена, а система не может вернуться в рабочее состояние. Это <Term id="metastable-failure">метастабильный отказ</Term>: у системы есть два устойчивых состояния, и короткий толчок переводит её из хорошего в плохое, из которого она сама не выходит.

**Симптом.** Основная база PostgreSQL переключилась на реплику. <Term id="failover">Переключение</Term> заняло 40 секунд. После этого API не отвечал 55 минут. Новая база при этом была исправна, и её процессор большую часть этого времени был загружен на 100%, а в логах — тысячи `FATAL: sorry, too many clients already`.

**Первая гипотеза.** Новый мастер слабее старого или у него холодный кэш страниц. Отчасти верно, но это объясняет минуты медленной работы, а не час простоя.

**Причина.** Четыре механизма, каждый из которых разумен сам по себе, замкнулись в петлю:

1. **Пулы соединений.** В сервисе 300 подов, у каждого `MaxOpenConns = 20`. В обычной жизни каждому поду хватает 2–3 соединений, в сумме ~800 при `max_connections = 1000`. Во время переключения запросы копились в очереди каждого пода, и после восстановления каждый под попытался открыть все 20 — это 6000 попыток. Каждое новое соединение в PostgreSQL — это новый процесс, аутентификация и TLS-рукопожатие. База тратила процессор на установку соединений, большинству из которых отказывала.
2. **Повторы.** Каждый упавший запрос повторялся трижды без случайного разброса, и клиенты мобильного приложения тоже повторяли. Входящий поток вырос в несколько раз — ровно тогда, когда база могла меньше обычного. Это <Term id="retry-backoff">шторм повторов</Term>.
3. **Проба живости.** <Term id="liveness-probe">Liveness-проба</Term> сервиса делала `SELECT 1` в базу. База отвечала медленно, пробы проваливались, Kubernetes начал перезапускать поды. Перезапуск — это пустой пул (снова 20 новых соединений) и пустой локальный кэш.
4. **Холодный кэш.** Локальный кэш в памяти подов обычно снимал с базы 85% чтений. Перезапущенные поды его потеряли, и все чтения пошли в базу. Нагрузка на базу выросла в шесть раз — прогреть кэш было нечем, потому что база не отвечала.

Каждый цикл «под перезапустился → открыл 20 соединений → не смог обслужить запросы из-за пустого кэша → провалил пробу → перезапустился» подпитывал следующий. База не могла восстановиться, потому что восстановление подов её добивало.

<Predict
  question="Дежурный видит: база перегружена установкой соединений, поды перезапускаются по кругу. Какое действие быстрее всего выведет систему из петли?"
  options={[
    'Увеличить max_connections в PostgreSQL до 10 000',
    'Добавить подов, чтобы разделить нагрузку',
    'Резко снизить входящий трафик на балансировщике и отключить проверку базы в liveness-пробе, затем поднимать трафик ступенями',
  ]}
  answer={2}
>
Увеличить `max_connections` — значит, дать базе ещё больше процессов, которые делят тот же процессор и ту же память; каждый процесс PostgreSQL стоит мегабайты. Добавить подов — это ещё 20 соединений и ещё один холодный кэш на каждый. Оба действия подливают масла в огонь.

Выход из метастабильного состояния — убрать нагрузку, которая его поддерживает. Когда входящий поток ограничен, база успевает обработать соединения, поды перестают проваливать пробы, кэш прогревается на малой нагрузке. Дальше поток поднимают ступенями — 10%, 25%, 50%, — каждый раз дожидаясь, пока задержки вернутся в норму. Именно так вышли из этого инцидента: на ingress поставили ограничение частоты, пробу временно сделали проверкой только самого процесса, и за 15 минут подняли трафик до полного.
</Predict>

**Что поменяли.**

- **Liveness проверяет только сам процесс.** Может ли он ответить на HTTP-запрос — да или нет. Состояние зависимостей проверяет <Term id="readiness-probe">readiness</Term>, да и то с осторожностью: если readiness всех подов зависит от одной базы, падение базы выводит из балансировки все поды сразу. Перезапуск пода никогда не чинит чужую базу.
- **Сумма пулов меньше предела базы.** Между сервисами и базой поставили PgBouncer в режиме транзакций (с его ограничениями — см. лекцию о [PostgreSQL в эксплуатации](/lectures/production/postgres-ops/)). `MaxOpenConns` на поде уменьшили до 5: больше соединений на под не ускоряет, а только увеличивает очередь в базе.
- **Переподключения с разбросом** и экспоненциальной задержкой; повторы — на одном уровне, с бюджетом.
- **Ограничение параллельности на входе.** Сервис принимает не больше N одновременных запросов, остальным сразу отвечает 503. Это <Term id="load-shedding">сброс нагрузки</Term>: он делает перегрузку ограниченной, и система не может провалиться в состояние, где очередь растёт без предела.
- **Плановая проверка.** Раз в квартал — управляемое переключение базы в рабочее время на стенде с реальной нагрузкой. Этот инцидент можно было найти за месяц до того, как он случился.

Проверочный вопрос для любого механизма восстановления: что будет, если он сработает на всех экземплярах одновременно? Повтор, перезапуск, переподключение, прогрев кэша — каждый безопасен по одному и опасен как синхронная волна.

## Ничего не выкатывали

**Симптом.** Субботнее утро, выкаток не было неделю, изменений конфигурации — тоже. Внутренние вызовы между сервисами падают с `x509: certificate has expired or is not yet valid`.

**Первая гипотеза.** Кто-то всё-таки что-то поменял. Час ушёл на поиск изменения, которого не было.

**Причина.** Внутренние сертификаты для mTLS выпускались на год. Их автоматически обновлял cert-manager — и обновил вовремя: новый сертификат лежал в секрете Kubernetes уже месяц. Но сервисы читали сертификат с диска один раз при старте:

```go
cert, _ := tls.LoadX509KeyPair("/certs/tls.crt", "/certs/tls.key")
cfg := &tls.Config{Certificates: []tls.Certificate{cert}}
```

Файл на диске обновился, а в памяти процесса остался старый. Поды, которые не перезапускались больше года, продолжали предъявлять истёкший сертификат. Частично спасло бы то, что обычно поды перезапускаются при выкатках, — но эти сервисы не выкатывали давно. Для полноты картины: секрет, смонтированный через `subPath`, вообще не обновляется в контейнере, пока тот не перезапустят.

Сертификат — один пример из класса «бомб замедленного действия»: отказов, которые заложены давно и срабатывают по календарю или по накоплению, без всякого изменения. Самые частые:

| Бомба | Как срабатывает | Где разобрано |
| --- | --- | --- |
| Срок сертификата | Годовой сертификат, продление, которое не доходит до процесса | этот раздел |
| Счётчик `int4` | Первичный ключ доходит до 2 147 483 647 | [PostgreSQL в эксплуатации](/lectures/production/postgres-ops/) |
| Счётчик транзакций | <Term id="xid-wraparound">Wraparound</Term>: вакуум не успевает, база уходит в режим только для чтения | [PostgreSQL](/lectures/databases/postgres/) |
| Забытый слот репликации | <Term id="replication-slot">Слот</Term> без читателя держит WAL, диск базы заполняется | [Репликация](/lectures/databases/replication/) |
| Хранение в Kafka | Потребитель простаивал дольше срока хранения, оффсеты указывают на удалённые данные | [Kafka в эксплуатации](/lectures/production/kafka-ops/) |
| Диск | Логи, дампы ядра, временные файлы без ротации; иногда кончаются inode, а не место | — |
| Переход на летнее время | Cron на 02:30 в локальном поясе не выполняется или выполняется дважды | — |
| Квоты облака и лимиты API | Лимит, до которого рост доходит постепенно, и однажды — внезапно | — |

**Как выходили.** Перезапустили все поды с mTLS по очереди — они прочитали новый сертификат.

**Что поменяли.**

- Сертификат читается при каждом рукопожатии через обратный вызов, с перечитыванием файла при изменении:

  ```go
  cfg := &tls.Config{
      GetCertificate: func(*tls.ClientHelloInfo) (*tls.Certificate, error) {
          return reloader.Current(), nil // перечитывает файл, если изменился
      },
  }
  ```

  Для клиентской стороны mTLS — `GetClientCertificate` так же.

- Метрика — дата истечения сертификата, **который предъявляет процесс**, а не того, что лежит в секрете. Алерт за 14 дней. Проверять нужно то, что видит собеседник; blackbox-проба на TLS-эндпоинт даёт именно это.
- Для каждой «бомбы» из таблицы — метрика в виде «сколько осталось»: процент использования последовательности, возраст самой старой транзакции, объём WAL, удерживаемый слотами, свободные inode. Алерт — не на отказ, а на скорость приближения к нему.
- Cron и расписания — в UTC. У CronJob в Kubernetes для этого есть поле `timeZone`.
- Сервисы перезапускаются хотя бы раз в неделю — не как решение, а как страховка: долго живущий процесс копит состояние, которое никто не проверял.

## Подписи проблем

Многие инциденты узнаются по форме графика раньше, чем по логам. Сводка признаков из этой лекции и всего курса:

| Что видно | Что проверить первым |
| --- | --- |
| Задержки ровно 1, 3, 5 секунд или ровно значение таймаута | Потерянные пакеты, DNS, таймауты — [сеть](/lectures/production/connections/) |
| Пики со строгим периодом | Синхронные TTL, тикеры, cron после одновременного старта |
| Проблема на одном узле, поде, шарде | Горячий ключ, соседи по узлу, часы, конфигурация этого узла |
| Больше ресурсов — не лучше или хуже | Общая блокировка, мьютекс, предел одного шарда или партиции |
| Процессор низкий, задержка высокая | Ожидание: мьютекс, пул соединений, блокировки в базе — профили mutex и block |
| Вертикальный скачок памяти | Один большой запрос, а не утечка; ищите по логам балансировщика |
| Плавный рост памяти или горутин | [Утечка](/lectures/production/go-service/) — горутины, незакрытые тела ответов |
| Причина устранена, а система не восстанавливается | Метастабильность: повторы, перезапуски, холодный кэш — снижайте входящий поток |
| Ошибок нет, а данные неверные | Заглушка, которую закэшировали; отставание реплики |
| Изменений не было | Календарь и накопление: сертификаты, счётчики, диск, слоты |
| Началось после выкатки, но в изменениях «ничего такого» | Сама выкатка: одновременный старт, пустые кэши и пулы, ребалансы |

И несколько правил ведения инцидента, которые повторяются во всех постмортемах:

- **Сначала остановить ущерб, потом искать причину.** Откат, ограничение трафика, отключение функции флагом — всё это делается до того, как понятно, что сломалось. В двух разборах выше срочное действие (перезапуск по одному, локальный кэш) было найдено раньше полного понимания причины.
- **«Что изменилось?» — первый вопрос, но изменение не обязательно ваше.** Выкатка соседа, обновление образа узла, рост одного клиента, календарь.
- **Первая гипотеза проверяется, а не доказывается.** Ищите факт, который её опровергнет: «если это утечка, куча на живых подах должна расти» — не растёт, значит, не утечка.
- **Действия после разбора меняют систему, а не людей.** «Быть внимательнее при выкатке» не работает. Работает алерт, предел, тест, ограничение в схеме базы.

## Итог

- Трудные инциденты складываются из нескольких механизмов, каждый из которых по отдельности разумен. Искать надо взаимодействие, а не одну поломку.
- Выкатка синхронизирует всё, что имеет период: TTL, тикеры, пулы. Случайный разброс нужен везде, где есть интервал.
- Функция, которая при ошибке возвращает нулевое значение, превращает незнание в факт, и кэш выше сохранит его надолго. Деградацию решают наверху, и деградированный ответ не кэшируют.
- Горячий ключ не лечится шардированием: один ключ живёт на одном узле. Кэш в процессе, копии ключа, кэширование на стороне клиента.
- На многоядерных машинах общий мьютекс в горячем пути ограничивает масштабирование, и профиль процессора этого не показывает. Смотрят профиль мьютексов, лечат шардированием.
- OOM от одного запроса не виден в логах сервиса: запрос не завершился. Потоковая обработка, жёсткие пределы, переборки для тяжёлых эндпоинтов.
- Время с разных машин нельзя сравнивать точно. Допуск при проверке сроков, алерт на смещение часов, порядок событий — по версиям.
- Распределённая блокировка уменьшает дублирование, но не гарантирует его отсутствие. Гарантию даёт хранилище: уникальность, токен ограждения, условная запись.
- Метастабильный отказ поддерживается собственными механизмами восстановления. Liveness не проверяет зависимости, сумма пулов меньше предела базы, на входе — ограничение параллельности, а выход — через снижение потока.
- У отказов «без изменений» есть календарь: сертификаты, счётчики, диски, слоты. Мерить нужно, сколько осталось до предела, а не факт его достижения.
