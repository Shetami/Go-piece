В прошлых лекциях горутины почти не делили данные: каждая писала в свою ячейку среза, а всё остальное передавалось по каналам. Это лучший вариант, и к нему стоит стремиться. Но у сервиса почти всегда есть что-то общее: кэш, счётчики, конфигурация, пул соединений, состояние сессий. Эта лекция — о том, как с таким состоянием обращаться.

## Гонка данных

<Term id="data-race">Гонка данных</Term> — это когда две горутины обращаются к одной переменной без синхронизации и хотя бы одна из них пишет. Самый частый пример:

```go
var hits int
for range 1000 {
    go func() { hits++ }()
}
```

`hits++` — это три операции: прочитать, прибавить, записать. Две горутины прочитали 41, обе записали 42 — одно увеличение пропало. Это самый мягкий исход.

Хуже то, что по модели памяти Go программа с гонкой данных **не имеет определённого поведения** в привычном смысле. Компилятор вправе держать переменную в регистре и ни разу не перечитать её из памяти:

```go
var done bool
go func() { work(); done = true }()
for !done { } // может крутиться вечно: компилятор вынес чтение из цикла
```

Значения из нескольких машинных слов — строки, интерфейсы, срезы — могут быть прочитаны наполовину: указатель от новой строки, длина от старой. Это уже не «неправильное число», а чтение чужой памяти. А конкурентная запись в `map` рантайм проверяет сам и роняет процесс с `fatal error: concurrent map writes`, который не перехватывается `recover`.

Корень всего — отсутствие отношения <Term id="happens-before" /> между записью и чтением. Синхронизация — мьютекс, канал, атомик, `WaitGroup` — это и есть способ его создать: всё, что сделано до `Unlock`, видно после следующего `Lock`.

### Детектор гонок

Гонки ловит детектор, встроенный в тулчейн:

```sh
go test -race ./...
```

Он отслеживает каждое обращение к памяти и находит пары, не упорядоченные синхронизацией. Ложных срабатываний почти не бывает: если детектор сказал «гонка» — она есть. Но он видит только то, что **случилось** в этом прогоне: гонку в ветке, которую тесты не прошли, он не найдёт. Поэтому тесты под `-race` должны действительно гонять код конкурентно — запускать обработчики из нескольких горутин одновременно, а не по одному.

Стоит детектор дорого — в несколько раз больше памяти и процессора. В CI он обязателен, в продакшене его не держат.

## Три способа не гоняться

Все способы защиты общего состояния сводятся к трём:

1. **Не делить.** Данные принадлежат одной горутине, остальные общаются с ней через каналы. Это <Term id="confinement">владение</Term>.
2. **Делить под замком.** Обращения к данным идут по очереди. Это <Term id="mutex">мьютекс</Term>.
3. **Делить атомарно.** Операции над одним машинным словом, которые не рвутся. Это <Term id="atomic-ops">атомики</Term>.

Разберём каждый и то, когда он подходит.

## Мьютекс

Самый универсальный инструмент. Правильная форма — мьютекс лежит рядом с данными, которые защищает, и не виден снаружи:

```go
type Sessions struct {
    mu   sync.Mutex
    byID map[string]*Session // защищено mu
}

func (s *Sessions) Get(id string) (*Session, bool) {
    s.mu.Lock()
    defer s.mu.Unlock()
    sess, ok := s.byID[id]
    return sess, ok
}
```

Правила, нарушение которых видно в каждом втором код-ревью:

- **Методы — на указателе, структура не копируется.** Копия структуры — это копия мьютекса, и две копии защищают каждая своё. `go vet` ловит передачу по значению.
- **Критическая секция — только работа с данными.** Никаких походов в сеть, записи в лог, отправки в канал под замком. Каждое ожидание внутри секции превращается в очередь горутин перед ней.
- **Не вызывать под замком чужой код.** Колбэк, переданный пользователем, может сам попытаться взять тот же мьютекс — мьютекс в Go не реентерабелен, и это вечная блокировка.
- **Не отдавать наружу то, что защищено.** `Get` выше возвращает указатель на `Session`. Если вызывающий будет менять сессию без замка, мьютекс защищал только map, а не сессии. Иногда правильнее вернуть копию.

### Проверка, потом действие

Мьютекс защищает каждую операцию по отдельности, но не последовательность операций. Классическая ошибка:

```go
if _, ok := cache.Get(key); !ok {
    cache.Set(key, load(key)) // между Get и Set другая горутина могла сделать то же самое
}
```

Каждый метод потокобезопасен, гонки данных нет — детектор промолчит. Но две горутины одновременно увидят промах, обе вызовут `load`, и одна перезапишет результат другой. Это логическая гонка, и она лечится только тем, что проверка и действие выполняются под **одним** захватом замка:

```go
func (c *Cache) GetOrLoad(key string, load func() V) V {
    c.mu.Lock()
    defer c.mu.Unlock()
    if v, ok := c.m[key]; ok {
        return v
    }
    v := load() // под замком — плохо, если load медленная
    c.m[key] = v
    return v
}
```

Если `load` медленная, держать замок на всё её время нельзя — остальные ключи тоже будут ждать. Тогда нужен другой паттерн: <Term id="singleflight">объединение запросов</Term>, о котором речь пойдёт в последней лекции курса.

## RWMutex

Когда чтений намного больше, чем записей, кажется естественным взять <Term id="rwmutex" />: читатели не мешают друг другу. Но он помогает реже, чем кажется.

Каждый `RLock` — атомарная операция над общим счётчиком читателей. На машине с 32 ядрами все читатели постоянно пишут в одну и ту же строку кэша, и она прыгает между ядрами. Для коротких секций — прочитать поле, найти ключ в map — это часто **медленнее** обычного мьютекса. RWMutex выигрывает, когда секции чтения длинные: обход большой структуры, сериализация.

И у него есть ловушка: ожидающий писатель блокирует новых читателей, поэтому повторный `RLock` в той же горутине может зависнуть навсегда. Не берите `RLock` в методе, который вызывается из другого метода, уже держащего `RLock`.

Правило: начинайте с `Mutex`. Переходите на `RWMutex`, только если профиль показывает борьбу за замок и секции чтения действительно длинные.

## Атомики

Для одной переменной — счётчика, флага, указателя — мьютекс избыточен. Пакет `sync/atomic` даёт операции, которые не рвутся и синхронизируют память:

```go
type Stats struct {
    requests atomic.Int64
    errors   atomic.Int64
    draining atomic.Bool
}

s.requests.Add(1)
if s.draining.Load() {
    return errShuttingDown
}
```

Типизированные обёртки (`atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`) появились в Go 1.19 и лучше старых функций `atomic.AddInt64(&x, 1)`: их невозможно случайно прочитать обычным обращением, и они сами выравнивают 64-битные значения на 32-битных платформах.

<Predict
  question="Stats хранит requests и errors в двух atomic.Int64; обработчик сначала увеличивает requests, потом, если нужно, errors. Метрика читает r := requests.Load(), затем e := errors.Load() и считает e/r. Может ли доля ошибок оказаться больше 100%?"
  options={[
    'Нет, атомики гарантируют согласованность',
    'Да: между двумя Load другие горутины успевают изменить счётчики',
    'Только на 32-битных платформах',
  ]}
  answer={1}
>
Может. Каждый `Load` атомарен сам по себе, но два `Load` вместе — нет. Между чтением `requests` и чтением `errors` сотня запросов успевает прийти и упасть: `errors` вырос, а `r` — старый. При резком всплеске ошибок доля легко переваливает за 100%.

Прочитать в обратном порядке — сначала `errors`, потом `requests` — в этом конкретном случае спасает: `requests` увеличивается раньше `errors` и потому не может от него отстать. Но это рассуждение хрупкое и держится на порядке строк в чужом коде.

Это главное ограничение атомиков: **они защищают одну переменную, а не отношения между переменными**. Если у данных есть инвариант, связывающий несколько полей, нужен мьютекс или неизменяемый снимок.
</Predict>

### Неизменяемый снимок

Сильный приём для данных, которые читают постоянно, а меняют редко, — конфигурация, таблица маршрутизации, список реплик. Данные не меняются на месте: писатель строит **новую** версию целиком и атомарно подменяет указатель.

```go
type Router struct {
    table atomic.Pointer[Table]
}

func (r *Router) Lookup(key string) Backend {
    return r.table.Load().Find(key) // без замков, сколько угодно читателей
}

func (r *Router) Reload(t *Table) {
    r.table.Store(t) // старую таблицу соберёт сборщик мусора, когда её дочитают
}
```

Читатели не блокируются никогда, писатель — тоже. Каждый читатель видит целостную версию: либо старую, либо новую, но не смесь. Условие одно — после `Store` таблицу никто не меняет. Если писателей несколько и каждый хочет изменить текущую версию, а не заменить целиком, — нужен CAS-цикл: `Load`, скопировать, изменить копию, `CompareAndSwap`, повторить при неудаче.

## Владелец

Третий путь — не делить вовсе. Состояние живёт в одной горутине, остальные присылают ей запросы:

```go
type Limiter struct {
    reqs chan request
}

type request struct {
    user  string
    reply chan bool
}

func (l *Limiter) run(ctx context.Context) {
    counts := map[string]int{}          // видит только эта горутина
    reset := time.NewTicker(time.Minute)
    defer reset.Stop()
    for {
        select {
        case r := <-l.reqs:
            counts[r.user]++
            r.reply <- counts[r.user] <= 100
        case <-reset.C:
            clear(counts)
        case <-ctx.Done():
            return
        }
    }
}
```

Владелец удобен, когда у состояния много разных событий: запросы, таймеры, фоновые сигналы, остановка. Всё это обрабатывается в одном `select`, по очереди, и о гонках не нужно думать вообще. Мьютексу здесь пришлось бы защищать и map, и сброс по таймеру, и порядок между ними.

Цена — производительность: каждая операция — это две передачи по каналу и переключения горутин. Для простой map под высокой нагрузкой мьютекс в разы быстрее. Выбирайте владельца за ясность логики, мьютекс — за скорость простых операций.

## Однократная инициализация

Ленивая инициализация общего ресурса — отдельный частый случай. Наивная версия гоняется:

```go
var client *Client
func getClient() *Client {
    if client == nil { // гонка: две горутины увидят nil
        client = newClient()
    }
    return client
}
```

Правильная — <Term id="sync-once" />. С Go 1.21 удобнее всего `sync.OnceValue`:

```go
var getClient = sync.OnceValue(func() *Client {
    return newClient()
})
```

Первый вызов выполнит функцию, остальные дождутся и получат тот же результат. Если инициализация может упасть — `sync.OnceValues` вернёт и значение, и ошибку. Но помните: ошибка запоминается навсегда, повторной попытки не будет.

## sync.Map

`sync.Map` — потокобезопасная map без внешнего мьютекса. Название провоцирует использовать её везде, где map делят горутины. Не надо: документация прямо говорит, что в большинстве случаев лучше обычная map с мьютексом — она типобезопасна и не медленнее.

`sync.Map` выигрывает в двух случаях: ключ записывается один раз, а читается много (кэш, который только растёт), или разные горутины работают с непересекающимися наборами ключей. С Go 1.24 она устроена как конкурентное хэш-дерево и масштабируется лучше прежнего, но правило выбора то же: сначала map с мьютексом, `sync.Map` — после профиля.

Если борьба за один мьютекс действительно видна в профиле, часто помогает шардирование: вместо одной map — 64, каждая со своим мьютексом, ключ выбирает шард по хэшу. Горутины, работающие с разными шардами, друг другу не мешают.

<Callout title="Как выбрать">
- Можно не делить — **не делите**: срез по индексу, данные внутри горутины, передача владения по каналу.
- Одна переменная — **атомик**.
- Редко меняется, часто читается — **неизменяемый снимок** в `atomic.Pointer`.
- Несколько полей с общим инвариантом — **мьютекс**.
- Сложная логика с таймерами и событиями — **горутина-владелец**.
- Инициализация один раз — **`sync.OnceValue`**.
</Callout>

## Итог

- [Гонка данных](/glossary/data-race/) — не «иногда неправильное число», а неопределённое поведение: вечные циклы, порванные строки, упавшая map. Ловится `go test -race`, но только на пройденных путях.
- Логическую гонку «проверил, потом сделал» детектор не видит. Проверка и действие должны быть под одним захватом замка.
- [Мьютекс](/glossary/mutex/) — рядом с данными, структура по указателю, в секции — ни ожиданий, ни чужого кода. [RWMutex](/glossary/rwmutex/) — только после профиля.
- [Атомики](/glossary/atomic-ops/) защищают одну переменную, а не связь между переменными. Для целостных данных — неизменяемый снимок в `atomic.Pointer`.
- [Владелец](/glossary/confinement/) медленнее, но избавляет от размышлений о гонках, когда логика сложная.
- Ленивая инициализация — [`sync.OnceValue`](/glossary/sync-once/). `sync.Map` — для узких случаев, по умолчанию map с мьютексом.

Общее состояние под контролем. В следующей лекции — о времени: таймауты, тикеры, ограничение частоты и почему всё это удобнее делать через контекст, чем через `time.After`.
