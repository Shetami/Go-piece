Типичная задача: прочитать миллион строк из файла, разобрать каждую, для каждой сходить в соседний сервис за дополнительными данными и записать результат в базу. Последовательный цикл тратит почти всё время на ожидание: пока идёт запрос в сервис, диск и база простаивают.

Каналы Go позволяют разрезать такой цикл на стадии, которые работают одновременно. Это <Term id="pipeline">конвейер</Term> — один из самых естественных паттернов для Go и один из самых лёгких способов написать утечку. Разберём, как сделать правильно.

## Стадия

Стадия конвейера — функция, которая принимает входной канал, запускает горутину и возвращает выходной канал:

```go
func parse(ctx context.Context, in <-chan string) <-chan Record {
    out := make(chan Record)
    go func() {
        defer close(out)
        for line := range in {
            rec, err := parseLine(line)
            if err != nil {
                continue // об ошибках — ниже
            }
            select {
            case out <- rec:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
```

Каждая строчка здесь не случайна.

- **Сигнатура с направленными каналами.** `<-chan string` на входе — стадия не может писать во вход или закрыть его. Компилятор проверит, что роли не перепутаны.
- **`defer close(out)`.** Стадия — единственный писатель в `out`, поэтому она и закрывает. Закрытие — сигнал следующей стадии, что данных больше не будет; без него следующий `range` никогда не закончится.
- **`for line := range in`.** Стадия читает вход, пока его не закроют. Ей не нужно знать, сколько данных придёт.
- **Отправка в `select` с `ctx.Done()`.** Это главная строчка. Без неё стадия заблокируется на отправке навсегда, если следующая стадия перестала читать.

Источник конвейера — такая же стадия без входа, её часто называют генератором:

```go
func lines(ctx context.Context, r io.Reader) <-chan string {
    out := make(chan string)
    go func() {
        defer close(out)
        sc := bufio.NewScanner(r)
        for sc.Scan() {
            select {
            case out <- sc.Text():
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
```

А собирается конвейер как композиция функций:

```go
ctx, cancel := context.WithCancel(ctx)
defer cancel()

for rec := range enrich(ctx, parse(ctx, lines(ctx, file))) {
    if err := save(ctx, rec); err != nil {
        return err // cancel в defer остановит все стадии
    }
}
```

## Два направления сигналов

В конвейере сигналы идут в две стороны, и важно не путать, какой механизм для какой.

**Закрытие идёт вперёд, от источника к стоку.** Генератор дочитал файл и закрыл выход. `parse` дочитала вход, вышла из `range`, её `defer` закрыл её выход. И так волной до стока. Это штатное завершение: «данных больше нет, доделайте что осталось».

**Отмена идёт поперёк, всем сразу.** Сток получил ошибку от базы и ушёл. Стадии об этом не знают: `enrich` пытается отправить следующую запись, и её никто не принимает. Именно поэтому отправка стоит в `select` с `ctx.Done()`: `cancel()` закрывает один канал, и все стадии одновременно видят, что пора уходить.

Сток перестал читать. `enrich` отправляет следующую запись — и засыпает на отправке, потому что никто не примет. Она больше не читает свой вход, поэтому `parse` засыпает на своей отправке. Та же участь постигает генератор. Три горутины, открытый файл и всё, на что они ссылаются, остаются в памяти до конца процесса.

Deadlock рантайм не обнаружит: на сервере работают другие горутины, и «все уснули» не наступает никогда. Это ровно та <Term id="goroutine-leak">утечка</Term>, о которой шла речь в прошлой лекции: ожидание без отмены.
</Predict>

А вот чтение из входа в `select` с отменой обычно не заворачивают. Если отменили, предыдущая стадия тоже увидит отмену, выйдет и закроет свой выход — `range` закончится сам. Цепочка разматывается с любого места.

## Кто закрывает канал

Всё выше держится на одном правиле, и его стоит сформулировать явно:

> **Канал закрывает тот, кто в него пишет. Если писателей несколько — тот, кто дождался их всех.**

Отсюда следствия:

- **Получатель никогда не закрывает канал.** Он не знает, закончил ли отправитель, а отправка в закрытый канал — паника, которую нельзя предотвратить проверкой.
- **Функция, создающая канал, — его владелец.** Она возвращает его только для чтения (`<-chan T`), и у вызывающего нет даже технической возможности его закрыть.
- **Остановить отправителя со стороны получателя** — только через отдельный сигнал: контекст или канал `done`.

## Бутылочное горлышко и fan-out

<Term id="backpressure">Обратное давление</Term> в конвейере получается само: медленная стадия не забирает значения, предыдущая стоит на отправке. Поэтому пропускная способность всего конвейера равна пропускной способности **самой медленной стадии**. Ускорять остальные бесполезно.

Если `enrich` ходит в сервис по 50 мс, а `parse` тратит на строку 10 мкс, весь конвейер обрабатывает 20 записей в секунду. Лечение — запустить несколько экземпляров медленной стадии, читающих один вход. Это <Term id="fan-out-fan-in">fan-out</Term>. А их выходы нужно слить обратно в один канал — это fan-in.

<FanOutIn />

```go
func enrichN(ctx context.Context, in <-chan Record, n int) <-chan Record {
    out := make(chan Record)
    var wg sync.WaitGroup
    for range n {
        wg.Go(func() {
            for rec := range in {
                rec.Extra = lookup(ctx, rec.ID)
                select {
                case out <- rec:
                case <-ctx.Done():
                    return
                }
            }
        })
    }
    go func() {
        wg.Wait()
        close(out)
    }()
    return out
}
```

Раздавать работу по воркерам не нужно — они сами разбирают общий вход: кто свободен, тот и берёт следующую запись. Балансировка получается идеальной без единой строчки кода.

Сложность на выходе: у `out` теперь `n` писателей, и ни один из них не может его закрыть — остальные ещё пишут. Поэтому закрытие вынесено в отдельную горутину, которая дожидается всех через `wg.Wait()`. Этот приём — «ещё одна горутина только для того, чтобы закрыть» — выглядит странно, но это стандартная идиома.

<Callout kind="warn" title="Буфер не лечит медленную стадию">
Частая попытка ускорить конвейер — добавить буферы: `make(chan Record, 1000)`. Буфер сглаживает **всплески**: если стадия то быстрая, то медленная, соседям не приходится ждать её на каждом значении. Но средней скорости он не меняет. Если стадия медленнее соседей всегда, буфер на 1000 заполнится за секунду, и дальше всё как без него — только в памяти лежит тысяча записей и обратное давление наступает позже. Буфер — это задержка перед давлением, а не ускорение.
</Callout>

## Порядок

После fan-out порядок записей теряется: воркер, которому досталась быстрая запись, отдаст её раньше соседа с медленной. Часто это не важно. Когда важно, есть три способа.

**Индекс вместе со значением и сборка на выходе.** Каждая запись несёт свой номер, сток складывает их в буфер и отдаёт по порядку, как только пришла следующая по номеру. Работает на бесконечном потоке, но буфер может расти, если одна запись зависла.

**Заранее выделенный срез.** Если объём известен, воркеры пишут результат прямо в `results[i]`. Порядок сохраняется бесплатно, синхронизация — только `Wait` в конце. Это самый простой вариант, и его стоит предпочитать, когда весь результат всё равно нужен в памяти.

**Канал на каждую запись.** Генератор отправляет в очередь воркерам задачу вместе с каналом для ответа, а в отдельную очередь — сам этот канал. Сток читает каналы ответов по порядку и ждёт каждый. Порядок сохраняется на бесконечном потоке, число одновременных задач ограничено размером очереди каналов.

```go
type job struct {
    rec   Record
    reply chan Record // буфер 1: воркер не ждёт стока
}
```

## Ошибки

В примере `parse` пропускала ошибки через `continue`. На деле есть три стратегии, и выбирать надо сознательно:

- **Ошибка — это данные.** Результат стадии содержит поле ошибки, и она идёт по конвейеру дальше: `type Result struct { Rec Record; Err error }`. Сток решает, что с ней делать — записать в лог, отложить в «плохие» записи. Подходит, когда одна плохая запись не должна останавливать миллион хороших.
- **Первая ошибка останавливает всё.** Стадии запускаются через `errgroup.WithContext`, возвращают ошибку из горутины, контекст отменяется, и конвейер разматывается. `Wait` отдаёт первую ошибку.
- **Ошибки в отдельный канал.** Работает, но у этого канала тоже должен быть читатель, иначе стадия заблокируется, пытаясь сообщить об ошибке. На практике первые два варианта проще.

Конвейер на errgroup выглядит так:

```go
g, ctx := errgroup.WithContext(ctx)
lines := make(chan string)
recs := make(chan Record)

g.Go(func() error {
    defer close(lines)
    return readLines(ctx, file, lines)
})
g.Go(func() error {
    defer close(recs)
    return parseAll(ctx, lines, recs)
})
g.Go(func() error {
    return saveAll(ctx, recs)
})
return g.Wait()
```

Каналы теперь создаёт тот, кто собирает конвейер, а стадии — просто функции, которые читают и пишут. Их проще тестировать, и все горутины гарантированно закончены к `return`.

## Когда конвейер не нужен

Конвейер хорош, когда у стадий **разные ресурсы**: диск, сеть, процессор, база. Тогда они действительно работают одновременно. Если все стадии — чистые вычисления над памятью, конвейер из каналов часто медленнее простого цикла: каждая передача значения — это блокировка мьютекса канала и, нередко, переключение горутины. Разрезать процессорную работу выгоднее по данным, а не по стадиям: разбить вход на `GOMAXPROCS` кусков и обработать каждый целиком. Об этом — в следующей лекции.

## Итог

- [Стадия конвейера](/glossary/pipeline/) — горутина, которая читает вход до закрытия, пишет выход и закрывает его в `defer`.
- Закрытие идёт вперёд — это штатный конец данных. Отмена идёт всем сразу — это контекст, и поэтому каждая отправка стоит в `select` с `ctx.Done()`.
- Канал закрывает писатель; если писателей несколько — тот, кто дождался их всех.
- Скорость конвейера — скорость самой медленной стадии. Её распараллеливают через [fan-out](/glossary/fan-out-fan-in/), результаты сливают через fan-in, а закрывает выход отдельная горутина после `wg.Wait()`.
- Буфер сглаживает всплески, но не ускоряет. Порядок после fan-out теряется — индекс, срез по индексу или канал на запись.
- Ошибки — либо данные в потоке, либо остановка всего через errgroup.

Fan-out в этой лекции уже был пулом воркеров, но пока только для одной стадии. Следующая лекция — о пулах как самостоятельном инструменте: как ограничить число одновременно работающих горутин и выбрать это число.
