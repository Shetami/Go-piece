Предыдущие лекции собрали инструменты: владение горутинами, конвейеры, пулы, защита общего состояния, время. Эта лекция — о паттернах, которые складываются из них, когда горутинам нужно договориться: кто ответил первым, кто делает общую работу, кому разослать событие и в каком порядке останавливаться.

## Первый ответ

Одинаковые данные лежат на трёх репликах или у трёх провайдеров. Нужен любой ответ — самый быстрый. Запускаем все три запроса, берём первый:

```go
func first(ctx context.Context, replicas []Replica, q Query) (Result, error) {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel() // остальные запросы отменятся, как только мы вернёмся

    type res struct {
        r   Result
        err error
    }
    ch := make(chan res, len(replicas)) // место под ответ каждого — проигравшим не нужно ждать

    for _, rep := range replicas {
        go func() {
            r, err := rep.Do(ctx, q)
            ch <- res{r, err}
        }()
    }

    var errs []error
    for range replicas {
        x := <-ch
        if x.err == nil {
            return x.r, nil
        }
        errs = append(errs, x.err)
    }
    return Result{}, errors.Join(errs...)
}
```

Здесь собраны три урока курса:

- **Буфер на все ответы.** Функция забирает первый успешный ответ и уходит. Остальные горутины отправят свои ответы в буфер и завершатся — никто не повиснет на отправке. Без буфера это была бы классическая <Term id="goroutine-leak">утечка</Term>.
- **`defer cancel()`.** Проигравшие запросы отменяются: соединения освобождаются, реплики не делают работу впустую.
- **Ошибка — не ответ.** Первым может прийти отказ — например, от реплики, которая лежит и отвечает мгновенно. Ждём первый **успешный**, и только если упали все — возвращаем все ошибки вместе.

Запускать сразу три запроса — значит утроить нагрузку на реплики. Это оправдано, когда запрос дешёвый, а задержка критична. Чаще выгоднее вариант поскромнее.

## Страхующий запрос

<Term id="tail-latency">Хвост задержки</Term> обычно вызван не запросом, а случайным состоянием конкретной реплики: сборка мусора, шумный сосед, очередь. Если реплика не ответила за время, за которое обычно отвечает 95% запросов, — скорее всего, ей просто не повезло, а другая реплика сейчас свободна.

<Term id="hedged-request">Страхующий запрос</Term> отправляет копию только тогда, когда первый задержался:

```go
func hedged(ctx context.Context, replicas []Replica, q Query, after time.Duration) (Result, error) {
    ctx, cancel := context.WithCancel(ctx)
    defer cancel()

    type res struct {
        r   Result
        err error
    }
    ch := make(chan res, len(replicas))
    launch := func(rep Replica) {
        r, err := rep.Do(ctx, q)
        ch <- res{r, err}
    }

    t := time.NewTimer(0) // первая попытка — сразу
    defer t.Stop()

    next, inflight := 0, 0
    var errs []error
    for {
        select {
        case <-t.C:
            // текущие попытки молчат слишком долго — пора страховать
        case x := <-ch:
            inflight--
            if x.err == nil {
                return x.r, nil
            }
            errs = append(errs, x.err)
            if next == len(replicas) && inflight == 0 {
                return Result{}, errors.Join(errs...)
            }
            // попытка упала — следующую запускаем сразу, не дожидаясь таймера
        case <-ctx.Done():
            return Result{}, ctx.Err()
        }
        if next < len(replicas) {
            go launch(replicas[next])
            next++
            inflight++
            t.Reset(after)
        }
    }
}
```

Новая попытка запускается в двух случаях: сработал таймер (текущие попытки задержались) или пришла ошибка (ждать таймера бессмысленно). После каждого запуска таймер перезапускается. Остальное — те же приёмы, что и в «первом ответе»: буфер на все попытки и отмена проигравших через `defer cancel()`.

Страховка полезна при трёх условиях: запрос **идемпотентный** (выполнить его дважды безопасно), порог — около p95 (тогда дополнительная нагрузка — около 5%), и реплики не перегружены все разом. Если перегружены все, страховка только добавит нагрузки, поэтому долю страхующих запросов часто ограничивают — например, не больше 5% от общего потока.

## Одна работа на всех

Обратная задача: не «несколько попыток за одним ответом», а «много одинаковых запросов — одна работа». Популярная запись пропала из кэша, и тысяча запросов одновременно идут за ней в базу. Это <Term id="cache-stampede">лавина промахов</Term>, и база от неё падает.

<Term id="singleflight">Объединение запросов</Term> пропускает к базе только первый запрос за ключом, остальные ждут его результат:

```go
var group singleflight.Group

func (s *Service) Product(ctx context.Context, id string) (Product, error) {
    if p, ok := s.cache.Get(id); ok {
        return p, nil
    }
    ch := group.DoChan(id, func() (any, error) {
        // Своя отмена: работа общая, её не должен отменять первый попавшийся клиент.
        ctx, cancel := context.WithTimeout(context.WithoutCancel(ctx), 2*time.Second)
        defer cancel()
        p, err := s.db.Product(ctx, id)
        if err == nil {
            s.cache.Set(id, p)
        }
        return p, err
    })
    select {
    case r := <-ch:
        if r.Err != nil {
            return Product{}, r.Err
        }
        return r.Val.(Product), nil
    case <-ctx.Done():
        return Product{}, ctx.Err() // этот клиент ушёл, работа продолжается для остальных
    }
}
```

Две тонкости этого кода — ровно те места, где singleflight обычно используют неправильно:

- **`DoChan` вместо `Do`.** `Do` блокирует до результата, и клиент с коротким дедлайном будет ждать вместе со всеми. `DoChan` отдаёт канал, который можно ждать в `select` с отменой.
- **`context.WithoutCancel`.** Функция выполняется в контексте **первого** пришедшего запроса. Если его клиент отключится, отменится и общая работа, и все остальные получат `context.Canceled`, хотя их клиенты на месте. `WithoutCancel` (Go 1.21) отвязывает общую работу от конкретного клиента, а собственный таймаут не даёт ей висеть вечно.

Singleflight работает внутри одного процесса. Десять реплик сервиса пошлют в базу десять запросов — это обычно приемлемо. Если нет — нужна распределённая блокировка на ключ в самом кэше.

## Рассылка многим

Событие нужно доставить нескольким подписчикам: изменилась конфигурация, пришло сообщение в чат, обновилась цена. У канала один получатель на значение, поэтому для рассылки нужен посредник — брокер, который держит список подписчиков и отправляет каждому.

```go
type Broker[T any] struct {
    mu   sync.Mutex
    subs map[chan T]struct{}
}

func (b *Broker[T]) Subscribe() (<-chan T, func()) {
    ch := make(chan T, 16)
    b.mu.Lock()
    b.subs[ch] = struct{}{}
    b.mu.Unlock()
    unsubscribe := func() {
        b.mu.Lock()
        if _, ok := b.subs[ch]; ok {
            delete(b.subs, ch)
            close(ch) // закрывает брокер — он единственный писатель
        }
        b.mu.Unlock()
    }
    return ch, unsubscribe
}

func (b *Broker[T]) Publish(v T) {
    b.mu.Lock()
    defer b.mu.Unlock()
    for ch := range b.subs {
        select {
        case ch <- v:
        default:
            // подписчик не успевает — пропускаем для него это событие
        }
    }
}
```

Главный вопрос рассылки — **что делать с медленным подписчиком**. Если отправлять блокирующе, один зависший подписчик остановит доставку всем остальным и повесит публикующего. Под мьютексом — ещё и всех, кто пытается подписаться. Вариантов три:

- **Пропустить событие** для медленного — как в коде выше. Подходит, когда события — это «последнее состояние», и следующее всё равно его заменит: котировки, прогресс, статус.
- **Отключить медленного** — закрыть его канал и удалить из подписчиков. Подписчик узнает об этом по закрытию и сможет переподключиться, запросив полное состояние заново.
- **Бесконечный буфер на подписчика** — очередь в памяти. Никто не теряет событий, но медленный подписчик съедает память без предела. Почти всегда плохая идея.

Выбор здесь — это решение о семантике доставки, и его нельзя оставлять на волю случая. «Все получают всё, и никто не тормозит» не бывает.

Отправка под мьютексом и `close` под тем же мьютексом нужны, чтобы `Publish` никогда не отправил в уже закрытый канал: иначе отписка во время публикации роняла бы процесс паникой.

<Callout title="Сигнал без данных">
Если событие не несёт данных — «конфигурация изменилась, перечитай» — рассылка упрощается до <Term id="chan-close">закрытия канала</Term>: закрытие будит всех ждущих сразу, без списка подписчиков. Для повторяющегося сигнала канал после закрытия подменяют новым под мьютексом, а ждущие берут текущий канал и ждут его закрытия. Это заменяет <Term id="sync-cond" /> и, в отличие от него, работает в `select` вместе с отменой.
</Callout>

## Остановка сервиса

Всё, что было в курсе, сходится в одной задаче: остановить сервис так, чтобы ни один принятый запрос не потерялся, ни одна фоновая горутина не оборвалась на середине записи и процесс вышел вовремя. Это <Term id="graceful-shutdown">плавная остановка</Term>, и порядок в ней важен.

```go
func main() {
    ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
    defer stop()

    if err := run(ctx); err != nil {
        log.Fatal(err)
    }
}

func run(ctx context.Context) error {
    db := openDB()
    defer db.Close() // 5. последним — то, чем пользуются все остальные

    // Фоновая работа живёт в своём контексте: её останавливаем после сервера.
    bgCtx, bgCancel := context.WithCancel(context.Background())
    defer bgCancel()
    bg, bgCtx := errgroup.WithContext(bgCtx)
    bg.Go(func() error { return consumeQueue(bgCtx, db) })
    bg.Go(func() error { return refreshLoop(bgCtx, db) })

    srv := &http.Server{Addr: ":8080", Handler: newHandler(db)}
    serveErr := make(chan error, 1)
    go func() { serveErr <- srv.ListenAndServe() }()

    select {
    case <-ctx.Done(): // 1. пришёл SIGTERM
    case err := <-serveErr:
        return err // сервер упал сам
    case <-bgCtx.Done():
        // фоновая задача упала — останавливаемся так же аккуратно
    }

    // 2. перестать принимать новые запросы и дождаться текущих
    shutdownCtx, cancel := context.WithTimeout(context.Background(), 20*time.Second)
    defer cancel()
    if err := srv.Shutdown(shutdownCtx); err != nil {
        log.Printf("shutdown: %v", err)
    }

    // 3. остановить фоновую работу 4. и дождаться её
    bgCancel()
    if err := bg.Wait(); err != nil && !errors.Is(err, context.Canceled) {
        return err
    }
    return nil
}
```

Порядок — от входа к зависимостям:

1. **Поймать сигнал.** `signal.NotifyContext` превращает SIGTERM в отмену контекста — тот же механизм, что и везде в курсе.
2. **Остановить приём и дождаться текущих запросов.** `srv.Shutdown` закрывает слушающий сокет и ждёт, пока завершатся активные обработчики. У него свой контекст с таймаутом, **не** производный от уже отменённого `ctx`, — иначе `Shutdown` сдастся мгновенно.
3. **Остановить фоновую работу.** После сервера, а не до: обработчики запросов могли ставить задачи фоновым воркерам.
4. **Дождаться фоновых горутин.** Правило владельца из первой лекции в действии: `run` запустила их — `run` и дожидается.
5. **Закрыть ресурсы.** База закрывается последней, потому что ею пользовались все предыдущие шаги. `defer` выполняется в обратном порядке, и это ровно то, что нужно.

В Kubernetes к этому добавляется задержка перед шагом 2: под убирают из балансировки не мгновенно, и несколько секунд после SIGTERM запросы ещё продолжают приходить. Поэтому перед `Shutdown` делают паузу в несколько секунд, а таймаут всей остановки должен укладываться в `terminationGracePeriodSeconds` пода.

  options={[
    'Ничего: Shutdown всё равно дождётся текущих запросов',
    'Shutdown вернётся сразу с ошибкой, текущие запросы оборвутся при выходе процесса',
    'Shutdown будет ждать вечно, потому что у ctx нет таймаута',
  ]}
  answer={1}
>
К моменту вызова `Shutdown` контекст `ctx` уже отменён — именно его отмена и вывела нас из `select`. `Shutdown` закроет слушающий сокет, увидит, что его контекст уже отменён, и сразу вернёт `context.Canceled`, не дождавшись активных соединений. Дальше `run` вернётся, `main` завершится, и обработчики, которые были на середине работы, оборвутся вместе с процессом.

Это частая ошибка: контекст отмены и контекст на само ожидание остановки — разные вещи. Первый говорит «пора», второй — «сколько даём на уборку».
</Predict>

## Итог курса

Все паттерны курса держатся на нескольких идеях, и их стоит держать в голове, а не конкретный код:

- **У каждой горутины есть владелец**, который её остановит и дождётся. Функции синхронны снаружи, к `return` их горутины завершены.
- **У каждого ожидания есть выход**: отмена через контекст, дедлайн или буфер, куда можно положить никому не нужный ответ.
- **У каждого канала есть один закрывающий** — писатель, или тот, кто дождался всех писателей.
- **Параллелизм ограничен тем, во что упирается работа**: ядрами, пулом соединений, соседом.
- **Общее состояние — последнее средство.** Сначала не делить, потом атомик или снимок, потом мьютекс.
- **Под перегрузкой нужно решение, а не случай**: ждать, отказать или пропустить — для пулов, лимитеров и подписчиков.

Первый ответ — буфер на всех и отмена проигравших. [Страхующий запрос](/glossary/hedged-request/) — только после p95 и только для идемпотентных. [Singleflight](/glossary/singleflight/) — `DoChan` и `WithoutCancel`. Рассылка — явное решение про медленного подписчика. [Остановка](/glossary/graceful-shutdown/) — от входа к зависимостям, со своим таймаутом на уборку.

Как все эти примитивы выглядят изнутри — каналы, планировщик, паркующиеся горутины — рассказывает курс [«Рантайм Go»](/lectures/go-runtime/channels/). А отработать паттерны руками можно в разделе [практики](/practice/).
