Горутина стоит несколько килобайт стека и микросекунду на запуск. Миллион горутин — нормально для Go. Отсюда соблазн: пришло десять тысяч задач — запусти десять тысяч горутин.

Проблема в том, что дешёвые горутины делают дорогие вещи. Каждая открывает соединение к базе, выделяет мегабайт под буфер или отправляет запрос соседнему сервису. Десять тысяч одновременных запросов — это исчерпанный <Term id="connection-pool">пул соединений</Term>, гигабайты памяти и сосед, лежащий под нагрузкой, которую ему никто не обещал. Go справится. Не справится всё вокруг.

<Term id="worker-pool">Пул воркеров</Term> — это потолок: одновременно выполняется не больше `n` задач, остальные ждут.

## Классический пул

`n` горутин читают один канал задач — тот самый fan-out из прошлой лекции:

```go
func process(ctx context.Context, jobs []Job, n int) []Result {
    results := make([]Result, len(jobs))
    idx := make(chan int)

    var wg sync.WaitGroup
    for range n {
        wg.Go(func() {
            for i := range idx {
                results[i] = handle(ctx, jobs[i])
            }
        })
    }

    for i := range jobs {
        select {
        case idx <- i:
        case <-ctx.Done():
        }
        if ctx.Err() != nil {
            break
        }
    }
    close(idx)
    wg.Wait()
    return results
}
```

Задачи раздаются по индексу, результаты складываются в `results[i]` — порядок сохранён, синхронизация только в `Wait`. Раздающий цикл — единственный писатель в `idx`, он его и закрывает; воркеры выходят из `range`, `Wait` возвращается.

Классический пул особенно хорош, когда у воркера есть **дорогое состояние**: соединение, клиент, буфер, подготовленный запрос. Воркер создаёт его один раз и переиспользует на все свои задачи.

## Семафор

Если состояния у воркера нет, пул можно заменить более простым приёмом: горутина на задачу, но перед работой — захват слота. Это <Term id="semaphore">семафор</Term>, и в Go его пишут буферизованным каналом:

```go
sem := make(chan struct{}, n)
var wg sync.WaitGroup
for i, j := range jobs {
    sem <- struct{}{} // занять слот; если все n заняты — ждать
    wg.Go(func() {
        defer func() { <-sem }()
        results[i] = handle(ctx, j)
    })
}
wg.Wait()
```

Разница с пулом: горутин может быть создано сколько угодно, но **работают** одновременно не больше `n`. Захват слота стоит **до** `go`, поэтому лишние горутины даже не создаются — цикл просто ждёт.

Ожидание в `sem <- struct{}{}` не отменяется. Когда это важно — `golang.org/x/sync/semaphore`:

```go
sem := semaphore.NewWeighted(int64(n))
for i, j := range jobs {
    if err := sem.Acquire(ctx, 1); err != nil {
        break // контекст отменён, пока ждали слот
    }
    go func() {
        defer sem.Release(1)
        results[i] = handle(ctx, j)
    }()
}
_ = sem.Acquire(context.Background(), int64(n)) // дождаться всех: забрать все слоты
```

Последняя строчка — приём, который заменяет WaitGroup: забрать все `n` слотов можно, только когда их все вернули.

У `Weighted` есть и главное преимущество перед каналом — **веса**. Если задачи разные по стоимости, тяжёлая берёт больше слотов: например, вес — размер файла в мегабайтах, а ёмкость семафора — сколько мегабайт можно держать в памяти одновременно.

## errgroup.SetLimit

На практике чаще всего нужно всё сразу: ограничение, ошибки и отмена. <Term id="errgroup" /> делает это одной строчкой:

```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(n)
for i, j := range jobs {
    g.Go(func() error {
        r, err := handle(ctx, j)
        results[i] = r
        return err
    })
}
return results, g.Wait()
```

`g.Go` блокируется, пока в группе уже `n` работающих горутин. Первая ошибка отменяет `ctx`. Если нет особых причин — дорогого состояния у воркера, весов, — это правильный выбор по умолчанию.

<Predict
  question="В цикле выше handle для пятой задачи вернула ошибку. В jobs ещё 10 000 задач. Что произойдёт с ними?"
  options={[
    'Не запустятся: errgroup перестанет принимать новые Go после ошибки',
    'Запустятся все, но быстро завершатся, если handle проверяет ctx',

  ]}
  answer={1}
>
errgroup после ошибки продолжает принимать `Go`: цикл честно запустит все оставшиеся 10 000 горутин (по `n` за раз). Отменён только контекст. Если `handle` первым делом смотрит в `ctx` — каждая задача завершится мгновенно, и цикл пролетит быстро. Если не смотрит — все задачи выполнятся полностью, и ошибка вернётся только в самом конце.

Поэтому в цикле раздачи полезно проверять контекст самому:

```go
for i, j := range jobs {
    if ctx.Err() != nil {
        break
    }
    g.Go(…)
}
```
</Predict>

## Какой размер

Размер пула выбирается не по числу ядер и не по вкусу, а по тому, **во что упирается работа**.

**Процессорная работа** — сжатие, хэширование, разбор. Больше горутин, чем может исполняться одновременно, не ускорит ничего, а только добавит переключений. Размер — `runtime.GOMAXPROCS(0)`, то есть сколько горутин Go исполняет параллельно (<Term id="gomaxprocs" />). В контейнере с лимитом по CPU это число, начиная с Go 1.25, учитывает лимит.

**Работа с ожиданием** — сеть, диск, база. Горутины почти всё время спят, процессор тут не ограничение. Ограничение — **тот, кого ждут**: сколько соединений в пуле базы, сколько одновременных запросов выдерживает соседний сервис, какой у него лимит частоты. Если в пуле базы 20 соединений, пул воркеров на 100 даст 80 горутин, стоящих в очереди за соединением, — то же ограничение, только спрятанное и без контроля.

Для работы с ожиданием полезно помнить <Term id="littles-law">закон Литтла</Term>: чтобы делать 500 запросов в секунду к сервису, отвечающему за 40 мс, нужно одновременно держать 500 × 0,04 = 20 запросов. Меньше — не хватит пропускной способности, больше — только нагрузите соседа.

<Callout kind="warn" title="Пул на каждый запрос — не пул">
Пул внутри обработчика HTTP-запроса на 10 воркеров ограничивает параллелизм **одного запроса**. Пришло 100 запросов — работает 1000 горутин. Если ограничение защищает общий ресурс (базу, соседа), оно должно быть общим на весь процесс: один семафор на сервис, созданный при старте. Это приём <Term id="bulkhead">переборок</Term> — отдельный лимит на каждую зависимость, чтобы медленный сосед не занял все горутины.
</Callout>

## Когда места нет

Пул ограничил число работающих задач. Но что делать с задачами, которые пришли, когда все воркеры заняты? Вариантов три, и выбор между ними — это решение о поведении сервиса под перегрузкой.

- **Ждать.** `g.Go` или `sem <- ` блокируется. Это обратное давление: вызывающий замедляется вместе с пулом. Правильно для пакетной обработки, где спешить некуда.
- **Ждать, но не дольше дедлайна.** `sem.Acquire(ctx, 1)` с контекстом запроса. Если слот не освободился до таймаута — ошибка. Правильно для запросов с дедлайном: ответ после таймаута всё равно никому не нужен.
- **Отказать сразу.** `g.TryGo` или `sem.TryAcquire` — вернуть `false`, если места нет. Вызывающий получает `503` или «попробуйте позже». Это <Term id="load-shedding">сброс нагрузки</Term>: лучше быстро отказать части запросов, чем медленно обслуживать все.

Чего делать **не надо** — это неограниченной очереди перед пулом: `make(chan Job, 1_000_000)` или срез, в который складываются задачи. Пул честно ограничивает параллелизм, но очередь растёт без предела, задержка каждой задачи растёт вместе с ней, а при падении процесса всё содержимое очереди теряется.

## Разрезать по данным

Для процессорной работы над большим массивом есть вариант проще пула: разрезать данные на `GOMAXPROCS` кусков и отдать каждый своей горутине целиком.

```go
func sumParallel(xs []float64) float64 {
    n := runtime.GOMAXPROCS(0)
    parts := make([]float64, n)
    chunk := (len(xs) + n - 1) / n

    var wg sync.WaitGroup
    for p := range n {
        lo := min(p*chunk, len(xs))
        hi := min(lo+chunk, len(xs))
        wg.Go(func() {
            var s float64
            for _, x := range xs[lo:hi] {
                s += x
            }
            parts[p] = s // одна запись в конце, а не на каждой итерации
        })
    }
    wg.Wait()

    var total float64
    for _, s := range parts {
        total += s
    }
    return total
}
```

Здесь нет ни каналов, ни мьютексов: каждая горутина владеет своим куском входа и своей ячейкой выхода. Обратите внимание на локальную переменную `s`: если бы горутины писали прямо в `parts[p] += x` на каждой итерации, соседние ячейки среза лежали бы в одной строке кэша, и ядра постоянно отбирали бы её друг у друга. Это называется ложным разделением, и оно легко съедает весь выигрыш от параллельности.

Разрезать по данным хорошо, когда куски равны по стоимости. Если нет — одна горутина закончит за секунду, другая за минуту. Тогда куски делают мельче (в несколько раз больше, чем воркеров) и раздают через пул: кто освободился, тот и берёт следующий.

## Итог

- Горутины дешёвые, ресурсы — нет. [Пул воркеров](/glossary/worker-pool/) ставит потолок на число одновременно выполняемых задач.
- Три инструмента: классический пул — когда у воркера дорогое состояние; [семафор](/glossary/semaphore/) — когда задачи разные по весу; [`errgroup.SetLimit`](/glossary/errgroup/) — по умолчанию.
- Размер — по узкому месту: `GOMAXPROCS` для процессора, ёмкость зависимости для сети. Закон Литтла подскажет, сколько нужно.
- Лимит на общий ресурс — общий на весь процесс, а не на запрос.
- Когда места нет: ждать, ждать до дедлайна или отказать сразу. Но не копить в бесконечной очереди.
- Процессорную работу над массивом проще разрезать на куски по числу ядер — без каналов и без общих записей.

До сих пор горутины почти не делили данные: каждая писала в свою ячейку. Но так бывает не всегда. Следующая лекция — об общем состоянии: мьютексах, атомиках и том, как понять, что нужно именно вам.
