В предыдущих лекциях горутины ждали друг друга: результата, закрытия канала, свободного слота. Но в сервисе горутины ждут и внешний мир — базу, соседний сервис, сеть. А внешний мир может не ответить никогда. Эта лекция — о том, как ограничить ожидание по времени и как делать что-то периодически или не чаще заданной частоты.

## У каждого ожидания есть предел

Запрос к соседнему сервису без таймаута — это горутина, которая может ждать вечно. Соединение повисло, пакет потерялся, сосед завис на блокировке — и горутина висит, держа память, соединение из пула и слот семафора. Сто таких запросов — и сервис перестал отвечать, хотя сам он совершенно здоров. Так начинается <Term id="cascading-failure">каскадный отказ</Term>.

Отсюда правило: **у любого ожидания внешнего мира должен быть дедлайн**. Вопрос только в том, как его передать.

## Дедлайн едет в контексте

Можно задать таймаут на каждом вызове отдельно: `http.Client{Timeout: 2 * time.Second}`, таймаут на запрос к базе, таймаут на чтение из Redis. Проблема — они не складываются. Обработчик, у которого на ответ одна секунда, делает три вызова по две секунды каждый — и отвечает через шесть, когда клиент давно ушёл.

Правильно — один <Term id="request-deadline">дедлайн запроса</Term>, который едет вниз по цепочке в контексте:

```go
func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 800*time.Millisecond)
    defer cancel()

    user, err := h.users.Get(ctx, id)      // сколько осталось из 800 мс
    if err != nil { … }
    orders, err := h.orders.List(ctx, id)  // то, что не потратил users
    if err != nil { … }
    …
}
```

Каждый следующий вызов получает остаток. `http.Client` и `database/sql` понимают контекст: при истечении дедлайна они разорвут запрос и вернут ошибку. А если клиент отключился раньше, `r.Context()` отменится, и вся цепочка остановится — никто не делает работу для того, кто уже ушёл.

Несколько деталей:

- **`defer cancel()` обязателен.** Без него таймер контекста живёт до срабатывания, а сам контекст остаётся привязанным к родителю.
- **Вложенный таймаут не может продлить родительский.** `WithTimeout(ctx, 5*time.Second)` внутри контекста с остатком в 100 мс даст 100 мс. Дедлайн выбирается самый ранний.
- **Отличайте причину.** `ctx.Err()` возвращает `context.DeadlineExceeded` или `context.Canceled`. Первое — мы не уложились (стоит посмотреть, кто медленный), второе — нас отменили (клиент ушёл, сосед по errgroup упал). В логах и метриках их стоит разделять.
- **Дедлайн полезно отправлять дальше по сети.** gRPC делает это сам через заголовок `grpc-timeout`. Для HTTP это приходится делать руками — и тогда сосед тоже не будет работать над ответом, который уже никому не нужен.

## Свои ожидания — через select

Когда ждёт ваш собственный код — канал, семафор, результат горутины, — таймаут добавляется через тот же контекст:

```go
select {
case res := <-results:
    return res, nil
case <-ctx.Done():
    return Result{}, ctx.Err()
}
```

Можно написать и `case <-time.After(time.Second)`. Для одиночного ожидания это нормально, но контекст лучше по двум причинам: он учитывает дедлайн всего запроса, а не только этого шага, и его отмену видят все вложенные вызовы.

До Go 1.23 таймер, созданный `time.After`, оставался в куче таймеров рантайма до срабатывания, даже если его канал уже никому не нужен. 10 000 событий в секунду × 60 секунд = 600 000 живых таймеров одновременно, и каждый держит свой канал. Отсюда старый совет: в цикле создайте таймер один раз и делайте `Reset`.

С Go 1.23 таймер, на который никто не ссылается, собирает сборщик мусора сразу, не дожидаясь срабатывания. Код из вопроса перестал течь. Важно: поведение определяется версией Go в `go.mod` модуля, а не версией компилятора, — старый модуль, собранный новым Go, ведёт себя по-старому.

Ещё одна тонкость этого кода, не связанная с памятью: таймер создаётся заново на каждой итерации, поэтому «тишина» напечатается только через минуту без **единого** события. Если нужно «раз в минуту, независимо от событий», это тикер.
</Predict>

## Тикеры и периодическая работа

Периодическая работа — сброс метрик, обновление кэша, проверка здоровья — делается <Term id="time-ticker">тикером</Term>:

```go
func (c *Cache) refreshLoop(ctx context.Context) {
    t := time.NewTicker(30 * time.Second)
    defer t.Stop()
    for {
        select {
        case <-ctx.Done():
            return
        case <-t.C:
            if err := c.refresh(ctx); err != nil {
                log.Printf("refresh: %v", err)
            }
        }
    }
}
```

Что важно знать про тикер:

- **Тикер не копит пропущенные тики.** Если `refresh` заняла 45 секунд, следующий тик придёт сразу после неё, но только один — остальные выброшены. Наложений не бывает: работа выполняется в той же горутине, что и ждёт тиков.
- **Период отсчитывается от старта, а не от конца работы.** Если нужна пауза именно **между** выполнениями, используйте таймер и `Reset` после работы.
- **Первый тик — через период, а не сразу.** Если работу нужно сделать при старте, вызовите её до цикла.
- **Много экземпляров сервиса с одинаковым периодом** стартуют одновременно после выкатки и бьют в одну зависимость синхронно. Небольшой случайный сдвиг — `jitter` — размазывает нагрузку:

```go
wait := period + time.Duration(rand.Int64N(int64(period/10)))
```

## Ограничение частоты

Пул воркеров из третьей лекции ограничивает, сколько задач выполняется **одновременно**. Но у многих внешних API ограничение другое — сколько запросов **в секунду**. Это <Term id="rate-limiting">ограничение частоты</Term>, и в Go его делают пакетом `golang.org/x/time/rate`.

Он реализует ведро с токенами: в ведре помещается `b` токенов, они пополняются со скоростью `r` в секунду, каждый запрос забирает один. Пока ведро не пусто — запросы идут без задержки. Опустело — ждут пополнения. Так разрешаются короткие всплески до `b` запросов, а средняя частота не превышает `r`.

```go
lim := rate.NewLimiter(rate.Limit(50), 10) // 50 в секунду, всплеск до 10

for _, item := range items {
    if err := lim.Wait(ctx); err != nil {
        return err // контекст отменён или дедлайн не позволит дождаться токена
    }
    if err := api.Send(ctx, item); err != nil {
        return err
    }
}
```

У лимитера три режима, как и у семафора:

- **`Wait(ctx)`** — ждать токена. Если по расчёту токен появится позже дедлайна контекста, `Wait` сразу вернёт ошибку, не тратя время на бессмысленное ожидание.
- **`Allow()`** — взять токен, если есть, иначе `false`. Для входящего трафика: лишний запрос получает `429 Too Many Requests`.
- **`Reserve()`** — забронировать токен и узнать, сколько ждать. Полезно, когда решать, ждать ли, нужно самому.

Лимитер потокобезопасен: один экземпляр на всех горутин ограничивает суммарную частоту. Для ограничения по клиентам — map лимитеров по ключу, под мьютексом, с периодической чисткой старых записей.

<Callout kind="warn" title="Лимит одного процесса — не лимит сервиса">
Лимитер в памяти ограничивает один экземпляр. Если реплик десять, внешний API получит в десять раз больше. Для общего лимита делят квоту на число реплик (просто, но неточно при автомасштабировании) или держат счётчик во внешнем хранилище, например в Redis.
</Callout>

## Debounce и throttle

Два паттерна для потока событий, который слишком частый, чтобы реагировать на каждое.

**Throttle** — реагировать не чаще раза в период. Пользователь двигает ползунок, событий сотни в секунду, пересчитывать нужно не чаще раза в 100 мс. Это ограничение частоты с ведром на один токен, `rate.NewLimiter(rate.Every(100*time.Millisecond), 1)` и `Allow()`.

**Debounce** — реагировать, когда поток **затих**. Файл сохраняют пачкой изменений, пересобирать проект нужно один раз, через 200 мс после последнего:

```go
func debounce(ctx context.Context, in <-chan Event, quiet time.Duration, fire func([]Event)) {
    var batch []Event
    t := time.NewTimer(quiet)
    t.Stop()
    for {
        select {
        case e := <-in:
            batch = append(batch, e)
            t.Reset(quiet) // каждое событие отодвигает срабатывание
        case <-t.C:
            fire(batch)
            batch = nil
        case <-ctx.Done():
            return
        }
    }
}
```

`Reset` на каждом событии отодвигает срабатывание, и `fire` вызывается, только когда `quiet` прошло без событий. С Go 1.23 после `Reset` из канала таймера гарантированно не придёт устаревшее значение, поэтому код выше корректен без старой идиомы «остановить и вычитать канал».

У debounce есть известная ловушка: при непрерывном потоке он не сработает никогда. Если реакция нужна хотя бы раз в какое-то время, добавляют второй таймер — максимальное ожидание от первого события в пачке.

## Как тестировать время

Код со временем тяжело тестировать: `time.Sleep(time.Minute)` в тесте — это минута в CI, а `time.Sleep(10 * time.Millisecond)` — нестабильный тест, который падает на загруженной машине.

С Go 1.25 для этого есть пакет `testing/synctest`. Тест запускается в «пузыре» с поддельными часами: время в нём идёт вперёд мгновенно, как только все горутины пузыря заблокированы.

```go
func TestRefreshLoop(t *testing.T) {
    synctest.Test(t, func(t *testing.T) {
        ctx, cancel := context.WithCancel(t.Context())
        c := newCache()
        go c.refreshLoop(ctx)

        time.Sleep(95 * time.Second) // в пузыре — мгновенно
        synctest.Wait()              // дождаться, пока горутины пузыря заблокируются
        if got := c.refreshes.Load(); got != 3 {
            t.Fatalf("refreshes = %d, want 3", got)
        }
        cancel()
    })
}
```

`time.Now`, `time.Sleep`, таймеры, тикеры и таймауты контекстов внутри пузыря пользуются поддельными часами. Тест на полтора минуты виртуального времени выполняется за миллисекунды и детерминированно. Для более старых версий Go время внедряют через интерфейс часов, который в тестах подменяют.

## Итог

- У каждого ожидания внешнего мира — предел. Один [дедлайн](/glossary/request-deadline/) на запрос, в [контексте](/glossary/context-cancellation/), а не набор независимых таймаутов.
- `defer cancel()` всегда. `DeadlineExceeded` и `Canceled` — разные причины, в логах их стоит разделять.
- С Go 1.23 [таймеры](/glossary/time-ticker/) без ссылок собирает сборщик мусора, а `Reset` и `Stop` не оставляют устаревших значений. Поведение зависит от версии в `go.mod`.
- Тикер не копит тики и не допускает наложений. Период — от старта. Для множества реплик — случайный сдвиг.
- [Ограничение частоты](/glossary/rate-limiting/) — `x/time/rate`, ведро с токенами: `Wait` для своих исходящих запросов, `Allow` для чужих входящих.
- Throttle — не чаще раза в период, debounce — после затишья.
- Время в тестах — `testing/synctest`, без настоящих `sleep`.

Мы научились ограничивать и дожидаться. Последняя лекция курса — о координации: как взять самый быстрый из нескольких ответов, не делать одну работу дважды, раздать событие многим подписчикам и остановить весь сервис без потерь.
