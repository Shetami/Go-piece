Запустить горутину в Go можно одним словом. Это делает конкурентность доступной — и это же главный источник проблем. `go f()` не возвращает ничего: ни хэндла, ни способа дождаться, ни способа остановить, ни ошибки. Горутина уходит в свободное плавание, и всё, что с ней будет дальше, программа должна организовать сама.

Весь этот курс — про то, как организовать. А начинается всё с одного правила, из которого следуют почти все остальные.

## Правило владельца

> **Кто запустил горутину, тот отвечает за то, чтобы она завершилась, и знает, когда это случилось.**

Звучит как банальность, но в нём три требования, и каждое нарушают по-своему:

1. **Горутина должна завершиться.** У неё должен быть путь к выходу при любом исходе: работа сделана, произошла ошибка, работу отменили.
2. **Запустивший должен уметь её остановить.** Не «она когда-нибудь закончится сама», а «я могу сказать ей хватит».
3. **Запустивший должен знать, когда она завершилась.** Иначе функция вернёт управление, а горутина всё ещё будет писать в структуру, которую вызывающий уже считает своей.

Горутина, у которой нет хотя бы одного из трёх, — это <Term id="goroutine-leak">утечка</Term> или <Term id="data-race">гонка</Term>, просто ещё не случившиеся.

Самый полезный вывод из правила: **функция не должна запускать горутины, которые переживут её вызов**, если только это не явно заявленная часть её контракта (как у `http.Server.ListenAndServe` или конструктора фонового воркера с методом `Close`). Синхронный API с конкурентностью внутри проще использовать правильно, чем асинхронный:

```go
// Плохо: вызывающий не знает, что внутри горутина, и не может её дождаться.
func (s *Store) Warmup() { go s.loadAll() }

// Хорошо: вызывающий сам решит, нужна ли ему конкурентность.
func (s *Store) Warmup(ctx context.Context) error { return s.loadAll(ctx) }
```

Если вызывающему нужно фоном — он напишет `go s.Warmup(ctx)` сам и сам будет за эту горутину отвечать.

## Дождаться: WaitGroup

Самое простое — дождаться, пока все горутины закончат. Для этого есть <Term id="waitgroup" />:

```go
func fetchAll(urls []string) []Page {
    pages := make([]Page, len(urls))
    var wg sync.WaitGroup
    for i, u := range urls {
        wg.Go(func() {
            pages[i] = fetch(u) // каждая пишет в свою ячейку — синхронизация не нужна
        })
    }
    wg.Wait()
    return pages
}
```

Здесь выполнены все три требования. Горутины завершаются, когда `fetch` вернётся. Функция знает, что они завершились, — после `Wait`. И никто не переживает вызов `fetchAll`: к `return` все горутины уже закончились.

Заметьте две детали, которые сделали код коротким:

- **`wg.Go`** появился в Go 1.25 и объединяет `Add(1)`, `go` и `defer Done()`. В старом коде вы увидите три строки, и главная ошибка в них — `Add` внутри горутины вместо перед `go`.
- **Переменные цикла `i` и `u`** с Go 1.22 свои на каждой итерации. До 1.22 все горутины видели бы последние значения, и в старом коде вы встретите `i, u := i, u` или передачу аргументами.

А ещё запись в `pages[i]` из разных горутин — не гонка: каждая горутина пишет в **свой** элемент, а `Wait` гарантирует, что все записи видны после него. Это частный случай <Term id="confinement">владения</Term>, и мы ещё не раз им воспользуемся.

Паника в горутине, которую никто не перехватил через `recover` **в этой же горутине**, роняет весь процесс. `recover` в вызывающей функции её не поймает: у каждой горутины свой стек, и паника раскручивает только его.

Поэтому горутины, выполняющие чужой или ненадёжный код — обработчики, плагины, задачи из очереди, — оборачивают в `defer func() { if r := recover(); r != nil { … } }()`. Так делает, например, `net/http` для каждого запроса. А для своего кода обычно правильнее упасть: паника означает баг, и продолжать с неизвестным состоянием опаснее.
</Predict>

## Дождаться с ошибкой: errgroup

WaitGroup не знает об ошибках. Если одна загрузка не удалась, мы хотим, во-первых, узнать об этом, а во-вторых — не ждать остальные, раз результат всё равно не нужен. Для этого есть <Term id="errgroup" />:

```go
func fetchAll(ctx context.Context, urls []string) ([]Page, error) {
    pages := make([]Page, len(urls))
    g, ctx := errgroup.WithContext(ctx)
    for i, u := range urls {
        g.Go(func() error {
            p, err := fetch(ctx, u)
            if err != nil {
                return fmt.Errorf("fetch %s: %w", u, err)
            }
            pages[i] = p
            return nil
        })
    }
    if err := g.Wait(); err != nil {
        return nil, err
    }
    return pages, nil
}
```

Первая ошибка отменяет `ctx`, остальные `fetch` видят отмену и возвращаются быстро, `Wait` отдаёт первую ошибку. В реальном коде errgroup встречается чаще WaitGroup: почти любая работа может завершиться ошибкой.

Обратите внимание: `g, ctx := errgroup.WithContext(ctx)` переприсваивает `ctx`, и дальше в функции есть только дочерний контекст. Это сделано нарочно — чтобы горутины случайно не взяли родительский контекст, который ошибка соседа не отменит.

## Остановить: context

Дождаться — половина дела. Вторая половина — уметь сказать горутине «хватит». В Go для этого один стандартный механизм — <Term id="context-cancellation">отмена через context</Term>.

`ctx.Done()` — это канал, который закрывается при отмене. <Term id="chan-close">Закрытие канала</Term> будит всех, кто его ждёт, поэтому одну отмену могут слушать сколько угодно горутин. Горутина, которую можно остановить, выглядит так:

```go
func (w *Worker) run(ctx context.Context) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()
        case job := <-w.jobs:
            if err := w.handle(ctx, job); err != nil {
                return err
            }
        }
    }
}
```

Две вещи, которые важно понимать про отмену:

- **Отмена кооперативная.** Контекст ничего не прерывает. Если `handle` занята пятиминутным вычислением и в `ctx` не смотрит, отмена подождёт пять минут. Долгие циклы должны проверять `ctx.Err()` сами — хотя бы раз на итерацию.
- **Каждое блокирующее ожидание должно быть в `select` с `ctx.Done()`.** Отправка в канал, приём из канала, ожидание семафора. Одно ожидание без отмены — и горутина может остаться висеть навсегда.

Вторая вещь — главный источник утечек, поэтому разберём её подробно.

## Откуда берутся утечки

Горутина утекает, когда она ждёт события, которое никогда не случится. Рантайм ловит только тот случай, когда ждут **все** горутины программы — это <Term id="deadlock" />. На сервере всегда кто-то работает, поэтому утечку не поймает никто: память растёт, горутин в профиле всё больше, и ни одной ошибки в логе.

Три классических сценария.

**Некому забрать результат.**

```go
func first(ctx context.Context) (Result, error) {
    ch := make(chan Result)
    go func() { ch <- slowQuery() }()
    select {
    case r := <-ch:
        return r, nil
    case <-ctx.Done():
        return Result{}, ctx.Err() // горутина висит на ch <- навсегда
    }
}
```

Лечение — `make(chan Result, 1)`. Отправка в буфер завершится без получателя, горутина выйдет, а канал уйдёт к сборщику мусора вместе со значением. Правило: **буфер на число ответов, которые могут остаться никому не нужными.**

**Некому закрыть вход.**

```go
func consume(in <-chan Event) {
    go func() {
        for e := range in { // ждёт close(in), а его никто не вызовет
            handle(e)
        }
    }()
}
```

`range` по каналу завершается только закрытием. Если отправитель просто перестал слать — потребитель ждёт вечно. Правило: **у каждого канала, по которому делают `range`, есть владелец, который его закроет.**

**Ожидание без отмены.**

```go
go func() {
    for {
        v := <-updates   // если updates больше никто не пишет — всё
        apply(v)
    }
}()
```

Не утекает, пока `updates` живёт. Но у такой горутины нет второго требования правила владельца: её нельзя остановить. На тестах, где сервис создаётся и закрывается сотни раз, это видно сразу.

Состояние `chan send` — горутина стоит на отправке. Значит, на другом конце никто не принимает. Картина ровно как в первом сценарии: обработчик запроса ушёл по `ctx.Done()`, а горутина с результатом так и ждёт получателя. Каждый запрос, закончившийся по таймауту, оставляет одну такую горутину.

## Как ловить утечки

Утечку не видно, пока её не ищешь. Три инструмента:

- **`runtime.NumGoroutine()` в метриках.** Число горутин должно колебаться вместе с нагрузкой. График, который только растёт, — утечка.
- **`/debug/pprof/goroutine?debug=1`** из `net/http/pprof`. Стеки всех горутин, сгруппированные по месту, с причиной ожидания: `chan send`, `chan receive`, `select`, `semacquire`. Группа с тысячами одинаковых стеков сразу показывает, где течёт.
- **`go.uber.org/goleak` в тестах.** Проверяет в конце теста, что лишних горутин не осталось:

```go
func TestMain(m *testing.M) {
    goleak.VerifyTestMain(m)
}
```

Последний инструмент самый ценный: он превращает утечку из загадки на проде в красный тест в CI. Это работает, только если у компонентов есть способ остановиться — ещё одна причина соблюдать правило владельца.

## Фоновые компоненты: Start и Stop

Не всякая горутина живёт в пределах одного вызова. Кэш с фоновым обновлением, отправитель метрик, потребитель очереди — живут, пока живёт сервис. Правило владельца для них выглядит так: **у компонента есть явный конец жизни, и после его вызова горутин не осталось.**

```go
type Refresher struct {
    cancel context.CancelFunc
    done   chan struct{}
}

func StartRefresher(parent context.Context, every time.Duration, f func(context.Context)) *Refresher {
    ctx, cancel := context.WithCancel(parent)
    r := &Refresher{cancel: cancel, done: make(chan struct{})}
    go func() {
        defer close(r.done)
        t := time.NewTicker(every)
        defer t.Stop()
        for {
            select {
            case <-ctx.Done():
                return
            case <-t.C:
                f(ctx)
            }
        }
    }()
    return r
}

// Stop просит горутину остановиться и ждёт, пока она выйдет.
func (r *Refresher) Stop() {
    r.cancel()
    <-r.done
}
```

`cancel` даёт второе требование — остановить. `done` даёт третье — узнать, что остановилась. Без `<-r.done` метод `Stop` вернулся бы, пока `f` ещё работает, и вызывающий закрыл бы базу у неё из-под ног.

<Callout title="Структурная конкурентность">
Всё это — ручная реализация идеи, которую в других языках называют структурной конкурентностью: время жизни горутин вложено в лексическую область, как время жизни переменных. В Go её нет на уровне языка, но errgroup и пара «cancel + done» дают почти то же самое. Если каждая горутина в программе запущена так, что её можно найти по дереву владельцев, — остановка сервиса превращается в отмену одного корневого контекста.
</Callout>

## Итог

- `go f()` ничего не возвращает. Всё, что нужно знать о горутине, программа организует сама — поэтому **кто запустил, тот и отвечает** за её завершение, остановку и ожидание.
- Функции лучше делать синхронными. Конкурентность внутри — пожалуйста, но к `return` все горутины должны закончиться.
- Дождаться — [`WaitGroup`](/glossary/waitgroup/), с ошибкой и отменой соседей — [`errgroup`](/glossary/errgroup/).
- Остановить — [`context`](/glossary/context-cancellation/). Отмена кооперативная: каждое блокирующее ожидание стоит в `select` с `ctx.Done()`.
- [Утечка](/glossary/goroutine-leak/) — это горутина, ждущая события, которое не случится. Буфер на число брошенных ответов, владелец у каждого канала, отмена у каждого ожидания. Ловить — `goleak` в тестах и pprof в проде.

Горутины научились заканчиваться. Теперь соединим их между собой: следующая лекция — о конвейерах, где данные текут через цепочку горутин, и о том, как такая цепочка останавливается.
