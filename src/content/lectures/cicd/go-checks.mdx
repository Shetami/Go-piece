У Go для конвейера почти всё есть из коробки: форматтер, который не обсуждают, статический анализ, детектор гонок, покрытие, проверка уязвимостей, воспроизводимые зависимости. Задача — собрать это в набор проверок, который ловит ошибки до ревью, укладывается в несколько минут и не врёт.

## Что проверять

Типичный набор проверок пулл-реквеста для сервиса на Go, от дешёвых к дорогим:

| Проверка | Команда | Что ловит |
| --- | --- | --- |
| Форматирование | `gofmt -l .` пусто | неотформатированный код; спор о стиле закрыт навсегда |
| Модули | `go mod tidy -diff` | забытый `go mod tidy`: лишние или недостающие зависимости |
| Сгенерированный код | `go generate ./... && git diff --exit-code` | изменили `.proto` или SQL, а код не перегенерировали |
| Статический анализ | `go vet ./...` | `Printf` с неправильными аргументами, копирование мьютекса, недостижимый код |
| Линтер | `golangci-lint run` | забытые ошибки, незакрытые `Body`, утечки контекста, стиль |
| Тесты | `go test -race -shuffle=on ./...` | логику, гонки, зависимость тестов от порядка |
| Интеграционные тесты | `go test -tags=integration ./...` | SQL, миграции, работу с настоящими брокерами |
| Уязвимости | `govulncheck ./...` | вызов уязвимого кода в зависимостях и стандартной библиотеке |
| Сборка | `go build ./...` и образ | то, что не покрыто тестами, но должно компилироваться |

Несколько пояснений.

**`go mod tidy -diff`** (с Go 1.23) печатает, что изменил бы `tidy`, и завершается с ошибкой, если что-то изменил бы. Раньше то же делали через `go mod tidy && git diff --exit-code go.mod go.sum`.

**`go vet`** частично запускается сам внутри `go test` — там включено небольшое подмножество анализаторов с почти нулевым числом ложных срабатываний. Полный `go vet` в CI всё равно нужен.

**golangci-lint** — не один линтер, а оболочка над десятками: `errcheck` (проигнорированная ошибка), `bodyclose` (незакрытое тело ответа — источник утечки соединений, о котором подробно в лекции [о Go-сервисе под нагрузкой](/lectures/production/go-service/)), `contextcheck`, `staticcheck` и так далее. Набор включённых линтеров и их настройки живут в `.golangci.yml` в репозитории. Включать всё подряд — плохая идея: половина линтеров — про вкус, и через неделю код обрастает `//nolint`. Лучше небольшой набор, который ловит настоящие ошибки, и нулевой допуск к его предупреждениям.

## Конвейер целиком

Вот так это выглядит в GitHub Actions. Логика — в `Makefile`, чтобы локально запускалось то же самое:

```yaml
name: ci
on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true   # новый пуш в ветку отменяет старый прогон

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod   # версия Go — из директивы go/toolchain
      - run: make check-fmt check-tidy check-generate
      - run: go vet ./...
      - uses: golangci/golangci-lint-action@v8
        with:
          version: v2.4.0           # закреплена, как и у разработчиков

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - run: go test -race -shuffle=on -coverprofile=cover.out ./...

  integration:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - run: go test -tags=integration -count=1 -p=4 ./...

  vuln:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with:
          go-version-file: go.mod
      - run: go run golang.org/x/vuln/cmd/govulncheck@latest ./...
```

Задачи независимы и идут параллельно на разных машинах. Кажется расточительным четыре раза делать checkout и ставить Go, но это секунды, а выигрыш — время самой длинной задачи вместо суммы всех.

`concurrency` с `cancel-in-progress` экономит машины: три быстрых пуша в ветку не должны запускать три полных прогона, результат нужен только для последнего. Для `main` и особенно для задач выкатки так делать нельзя — об этом в лекции [о доставке](/lectures/cicd/delivery/).

## Три кэша

Без кэша каждый запуск скачивает все модули и компилирует все пакеты, включая стандартную библиотеку с детектором гонок. На среднем сервисе это минуты, которые повторяются в каждом прогоне. У Go три разных кэша, и полезно понимать, что лежит в каждом:

- **кэш модулей** (`GOMODCACHE`, по умолчанию `~/go/pkg/mod`) — исходники зависимостей. Ключ — содержимое `go.sum`: пока зависимости не менялись, кэш полностью годен;
- <Term id="go-build-cache">**кэш сборки**</Term> (`GOCACHE`, `~/.cache/go-build`) — скомпилированные пакеты. Ключ каждой записи — хеш входов: исходников, флагов, версии компилятора, переменных окружения, влияющих на сборку. Устаревшим он быть не может: если вход изменился, это просто другой ключ;
- **кэш результатов тестов** — живёт там же, в `GOCACHE`. Если тестовый бинарник и его входы не изменились, `go test` не запускает тест, а печатает старый результат с пометкой `(cached)`.

`actions/setup-go` по умолчанию сохраняет и восстанавливает оба каталога с ключом по `go.sum`. Особенность: кэш сохраняется один раз для ключа и потом не обновляется, пока не изменится `go.sum`. Через месяц после последнего обновления зависимостей кэш сборки в нём сильно отстаёт от кода, и выигрыш тает. Если это заметно, ключ дополняют чем-то меняющимся — например, неделей.

Кэш результатов тестов учитывает то, что Go видит: код, флаги, переменные окружения, которые тест прочитал через `os.Getenv`, и файлы, которые тест открыл через пакет `os`, — если они внутри модуля. Состояние базы в соседнем контейнере он не видит и видеть не может. Для Go входы не изменились — значит, результат прежний.

Правило простое: **тесты, которые ходят наружу, запускают с `-count=1`** — этот флаг отключает кэширование результата. Для юнит-тестов кэш, наоборот, полезен: в большом репозитории он пропускает тесты незатронутых пакетов и экономит минуты.

Кэш результатов работает только в режиме списка пакетов — `go test ./...` или `go test ./store`. Просто `go test` в каталоге пакета результаты не кэширует, поэтому на ноутбуке проблема часто не видна, а в CI, где запускают `./...`, появляется. Не полагайтесь на эту разницу: `-count=1` явно говорит, что тест нужно выполнить.
</Predict>

## Что ловит детектор гонок

<Term id="race-detector">Детектор гонок</Term> (`-race`) инструментирует каждое обращение к памяти и во время выполнения отслеживает, какие обращения из разных горутин ничем не упорядочены. Нашёл — печатает оба стека и роняет тест.

Цена — время и память: по документации Go выполнение замедляется в 2–20 раз, память растёт в 5–10 раз. Для тестов это приемлемо, для прода — обычно нет. Поэтому `-race` — стандарт для `go test` в CI.

  options={[
    'Да: детектор проверяет весь код пакета',
    'Нет: детектор видит только те гонки, которые реально произошли во время прогона. Один вызов из одной горутины не даёт двух конкурирующих обращений',
    'Да, если покрытие этого файла 100%',
  ]}
  answer={1}
>
Детектор гонок — динамический инструмент. Он не анализирует код, а наблюдает за выполнением: чтобы заметить гонку, два обращения без синхронизации должны **действительно случиться** в этом прогоне. Одна горутина, один вызов — конкурирующих обращений нет, сообщать не о чем. Покрытие здесь ни при чём: строка может быть выполнена, но из одной горутины.

Поэтому для кода, который работает конкурентно, нужны тесты, которые создают эту конкурентность: запускают обработчик из нескольких горутин одновременно, гоняют `httptest.Server` параллельными запросами. Ложных срабатываний у детектора практически не бывает — если он что-то нашёл, это настоящая ошибка, даже если тест «обычно проходит».

Вторая подсказка — `-race` в нагрузочных и интеграционных прогонах, где конкурентность возникает сама. Некоторые команды держат одну реплику staging со сборкой `-race`, чтобы ловить то, что не создают тесты.
</Predict>

## Интеграционные тесты

Юнит-тест с моком базы проверяет, что код вызывает мок. Правильность SQL, работу миграций, поведение уникального индекса при конкурентной вставке он не проверяет. Для этого нужна настоящая база — и в CI её легко получить.

Интеграционные тесты отделяют от юнит-тестов, чтобы `go test ./...` на ноутбуке работал без Docker:

```go
//go:build integration

package store_test

func TestCreateOrder_DuplicateKey(t *testing.T) {
	db := testdb.New(t) // своя база или схема на каждый тест
	...
}
```

Базу поднимают либо сервисом CI (`services: postgres:` в GitHub Actions), либо из самого теста через **testcontainers-go**: тест запускает контейнер с нужной версией Postgres, ждёт готовности и удаляет его по `t.Cleanup`. Второй способ одинаково работает локально и в CI и не требует ничего настраивать в YAML.

Чтобы параллельные тесты не мешали друг другу, каждому нужна изоляция:

- **своя база** из шаблона: `CREATE DATABASE test_123 TEMPLATE migrated` — Postgres копирует уже промигрированную базу за доли секунды;
- **своя схема** на тест;
- **транзакция с откатом** в конце — самый быстрый вариант, но не подходит, если код сам управляет транзакциями.

Общая база с очисткой таблиц между тестами — прямой путь к нестабильным тестам из прошлой лекции.

## Уязвимости

<Term id="govulncheck">govulncheck</Term> сверяет зависимости и версию Go с базой уязвимостей Go (vuln.go.dev). Главное его отличие от сканеров, которые смотрят только на список версий: он строит граф вызовов и сообщает об уязвимости, только если ваш код **может дойти** до уязвимой функции.

    'Завершится с ошибкой: уязвимый модуль в зависимостях',
    'Упомянет, что уязвимый модуль есть, но завершится успешно: уязвимая функция недостижима из вашего кода',
    'Ничего не заметит: он проверяет только стандартную библиотеку',
  ]}
  answer={1}
>
govulncheck сообщает об уязвимостях на трёх уровнях: модуль в зависимостях, пакет импортирован, уязвимая функция достижима. Код возврата ненулевой только в последнем случае. Это сильно снижает шум: большинство найденных сканерами уязвимостей лежат в функциях, которые конкретный сервис не вызывает, и обновлять зависимость в панике ради них не нужно.

Обратная сторона — граф вызовов строится статически. Вызов через рефлексию или через интерфейс, реализация которого определяется во время выполнения, анализ может посчитать недостижимым или, наоборот, достижимым с запасом. Для отчётности и аудита полезно смотреть и на уровень модулей.

Уязвимость, которая всплыла **после** слияния, в пулл-реквестах не видна: код не менялся, а база уязвимостей пополнилась. Поэтому `govulncheck` запускают ещё и по расписанию на `main` — и на уже собранном бинарнике: `govulncheck -mode=binary ./server`.
</Predict>

## Покрытие

`go test -coverprofile=cover.out` сохраняет, какие строки выполнились, `go tool cover -html=cover.out` показывает их. Полезно смотреть на **непокрытые** участки в изменённом коде: чаще всего это ветки обработки ошибок, которые никто не проверял.

Два предупреждения:

- **порог покрытия как обязательная проверка** быстро приводит к тестам, которые вызывают код и ничего не проверяют. Покрытие говорит, что строка выполнилась, но не что результат правильный. Разумнее показывать дельту покрытия в PR, чем валить сборку на 79,9%;
- **по умолчанию покрытие считается только внутри пакета**, который тестируется. Код, выполненный из тестов другого пакета, не засчитывается — для сквозной картины есть `-coverpkg=./...`. А покрытие интеграционных и сквозных прогонов собирают, собрав сам бинарник с `go build -cover` и указав каталог в `GOCOVERDIR`.

## Итог

- Набор проверок: `gofmt`, `go mod tidy -diff`, перегенерация без диффа, `go vet`, `golangci-lint` с небольшим набором полезных линтеров, `go test -race -shuffle=on`, интеграционные тесты, `govulncheck`.
- Проверки — параллельными задачами, логика — в `Makefile`, версии инструментов закреплены.
- Три кэша: модулей (ключ — `go.sum`), [сборки](/glossary/go-build-cache/) (ключ — хеш входов, устаревшим не бывает) и результатов тестов. Тесты, которые ходят наружу, — с `-count=1`, иначе кэш вернёт старый результат.
- [Детектор гонок](/glossary/race-detector/) видит только гонки, которые случились в прогоне. Для конкурентного кода нужны тесты, которые создают конкурентность.
- Интеграционные тесты — за тегом сборки, с настоящей базой (testcontainers-go или сервис CI) и изоляцией на каждый тест.
- [govulncheck](/glossary/govulncheck/) сообщает об ошибке, только если уязвимая функция достижима. Запускать и в PR, и по расписанию на `main` и собранном бинарнике.
- Покрытие — чтобы находить непроверенный код, а не как порог, который нужно преодолеть.

Проверки прошли — дальше из кода нужно собрать то, что поедет в прод: образ.
