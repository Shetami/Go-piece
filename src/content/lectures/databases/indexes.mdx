В первой лекции курса мы разобрали, как устроено B-дерево и почему индекс иногда проигрывает полному чтению. Теперь практика: как выбрать индекс под конкретный запрос, какие бывают кроме B-дерева и почему индекс, созданный «как положено», планировщик не использует.

Стенда в этой лекции нет. Индексы проверяются на настоящих данных: `EXPLAIN (ANALYZE, BUFFERS)` на копии прода честнее любой модели. Вместо стенда — схемы и вопросы.

## Сначала — план

Любая работа с индексами начинается с плана запроса. В <Term id="explain">EXPLAIN ANALYZE</Term> для индексов важны две строки узла:

```
Index Scan using orders_tenant_created_idx on orders  (actual rows=20 loops=1)
  Index Cond: ((tenant_id = 7) AND (created_at > '2026-09-01'))
  Filter: (status = 'new')
  Rows Removed by Filter: 1840
```

- **Index Cond** — условия, по которым индекс *ищет*. Они сужают кусок индекса, который вообще читается.
- **Filter** — условия, которые проверяются *после* чтения. Каждая отброшенная строка — прочитанная зря.

Здесь индекс нашёл 1 860 строк, а нужны были 20. Индекс есть и используется, но работает плохо: `status` в нём нет. Хороший индекс под запрос — тот, где почти всё уходит в Index Cond, а Rows Removed by Filter близко к нулю.

## Составной индекс: порядок колонок

<Term id="composite-index">Составной индекс</Term> упорядочен сначала по первой колонке, внутри неё — по второй, и так далее. Порядок колонок решает, какие запросы он обслужит.

<CompositeIndex />

Правило выбора порядка короткое:

1. **Сначала колонки, которые в запросе сравниваются через равенство.**
2. **Потом одна колонка с диапазоном или сортировкой.**
3. Всё, что после диапазона, уже не сужает поиск — только фильтрует найденное.

<Predict
  question="Частый запрос: WHERE status = 'new' AND created_at > $1 ORDER BY created_at LIMIT 50. Какой индекс ему нужен?"
  options={[
    '(created_at, status): created_at селективнее, его и первым',
    '(status, created_at)',
    'Два отдельных индекса — по status и по created_at',
  ]}
  answer={1}
>
`(status, created_at)`. Равенство по `status` выбирает один непрерывный кусок индекса. Внутри него записи уже упорядочены по `created_at`, так что спуск идёт к первой дате после `$1`, а дальше пятьдесят записей подряд — и сортировка не нужна.

С `(created_at, status)` пришлось бы пройти все записи после `$1` со всеми статусами и отфильтровать чужие. «Селективную колонку — первой» — популярный, но неверный совет: решает форма запроса, а не селективность.

Два отдельных индекса PostgreSQL умеет склеить через BitmapAnd, но это два прохода, построение битовых карт и потерянный порядок — сортировать всё равно придётся.
</Predict>

Составной индекс заменяет индекс по своему началу: при `(status, created_at)` отдельный индекс по `status` лишний. А вот наоборот — нет.

## Покрывающий индекс и Index Only Scan

Обычный Index Scan находит в индексе адрес строки и идёт за ней в таблицу. Если строки разбросаны, это случайное чтение на каждую. Если же в индексе есть **все** колонки, нужные запросу, в таблицу можно не ходить. Такой индекс — <Term id="covering-index">покрывающий</Term>:

```sql
CREATE INDEX orders_user_recent_idx ON orders (user_id, created_at) INCLUDE (total, status);
```

Колонки из `INCLUDE` лежат только в листьях: по ним нельзя искать, но их можно отдать.

<IndexOnlyScan />

Но у PostgreSQL есть тонкость, которой нет у многих других баз. Индекс не знает, видна ли версия строки вашему снимку, — информация о видимости есть только в таблице. Поэтому Index Only Scan смотрит в <Term id="visibility-map">карту видимости</Term>. Для страниц, отмеченных «всё видно всем», таблицу не читают. Для остальных — читают.

<Predict
  question="Таблицу только что залили миллионом строк. Запрос использует Index Only Scan, но в плане Heap Fetches: 1000000 — в таблицу сходили за каждой строкой. Почему?"
  options={[
    'Индекс построен неправильно, нужен REINDEX',
    'Карта видимости пуста: VACUUM ещё не прошёл',
    'Колонок в INCLUDE не хватает',
  ]}
  answer={1}
>
Карта видимости пуста. Биты «всё видно всем» ставит VACUUM, а после массовой загрузки он ещё не приходил. Пока бита нет, Index Only Scan обязан проверять видимость по таблице — то есть делать ровно то, от чего индекс должен был избавить.

После заливки данных выполняйте `VACUUM (ANALYZE)` вручную: он и карту видимости заполнит, и статистику для планировщика соберёт. На таблицах, где постоянно меняются одни и те же строки, биты сбрасываются так же быстро, как ставятся, — покрывающие индексы там приносят меньше пользы, чем на таблицах, которые в основном дописываются.
</Predict>

## Частичный индекс

Из миллиона заказов в статусе `pending` сотня, а запрос «следующий необработанный» выполняется постоянно. Индекс по всем заказам огромен, и почти все его записи — о заказах, которые так никто не ищет. <Term id="partial-index">Частичный индекс</Term> хранит только нужные:

```sql
CREATE INDEX orders_pending_idx ON orders (created_at) WHERE status = 'pending';
```

Он крошечный, всегда в кэше, а изменения заказов в других статусах его не трогают вовсе.

Планировщик воспользуется им, только если сможет **доказать**, что условие запроса влечёт условие индекса. `WHERE status = 'pending'` — да. `WHERE status = $1` — только если план строится под конкретное значение параметра. pgx по умолчанию готовит запросы, и после пяти выполнений PostgreSQL может перейти на общий план, который не знает значения `$1`. Если частичный индекс не подхватывается из Go, хотя в psql работает, пишите условие литералом или проверьте `plan_cache_mode`.

Частичный уникальный индекс выражает правила, которые не умеет `UNIQUE`:

```sql
-- один активный email на пользователя; удалённые не мешают зарегистрироваться снова
CREATE UNIQUE INDEX users_email_active_idx ON users (email) WHERE deleted_at IS NULL;
```

## Индекс по выражению

`WHERE lower(email) = lower($1)` не может использовать индекс по `email`: в индексе лежат значения колонки, а не результат функции. <Term id="expression-index">Индекс по выражению</Term> хранит именно результат:

```sql
CREATE INDEX users_email_lower_idx ON users (lower(email));
CREATE INDEX events_author_idx ON events ((payload->>'author'));
```

Два условия. Выражение в запросе должно совпадать с выражением индекса буквально, с точностью до функции и приведения типов. И функция должна быть `IMMUTABLE` — всегда давать один результат для одних аргументов. Поэтому нельзя проиндексировать `created_at::date` у `timestamptz`: результат зависит от часового пояса сессии.

## Не только B-дерево

B-дерево умеет то, что укладывается в линейный порядок: равенство, диапазоны, сортировку, префиксный `LIKE`. Для остального у PostgreSQL есть другие индексы.

**GIN — обратный индекс.** Для jsonb, массивов и полнотекстового поиска: значение разбирается на элементы, и для каждого элемента хранится список строк.

<GinIndex />

<Term id="gin-index">GIN</Term> отлично отвечает на «содержит» (`@>`, `?`, `@@`) и дорого обходится при записи: строка с двадцатью тегами — двадцать вставок в индекс. С расширением pg_trgm GIN ускоряет и `LIKE '%подстрока%'`, недоступный B-дереву.

**GiST — для того, что не упорядочить в линию.** <Term id="gist-index">GiST</Term> работает с геоданными, диапазонами и сетями и отвечает на «пересекается», «внутри», «ближайшие». Его лучшее применение в обычном приложении — ограничение исключения:

```sql
CREATE EXTENSION btree_gist;
ALTER TABLE bookings ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (room_id WITH =, during WITH &&);
```

Две брони одной переговорки на пересекающееся время база теперь не пропустит сама — при любом уровне изоляции. Это самое надёжное лекарство от перекоса записи в бронированиях.

**BRIN — для огромных таблиц, записанных по порядку.**

<BrinIndex />

<Term id="brin-index">BRIN</Term> хранит на каждую группу страниц только минимум и максимум. На журнале событий в терабайт он занимает мегабайты, а запрос «за вчера» с ним читает только вчерашние группы. Но если строки лежат вперемешку, BRIN бесполезен. Проверить порядок можно в `pg_stats.correlation`: нужны значения, близкие к 1 или −1.

| Задача | Индекс |
| --- | --- |
| равенство, диапазон, сортировка, `LIKE 'abc%'` | B-дерево |
| регистронезависимый поиск, поле JSON | B-дерево по выражению |
| jsonb `@>`, теги, полнотекстовый поиск, `LIKE '%abc%'` | GIN (+ pg_trgm) |
| геоданные, диапазоны, запрет пересечений | GiST |
| время в огромном журнале, который только дописывается | BRIN |
| только равенство на очень длинных значениях | hash — редко выигрывает у B-дерева |

## Почему индекс не используется

Индекс создан, а в плане Seq Scan. Самые частые причины:

- **Нужна большая доля строк.** Планировщик прав: полное чтение дешевле. Проверьте `rows` в плане.
- **Функция или приведение над колонкой.** `WHERE date(created_at) = …`, `WHERE id::text = $1`. Переписать условие на саму колонку (`created_at >= $1 AND created_at < $2`) или сделать индекс по выражению.
- **Разные типы.** Колонка `bigint`, параметр пришёл как `numeric`. Обычно это случайность в коде, но индекс из-за неё может не подойти.
- **`LIKE 'abc%'` при не-C коллации.** Обычному B-дереву в `ru_RU.UTF-8` префиксный `LIKE` недоступен. Нужен индекс с `text_pattern_ops`.
- **`LIKE '%abc'` и `ILIKE`.** B-дерево не поможет вовсе, нужен GIN с pg_trgm.
- **`OR` по разным колонкам.** Два индекса склеятся через BitmapOr, если они есть оба. Иначе — полное чтение.
- **Устаревшая статистика.** После массовой загрузки планировщик думает, что таблица пуста. Лечится `ANALYZE`.
- **Порядок сортировки.** `ORDER BY a ASC, b DESC` не обслужит индекс `(a, b)` — нужен `(a, b DESC)`.

Отличить «индекс не подходит» от «планировщик считает его дорогим» можно, выключив Seq Scan в текущей сессии: `SET enable_seqscan = off`. Если индекс всё равно не используется, он для этого запроса непригоден. Если используется и выходит быстрее — ошибается оценка, и дело в статистике или в `random_page_cost`.

## Сколько стоит индекс

Каждый индекс — это:

- **Запись.** Каждая вставка и каждый не-HOT UPDATE обновляют все индексы таблицы. Индекс на часто меняющуюся колонку ещё и отключает HOT-обновления для неё.
- **Память.** Индексы конкурируют с таблицами за буферный кэш.
- **Раздувание.** Индексы B-дерева тоже распухают от мёртвых записей. Пересобрать без простоя — `REINDEX INDEX CONCURRENTLY`.

Найти лишние индексы:

```sql
SELECT relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan = 0
ORDER BY pg_relation_size(indexrelid) DESC;
```

Индекс с нулём сканирований за месяц — кандидат на удаление. Сначала убедитесь, что он не обеспечивает уникальность и не нужен на репликах: статистика считается на каждом сервере отдельно.

Отдельно про внешние ключи. PostgreSQL сам индексирует первичный ключ, но не колонку, которая на него ссылается. Удаление строки из `users` без индекса на `orders.user_id` — полное чтение `orders` на каждое удаление, под блокировкой.

<Callout kind="warn" title="Индекс на живой таблице">
Обычный `CREATE INDEX` запрещает запись в таблицу на всё время построения. В проде индексы строят только через <Term id="create-index-concurrently">CREATE INDEX CONCURRENTLY</Term>. Он дольше, не работает внутри транзакции и ждёт завершения всех старых транзакций. Инструменты миграций в Go по умолчанию оборачивают каждую миграцию в транзакцию: в goose для такой миграции нужна пометка `-- +goose NO TRANSACTION`, в golang-migrate — отдельный файл без других команд. Если построение упало, останется невалидный индекс: он замедляет запись и не используется. Его нужно удалить и построить заново.
</Callout>

## Итог

- Начинайте с плана: условия должны уходить в **Index Cond**, а не в Filter.
- [Составной индекс](/glossary/composite-index/): сначала равенства, потом один диапазон или сортировка.
- [Покрывающий индекс](/glossary/covering-index/) избавляет от походов в таблицу, пока [карта видимости](/glossary/visibility-map/) свежая.
- [Частичный индекс](/glossary/partial-index/) — для запросов по малой части таблицы и для уникальности с условием.
- [Индекс по выражению](/glossary/expression-index/) — когда в условии функция; выражение должно совпадать буквально.
- [GIN](/glossary/gin-index/) — «содержит», [GiST](/glossary/gist-index/) — «пересекается», [BRIN](/glossary/brin-index/) — огромные упорядоченные журналы.
- Каждый индекс замедляет запись. Удаляйте неиспользуемые, индексируйте внешние ключи, стройте [CONCURRENTLY](/glossary/create-index-concurrently/).
