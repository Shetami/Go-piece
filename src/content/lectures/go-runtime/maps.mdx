Карта — второй после слайса встроенный контейнер Go. `map[string]*User` — индекс в памяти, `map[int]struct{}` — множество, `map[Key]int` — счётчики. Снаружи всё просто: положить, достать, удалить, обойти, и всё за O(1).

Под этой простотой — одна из самых сложных структур рантайма, почти три тысячи строк в `internal/runtime/maps`. И её устройство видно из программы: порядок обхода меняется от запуска к запуску, `&m[k]` не компилируется, память после удаления миллиона ключей не возвращается, обход карты из десяти элементов может занимать миллисекунду, а две горутины, пишущие в одну карту, валят весь процесс с `fatal error`, который не перехватить `recover`.

В Go 1.24 реализация карт была полностью заменена: вместо классической таблицы с корзинами и цепочками переполнения — <Term id="swiss-table">Swiss table</Term>, конструкция из библиотеки Abseil от Google, доработанная под требования Go. Пройдём её целиком — от того, во что компилятор превращает `m[k]`, до того, как итератор переживает рост карты у себя под ногами. Все числа в лекции измерены на Go 1.27, а код рантайма приведён по его исходникам с сокращениями.

## Что лежит в переменной

`make(map[K]V)` возвращает указатель на структуру `maps.Map`. Вот она целиком, без комментариев:

```go
// internal/runtime/maps/map.go
type Map struct {
    used        uint64         // число элементов; len(m) читает это поле
    seed        uintptr        // случайная соль хэша, своя у каждой карты
    dirPtr      unsafe.Pointer // каталог таблиц — или одна группа у маленькой карты
    dirLen      int            // длина каталога; 0 у маленькой карты
    globalDepth uint8          // сколько старших бит хэша выбирают таблицу
    globalShift uint8          // 64 - globalDepth
    writing     uint8          // флаг «идёт запись» — ловит гонки
    tombstonePossible bool     // есть ли где-то надгробия
    clearSeq    uint64         // счётчик вызовов clear — для итераторов
}
```

Отсюда сразу несколько следствий:

- **переменная карты — это указатель.** Функция, получившая карту, меняет ту же карту; `m2 := m` — вторая ссылка, а не копия. Копия — `maps.Clone(m)`;
- **`len(m)` — O(1).** Компилятор читает первое поле структуры, `used`, без вызова рантайма;
- **nil-карта — nil-указатель.** Чтение, `len`, `range` и даже `delete` на ней работают как на пустой, а запись паникует: `assignment to entry in nil map`. Типичный источник — поле-карта в структуре, созданной литералом `&Cache{}` без `make`.

Сама карта не обязана жить в куче. Если [анализ побега](/glossary/escape-analysis/) доказывает, что карта не переживёт функцию, компилятор кладёт на стек и `Map`, и первую группу из восьми слотов. Локальная карта-«словарик» на несколько ключей тогда не стоит ни одной аллокации — до тех пор, пока не вырастет больше восьми элементов.

## Во что компилятор превращает m[k]

Карта — не обобщённый тип, а встроенный: у рантайма один набор функций на все типы карт, и тип передаётся им параметром — дескриптором `abi.MapType` с размерами, смещениями, функцией хэша и функцией сравнения ключей. Компилятор переводит операции так:

| В коде | Вызов рантайма |
| --- | --- |
| `v := m[k]` | `mapaccess1` — возвращает указатель на значение или на общий нулевой буфер |
| `v, ok := m[k]` | `mapaccess2` |
| `m[k] = v` | `mapassign` — возвращает **указатель на слот**, запись делает сгенерированный код |
| `delete(m, k)` | `mapdelete` |
| `for k, v := range m` | `mapIterStart` + `mapIterNext` |
| `clear(m)` | `mapclear` |

У каждого, кроме обхода и `clear`, есть быстрые варианты, специализированные под тип ключа: `_fast32`, `_fast64`, `_faststr` (и `_fast64ptr` для указателей). Они не вызывают хэш-функцию через указатель и сравнивают ключи одной инструкцией. Компилятор выбирает их, когда:

- ключ — 4 или 8 байт без указателей (`int32`, `uint64`, `[2]uint32`…), 8-байтовый указатель или строка;
- **и** значение не больше 128 байт.

`map[string]int` и `map[int64]*User` идут по быстрому пути, `map[[16]byte]int` и `map[struct{ A, B int64 }]int` — по общему. Разница — наносекунды на операцию, но в горячем цикле заметная.

Две оптимизации, о которых полезно знать:

```go
m[k] += 1                  // один вызов mapassign: поиск ключа — один раз
m[k] = append(m[k], v)     // и тут тоже один mapassign, без отдельного mapaccess
v := m[string(buf)]        // []byte → string без аллокации: строка живёт только на время поиска
```

`mapassign` возвращает адрес слота, и компилятор читает старое значение через него же. Поэтому «прочитать и изменить» по одному ключу не стоит двух поисков. И поэтому же `delete` **всегда** обнуляет значение в слоте, даже если в нём нет указателей: следующий `m[k] += 1` по удалённому ключу получит слот с нулём, а не со старым мусором.

Обратная сторона: ключ-указатель, который кладут в карту, **всегда убегает в кучу** — даже если сама карта на стеке. Хэш указателя — его адрес, а объекты на стеке переезжают при [росте стека](/glossary/stack-growth/). Для поиска это не нужно, только для записи.

## Хэш: соль и её смена

Функция хэша берётся из дескриптора типа. Для строк и простых блоков памяти это `memhash` — на процессорах с AES-инструкциями (все современные amd64 и arm64) он построен на аппаратных раундах AES. Структура без «дыр» выравнивания хэшируется одним блоком памяти, иначе — по полям; интерфейс — хэш-функцией своего динамического типа.

В хэш подмешивается **seed** — случайное число, своё у каждой карты. Без соли хэш ключа был бы известен заранее, и злоумышленник, контролирующий ключи (заголовки HTTP, поля JSON), мог бы подобрать миллион ключей, попадающих в одну группу, и превратить каждую вставку в линейный проход. Это атака hash flooding, она роняла веб-серверы на многих языках в 2011 году.

Соль меняется, когда карта опустела — через `delete` последнего ключа или `clear`. Иначе атакующий мог бы нащупать коллизии на одной карте и переиспользовать их: долгоживущая карта, которую регулярно очищают, получает новую соль при каждой очистке.

Хэш не бесплатен, и его цена растёт с длиной ключа:

| Ключ, карта на 100 000 записей | Поиск |
| --- | --- |
| `int64` | 3,1 нс |
| строка 8–14 байт | 6,0 нс |
| строка ~70 байт | 6,9 нс |
| строка ~1 КБ | 18,1 нс |

Каждый поиск по длинному строковому ключу — это полный проход хэша по строке плюс сравнение с найденным ключом. Если ключи длинные (URL, SQL-запросы, JSON), выгоднее один раз посчитать от них собственный 64- или 128-битный хэш и использовать его ключом — если допустима исчезающе редкая коллизия.

### Курьёзы с плавающей точкой

```go
m := map[float64]int{}
m[math.NaN()] = 1
m[math.NaN()] = 2
fmt.Println(len(m))          // 2
_, ok := m[math.NaN()]       // false
```

`NaN != NaN`, поэтому найти ранее вставленный NaN невозможно — и чтобы такие ключи не сваливались в одну группу, рантайм хэширует NaN **случайным числом**. Каждая запись по NaN — новая запись, достать её можно только обходом, удалить — только `clear` (Go 1.21). А `+0.0` и `-0.0` равны и хэшируются одинаково — это один ключ.

С интерфейсами — другая ловушка: `map[any]int` компилируется, но ключ несравнимого динамического типа роняет программу при хэшировании:

```go
m := map[any]int{}
m[[]int{1}] = 1 // panic: runtime error: hash of unhashable type []int
```

## Группа и контрольное слово

Теперь сама таблица. Это хэш-таблица с **открытой адресацией**: ключи и значения лежат прямо в массиве, без списков и отдельных узлов. Массив нарезан на **группы** по восемь слотов, и в начале каждой группы лежит 8-байтовое **контрольное слово** — по байту на слот:

```go
// Раскладка группы для map[K]V (по умолчанию слоты чередуются):
type group struct {
    ctrls ctrlGroup // uint64: 8 контрольных байтов
    slots [8]struct {
        key  K
        elem V
    }
}
```

Контрольный байт кодирует состояние слота:

```text
  empty:   1 0 0 0 0 0 0 0    0x80
deleted:   1 1 1 1 1 1 1 0    0xfe   — «надгробие»
   full:   0 h h h h h h h           — h: младшие 7 бит хэша ключа (H2)
```

Старший бит отличает занятый слот от свободного. У занятого в оставшихся семи битах хранится кусок хэша его ключа — это главный трюк конструкции.

<SwissGroup />

64-битный хэш делится на две части:

- **H2** — младшие 7 бит. Они лежат в контрольном байте и позволяют отсеять чужие слоты, не трогая сами ключи;
- **H1** — старшие 57 бит. Их младшие биты выбирают группу, с которой начинается поиск, а самые старшие — таблицу в каталоге (о нём ниже).

### Восемь сравнений за одну операцию

Поиск в группе — это вопрос «в каких слотах контрольный байт равен H2?». Swiss table отвечает на него для всех восьми слотов сразу:

<MatchH2 />

```go
// internal/runtime/maps/group.go — переносимая версия
func ctrlGroupMatchH2(g ctrlGroup, h uintptr) bitset {
    v := uint64(g) ^ (bitsetLSB * uint64(h)) // bitsetLSB = 0x0101010101010101
    return bitset(((v - bitsetLSB) &^ v) & bitsetMSB) // bitsetMSB = 0x8080808080808080
}
```

Результат — маска кандидатов. Цикл проходит по её установленным битам (`TrailingZeros64` — одна инструкция) и сравнивает ключи целиком только у кандидатов. На amd64 весь `matchH2` заменён несколькими SSE-инструкциями.

Ложное совпадение по 7 битам случается с вероятностью 1/128 на слот. По оценке в исходниках, даже при высокой заполненности на один успешный поиск приходится меньше 1/8 лишнего сравнения ключей. Для строковых ключей это главное: каждое лишнее сравнение — поход по чужому указателю в другую строку памяти.

Той же техникой считаются `matchEmpty` (найти пустые) и `matchEmptyOrDeleted` (найти свободные) — по одному-двум сдвигам и маскам.

### Цена раскладки в памяти

Слоты хранят ключи и значения **по значению**, с выравниванием. Для `map[int64]int64` группа — это 8 + 8 × 16 = 136 байт, 17 байт на слот. Для `map[uint8]uint64` слот тоже 16 байт — ключ в 1 байт выравнивается до 8, семь байт пропадают. (Есть `GOEXPERIMENT=mapsplitgroup`, раскладывающий ключи и значения отдельными массивами ради таких случаев, но по умолчанию он выключен.)

Ключ или значение больше **128 байт** хранятся **косвенно**: в слоте лежит указатель, а сам объект выделяется отдельно при вставке. Карта `map[string][256]byte` — это отдельная аллокация на каждую запись.

## Поиск: пробы по группам

Если нужного ключа в первой группе нет, поиск идёт дальше — по **квадратичной последовательности проб**:

<MapProbe />

```go
// internal/runtime/maps/table.go, сокращённо
func (t *table) getWithKey(typ *abi.MapType, hash uintptr, key unsafe.Pointer) (unsafe.Pointer, unsafe.Pointer, bool) {
    seq := makeProbeSeq(h1(hash), t.groups.lengthMask)
    for ; ; seq = seq.next() { // offset += ++index, по модулю числа групп
        g := t.groups.group(typ, seq.offset)

        match := g.ctrls().matchH2(h2(hash))
        for match != 0 {
            i := match.first()
            if typ.Key.Equal(key, g.key(typ, i)) {
                return g.key(typ, i), g.elem(typ, i), true
            }
            match = match.removeFirst()
        }

        if g.ctrls().matchEmpty() != 0 {
            return nil, nil, false // группа с пустым слотом — конец последовательности
        }
    }
}
```

Шаг растёт на единицу: смещения `h, h+1, h+3, h+6, …`. Если число групп — степень двойки, такая треугольная последовательность обходит все группы ровно по разу, поэтому размеры таблиц в Go — всегда степени двойки, а «по модулю» — это `& lengthMask`.

Ключевой инвариант: **вставка кладёт ключ в первую свободную группу на его последовательности**. Значит, если поиск встретил группу, где есть `empty`, — ключ не мог уйти дальше, его в таблице нет. Поэтому таблица никогда не заполняется целиком: где-то на любой последовательности должен найтись пустой слот, иначе поиск отсутствующего ключа не остановится.

### Маленькая карта

Карта, в которой никогда не было больше восьми элементов, устроена ещё проще: у неё нет ни каталога, ни таблицы. `dirLen == 0`, а `dirPtr` указывает прямо на одну группу. Поиск — один `matchH2` без проб; пустой слот для остановки не нужен, так что заняты могут быть все восемь.

Для строковых ключей длиннее 64 байт маленькая карта не считает хэш вообще: сначала сравнивает у каждого слота длину, первые и последние 8 байт. Если под эту проверку подошёл ровно один ключ — одно полное сравнение, и готово.

`make(map[K]V, n)` при `n ≤ 8` ничего не выделяет: группа появится при первой записи.

Слайс остаётся хорошим выбором, когда элементов единицы, ключи — маленькие числа, или нужен порядок. Но «заменить карту слайсом ради скорости» стоит только после бенчмарка на своих данных.

## Вставка и надгробия

Вставка идёт по той же последовательности проб, что и поиск, — ей нужно убедиться, что ключа ещё нет:

```go
// table.PutSlot, суть
for ; ; seq = seq.next() {
    g := группа(seq.offset)
    if ключ найден по matchH2 {
        return адрес его значения        // перезапись существующего
    }
    free := g.ctrls().matchEmptyOrDeleted()
    if free == 0 {
        continue                          // группа забита — пробуем следующую
    }
    if в группе только надгробия {
        запомнить первое надгробие; continue  // ключ может быть дальше
    }
    // Нашли empty — ключа в таблице точно нет.
    слот := первое запомненное надгробие, иначе этот empty
    if growthLeft == 0 { pruneTombstones(); если не помогло — rehash() }
    записать ключ, ctrl[слот] = H2
}
```

Две детали:

- **Надгробие переиспользуется в первую очередь** — и это не тратит `growthLeft`, запас свободных мест: слот и так считался занятым.
- **Перезапись существующего строкового ключа меняет и сам ключ.** Для строк, чисел с плавающей точкой и интерфейсов рантайм копирует в слот новый ключ, даже если старый ему равен. У `+0.0`/`-0.0` так сохраняется последний записанный вариант, а у строк — отпускается старый буфер: если ключ когда-то был срезом огромного ответа, перезапись свежей строкой перестаёт его держать.

### Удаление

`delete` находит ключ, обнуляет слот (ключ — если в нём есть указатели, значение — всегда) и ставит контрольный байт:

- **`empty`**, если в группе уже есть пустой слот. Такая группа и так останавливает поиск, ничего не ломается;
- **`deleted`** — надгробие, если группа была полной. Пустой слот в полной группе оборвал бы поиск ключей, которые при вставке «проскочили» её дальше по своей последовательности.

Надгробие ведёт себя как занятый слот, который ни с чем не совпадает: поиск через него идёт дальше. В маленькой карте надгробий нет вовсе — там нет проб.

Надгробия занимают место в `growthLeft`. Когда запас кончается, рантайм сначала пробует **прополку** (`pruneTombstones`): если надгробий больше 10% ёмкости, он проходит по последовательностям проб всех живых ключей, помечает группы, через которые кто-то «проскакивает», а надгробия во всех остальных превращает обратно в `empty`. Прополка стоит O(ёмкость) и запускается, только если вернёт хотя бы 10% места. Если нет — таблица растёт. Благодаря этому карта с постоянным потоком вставок и удалений (сессии, дедупликация) не пухнет бесконечно.

## Рост: каталог таблиц

Таблица заполняется не больше чем на **7/8** — это `growthLeft` у свежей таблицы. Когда место кончилось, её нужно увеличить, а при открытой адресации это значит **перехэшировать всё**: последовательность проб зависит от числа групп, и каждый ключ нужно положить заново. Для карты на десять миллионов ключей это пауза на сотни миллисекунд на одной невезучей вставке.

Go решает это <Term id="map-growth">расширяемым хэшированием</Term>: карта — не одна таблица, а **каталог** таблиц, каждая не больше 1024 слотов.

<MapDirectory />

- Каталог — массив указателей длины `2^globalDepth`. Индекс в нём — старшие `globalDepth` бит хэша.
- Таблица помнит `localDepth` — сколько бит хэша на самом деле определяют её ключи. Если `localDepth < globalDepth`, на неё указывают несколько соседних строк каталога.
- Таблица меньше 1024 слотов **удваивается**: новый массив групп, все её ключи перекладываются (`grow`).
- Таблица на 1024 слота **делится** (`split`) на две новые таблицы по 1024 слота каждая, по биту `localDepth + 1` хэша. В каталоге перенаправляются только её строки.
- Если делится таблица с `localDepth == globalDepth`, строк на неё не хватает — каталог удваивается. Это массив указателей: на карте в 10 миллионов ключей в нём десятки тысяч элементов, копируются они за микросекунды.

Итог: одна вставка перестраивает не больше одной таблицы — не больше 1024 записей, сколько бы их ни было в карте. На вставке 10 миллионов ключей подряд самая медленная отдельная вставка у нас заняла 78 мкс при выключенном GC. С включённым встречаются выбросы в сотни микросекунд — это уже [помощь в разметке](/glossary/mark-assist/), а не карта.

Старая реализация (до Go 1.24) решала ту же задачу иначе — постепенной эвакуацией: массив корзин удваивался сразу, а старые корзины переносились по одной-две при каждой следующей записи.

```go

dirSize := степень двойки ≥ targetCapacity / 1024
// каждая из dirSize таблиц — ёмкостью targetCapacity / dirSize
```

### Сколько стоит запись в памяти

Сложим всё вместе для `map[int64]int64`: 17 байт на слот, заполненность таблиц — от 7/16 (сразу после деления или удвоения) до 7/8 (перед следующим). Значит, на одну запись с 16 байтами полезных данных карта тратит **от 19 до 39 байт**, и число прыгает пилой в зависимости от того, где в цикле роста оказалась каждая таблица. Мы намерили 23,6 байта на запись для 100 тысяч ключей и 37,8 — для миллиона.

Для оценки памяти большой карты: `(размер ключа + размер значения, с выравниванием) × 1,15 … 2,3` плюс всё, на что указывают ключи и значения.

## Обход

`for k, v := range m` превращается в итератор `maps.Iter`. Спецификация обещает от обхода немного, но строго:

1. каждая запись возвращается не больше одного раза — даже если карту меняют во время обхода;
2. записи, добавленные во время обхода, **могут** вернуться, а могут и нет;
3. изменённая во время обхода запись возвращается с последним значением;
4. удалённая во время обхода, но ещё не пройденная запись не возвращается;
5. порядок не определён.

### Порядок случаен намеренно

При старте итератор берёт два случайных числа: смещение по каталогу и смещение по слотам. Дальше он идёт по таблицам и по слотам **последовательно**, начиная с этих смещений и заворачивая по кругу. Поэтому у маленькой карты разные обходы — просто циклические сдвиги одного порядка:

```go
m := map[string]int{"a": 1, "b": 2, "c": 3, "d": 4}
for k := range m {
    fmt.Print(k)
}
// abcd, cdab, bcda… — от запуска к запуску и от цикла к циклу
```

Случайность — решение, а не побочный эффект. В ранних версиях порядок на маленьких картах был почти стабилен, и код начинал на него полагаться: тесты сравнивали вывод со строкой, ответы кэшировались по хэшу. Ломалось это при смене версии Go или росте карты — в проде. Случайный старт делает зависимость видимой с первого прогона.

Нужен порядок — сортируйте ключи: `for _, k := range slices.Sorted(maps.Keys(m))`. `fmt.Print` и `encoding/json` сортируют ключи карты сами — их вывод детерминирован, сам `range` — нет.

### Обход стоит O(ёмкости), а не O(len)

Итератор проверяет каждый слот каждой таблицы — занят он или нет. Пустые слоты пропускаются быстро, но их тоже нужно пройти.

### Изменения во время обхода

Удалять во время обхода безопасно — удалённый ключ просто не встретится. Добавлять — тоже, но с оговоркой (2). Самое сложное — когда добавление заставляет таблицу **вырасти** прямо под итератором.

Итератор держит ссылку на таблицу, которую обходит сейчас, даже если в каталоге её уже заменили новой. Он продолжает выбирать ключи из **старой** таблицы — только так можно не вернуть запись дважды: в новой таблице другой порядок проб, и позиция «где я был» в ней ничего не значит. Но значение по каждому ключу итератор **перечитывает из новой таблицы**: вдруг его изменили или удалили — это правила (3) и (4). Ключи, добавленные только в новую таблицу, итератор пропускает — это законно по правилу (2). Если таблица поделилась, итератор после старой перепрыгивает через строки каталога, которые теперь занимает её вторая половина. А `clearSeq` позволяет заметить, что во время обхода карту очистили целиком.

Отсюда практическое правило: код «обходим и добавляем производные ключи» работает, но число итераций в нём не определено. Если результат не должен от этого зависеть — собирайте новые ключи в отдельную карту и сливайте после.

```go
for k, v := range sessions {
    if v.Expired(now) {
        delete(sessions, k) // безопасно
    }
}
// или: maps.DeleteFunc(sessions, func(_ string, v Session) bool { return v.Expired(now) })
```

## Нельзя взять адрес элемента

```go
m := map[string]User{"ann": {Age: 30}}
p := &m["ann"]     // ошибка компиляции: cannot take address of m["ann"]
m["ann"].Age = 31  // ошибка компиляции: cannot assign to struct field m["ann"].Age in map
```

Теперь причина видна: при `grow` и `split` все записи таблицы перекладываются в новый массив групп, а старый становится мусором. Указатель на слот, полученный до роста, смотрел бы в брошенный массив — запись через него пропала бы, а чтение вернуло бы устаревшее значение. У слайса такого запрета нет, потому что старый массив после `append` продолжает жить, пока на него есть указатели. Карте пришлось бы держать все старые таблицы вечно.

Изменить поле структуры в карте — через копию или через указатель:

```go
u := m["ann"] // копия
u.Age = 31
m["ann"] = u  // один mapassign; значение перезаписывается целиком

users := map[string]*User{"ann": {Age: 30}}
users["ann"].Age = 31 // слот хранит указатель, сам User не двигается
```

Выбор между `map[K]V` и `map[K]*V` — компромисс. Значения прямо в слотах — меньше аллокаций и указателей для сборщика, но каждое изменение — копия туда и обратно, а при росте перекладываются целые структуры. Указатели — аллокация на запись и нагрузка на GC, зато изменения на месте и дешёвый рост. Для маленьких неизменяемых значений — по значению, для больших или часто изменяемых — указатели.

### Карта и сборщик мусора

Если ни в ключе, ни в значении нет указателей, массив групп выделяется как `noscan`: [сборщик](/lectures/go-runtime/gc/) знает, что внутри нет ссылок, и не заходит туда вовсе. Если указатели есть, на каждом цикле разметки он обходит каждый слот.

Цена этого различия на картах по 5 миллионов записей:

| Карта | Время одного `runtime.GC()` |
| --- | --- |
| `map[int64]int64` | 0,35 мс |
| `map[string]int64` | 13,7 мс |

Сорок раз. И это полный цикл, где карта — почти вся куча. В живом сервисе с кэшем на десятки миллионов строковых ключей разметка съедает заметную долю CPU, а при нехватке — растягивает [помощь в разметке](/glossary/mark-assist/) на горутины, обслуживающие запросы.

Приёмы для больших кэшей в памяти:

- **ключ фиксированной длины без указателей** — `[16]byte` (UUID, хэш от строки), `uint64` (ID). Строка нужна — храните её в значении или в отдельном большом `[]byte`, а в карте — смещение;
- **значение без указателей** — индекс в слайсе структур вместо `*Entry`;
- **множество — `map[K]struct{}`**: `struct{}` занимает ноль байт, в слоте только ключ.

## Одновременная запись — fatal error

Карта не потокобезопасна. Одновременные чтения допустимы, но если хотя бы одна горутина пишет, все обращения нужно синхронизировать. Рантайм пытается поймать нарушение с помощью поля `writing`:

```go
// Map.PutSlot, сокращённо
if m.writing != 0 {
    fatal("concurrent map writes")
}
hash := typ.Hasher(key, m.seed) // сначала хэш: он может паниковать, а запись ещё не началась
m.writing ^= 1                  // «пишу»

// … поиск слота, возможно рост …

if m.writing == 0 {
    fatal("concurrent map writes")  // кто-то переключил флаг, пока мы писали
}
m.writing ^= 1
```

Флаг **переключается** через XOR, а не ставится в единицу. Если два писателя вошли одновременно, каждый переключит флаг, и на выходе хотя бы один увидит ноль вместо ожидаемой единицы. Чтение, обход и `maps.Clone` проверяют флаг на входе. Отсюда четыре сообщения:

```text
fatal error: concurrent map writes
fatal error: concurrent map read and map write
fatal error: concurrent map iteration and map write
fatal error: concurrent map clone and map write
```

Это `fatal`, а не `panic`: <Term id="concurrent-map-writes">`recover` не срабатывает</Term>, `defer` не выполняются, процесс умирает со стеками всех горутин. Одновременная запись могла уже испортить контрольные байты или каталог, и работать дальше с такой картой опаснее, чем упасть.

Проверка — эвристика: флаг — обычная переменная без атомарных операций, и гонка, не совпавшая по времени, пройдёт незамеченной, испортит данные и, может быть, упадёт потом в другом месте. Надёжно ловит только детектор гонок, `go test -race`.

Как защищать:

| Способ | Когда |
| --- | --- |
| `sync.Mutex` + карта | по умолчанию; просто и предсказуемо |
| `sync.RWMutex` + карта | чтений на порядок больше, и секции не крошечные; под большой конкуренцией сам `RLock` становится узким местом — все читатели пишут в один счётчик |
| шарды: N пар «мьютекс + карта», шард по хэшу ключа | много ядер и горячая запись — конкуренция делится на N |
| `sync.Map` | ключи пишутся один раз и дальше только читаются, или горутины работают с непересекающимися ключами |
| карта во владении одной горутины | остальные общаются с ней через каналы — [ограничение владением](/glossary/confinement/) |

`sync.Map` с Go 1.24 построена на конкурентном хэш-префиксном дереве (`HashTrieMap`), а не на паре карт с мьютексом, и стала заметно лучше на смешанной нагрузке. Но она всё ещё не типизирована (`any` в ключах и значениях — аллокации при упаковке), и её `Range` не даёт согласованного снимка. Подробнее о выборе — в лекции об [общем состоянии](/lectures/concurrency/shared-state/).

## Ключи на практике

Ключом может быть любой **сравнимый** тип: числа, строки, указатели, каналы, массивы и структуры из сравнимых полей, интерфейсы. Слайсы, карты и функции — ошибка компиляции.

Составной ключ — структура: `map[struct{ UserID, ItemID int64 }]int`. Это быстрее и надёжнее, чем склеивать строку через `fmt.Sprintf("%d:%d", …)`: ни аллокации на каждый поиск, ни хэширования строки, ни коллизий вида `"1:23"` против `"12:3"`, если разделитель забыли. А ключ из двух `int32` умещается в 8 байт и идёт по быстрому пути `fast64`.

## Пакет maps и встроенные функции

| Задача | Как |
| --- | --- |
| копия | `maps.Clone(m)` — клонирует таблицы целиком, без перехэширования; поверхностная: указатели в значениях общие |
| очистить | `clear(m)` — `len` станет 0, соль сменится, память останется |
| удалить по условию | `maps.DeleteFunc(m, f)` |
| ключи и значения | `maps.Keys(m)`, `maps.Values(m)` — итераторы (Go 1.23), не слайсы |
| отсортированные ключи | `slices.Sorted(maps.Keys(m))` |
| сравнить | `maps.Equal(a, b)` |
| слить | `maps.Copy(dst, src)` |

## Как было до Go 1.24

Классическую реализацию до сих пор описывают в статьях и спрашивают на собеседованиях, поэтому коротко. В Go 1.27 её в исходниках уже нет, `GOEXPERIMENT=noswissmap` больше не существует.

- Карта `hmap` — массив из `2^B` **корзин** по 8 слотов; к полной корзине цеплялись **корзины переполнения** — связный список.
- В корзине — массив `tophash`: старшие 8 бит хэша каждого слота для быстрой отбраковки. Корзину выбирали младшие `B` бит хэша. Сравнение `tophash` шло по одному байту за раз, не сразу по восьми.
- Рост — при средней заполненности 6,5 элемента на корзину (≈81%) или при слишком большом числе корзин переполнения. Во втором случае карта «росла» до того же размера — перекладывала записи, чтобы избавиться от длинных цепочек.
- При росте массив корзин удваивался сразу, а старые корзины **эвакуировались постепенно** — по одной-две при каждой следующей записи. Чтение во время роста проверяло, эвакуирована ли нужная корзина.

Swiss table выиграл за счёт трёх вещей: открытая адресация без цепочек (меньше промахов кэша процессора), параллельная проверка восьми слотов, заполнение до 87,5% без деградации. По данным команды Go, отдельные операции на микробенчмарках ускорились до 60%, а на наборе реальных программ в среднем получилось около 1,5% CPU. Всё, что видно из языка, — случайный порядок, запрет на `&m[k]`, отсутствие сжатия, fatal error при гонке — осталось прежним.

## Итог

- Переменная карты — указатель на `maps.Map`. `len` — чтение поля, nil-карта читается, но паникует при записи. Карта, которая не убегает, может целиком жить на стеке.
- Компилятор переводит операции в `mapaccess`/`mapassign`/`mapdelete`, для 4- и 8-байтовых ключей и строк — в быстрые варианты. `m[k] += v` и `m[k] = append(m[k], v)` — один поиск.
- Хэш солится случайным seed, своим у каждой карты, и соль меняется, когда карта опустела. Цена хэша растёт с длиной ключа; NaN хэшируется случайно.
- [Swiss table](/glossary/swiss-table/): группы по 8 слотов и контрольное слово. В контрольном байте занятого слота — 7 бит хэша (H2); одна битовая операция находит кандидатов среди восьми слотов, ключи сравниваются только у них.
- Поиск идёт по квадратичной последовательности групп и останавливается на группе с `empty`. [Надгробия](/glossary/map-tombstone/) нужны, чтобы удаление из полной группы не обрывало чужие поиски; их пропалывают перед ростом.
- Карта — [каталог таблиц](/glossary/map-growth/) до 1024 слотов. Таблица растёт вдвое или делится; одна вставка перестраивает не больше 1024 записей. Размер известен — `make(map[K]V, n)`.
- Запись `map[int64]int64` стоит 19–39 байт. Карта без указателей не сканируется сборщиком — на миллионах записей это разница в десятки раз.
- [Обход](/glossary/map-iteration/) начинается со случайного места и стоит O(ёмкости). Итератор переживает рост карты: ключи берёт из старой таблицы, значения — из новой.
- Элементы переезжают при росте, поэтому `&m[k]` запрещён. `delete` и `clear` не возвращают память — вернуть её может только новая карта.
- Одновременная запись — [fatal error](/glossary/concurrent-map-writes/), который не ловит `recover`, и ловится он не всегда. Мьютекс по умолчанию, шарды под горячей записью, `sync.Map` — для «записал один раз, читаю много».

Слайсы и карты замыкают картину из [лекции о памяти](/lectures/go-runtime/memory/): аллокатор выдаёт блоки, а эти две структуры решают, когда их просить, сколько и сколько держать после того, как они перестали быть нужны.
