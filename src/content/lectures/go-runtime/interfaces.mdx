Интерфейсы — то, на чём держится стандартная библиотека Go. `io.Reader` читает из файла, сокета, gzip-архива и тела HTTP-запроса одним и тем же кодом. `error` — тоже интерфейс. `http.Handler`, `sort.Interface`, `fmt.Stringer`, `context.Context` — всё это интерфейсы.

При этом они самая «незаметная» часть языка: никаких `implements`, никаких иерархий классов. Тип просто имеет нужные методы — и подходит. Эта простота скрывает несколько деталей, которые регулярно ломают программы: ошибка, которая `!= nil`, хотя функция вернула nil-указатель; обёртка над `http.ResponseWriter`, после которой перестаёт работать стриминг; паника при сравнении двух значений `any`.

Лекция идёт от смысла к устройству: сначала — что такое интерфейс и зачем он нужен, потом — что лежит в памяти и сколько это стоит, и в конце — как их проектировать. Если вы уже прочли лекции о [слайсах](/lectures/go-runtime/slices/) и [картах](/lectures/go-runtime/maps/), подход знакомый: за каждым правилом языка стоит конкретная структура в рантайме.

## Интерфейс — это набор методов

Интерфейс описывает **поведение**: какие методы должны быть у значения. Не поля, не данные, не происхождение — только методы.

```go
type Shape interface {
    Area() float64
    Perimeter() float64
}
```

Любой тип, у которого есть оба метода с такими сигнатурами, **реализует** `Shape`. Объявлять это не нужно:

```go
type Rect struct{ W, H float64 }

func (r Rect) Area() float64      { return r.W * r.H }
func (r Rect) Perimeter() float64 { return 2 * (r.W + r.H) }

type Circle struct{ R float64 }

func (c Circle) Area() float64      { return math.Pi * c.R * c.R }
func (c Circle) Perimeter() float64 { return 2 * math.Pi * c.R }

func Describe(s Shape) string {
    return fmt.Sprintf("площадь %.1f, периметр %.1f", s.Area(), s.Perimeter())
}

Describe(Rect{3, 4})   // работает
Describe(Circle{1})    // тоже работает
```

`Describe` ничего не знает о прямоугольниках и кругах. Она знает только, что у аргумента можно спросить площадь и периметр. Завтра появится `Triangle` — `Describe` не придётся менять.

### Неявная реализация

В Java или C# класс обязан объявить `implements Shape`. В Go связь между типом и интерфейсом **проверяет компилятор в момент использования**: при присваивании `Rect` в переменную типа `Shape` он смотрит, есть ли у `Rect` нужные методы. Нет — ошибка компиляции с точным списком того, чего не хватает:

```
cannot use Triangle{} (value of struct type Triangle) as Shape value:
    Triangle does not implement Shape (missing method Perimeter)
```

Это называют структурной типизацией — «утиной», но проверенной компилятором. Последствия у неё большие:

- **интерфейс может появиться позже типа.** Тип `*os.File` написан задолго до того, как вы объявили свой `type Source interface{ Read([]byte) (int, error) }` — и он его уже реализует;
- **пакет с типом не зависит от пакета с интерфейсом.** Не нужно импортировать интерфейс, чтобы его реализовать. Отсюда идиома Go: интерфейс объявляет тот, кто его **использует**, а не тот, кто реализует (подробно — в разделе о проектировании);
- **реализацию легко подменить** в тестах: любой тип с нужными методами подходит.

Если хочется, чтобы компилятор проверил реализацию заранее, а не в месте использования, пишут проверку без затрат в рантайме:

```go
var _ Shape = Rect{}           // для типа-значения
var _ io.Writer = (*Buffer)(nil) // для типа-указателя: nil не требует создавать объект
```

Переменная `_` никуда не попадает, а строка не скомпилируется, если `Rect` перестанет соответствовать `Shape`.

### Зачем это нужно

Интерфейс разделяет две вещи: **что** нужно сделать и **как** это сделано. На практике это даёт три выгоды.

1. **Один код для многих типов.** `io.Copy(dst, src)` копирует из чего угодно куда угодно: файл в сокет, HTTP-ответ в gzip, буфер в хэш. Это полиморфизм без наследования.
2. **Развязка частей программы.** Сервис заказов зависит от «чего-то, что умеет `Charge`», а не от конкретного платёжного шлюза. Шлюз можно поменять, не трогая логику заказов.
3. **Тестируемость.** В тест вместо настоящей базы или HTTP-клиента передают простой фейк с теми же методами.

```go
type Notifier interface {
    Notify(ctx context.Context, userID int64, text string) error
}

type OrderService struct {
    notify Notifier // не *SMTPClient и не *TelegramBot
}

// В тесте:
type fakeNotifier struct{ sent []string }

func (f *fakeNotifier) Notify(_ context.Context, _ int64, text string) error {
    f.sent = append(f.sent, text)
    return nil
}
```

## Статический и динамический тип

У переменной интерфейсного типа два типа сразу.

- **Статический** — тот, что написан в объявлении: `var s Shape`. Он известен компилятору и определяет, какие методы можно вызвать. Через `s` нельзя достать `s.W` — у `Shape` нет полей, даже если внутри лежит `Rect`.
- **Динамический** — тип значения, которое лежит внутри **сейчас**. После `s = Rect{3, 4}` это `Rect`, после `s = Circle{1}` — `Circle`. Он меняется во время выполнения и известен только рантайму.

Значит, переменная интерфейса должна хранить не только само значение, но и сведения о его типе — иначе при вызове `s.Area()` неизвестно, чью `Area` вызывать. Ровно это и лежит в памяти.

## Как интерфейс устроен в памяти

Значение интерфейса — пара из двух машинных слов, 16 байт на 64-битной платформе. Таких структур в рантайме две — <Term id="iface">iface и eface</Term>:

```go
// runtime/runtime2.go
type iface struct {     // интерфейс с методами: Shape, io.Reader, error
    tab  *itab
    data unsafe.Pointer
}

type eface struct {     // пустой интерфейс: any (он же interface{})
    _type *_type
    data  unsafe.Pointer
}
```

- **`data`** указывает на значение. Если значение само является указателем (`*T`, карта, канал, функция), оно кладётся прямо в это слово. Иначе — в `data` адрес **копии** значения.
- **Первое слово** говорит, что внутри. У `any` это просто указатель на описание типа: методов `any` не обещает, искать их незачем. У интерфейса с методами это указатель на <Term id="itab">itab</Term> — таблицу для конкретной пары «интерфейс + тип».

```go
// internal/abi/iface.go
type ITab struct {
    Inter *InterfaceType // какой интерфейс: Shape
    Type  *Type          // какой тип внутри: Rect
    Hash  uint32         // хэш типа — ускоряет type switch
    Fun   [1]uintptr     // адреса методов; на деле их столько, сколько методов в интерфейсе
}
```

<IfaceLayout />

itab создаётся **одна на пару** `(Shape, Rect)` на всю программу. Миллион переменных `Shape` с прямоугольниками внутри указывают на одну и ту же itab. Методы в `Fun` расположены в порядке сортировки по имени: `Area` — `Fun[0]`, `Perimeter` — `Fun[1]`.

### Присваивание копирует

Раз в `data` лежит копия, интерфейс не связан с исходной переменной — если только в нём не указатель.

```go
type Counter struct{ n int }

func (c Counter) Get() int { return c.n }

type Getter interface{ Get() int }

c := Counter{n: 1}
var g Getter = c
c.n = 5
fmt.Println(g.Get())
```

<Predict
  question="Что напечатает программа?"
  options={['1', '5', '0', 'Ошибка компиляции']}
  answer={0}
>
`1`. В момент `var g Getter = c` значение `Counter{n: 1}` скопировано, и `data` указывает на эту копию. Дальнейшие изменения `c` её не касаются.

Если бы мы написали `var g Getter = &c`, в интерфейсе лежал бы указатель, и `g.Get()` вернул бы `5`: метод с получателем-значением можно вызвать и через указатель, а указатель смотрит на исходную переменную.

Это та же логика, что у присваивания любых значений в Go: копируется то, что лежит в переменной. Просто у интерфейса «то, что лежит», — это пара (тип, указатель на копию).
</Predict>

### Упаковка стоит аллокации

Копию значения нужно где-то хранить. Если компилятор не может доказать, что интерфейс не переживёт функцию, копия уезжает в кучу — это та же логика, что в <Term id="escape-analysis">анализе побега</Term>. За каждым `fmt.Println(x)`, `log.Printf("%d", n)` и `any(v)` в горячем цикле может стоять вызов `runtime.convT64`, `convTstring` и `mallocgc`.

У рантайма есть несколько способов эту аллокацию не делать:

- **указатели, карты, каналы и функции** кладутся в `data` как есть — копировать нечего;
- **целые от 0 до 255** берутся из статического массива `runtime.staticuint64s`. `any(7)` не аллоцирует, `any(300)` — аллоцирует 8 байт;
- **константы** (`any("hello")`, `any(Rect{1, 2})`) компилятор кладёт в данные только для чтения;
- **пустая строка и нулевые значения** указывают на общий `runtime.zeroVal`;
- **копия, которая не убегает**, остаётся на стеке.

```bash
$ go build -gcflags=-m ./...
./main.go:14:13: ... argument does not escape
./main.go:20:9: n escapes to heap
```

В обычном коде это неважно. Важно в горячем пути: логирование с `any`-аргументами в цикле на миллион итераций — миллион мелких аллокаций и работа для [сборщика мусора](/lectures/go-runtime/gc/). Поэтому быстрые логгеры (`slog`, zap) имеют типизированные конструкторы вроде `slog.Int("n", n)`, которые не упаковывают значение в `any`.

## Вызов метода через интерфейс

`s.Area()` компилируется примерно в такой код:

```go
tab := s.tab
fn := tab.Fun[0]   // Area — первый по алфавиту
fn(s.data)         // получатель — указатель на данные
```

Это **косвенный вызов**: адрес функции становится известен только во время выполнения. Сам по себе он дешёвый — пара загрузок из памяти и `call` по регистру, единицы наносекунд. Настоящая цена в другом:

- **компилятор не может встроить метод** — он не знает, какой именно. Для крошечных методов вроде геттера потеря встраивания стоит дороже самого вызова;
- **аргументы считаются убегающими.** Раз неизвестно, что метод сделает с аргументом, компилятор предполагает худшее, и то, что передано в метод интерфейса, часто оказывается в куче.

### Девиртуализация

Компилятор умеет снимать косвенность, когда тип внутри известен. Это <Term id="devirtualization">девиртуализация</Term>:

```go
var s Shape = Rect{2, 3}
s.Area() // devirtualizing s.Area to Rect → прямой вызов, а затем встраивание
```

То же происходит, если функцию, принимающую интерфейс, встроили в место вызова с конкретным типом. А с Go 1.21 есть девиртуализация по профилю (PGO): если `default.pgo` показывает, что в горячем месте почти всегда лежит `*bufio.Reader`, компилятор вставляет быструю ветку с прямым вызовом для этого типа и оставляет косвенный вызов для остальных.

<Callout kind="model" title="Интерфейсы не медленные">
Миф «интерфейсы — это медленно» происходит из микробенчмарков, где метод из одной строки вызывают миллиард раз. В реальном сервисе вызов через интерфейс почти никогда не появляется в профиле — там видны сеть, сериализация, аллокации и блокировки. Проектируйте через интерфейсы там, где они нужны по смыслу, и оптимизируйте, только когда профиль показал на конкретное место.
</Callout>

### Откуда берётся itab

Для каждого присваивания, видимого в коде (`var s Shape = Rect{}`), компилятор строит itab заранее и кладёт её в бинарник — в символах это выглядит как `go:itab.main.Rect,main.Shape`. В рантайме при таком присваивании ничего искать не нужно.

Иначе обстоит дело, когда пара появляется только во время выполнения — при утверждении типа к интерфейсу `x.(io.WriterTo)`. Тогда рантайм вызывает `getitab`: сливает отсортированные списки методов типа и интерфейса за один проход и сохраняет результат в глобальной хэш-таблице `itabTable`. Следующая проверка той же пары — один поиск в таблице, а с Go 1.22 у каждого места утверждения и type switch есть ещё и собственный маленький кэш. Неудачный результат тоже кэшируется — у такой itab `Fun[0] == 0`.

## Получатель-значение и получатель-указатель

Метод можно объявить на значении `func (c Counter) Get()` или на указателе `func (c *Counter) Inc()`. Для прямых вызовов разница почти незаметна: компилятор сам возьмёт адрес, если переменная адресуема. Для интерфейсов разница принципиальная. У каждого типа есть <Term id="method-set">набор методов</Term>:

| Тип | Методы с получателем `T` | Методы с получателем `*T` |
| --- | --- | --- |
| `T` | есть | **нет** |
| `*T` | есть | есть |

```go
type Counter struct{ n int }

func (c *Counter) Inc() { c.n++ }

type Incer interface{ Inc() }

var c Counter
c.Inc()            // (1)
var a Incer = &c   // (2)
var b Incer = c    // (3)
```

<Predict
  question="Какая строка не скомпилируется?"
  options={['(1) — c не указатель', '(2) — нельзя брать адрес для интерфейса', '(3) — у Counter нет метода Inc', 'Компилируются все три']}
  answer={2}
>
Строка (3): `Counter does not implement Incer (method Inc has pointer receiver)`.

Строка (1) работает — `c` адресуемая переменная, и компилятор превращает вызов в `(&c).Inc()`. Строка (2) — обычный случай: у `*Counter` есть `Inc`.

А в (3) интерфейс получил бы **копию** `c`. Метод `Inc` по смыслу должен менять исходный счётчик, но через интерфейс он мог бы поменять только копию — и вызывающий никогда бы этого не увидел. Чтобы такая ошибка не прошла молча, язык запрещает присваивание целиком: значение, которое лежит в интерфейсе, не адресуемо.
</Predict>

Практические правила выбора получателя:

- **указатель**, если метод меняет получателя; если структура большая и копировать её дорого; если в ней есть `sync.Mutex` или другие поля, которые нельзя копировать;
- **значение** для маленьких неизменяемых типов: `time.Time`, координаты, деньги, идентификаторы;
- **не смешивайте** без причины. Если хоть один метод на указателе, делайте на указателе все — тогда в интерфейс всегда передаётся `&v`, и никто не удивится, что `T` вдруг «не реализует» интерфейс.

Метод с получателем-указателем можно вызвать на nil-указателе — Go не проверяет получателя заранее. Если метод не обращается к полям, это законно и иногда полезно (`func (t *Tree) Len() int { if t == nil { return 0 } ... }`). Но именно это делает возможной следующую ловушку.

## nil-интерфейс и nil внутри интерфейса

Самый известный вопрос об интерфейсах на собеседованиях:

```go
type MyErr struct{}

func (*MyErr) Error() string { return "my error" }

func find(fail bool) error {
    var e *MyErr
    if fail {
        e = &MyErr{}
    }
    return e
}

func main() {
    err := find(false)
    fmt.Println(err == nil)
}
```

<Predict
  question="Что напечатает программа?"
  options={['true', 'false', 'Паника: nil pointer dereference', 'Ошибка компиляции']}
  answer={1}
>
`false`. `e` — nil-указатель типа `*MyErr`. При `return e` он упаковывается в `error`, и в интерфейсе оказывается `tab = itab(*MyErr, error)`, `data = nil`. Интерфейс равен `nil`, только когда **оба** слова пусты, а здесь тип известен.

Вызывающий видит «ошибку», логирует её, отвечает клиенту 500 — хотя всё прошло успешно. А если `Error()` обращается к полям получателя, `err.Error()` ещё и упадёт с nil pointer dereference.
</Predict>

<TypedNil />

Это состояние называют <Term id="typed-nil">nil с типом</Term>. Возникает оно всегда одинаково: переменная конкретного типа-указателя, которая «может быть nil», попадает в интерфейс. Правила, которые закрывают проблему:

- **возвращайте литерал `nil`**, а не переменную конкретного типа: `if !fail { return nil }`;
- **функции, возвращающие ошибку, объявляйте с результатом `error`**, а не `*MyErr`. Иначе ловушка переедет к вызывающему: `var err error = f()`;
- при отладке печатайте тип: `fmt.Printf("%T %v\n", err, err)` выведет `*main.MyErr <nil>` — сразу видно, что внутри.

Проверить, что внутри интерфейса nil-указатель, можно только зная тип (`p, ok := err.(*MyErr); ok && p == nil`) или через `reflect.ValueOf(x).IsNil()`. Но нужда в такой проверке почти всегда означает, что nil с типом стоило не создавать.

## Сравнение интерфейсов

Два значения интерфейса равны, если у них **одинаковый динамический тип и равные значения**. Отсюда три следствия.

**Разные типы — не равны, даже если «число одно и то же»:**

```go
var a any = 1         // int
var b any = int64(1)  // int64
fmt.Println(a == b)   // false
```

**Несравнимый тип внутри — паника во время выполнения.** Слайсы, карты и функции нельзя сравнивать через `==`. Компилятор запрещает это для конкретных типов, но для интерфейсов проверить заранее не может:

```go
var x, y any = []int{1}, []int{1}
fmt.Println(x == y) // panic: runtime error: comparing uncomparable type []int
```

**Интерфейс как ключ карты** сравнивается и хэшируется по тем же правилам:

```go
seen := map[any]bool{}
seen[1] = true
fmt.Println(seen[int64(1)])
seen[[]int{1}] = true
```

  answer={1}
>
`false`: ключ `int(1)` и ключ `int64(1)` — разные, потому что разные типы. А последняя строка падает с `panic: runtime error: hash of unhashable type []int`: чтобы положить ключ в карту, его нужно захэшировать, а у слайса хэша нет.

Компилятор пропустил обе ошибки — тип ключа `any` разрешает всё. Если ключ карты `any` приходит из внешних данных (например, из разобранного JSON), такая паника — вопрос времени.
</Predict>

## Утверждение типа и type switch

Из интерфейса можно достать конкретное значение. Это **утверждение типа** (type assertion):

```go
var s Shape = Rect{3, 4}

r := s.(Rect)          // r — Rect; если внутри не Rect — паника
c, ok := s.(Circle)    // форма с ok: паники нет, ok == false, c — нулевой Circle
```

Почти всегда используйте форму с `ok` — паника из-за неожиданного типа в проде хуже любой обработки ошибки.

Проверка выполняется дёшево: для конкретного типа это одно сравнение указателя `tab` (или `_type` у `any`) с известной компилятору itab. Никакого поиска по именам методов.

### Type switch

Когда вариантов несколько, удобнее `switch`:

```go
func describe(v any) string {
    switch x := v.(type) {
    case nil:
        return "ничего"
    case int, int64:
        return fmt.Sprintf("целое %v", x)   // x — any: в case перечислено два типа
    case string:
        return "строка длиной " + strconv.Itoa(len(x)) // x — string
    case error:
        return "ошибка: " + x.Error()
    case fmt.Stringer:
        return "умеет String: " + x.String()
    default:
        return fmt.Sprintf("неизвестно: %T", x)
    }
}
```

Важные детали:

- **`x` в каждой ветке имеет тип этой ветки.** Если в `case` перечислено несколько типов, `x` остаётся типа исходного интерфейса;
- **ветки проверяются сверху вниз**, срабатывает первая подходящая. Если значение реализует и `error`, и `fmt.Stringer`, сработает `error`. Ставьте более узкие проверки выше;
- **`case nil`** ловит только настоящий nil-интерфейс, а не nil с типом.

### Утверждение к интерфейсу: «а умеешь ли ты ещё и это?»

Утверждать можно не только к конкретному типу, но и к другому интерфейсу. Это главный приём расширяемости в стандартной библиотеке: функция принимает минимальный интерфейс, а затем проверяет, нет ли у значения более эффективного способа сделать работу.

```go
// Упрощённый io.Copy
func Copy(dst Writer, src Reader) (int64, error) {
    if wt, ok := src.(WriterTo); ok {
        return wt.WriteTo(dst)   // источник умеет писать сам — например, *os.File через sendfile
    }
    if rf, ok := dst.(ReaderFrom); ok {
        return rf.ReadFrom(src)
    }
    // ... обычный цикл через буфер 32 КБ
}
```

Так же устроены `http.Flusher`, `http.Hijacker`, `io.StringWriter`. Цена приёма — **обёртки прячут возможности**.

```go
// Middleware, которое запоминает код ответа для логов
type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (r *statusRecorder) WriteHeader(code int) {
    r.status = code
    r.ResponseWriter.WriteHeader(code)
}
```

<Predict
  question="Обработчик за этим middleware отдаёт события через Server-Sent Events и после каждого события делает if f, ok := w.(http.Flusher); ok { f.Flush() }. Что увидит клиент?"
  options={[
    'События по мере отправки — встроенное поле даёт все методы',
    'Ничего до заполнения буфера или конца ответа: ok == false, Flush не вызывается',
    'Панику при первом же событии',
    'Ошибку компиляции: statusRecorder не реализует Flusher',
  ]}
  answer={1}
>
Встраивание поля типа `http.ResponseWriter` даёт `statusRecorder` **только методы интерфейса `ResponseWriter`**: `Header`, `Write`, `WriteHeader`. То, что внутри лежит `*http.response` с методом `Flush`, на набор методов обёртки не влияет — статический тип поля `ResponseWriter`, и у него `Flush` нет.

Утверждение `w.(http.Flusher)` смотрит на динамический тип `*statusRecorder`, не находит `Flush` и возвращает `ok == false`. Код не падает и не ругается — просто события копятся в буфере и приходят пачкой.

Лечится двумя способами: добавить обёртке метод `Flush`, который проверяет и вызывает внутренний, и метод `Unwrap() http.ResponseWriter`; а в обработчике пользоваться `http.NewResponseController(w).Flush()` (Go 1.20+) — он сам разворачивает обёртки через `Unwrap`.
</Predict>

## Встраивание

### Интерфейс в интерфейсе

Большие интерфейсы собираются из маленьких:

```go
type Reader interface{ Read(p []byte) (n int, err error) }
type Writer interface{ Write(p []byte) (n int, err error) }
type Closer interface{ Close() error }

type ReadWriter interface {
    Reader
    Writer
}

type ReadWriteCloser interface {
    Reader
    Writer
    Closer
}
```

`ReadWriter` — ровно объединение методов. Любой `ReadWriter` можно передать туда, где ждут `Reader`, — преобразование к меньшему интерфейсу всегда разрешено и проверяется компилятором.

### Интерфейс в структуре

Встроенный в структуру интерфейс даёт ей все его методы, которые делегируются полю. Это удобно для **декораторов** — переопределить один метод, а остальные пробросить:

```go
type countingReader struct {
    io.Reader // все методы Reader делегируются полю
    n int64
}

func (c *countingReader) Read(p []byte) (int, error) {
    n, err := c.Reader.Read(p)
    c.n += int64(n)
    return n, err
}
```

И для **частичных фейков** в тестах: структура «реализует» большой интерфейс, переопределяя только нужные методы.

```go
type fakeStore struct {
    Store // nil — для методов, которые тест не вызывает
}

func (fakeStore) GetUser(ctx context.Context, id int64) (User, error) {
    return User{ID: id, Name: "test"}, nil
}
```

<Callout kind="warn">
Встроенное поле-интерфейс по умолчанию `nil`. Вызов метода, который вы не переопределили, — это вызов метода у nil-интерфейса и паника `invalid memory address or nil pointer dereference`. Для фейков это даже хорошо: тест громко упадёт, если код вызвал то, чего тест не ожидал. Для декораторов в проде — следите, чтобы поле всегда было заполнено.
</Callout>

## Пустой интерфейс any

`any` — псевдоним `interface{}`, интерфейса без методов. Ему удовлетворяет любой тип. Он нужен там, где тип значения действительно заранее неизвестен:

- `fmt.Println(a ...any)` — печатает что угодно через рефлексию;
- `json.Unmarshal(data, &v)` в `map[string]any` для произвольного JSON;
- `context.WithValue(ctx, key, val any)`;
- контейнеры, написанные до появления дженериков.

Платить за `any` приходится проверкой типов во время выполнения вместо компиляции: любое использование значения начинается с утверждения типа или type switch, а ошибка в типе всплывает в проде, а не в редакторе. Плюс упаковка в `eface` и, часто, аллокация.

Правило: **если тип известен — пишите тип; если типов несколько, но они известны на этапе компиляции, — пишите дженерик**. `any` — для настоящей неизвестности.

## Интерфейсы и дженерики

С Go 1.18 интерфейсы используются ещё и как **ограничения** параметров типа. Здесь у них двойная роль.

```go
// Обычный интерфейс как ограничение — «любой T, у которого есть String()»
func Join[T fmt.Stringer](xs []T, sep string) string {
    parts := make([]string, len(xs))
    for i, x := range xs {
        parts[i] = x.String()
    }
    return strings.Join(parts, sep)
}

// Интерфейс с набором типов — только для ограничений, переменную такого типа объявить нельзя
type Number interface {
    ~int | ~int64 | ~float64 // ~ — «любой тип с таким базовым типом», включая type ID int
}

func Sum[T Number](xs []T) T {
    var s T
    for _, x := range xs {
        s += x // + разрешён: все типы набора его поддерживают
    }
    return s
}
```

Чем отличаются `func F(s Shape)` и `func F[T Shape](s T)`:

| | Интерфейс-параметр | Параметр типа |
| --- | --- | --- |
| что внутри | может меняться от вызова к вызову | один тип на всё тело функции |
| `[]Shape` | можно смешивать `Rect` и `Circle` | `[]T` — все элементы одного типа |
| упаковка | значение копируется в интерфейс | `[]Rect` передаётся без преобразования |
| возвращаемый тип | теряет конкретный тип: вернули `Shape` | сохраняет: вернули `T` = `Rect` |
| операторы `+`, `<` | нельзя | можно через ограничение с набором типов |

Выбор простой. **Нужно хранить вместе значения разных типов или выбирать реализацию во время работы** (стратегия, плагин, зависимость сервиса) — интерфейс. **Нужно написать один алгоритм для разных типов** и не потерять тип на выходе (контейнер, `Map`/`Filter`, `Max`) — дженерик.

<Callout kind="model" title="Дженерики не всегда быстрее интерфейсов">
Go компилирует дженерики не отдельной копией на каждый тип, а одной копией на **форму** типа (GC shape): все типы-указатели, например, делят одну реализацию. Методы параметра типа в такой реализации вызываются через словарь — то есть тоже косвенно. Поэтому `Join[T fmt.Stringer]` не обязательно быстрее `func Join(xs []fmt.Stringer)`. Выигрыш дженериков — в типобезопасности и отсутствии упаковки, а скорость надо мерить.
</Callout>

## error — тоже интерфейс

```go
type error interface {
    Error() string
}
```

Всё, что было сказано выше, к ошибкам применимо напрямую: nil с типом — самая частая ловушка именно с `error`; утверждение типа — способ узнать подробности. Но для ошибок, которые оборачиваются через `fmt.Errorf("...: %w", err)`, прямое утверждение не работает — внутри лежит обёртка `*fmt.wrapError`. Поэтому:

```go
// Плохо: не увидит обёрнутую ошибку
if _, ok := err.(*NotFoundError); ok { ... }

// Хорошо: разворачивает цепочку через Unwrap
var nf *NotFoundError
if errors.As(err, &nf) {
    log.Println("не найден:", nf.ID)
}

if errors.Is(err, sql.ErrNoRows) { ... } // для сравнения с конкретным значением
```

`errors.As` идёт по цепочке `Unwrap()` и на каждом шаге делает то самое утверждение типа — тот же механизм, что разобран выше, только в цикле.

## Как проектировать интерфейсы

Механика интерфейсов простая. Сложнее решить, **где** их вводить. Несколько правил, проверенных стандартной библиотекой и большими кодовыми базами.

### Маленькие интерфейсы

> The bigger the interface, the weaker the abstraction. — Rob Pike

`io.Reader` — один метод, и поэтому его реализует сотня типов. Интерфейс из двадцати методов реализует один тип — ваш, — и абстракцией он не является: это просто копия публичных методов структуры. Интерфейсы из одного-трёх методов — норма. Больше — сигнал, что интерфейс нужно разделить или что он не нужен.

Имена интерфейсов из одного метода по соглашению — метод плюс `-er`: `Reader`, `Writer`, `Closer`, `Stringer`, `Notifier`.

### Интерфейс объявляет потребитель

В Java интерфейс обычно лежит рядом с реализацией. В Go — рядом с **тем, кто его использует**:

```go
// package orders — потребитель
type paymentGateway interface {
    Charge(ctx context.Context, amount Money, card Token) (TxID, error)
}

type Service struct {
    pay paymentGateway
}

// package stripe — реализация. Об интерфейсе orders она не знает
// и экспортирует конкретный тип.
type Client struct{ ... }

func (c *Client) Charge(ctx context.Context, amount orders.Money, card orders.Token) (orders.TxID, error) { ... }
func (c *Client) Refund(...) error { ... }
func (c *Client) ListDisputes(...) ([]Dispute, error) { ... }
```

Пакету `orders` нужен только `Charge` — он и описан. Тестовый фейк реализует один метод, а не все десять. Когда другому пакету понадобится `Refund`, он объявит свой интерфейс.

### Принимайте интерфейсы, возвращайте структуры

Функция, которая **принимает** интерфейс, гибкая: ей подойдёт любая реализация. Функция, которая **возвращает** конкретный тип, честная: вызывающий получает все методы, а не урезанный набор, и сам решает, к какому интерфейсу его привести.

```go
func NewClient(cfg Config) *Client             // хорошо
func NewClient(cfg Config) PaymentGateway       // обычно плохо: прячет методы, мешает развитию
```

Исключения есть — например, когда реализаций несколько и выбор между ними — внутреннее дело пакета (`hash.Hash` из `sha256.New()`) или когда конкретный тип нельзя показывать. Но по умолчанию — структура.

### Не вводите интерфейс заранее

Интерфейс с единственной реализацией и без тестов, которые её подменяют, — лишний уровень косвенности: чтобы найти код, приходится сначала искать, кто реализует. Go позволяет ввести интерфейс **потом**, не трогая реализацию — благодаря неявной реализации это бесплатно. Поэтому правило: начинайте с конкретного типа, а интерфейс объявите, когда появится вторая реализация или потребность подменить первую в тесте.

## Итог

- Интерфейс — набор методов. Тип реализует его неявно, просто имея нужные методы; проверяет компилятор в месте использования. `var _ I = (*T)(nil)` проверяет заранее.
- Значение интерфейса — два слова. [iface](/glossary/iface/) — `(itab, data)` для интерфейсов с методами, eface — `(_type, data)` для `any`. `data` указывает на **копию** значения; указатели кладутся в него напрямую.
- [itab](/glossary/itab/) одна на пару «интерфейс + тип»: ссылки на оба типа и адреса методов. Для видимых в коде пар её строит компилятор, для остальных — рантайм с кэшем.
- Упаковка в интерфейс может стоить аллокации. Не аллоцируют указатели, целые 0–255, константы и значения, которые не убегают.
- Вызов метода через интерфейс — косвенный: дёшев сам по себе, но мешает встраиванию и анализу побега. [Девиртуализация](/glossary/devirtualization/) снимает косвенность, когда тип известен статически или по профилю.
- [Набор методов](/glossary/method-set/) `T` не включает методы с получателем `*T`. Поэтому `var i I = v` не компилируется, если метод на указателе, — нужно `&v`.
- Интерфейс равен `nil`, только когда пусты оба слова. [nil с типом](/glossary/typed-nil/) — nil-указатель в интерфейсе — не равен `nil`. Возвращайте литерал `nil`, объявляйте результат как `error`.
- `==` сравнивает динамический тип и значение: `any(1) != any(int64(1))`, а несравнимый тип внутри — паника, в том числе для ключей `map[any]`.
- Утверждение типа — дешёвое сравнение указателей; используйте форму с `ok`. Утверждение к интерфейсу находит дополнительные возможности, а обёртки их прячут — давайте обёрткам `Unwrap` и пользуйтесь `http.ResponseController`.
- `any` — для настоящей неизвестности типа. Несколько известных типов и один алгоритм — дженерики; разные реализации во время работы — интерфейсы.
- Интерфейсы маленькие, объявляются у потребителя и появляются тогда, когда нужны. Принимайте интерфейсы, возвращайте структуры.

Интерфейсы замыкают тему «что лежит в переменной»: [слайс](/lectures/go-runtime/slices/) — три слова и массив, [карта](/lectures/go-runtime/maps/) — указатель на таблицу, интерфейс — два слова: тип и данные. Зная, что лежит в переменной, можно предсказать, что скопирует присваивание, что увидит функция и что останется в памяти.
