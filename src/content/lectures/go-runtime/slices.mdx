Слайс — самый частый тип в программах на Go. Через него читают тело запроса, собирают результат запроса к базе, передают батч в Kafka. И почти всегда он ведёт себя как динамический массив из любого другого языка: положил, прочитал, прошёлся циклом.

Пока однажды функция не поменяет данные, которые ей не передавали. Или два результата `append` не окажутся одним и тем же. Или сервис не будет держать в памяти гигабайт ради сотни байт, которые он закэшировал. Всё это — одна и та же деталь устройства, и она помещается в три машинных слова.

В [лекции о памяти](/lectures/go-runtime/memory/) мы разобрали, где живут объекты и как работает аллокатор. Здесь — самый частый его клиент: что происходит при `append`, `s[i:j]` и передаче слайса в функцию.

## Массив и слайс

В Go есть массивы — `[4]int`. Длина массива — часть типа: `[4]int` и `[5]int` — разные типы, и переменная такого типа — это сами четыре числа. Массив — значение: присваивание и передача в функцию копируют его целиком.

Слайс — `[]int` — это не массив, а **окно в массив**. В рантайме это структура из трёх полей — <Term id="slice-header">заголовок слайса</Term>:

```go
// runtime/slice.go
type slice struct {
    array unsafe.Pointer // указатель на первый видимый элемент
    len   int            // сколько элементов видно
    cap   int            // сколько есть до конца массива
}
```

<SliceHeader />

Элементы лежат в отдельном массиве, а переменная хранит только указатель на него. Отсюда всё поведение слайсов:

- **копия слайса — это копия заголовка.** `t := s` даёт второй заголовок на тот же массив, изменение `t[0]` видно через `s[0]`;
- **срез `s[i:j]` ничего не копирует.** Он вычисляет новый заголовок: `array` сдвигается на `i` элементов, `len = j - i`, `cap = cap(s) - i`;
- **`len` — граница для чтения**, `s[len(s)]` — паника. **`cap` — граница для роста**: срезать можно и за `len`, до `cap` — `s[:cap(s)]` законно и открывает «спрятанные» элементы.

Сравнить два слайса через `==` нельзя (только с `nil`) — неясно, что сравнивать: заголовки или содержимое. Для содержимого есть `slices.Equal`.

## Слайс в функции

Go передаёт аргументы по значению. Для слайса «значение» — это три слова заголовка. Функция получает свою копию заголовка, но массив под ним общий.

```go
func fill(s []int) {
    s[0] = 100
    s = append(s, 4)
    s[1] = 200
}

func main() {
    s := []int{1, 2, 3}
    fill(s)
    fmt.Println(s)
}
```

<Predict
  question="Что напечатает программа?"
  options={['[1 2 3]', '[100 2 3]', '[100 200 3]', '[100 200 3 4]']}
  answer={1}
>
`s[0] = 100` пишет в общий массив — вызывающий это видит. Дальше `append`: у литерала `[]int{1, 2, 3}` ёмкость 3, места нет, и рантайм выделяет новый массив. Локальная `s` теперь смотрит в него, и `s[1] = 200` меняет уже новый массив, о котором `main` не знает. А длина слайса в `main` осталась 3 в любом случае: она лежит в его собственном заголовке.

Если бы ёмкости хватило (`make([]int, 3, 10)`), вывод был бы `[100 200 3]` — четвёрка записалась бы в общий массив, но за пределами `len` у `main`. Поведение функции зависит от ёмкости, которую она не выбирала. Поэтому функция, которая добавляет элементы, **возвращает слайс**: `s = add(s, x)` — ровно как сам `append`.
</Predict>

Вывод на практике: изменить элементы переданного слайса функция может, изменить его длину — нет. Если нужно добавлять, возвращайте новый слайс. Передавать `*[]T` почти никогда не нужно — исключение составляют методы с получателем-указателем на тип-слайс вроде `func (s *Stack) Push(x int)`.

## append и ёмкость

`append(s, x)` делает одно из двух:

1. **Если `len(s) < cap(s)`** — пишет `x` в `s.array[len]` и возвращает заголовок с `len + 1`. Никакой аллокации, тот же массив.
2. **Если места нет** — вызывает <Term id="growslice">`runtime.growslice`</Term>: выделяет новый массив побольше, копирует туда старые элементы, дописывает `x` и возвращает заголовок на новый массив. Старый массив остаётся как был — его соберёт сборщик, когда на него не останется ссылок.

<SliceAppend />

Отсюда главная ловушка слайсов — <Term id="slice-aliasing">общий массив</Term>. Пока ёмкость есть, `append` пишет в чужую память.

```go
base := make([]int, 3, 10)
a := append(base, 1)
b := append(base, 2)
fmt.Println(a[3], b[3])
```

<Predict
  question="Что напечатает программа?"
  options={['1 2', '2 2', '1 1', 'паника: индекс за пределами']}
  answer={1}
>
`2 2`. У `base` длина 3 и ёмкость 10 — оба `append` пишут без переезда, в **одну и ту же** ячейку `array[3]`. Сначала туда легла единица, потом двойка. `a` и `b` — два заголовка на один массив с одинаковой длиной, то есть фактически один и тот же слайс.

Эта ошибка встречается в живом коде в таком виде: общий префикс, к которому в цикле добавляют разные хвосты — пути в обходе дерева, аргументы команд, ключи. Всё работает, пока префикс создан литералом (ёмкость ровно по длине, каждый `append` переезжает), и ломается, как только префикс сам вырос через `append` и у него появился запас.

Лечится явной копией (`slices.Clone(base)` перед `append`) или трёхиндексным срезом — о нём ниже.
</Predict>

### Трёхиндексный срез

`s[low:high:max]` задаёт не только длину, но и ёмкость: `cap = max - low`. Главное применение — `s[:n:n]`: слайс с ёмкостью, равной длине. Первый же `append` к нему обязан переехать и не тронет исходный массив.

```go
// Отдаём наружу часть внутреннего буфера. Без третьего индекса вызывающий
// мог бы append'ом переписать наши данные за границей n.
func (b *Buffer) Head(n int) []byte {
    return b.buf[:n:n]
}
```

Это дешёвая защита для API, которые возвращают часть своего слайса. Читать через такой срез можно, `append` к нему — безопасен. Записать в `s[i]` он, конечно, по-прежнему может: общий массив никуда не делся.

### Как растёт ёмкость

Если места нет, `growslice` выбирает новую ёмкость по такому правилу (`runtime.nextslicecap`):

- нужно больше, чем вдвое, — берётся ровно нужное (`append(s, many...)`);
- ёмкость меньше 256 — удваивается;
- дальше рост плавно снижается от ×2 к ×1,25: `newcap += (newcap + 3*256) / 4`, пока не хватит.

Затем размер в байтах округляется вверх до [класса размера](/glossary/size-class/) аллокатора — память всё равно выделится блоком этого класса, и ёмкость растягивается на весь блок.

```go
s := make([]int, 256)
s = append(s, 1)       // cap 512  — ещё удвоение
s = make([]int, 512)
s = append(s, 1)       // cap 848  — 512 + (512+768)/4 = 832, округлено до класса
s = make([]int, 1024)
s = append(s, 1)       // cap 1536 — 1472 по формуле, округлено до класса

s2 := append([]int{}, 1, 2, 3, 4, 5)
fmt.Println(cap(s2))   // 6: 40 байт округлены до класса 48
```

Удвоение даёт **амортизированно O(1)** на `append`: каждый элемент копируется в среднем константное число раз. Но амортизация не бесплатна: при росте с нуля до миллиона элементов создаётся около 40 промежуточных массивов, и все, кроме последнего, — мусор для [сборщика](/lectures/go-runtime/gc/). В горячем пути это видно в профиле как `runtime.growslice` и `runtime.mallocgc`.

<Callout kind="model" title="Точные числа ёмкости — деталь реализации">
Формула менялась: до Go 1.18 порог был 1024 и рост за ним — сразу ×1,25. А в свежих версиях (проверено на Go 1.27) компилятор умеет начинать слайс, который растёт `append`'ом в цикле, в 32-байтовом буфере на стеке, и пока слайс там, ёмкость растёт по классам размеров: `1, 2, 3, 4` для `[]int`, а не `1, 2, 4, 8`. Если слайс в итоге убегает в кучу, его переносят туда одним копированием.

Поэтому код не должен зависеть от конкретной ёмкости после `append`. Правило «если `append` переехал — массив новый, если нет — общий» верно всегда; на каком именно `append` произойдёт переезд, — нет.
</Callout>

### Выделяйте заранее

Когда итоговый размер известен или хотя бы оценивается, ёмкость задают сразу:

```go
ids := make([]int64, 0, len(users))
for _, u := range users {
    ids = append(ids, u.ID)
}
```

Одна аллокация вместо двадцати, ноль копирований. Внимание на `make([]T, 0, n)` против `make([]T, n)`: второй создаёт `n` нулевых элементов, и `append` допишет **после** них — классическая ошибка, из-за которой в результате оказываются `n` нулей и следом нужные данные. Если длина известна точно, можно и `make([]T, n)` с записью по индексу — это даже чуть быстрее, `append` каждый раз проверяет ёмкость.

Для уже существующего слайса есть `slices.Grow(s, n)` — гарантирует место ещё под `n` элементов одной аллокацией.

## Слайс держит весь массив

Сборщик мусора не знает, какая часть массива «видна» через слайс. Пока жив хоть один заголовок, указывающий внутрь массива, жив **весь массив**. Это частная форма <Term id="memory-retention">удержания памяти</Term>.

<Predict
  question="Сервис читает ответ внешнего API размером 2 МБ и кладёт в кэш первые 64 байта: cache[k] = body[:64]. В кэше 10 000 записей. Сколько памяти он держит?"
  options={[
    'Около 640 КБ: 10 000 × 64 байта',
    'Около 20 ГБ: каждая запись держит свой двухмегабайтный массив',
    'Около 2 МБ: массивы общие',
  ]}
  answer={1}
>
Каждый `body[:64]` — заголовок, указывающий в начало двухмегабайтного массива. Сборщик видит живой указатель и не может освободить ни байта из этих 2 МБ. 10 000 записей — 20 ГБ, и в профиле кучи (`inuse_space`) виноватым будет место, где читается тело, а не кэш.

Лечится копией: `bytes.Clone(body[:64])` или `slices.Clone` — новый массив ровно нужного размера, и большой можно выбросить. То же со строками: подстрока большой строки держит всю строку, лечится `strings.Clone`.
</Predict>

Второй вариант той же проблемы — **указатели за границей `len`**. Если слайс хранит указатели и вы «удаляете» последний элемент через `s = s[:len(s)-1]`, указатель остаётся в массиве, за границей длины. Объект, на который он ссылается, не будет собран, пока жив массив. Поэтому при ручном удалении хвост зануляют:

```go
last := s[len(s)-1]
s[len(s)-1] = nil // или нулевое значение: отпускаем объект для сборщика
s = s[:len(s)-1]
```

С Go 1.22 `slices.Delete`, `slices.Compact` и их родственники зануляют освободившийся хвост сами.

## nil и пустой слайс

`var s []int` — nil-слайс: заголовок из нулей. `s := []int{}` — пустой, но не nil: указатель на что-то (обычно на общий нулевой адрес `runtime.zerobase`), длина 0.

Почти всё работает с ними одинаково: `len` и `cap` дают 0, `range` не делает ни одной итерации, `append` к nil-слайсу выделяет массив как обычно. Поэтому инициализировать слайс перед `append` не нужно — `var out []T` идиоматичен.

Разница видна в двух местах:

- `s == nil` — истина только для nil-слайса;
- **`encoding/json` пишет nil-слайс как `null`, а пустой — как `[]`.** Для клиента на JavaScript это разница между `.length` и `TypeError`. Если API обещает массив, отдавайте `[]T{}` или инициализируйте поле.

Возвращая «ничего» из функции, пишите `return nil` — и проверяйте результат через `len(s) == 0`, а не `s == nil`: так код работает для обоих вариантов.

## range по слайсу

`for i, v := range s` вычисляет `s` один раз, до первой итерации, и на каждой итерации **копирует** `s[i]` в `v`.

- изменение `v` не меняет слайс. Чтобы изменить элемент — `s[i].Count++`;
- для больших структур копия на каждой итерации стоит времени — там пишут `for i := range s` и работают через `s[i]` или `p := &s[i]`;
- `append` к `s` внутри цикла не продлит цикл: длина запомнена в начале.

С Go 1.22 переменные цикла `i` и `v` свои на каждой итерации, поэтому классическая ловушка «все горутины видят последний элемент» и `&v`, который всегда указывает на одну ячейку, ушли в прошлое. Но `&v` — это по-прежнему адрес копии, а не элемента слайса.

## Слайсы и горутины

Слайс не защищён ничем. Правила такие же, как для любой памяти, — разобраны в лекции об [общем состоянии](/lectures/concurrency/shared-state/):

- **разные горутины пишут в разные индексы** заранее созданного слайса — это безопасно, гонки нет: `results[i] = f(i)` в `i`-й горутине — идиоматичный способ собрать результаты параллельной работы;
- **`append` из нескольких горутин в один слайс — <Term id="data-race">гонка данных</Term>.** Две горутины читают один и тот же `len`, пишут в одну ячейку, и один результат пропадает. А если одна из них переехала, запись второй уходит в брошенный массив. Никакой паники — просто меньше элементов, чем должно быть. `go test -race` находит это сразу.

```go
results := make([]Result, len(tasks))
var wg sync.WaitGroup
for i, t := range tasks {
    wg.Go(func() {
        results[i] = process(t) // своя ячейка у каждой горутины
    })
}
wg.Wait()
```

## Строки и []byte

Строка устроена как слайс без `cap`: указатель и длина. Но строка неизменяема, а `[]byte` — нет, поэтому преобразование `[]byte(s)` и `string(b)` в общем случае **копирует** данные — иначе через слайс можно было бы изменить строку.

Компилятор убирает копию там, где может доказать, что она не нужна: ключ карты `m[string(b)]`, сравнение `string(b) == "GET"`, конкатенация во временную строку, `for i, c := range []byte(s)`. В горячем коде полезно держать данные в одном представлении и не гонять их туда-обратно; `bytes` и `strings` для этого содержат зеркальные наборы функций.

## Пакет slices

С Go 1.21 большая часть ручной работы со слайсами есть в стандартном пакете `slices`:

| Задача | Функция | Заметка |
| --- | --- | --- |
| скопировать | `slices.Clone(s)` | новый массив ёмкостью по длине |
| удалить диапазон | `slices.Delete(s, i, j)` | сдвигает хвост, зануляет освободившееся |
| вставить | `slices.Insert(s, i, v...)` | может переехать — используйте результат |
| найти | `slices.Index`, `slices.Contains`, `slices.BinarySearch` | |
| отсортировать | `slices.Sort`, `slices.SortFunc` | pdqsort, не стабильная; стабильная — `SortStableFunc` |
| убрать соседние дубли | `slices.Compact(s)` | после `Sort` — уникальные значения |
| запас ёмкости | `slices.Grow(s, n)` | |
| сравнить | `slices.Equal(a, b)` | |

Все функции, которые меняют длину, возвращают новый слайс — по тем же причинам, что и `append`. Забытое `s = ` перед `slices.Delete` оставит в `s` старую длину и нули в хвосте.

## Итог

- Слайс — это [заголовок](/glossary/slice-header/) из трёх слов: указатель, `len`, `cap`. Элементы лежат в отдельном массиве. Копия слайса и срез `s[i:j]` копируют только заголовок.
- Функция может изменить элементы переданного слайса, но не его длину. Добавляет — возвращает новый слайс.
- `append` при свободной ёмкости пишет в [общий массив](/glossary/slice-aliasing/) и может затереть данные другого слайса. Без места — [переезжает](/glossary/growslice/) в новый массив и отцепляется. Какой из исходов случится, по коду обычно не видно.
- `s[:n:n]` ограничивает ёмкость, и первый `append` к результату гарантированно переедет. `slices.Clone` — когда нужна независимая копия.
- Ёмкость растёт вдвое до 256 элементов, дальше плавно к ×1,25, с округлением до класса размера. Точные числа — деталь реализации; если размер известен — `make([]T, 0, n)`.
- Маленький подсрез держит весь массив, указатель за `len` — весь объект. Нужная часть большого буфера — через копию.
- nil-слайс и пустой отличаются только сравнением с `nil` и JSON (`null` против `[]`). Проверяйте `len(s) == 0`.
- Писать в разные индексы из разных горутин можно, `append` в общий слайс — гонка.
